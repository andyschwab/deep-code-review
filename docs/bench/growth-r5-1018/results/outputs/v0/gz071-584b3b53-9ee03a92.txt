### Executive Summary: Tender Posting Funnel Redefinition

To secure engineering resources for the Q2 board review, we must replace the current binary "visited vs. completed" view with a granular, five-stage funnel. This structure isolates the document upload hypothesis and accounts for the unknown mobile/desktop variance.

**Proposed Event Taxonomy & Stages**
Instrument the following discrete events immediately. Each event answers a specific diagnostic question:

1.  **`tender_initiated`** (User clicks "Post New Tender")
    *   *Question:* Is the entry point clear?
    *   *Properties:* `device_type` (critical unknown), `user_segment`.
2.  **`tender_details_saved`** (User completes core metadata fields)
    *   *Question:* Is the form length or complexity causing early abandonment?
    *   *Properties:* `time_spent_seconds`, `field_count_completed`.
3.  **`upload_attempted`** (User interacts with the file drop zone)
    *   *Question:* Are users reaching the suspected friction point?
    *   *Properties:* `file_type`, `file_size_mb`, `device_type`.
4.  **`upload_successful`** (Backend confirms file receipt)
    *   *Question:* **Is the hypothesis correct?** This isolates technical failure vs. user hesitation.
    *   *Properties:* `retry_count`, `error_code` (if failed).
5.  **`tender_published`** (Final submission confirmation)
    *   *Question:* Is there friction after the upload (e.g., preview or payment)?

**Interpretation Logic for the Steering Committee**
Do not present raw counts alone. Present **conversion rates between adjacent stages** to pinpoint the leak:

*   **Validating the Upload Hypothesis:** Compare the drop-off rate between `upload_attempted` and `upload_successful`.
    *   If `attempted` → `successful` drops significantly (e.g., >40% loss) while previous stages hold steady, the hypothesis is **confirmed**. This indicates a technical barrier (timeout, format rejection, UI bug) justifying immediate engineering intervention.
    *   If `attempted` → `successful` is high, but `details_saved` → `upload_attempted` is low, the hypothesis is **incorrect**. The friction is psychological (fear of complexity) or design-related before the upload begins.
*   **Addressing the Device Unknown:** Since `device_type` is currently untracked, the first engineering sprint must include adding this property to all five events. If the overall conversion is 2% (85/4,200), but mobile users (once identified) show a 0.5% conversion at the upload stage versus 5% on desktop, the business case shifts from "fixing the module" to "fixing mobile responsiveness."
