### Data Cleansing and Validation Strategy for Thermostat Event Logs

**Executive Summary**
To preserve the integrity of energy-saving statistics for retail partners, we must treat the 20% of events missing the `source` property as `UNVERIFIED` rather than imputing values. Imputation based on timestamp patterns introduces unquantifiable bias into usage behavior analysis, risking the credibility of our reports. The following plan prioritizes data honesty over completeness.

**1. Immediate Data Cleansing (Existing Dataset)**
*   **Segmentation, Not Imputation:** Do not guess the source for the 10,000 affected events. Instead, tag them explicitly as `source: unknown_offline_gap`.
*   **Dual-Track Reporting:** Generate two versions of the heating usage report:
    *   *Verified Track:* Includes only the 40,000 events with confirmed sources. Use this for specific channel analysis (e.g., "App-driven savings").
    *   *Total Volume Track:* Includes all 50,000 events for aggregate energy consumption totals, with a clear footnote that 20% of interaction sources are unverified due to a firmware gap.
*   **Impact Assessment:** Calculate the variance in energy savings metrics between the two tracks. If the difference is negligible (<2%), proceed with the Verified Track for detailed breakdowns. If significant, present the range to partners rather than a single precise figure.

**2. Prevention Strategy (Future Firmware)**
*   **Local Buffering Logic:** Update the firmware logging logic to buffer events locally when offline. Upon reconnection, the device must flush the buffer with the original `source` property intact, rather than attempting to reconstruct it server-side.
*   **Schema Validation at Edge:** Implement a pre-flight check in the firmware (v2.5+) that prevents an event from being queued for transmission unless mandatory properties (`source`, `timestamp`, `device_id`) are populated.
*   **Canary Deployment:** Roll out the fix to 5% of devices first. Monitor the "missing source" rate in real-time; it must drop to near 0% before full deployment.

**3. Validation & Governance**
*   **Automated Alerting:** Set up a daily job that triggers an alert if the percentage of events with missing `source` properties exceeds 0.5%.
*   **Data Dictionary Update:** Explicitly document the `unknown_offline_gap` flag in the event taxonomy, noting it applies only to Firmware v2.4 during offline states. This ensures future analysts do not mistake these records for data corruption.

**This Week's Actions**
1.  **Query Execution:** Run a query to segment the last 30 days of data into "Verified Source" vs. "Unknown Source" and calculate the delta in average energy savings per adjustment for the analytics director's draft.
2.  **Ticket Creation:** File a high-priority engineering ticket for Firmware v2.5 to enforce local buffering of the `source` property during offline modes, with a target deployment date set for three weeks from now to meet the quarter-end deadline.

*Note: This strategy adheres to the principle of never fabricating benchmarks or data points; unknowns remain flagged to maintain trust with retail partners.*
