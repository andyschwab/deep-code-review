### Event Taxonomy & Measurement Plan for StreamHub Live Beta

**North Star Metric:** 48-Hour Return Rate of "Active Participators" (users who send ≥1 comment).
*Rejects vanity metrics like total watch time or peak concurrents for this specific hypothesis, as they do not isolate the causal link between commenting and retention.*

#### 1. Required Event Instrumentation
To validate your hypothesis without tracking message content, instrument the following three events. Each answers a specific question and enables the backend/community teams to plan accordingly.

| Event Name | Properties to Capture | Question Answered | Stakeholder Value |
| :--- | :--- | :--- | : |
| `live_session_started` | `user_id`, `stream_id`, `timestamp`, `device_type` | Did the user enter the environment? | **Backend:** Baseline load; **Community:** Total addressable audience. |
| `chat_interface_toggled` | `user_id`, `stream_id`, `timestamp`, `state` (open/close) | Did the user show intent to participate? | **Product:** Validates if "opening chat" is a leading indicator vs. actual commenting. |
| `comment_sent` | `user_id`, `stream_id`, `timestamp`, `message_length` (int only) | Did the user complete the core action? | **Community:** Direct trigger for moderator staffing models; **Product:** Defines the "Active" cohort. |

**Note on PII:** Do not capture message text. `message_length` is sufficient to filter bots (e.g., length < 2) without violating privacy.

#### 2. Analysis Logic: Validating the Hypothesis
You must compare two distinct retention cohorts after 48 hours:
1.  **Passive Viewers:** Users with `live_session_started` but NO `comment_sent`.
2.  **Active Participators:** Users with ≥1 `comment_sent`.

**The Calculation:**
*(Count of Active Participators who triggered `live_session_started` again within 48h) / (Total Count of Active Participators)*

If this result approaches your 35% hypothesis while Passive Viewer retention is significantly lower, the hypothesis holds. If both groups retain at the same rate, commenting is not the driver, and you should investigate `chat_interface_toggled` as an alternative predictor.

#### 3. Implementation Constraints & Stage Fit
Since this is an **MVP/Beta** launch to 10,000 users:
*   **Do not** instrument "watch time" granularity yet. It adds noise and storage cost without answering the specific "comment → retention" question.
*   **Identifier Seam:** Ensure `user_id` is a stable, pseudonymous ID persisted across sessions to accurately track the 48-hour return. This differs from ops logging which often drops user context; here, it is mandatory.
*   **Baseline Check:** You currently lack a baseline for "live" retention. The first 7 days will establish your *own* benchmark. Do not compare against external industry standards.

#### 4. This-Week Steps
1.  **Backend Team:** Schema-define the three events above with strict typing for `timestamp` and `user_id` to ensure queryability by July 10.
2.  **Community Lead:** Build a staffing model assuming X% of `live_session_started` users will trigger `comment_sent`; prepare to adjust if the "toggle" rate is high but "send" rate is low.
3.  **Product Analytics:** Pre-build the cohort query filtering for `comment_sent` ≥ 1 and lookback window = 48h. Verify data flow on July 11 using only the first 24h of beta traffic.

*No external benchmarks were used; success is defined strictly by the delta between your passive and active cohorts.*
*If `comment_sent` volume is too low to be statistically significant after 3 days, pivot to measuring `chat_interface_toggled` as the primary activation event.*
