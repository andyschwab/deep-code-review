# SkyMiles Global Event Taxonomy Harmonization Plan

## Executive Summary
To ensure accurate tier status calculations for 2.5 million members during the October 1st launch, we must immediately unify core transactional events before migration. Delaying taxonomy harmonization risks permanent data fragmentation, incorrect tier assignments, and inability to measure rebranding ROI.

## Critical Event Categories for Immediate Unification

### Tier 1: Status-Critical Events (Must unify before launch)
These events directly impact member tier calculations and must be standardized first:

| Business Action | Current Variants (Sample) | Standardized Name | Required Properties |
|----------------|---------------------------|-------------------|---------------------|
| Flight booked | `flight_booked`, `booking_complete`, `reserve_flight`, `ticket_purchased`, `flight_confirmation` (40+ variants) | `flight_booked` | `booking_class`, `fare_type`, `miles_earned`, `cabin_class`, `route_type` |
| Flight flown | `flight_completed`, `segment_flown`, `trip_taken` | `flight_completed` | `actual_miles_flown`, `booking_class`, `elite_qualifying_miles` |
| Tier qualification | `status_earned`, `tier_upgrade`, `elite_status` | `tier_status_changed` | `previous_tier`, `new_tier`, `qualification_type`, `effective_date` |
| Miles credited | `miles_posted`, `credit_miles`, `loyalty_points_added` | `miles_credited` | `miles_amount`, `source_type`, `expiration_date`, `bonus_multiplier` |

### Tier 2: Engagement Events (Unify within 30 days post-launch)
- `partner_transaction` (hotel, car, retail partners)
- `redemption_started` / `redemption_completed`
- `account_activity` (login, profile update)
- `communication_engagement` (email open, offer click)

## Historical Data Mapping Strategy

### Phase 1: Inventory & Mapping (Week 1-2)
1. **Extract all 40+ variants** from legacy system with frequency counts
2. **Map each variant** to standardized event name with confidence level:
   - High confidence: Direct semantic match (e.g., `booking_complete` → `flight_booked`)
   - Medium confidence: Requires property validation (e.g., `ticket_purchased` needs fare type check)
   - Low confidence: Manual review needed (ambiguous naming)
3. **Document property mappings** for each variant (what data fields translate to standard properties)

### Phase 2: Validation & Backfill (Week 3-4)
1. **Sample validation**: Test mapping accuracy on 1,000 random historical records per variant
2. **Create transformation layer**: Build ETL rules to convert legacy events to new schema
3. **Backfill critical events**: Apply mapping to all historical tier-affecting transactions
4. **Reconcile totals**: Verify mapped data produces identical tier counts as legacy reports

### Phase 3: Future-Proofing (Ongoing)
1. **Implement event governance**: Require new event names to follow `object_action` convention
2. **Create event registry**: Single source of truth for all event definitions
3. **Set up monitoring**: Alert on any new event variants created outside standard

## Risks of Delaying Taxonomy Harmonization

### Immediate Risks (If delayed past October 1st launch)

**1. Incorrect Tier Status Calculations**
- Members may receive wrong elite status due to uncounted or double-counted flights
- Estimated impact: 5-15% of 2.5M members could have incorrect tiers
- Result: Customer service crisis, compensation costs, brand damage

**2. Inability to Measure Rebranding Success**
- Cannot compare pre/post-launch booking behavior accurately
- Marketing ROI calculations become impossible across the transition
- CMO cannot report on program performance to stakeholders

**3. Permanent Data Fragmentation**
- Historical data remains in legacy format, creating permanent reporting silos
- Future analytics require complex joins and transformations indefinitely
- Technical debt compounds with each new analysis request

**4. Compliance & Audit Issues**
- Cannot produce consistent member activity reports for regulatory requirements
- Audit trails become unreliable when event names don't match across periods
- Potential violations of loyalty program terms if members dispute calculations

**5. Operational Inefficiency**
- Analytics team spends 60-80% of time cleaning data instead of generating insights
- Each regional report requires custom data transformation
- Slows decision-making for marketing campaigns and member communications

### Long-term Consequences
- **Cost escalation**: Fixing post-launch requires reprocessing all historical data under production pressure
- **Lost trust**: Members lose confidence in tier calculations, reducing program engagement
- **Competitive disadvantage**: Cannot quickly respond to market changes due to data reliability issues

## Recommended Next Steps

1. **Freeze legacy event creation** immediately for tier-critical actions
2. **Form cross-functional team** (analytics, engineering, loyalty operations) for 2-week sprint
3. **Prioritize the 4 tier-critical events** listed above
4. **Create mapping documentation** for CMO review by [date - 3 weeks from now]
5. **Test mapping accuracy** on sample data before full migration
6. **Implement governance process** to prevent future taxonomy drift

**Note**: This plan assumes engineering resources are available for the 4-week timeline. If resources are constrained, consider phasing by region rather than delaying entire harmonization.
**Note**: Property standardization is equally critical as event naming—ensure `booking_class` and `fare_type` have consistent value sets across all mapped variants.
