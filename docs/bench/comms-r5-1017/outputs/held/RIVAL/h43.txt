Ravi, this PR adds a composite index on `(customer_id, created_at)` to the orders table to speed up order history queries. The changes include the migration file, the new index definition, and a config update (+120 lines, -15 lines). Two risks remain untested because our staging environment (1 million rows) is much smaller than production (50 million rows):
1. **Disk Space:** We haven't measured the index size on a production-sized table, so it's unclear if it fits our disk budget.
2. **Migration Time & Locking:** The migration uses a standard `ALTER TABLE`. In Postgres, this can lock the table for a significant duration on large datasets. We don't know if the downtime will be acceptable.

Please review the migration strategy. We need your decision on whether to proceed as-is, add tests for index size and migration time on a larger dataset, or switch to a different migration approach that avoids locking.
