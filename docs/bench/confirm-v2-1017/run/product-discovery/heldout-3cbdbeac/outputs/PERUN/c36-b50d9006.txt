### Decision Framework: Notification Center vs. Alert Filtering

**Current Evidence**
*   **Problem Signal:** 70% of Tokyo user testing participants could not locate recent alerts, resulting in missed deadlines.
*   **Current State:** Notifications are pushed directly to the device OS; users report feeling overwhelmed.
*   **Proposed Solution:** A centralized in-app notification hub.
*   **Primary Risk:** Adding a new layer may increase cognitive load and create another ignored surface (feature bloat) rather than solving the root cause of overwhelm.

**Option A: Build a Centralized Notification Hub**
*   **Hypothesis:** Aggregating alerts in one place reduces confusion and improves task completion.
*   **Potential Upside:** Creates a single source of truth; allows users to catch up on missed items they dismissed from the OS.
*   **Potential Downside:** Increases interface complexity; risks becoming a "graveyard" for ignored alerts; requires significant UI real estate and maintenance.
*   **Verdict Condition:** Build only if users explicitly express a need to *review history*, not just manage current noise.

**Option B: Improve Filtering and Categorization (Pre-Delivery)**
*   **Hypothesis:** Users are overwhelmed by volume, not lack of visibility. Reducing noise at the source improves focus without adding UI layers.
*   **Potential Upside:** Directly addresses the "overwhelmed" feedback; lower development cost; reduces cognitive load by preventing unnecessary interruptions.
*   **Potential Downside:** Does not solve the "cannot find recent alerts" issue if the alert was filtered out or dismissed too quickly.
*   **Verdict Condition:** Prioritize if the root cause is identified as "too many low-value pings" rather than "poor organization."

**Riskiest Assumption & Required Test**
*   **Assumption:** The inability to find alerts is caused by a lack of a central list, rather than the sheer volume or poor categorization of incoming alerts.
*   **Cheapest Test (Before April 22nd Sprint):** Conduct a "Switch Interview" or targeted follow-up with 5 of the users who missed deadlines. Ask specifically: *"Walk me through the last time you missed a deadline. Were you unaware the alert existed, or did you see it and choose to ignore it?"*
*   **Kill Threshold:** If >50% of respondents say they "saw it but ignored it" or "didn't notice it because of too many other pings," **do not build the Hub**. Pivot to filtering/categorization. If >50% say "I dismissed it by accident and couldn't find it again," proceed with the Hub prototype.

**Recommendation for Design Team & CEO**
Do not commit the full 10-day sprint to building the Hub yet. The evidence (70% can't find alerts) supports a visibility problem, but the user sentiment (feeling overwhelmed) suggests a volume problem. Building a Hub solves visibility but exacerbates volume.
1.  **Immediate Action:** Run the 5-user diagnostic test described above to distinguish between "lost" vs. "ignored" alerts.
2.  **Sprint Strategy:** If the test confirms users are losing track of *important* alerts after dismissal, prototype the Hub. If the test confirms users are drowning in noise, use the sprint to build smart filtering/categorization rules instead.
3.  **Non-Goal for This Stage:** Do not build complex archiving, search, or bulk-action features for the Hub until the core value of "reducing missed deadlines" is validated.

**Note:** This analysis relies strictly on the provided user testing data; no market size or competitor features were assumed.
