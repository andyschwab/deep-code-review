### Strategic Evaluation: Public API for Sydney Connect

**Current Evidence Status**
The current data indicates **insufficient evidence** to justify a full public API build at this stage. While three integration requests represent a clear signal from 20% of your active user base (3 out of 150 companies), this sample size is too small to validate the assumption that an API will reduce support volume by ten hours weekly or that it serves the broader market. Proceeding to a full build now risks consuming your lead developer's capacity on an untested assumption regarding engineering overhead versus support savings.

**Pros (Based on Provided Facts)**
*   **Targeted Demand:** Three distinct developer teams have explicitly requested direct access to routing data for internal dashboards.
*   **Potential Efficiency:** There is a hypothesis that automating data exports could save approximately ten hours of manual support work per week.
*   **Customer Retention:** Delivering on these specific requests may secure the loyalty of these three early-adopter companies.

**Cons & Risks (Based on Provided Facts)**
*   **Resource Constraint:** Your lead developer is already at capacity with core feature work; adding API stability and documentation maintenance creates an immediate bottleneck.
*   **Unverified Assumption:** The belief that support tickets will drop by ten hours/week is unproven. These three users might require *more* support during integration than they save in exports.
*   **Limited Sample:** Three requests (2% of total market potential if scaling, or 20% of current base) do not confirm a broader market need worthy of a "public" API infrastructure.
*   **Opportunity Cost:** Diverting focus from core features to API infrastructure could stall the primary product roadmap without a guaranteed return.

**Recommendation: The "Concierge" Test (Next Steps)**
Do not build the public API infrastructure yet. Instead, run a **cheapest-possible test** before next Friday's update:
1.  **Manual Concierge:** Offer the three requesting teams a manual, scripted data export service (e.g., a secure webhook or scheduled CSV delivery) that mimics the API output.
2.  **Measure Real Effort:** Track exactly how many hours your team spends maintaining this manual process for three clients. If it takes >2 hours/week for three clients, a full API will likely exceed your capacity.
3.  **Validate Support Reduction:** Verify if these users actually stop sending support tickets once they have the data.
4.  **Decision Rule:** If the manual process saves net time and the users remain engaged after two weeks, *then* prioritize the API build. If the manual process drains resources, the API is likely a net negative at this stage.

**Response to Interested Parties:**
Inform the three teams that you are launching a "Developer Early Access" program starting next week where you will personally facilitate their data integration to ensure it meets their exact needs, rather than releasing a generic public API immediately. This buys time for validation without over-promising infrastructure you cannot yet support.

*Note: This evaluation relies strictly on the "riskiest assumption" framework; do not fabricate market size or developer hours beyond the figures provided.*
*The "20% of active users" metric is significant but must be weighed against the absolute volume (3 companies) before committing scarce engineering resources.*
