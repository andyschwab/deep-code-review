### Decision Framework: Offline Mode vs. Low-Bandwidth Optimization

**Current Status:** UNVERIFIED. You have strong evidence of a problem (47 complaints), but no evidence that your proposed solution (full offline sync) is the *cheapest* way to solve it, or that the technical risk is acceptable within your constraints.

#### 1. The Riskiest Assumption Gate
**Assumption:** "A robust local database sync is the only way to stop data loss, and the technical complexity of conflict resolution can be solved within 8 weeks."
**Risk Level:** Critical (High Impact × High Uncertainty). If conflict resolution fails, you corrupt farmer data, destroying trust permanently.

**Required Test Before Full Build:**
Do not start the 8-week build yet. Run a **Concierge/Wizard-of-Oz test** for 10 days:
*   **Action:** Equip 5 users in remote zones with a simplified form tool that saves locally but *does not* auto-sync complex edits. When they reconnect, a human operator manually merges their entries or calls them to resolve conflicts.
*   **Metric:** Time spent resolving conflicts per user vs. data recovered.
*   **Kill Threshold:** If manual conflict resolution takes >15 minutes per user per day, or if >10% of records cannot be reconciled logically, **DROP** the automatic sync plan. The complexity is too high for an 8-week window; pivot to "submit-only" offline mode (no edits) or low-bandwidth optimization.

#### 2. Critical Unknowns (To Be Filled by Technical Co-Founder)

| Unknown | How to Obtain Evidence | Decision Rule |

#### 3. Critical Unknowns (To Be Filled by Field Ops Manager)

| Unknown | How to Obtain Evidence | Decision Rule |
| :--- | :--- | :--- |
| **Workflow Reality** | "Show me the last time you lost data." Watch them simulate the entry. | If they usually work alone on a plot, conflict risk is low. If they collaborate in real-time, risk is high. |

| **Impact on DAU** | Define the baseline: What is the current DAU of the 47 complainers? | If offline mode only recovers lost data but doesn't enable *new* workflows, the 20% DAU increase assumption is unproven. |

#### 4. Recommendation Path
*   **Path A (Build Offline):** ONLY IF conflict frequency is low (<5%) OR the concierge test shows conflicts are easily resolved manually.
*   **Path B (Optimize Bandwidth):** IF the root cause is timeouts rather than total disconnection, or if conflict complexity exceeds the 8-week capacity. This is the safer fallback to meet the June 30 deadline.
*   **Path C (Hybrid "Submit-Only"):** Allow offline data *entry* but disable offline *editing* of existing records. This eliminates 90% of conflict logic while solving the data loss complaint.

**Next Step:** Run the 2-day technical spike on conflict logic and the 5-user concierge test immediately. If either fails the kill thresholds, switch to Path C or B.
