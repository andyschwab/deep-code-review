**Subject: Decision Brief – Public API vs. Mobile Dashboard (Oct 30 Review)**

**Current Evidence Status: UNVERIFIED**
We possess three specific requests (Maplesoft + 2 others) citing a 24-hour CSV delay. We lack evidence that this represents broader market demand or that an API will secure longer contracts. Building a public API now carries a high risk of over-engineering a niche workflow.

**1. The Riskiest Assumption**
*Assumption:* "Three enterprise requests indicate a broader market need, and a public API is the primary driver for contract renewal."
*Risk:* If this is isolated to these three partners, building a secure, documented, public-facing API is wasted capacity that delays the mobile dashboard (which may serve a larger user base).
*Status:* Untested. Do not build the full solution yet.

**2. Required Validation (Before Oct 30 Commitment)**
Do not rely on stated intent ("we want an API"). Validate via behavior or specific constraints before the roadmap meeting:
*   **The "Willingness to Pilot" Test:** Contact the three requesting partners immediately. Offer a **private, undocumented beta endpoint** (Concierge/Wizard-of-Oz style) within 5 days if they commit to a 3-month contract extension or a paid pilot fee.
    *   *Kill Threshold:* If fewer than 2 of the 3 partners agree to a committed pilot or payment in exchange for early access, the assumption of "strategic lock-in" is false. Treat as a niche custom integration, not a public product feature.
*   **The "Broader Demand" Check:** Survey the top 20 customers (excluding the 3 requesters). Ask: "How many hours per week do you spend manually reconciling inventory data?"
    *   *Kill Threshold:* If fewer than 20% report >2 hours/week of manual friction, broader demand is unproven.

**3. Strategic Recommendation for Oct 30**
*   **If Validation Fails (Likely):** Classify "Public API" as a **Non-Goal** for the next stage.
    *   *Action:* Build a narrow, private script solely for the three partners (manual deployment). This solves their 24-hour delay without incurring the maintenance burden of a public API.
    *   *Focus:* Proceed with the **Mobile Dashboard Redesign**, assuming it addresses a verified, broader user pain point.
*   **If Validation Passes:** Only then prioritize the Public API.
    *   *Scope:* Define the MVP strictly around the data fields these three partners actually use. Do not build "generic" endpoints.

**4. Non-Goals (Explicit Scope Defense)**
*   **No Public Documentation/Developer Portal:** Until 5+ paying customers commit to an API-driven workflow, do not build self-serve docs or key management UI.
*   **No Generic Data Model Expansion:** Do not expose full inventory schema. Expose only the specific fields requested by the pilot partners.
*   **No SLA Guarantees:** Until the API is a core revenue driver, explicitly exclude API uptime from standard SLAs to prevent operational fragility.

**Decision Rule:**
If the "Willingness to Pilot" test does not yield signed commitments by Oct 25, the steering committee must reject the Public API proposal. The cost of building/maintaining a secure public interface exceeds the value of three manual CSV uploads. Solve the immediate problem with a private script; reserve engineering capacity for the Mobile Dashboard until broader API demand is empirically proven.

**Next Step:** Run the "Willingness to Pilot" conversation with the three partners within 48 hours and report the binary outcome (Commitment Yes/No) to the CTO prior to the grooming session.

*Note: This assessment relies strictly on the three known requests; no market size or broader adoption figures were invented. The "kill thresholds" above are proposed decision rules based on your team's capacity costs, to be confirmed by you.*
