### Emergency Migration Plan: Horizon Stays (8-Hour Window)

**1. Immediate Decision Required: Fallback Protocol**
You must decide **now** on the "Read-Only Freeze" trigger.
*   **Decision:** Authorize a hard freeze on all write operations (new bookings/modifications) to the *old* system at **T-minus 2 hours** (4:00 AM).
*   **Rationale:** Since rollback is impossible, you cannot risk data divergence. Any booking attempted after the freeze begins must be queued manually or directed to a static landing page until the new system confirms write stability. Do not attempt a live dual-write synchronization; the risk of conflict is too high given the timeline.

**2. Work Session Structure (Next 8 Hours)**

*   **Phase 1: Validation & Freeze Prep (Hours 0–2)**
    *   Verify integrity of the 450-hotel dataset in the staging environment of the new system.
    *   Prepare the "Maintenance Mode" switch for the old platform.
    *   **Goal:** Confirm data parity and ready the kill-switch for incoming traffic.

*   **Phase 2: The Cutover Window (Hours 2–4)**
    *   Execute the Read-Only Freeze on the old system.
    *   Perform the final delta migration (capturing the last 48 hours of transactions).
    *   Run automated checksums on critical tables (Bookings, Payments, Guest Profiles).
    *   **Goal:** Zero data loss confirmation.

*   **Phase 3: Smoke Testing & Warm-Up (Hours 4–6)**
    *   Internal team tests real-world booking flows on the new system.
    *   Load balancers gradually shift 5% of read traffic to verify performance under load.
    *   **Goal:** System stability verification before public exposure.

*   **Phase 4: Go-Live & Monitoring (Hours 6–8)**
    *   Switch DNS to point 100% to the new platform.
    *   Lift the maintenance freeze; enable public bookings.
    *   Engineering team shifts to high-intensity monitoring of error logs and latency.
    *   **Goal:** Live and stable by 6:00 AM.

**3. Task Delegation**

*   **Database Specialists (6 Engineers)**
    *   **Primary Owner:** Final Delta Migration & Checksums.
    *   **Tasks:**
        *   Script and execute the extraction of the last 48 hours of transaction logs.
        *   Perform row-level counts and hash validation between old and new databases.
        *   Manage the database connection pooling and indexing optimization on the new cluster to handle the morning surge.
        *   Stand by to manually reconcile any failed transaction records identified during the checksum phase.

*   **Frontend/Platform Team (6 Engineers)**
    *   **Primary Owner:** Traffic Control & User Experience.
    *   **Tasks:**
        *   Deploy the "System Maintenance" static page for the freeze window.
        *   Update API endpoints to point to the new database cluster.
        *   Implement client-side queuing logic for any users attempting to book during the cutover.
        *   Monitor real-user metrics (RUM) for latency spikes or JavaScript errors post-switch.
        *   Prepare customer-facing communication templates in case of minor delays.

**4. First Concrete Action**
**Convene a 15-minute war room sync immediately.** Have the Lead DBA present the exact script for the "Read-Only Freeze" and the Lead Frontend Engineer confirm the deployment status of the maintenance page. Once these two artifacts are verified, authorize the timeline start. Do not write a single line of code or run a migration script until this alignment is confirmed.

*Note: This plan assumes the new infrastructure is already provisioned and capable of handling the load; if infrastructure scaling is incomplete, the 6 AM deadline is at extreme risk.*
*Prioritize data integrity over feature completeness; if a non-critical module fails, disable it rather than delaying the launch.*
