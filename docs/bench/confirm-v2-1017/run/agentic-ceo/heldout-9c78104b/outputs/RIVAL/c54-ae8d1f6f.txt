**Pre-Deployment Migration Sequence**

1.  **Pre-Staging Verification:** Confirm integrity of the full dataset on the test server and validate that the 50 Mbps satellite uplink is dedicated solely to migration traffic.
2.  **Incremental Data Sync:** Begin transferring static assets and historical booking data to the shipboard network, leaving only real-time changes for the final window.
3.  **System Freeze:** Implement a read-only lock on the test server's booking system to prevent new guest preference updates during the final cutover.
4.  **Final Delta Sync:** Transmit only the data changed since the incremental sync began.
5.  **Local Integrity Check:** The shipboard team verifies database schema and record counts against source checksums before enabling local services.
6.  **Controlled Cutover:** Switch DNS routing from the test server to the shipboard network.
7.  **Smoke Testing:** Execute limited internal transactions to confirm end-to-end functionality for dining, shows, and excursions.
8.  **Go/No-Go Decision:** Based on smoke test results, officially open the system to the 4,000 passengers and crew.

**Required Fallback Scenarios for Approval**

*   **Scenario A (Corruption Detected):** If the local integrity check reveals any mismatch in guest preference profiles, immediately abort the cutover. Revert DNS to the test server and operate in "offline mode" using the last known good local cache until satellite bandwidth allows a re-sync.
*   **Scenario B (Bandwidth Saturation):** If the final delta sync exceeds the estimated time window due to throughput drops, halt non-essential transfers. Proceed with cutover using only critical reservation data, deferring large media assets to post-departure overnight updates.
*   **Scenario C (Service Failure):** If smoke testing fails on core modules (dining or shows), trigger an immediate rollback to the test server. Activate manual paper-based backup protocols for onboard activities while the development team diagnoses the shipboard environment.

**First Diagnostic Check for Network Lead**

The network lead must immediately perform a **bidirectional latency and packet loss test** between the ship's local database server and the application server cluster over the internal shipboard LAN. This confirms that the local network infrastructure can handle the high-concurrency load of 4,000 users before any external data migration attempts begin, ensuring that potential bottlenecks are identified as local hardware issues rather than migration errors.

Note: Ensure all fallback protocols are documented in the captain's log before the September 1st departure. Manual backup forms must be physically printed and distributed to activity desks prior to the system freeze.
