### Shield Mutual Claims Engine Rewrite: 10-Day Execution Plan

**Immediate Action (First 15 Minutes)**
Convene the 15 engineers and the founder for a strict "Code Freeze & Triage" standup.
1.  **Freeze:** Halt all non-critical maintenance on the old system; only life-critical bugs get fixes.
2.  **Assign Scribes:** Designate two seniors to document the exact schema of "pending claims" to isolate the migration risk immediately.
3.  **Split Teams:** Formally assign the 4 Senior Architects to the Core Logic and Migration Strategy. Assign the 11 Junior/Mid engineers to the Peripheral Modules and Test Harness creation.

**Order of Operations (Days 1–10)**
*   **Days 1–2: Architecture & Migration Sandbox.** Seniors define the new data model and build a read-only mirror of the production database. Juniors build the automated test suite based on current production behaviors. *Goal: Zero writes to production yet.*
*   **Days 3–5: Core Logic Development.** Seniors code the new claims processing engine using the frozen schema. Juniors build the API wrappers and UI connectors. Parallel execution is critical here.
*   **Day 6: Internal Integration & Dry Run.** Merge code. Run the first full data migration simulation on the mirror environment. Validate that "pending claims" history remains intact and queryable.
*   **Day 7: Remediation.** Fix any data corruption or logic errors found in the Day 6 dry run. This is the last chance to alter code before the audit.
*   **Day 8: External Audit.** Submit the system and the Day 6 migration logs for the mandatory compliance audit. No new code changes during the audit window.
*   **Day 9: Audit Remediation & Final Polish.** Address only critical findings from the audit. Prepare the deployment script.
*   **Day 10: Deployment & Monitoring.** Execute the migration during the lowest-traffic window. Monitor the first 1,000 live claims closely.

**Team Assignments**
*   **Senior Architects (4 People):**
    *   **Responsibility:** Data Migration Strategy, Core Claims Logic, Compliance Schema, and Audit Preparation.
    *   **Reasoning:** They hold the institutional knowledge required to prevent data corruption and ensure the logic handles edge cases without violating regulations. They must own the "risky" path.
*   **Junior/Mid Engineers (11 People):**
    *   **Responsibility:** Building the Test Harness, API Endpoints, Frontend Integration, Logging Infrastructure, and Documentation.
    *   **Reasoning:** Their work is essential but modular. If they make mistakes, it rarely results in permanent data loss. They provide the safety net (tests) and the interface for the seniors' core logic.

**Critical Architectural Decisions Required Today**
1.  **Migration Strategy:** Will you use a "Strangler Fig" pattern (routing traffic gradually) or a "Big Bang" cutover? Given the 10-day constraint and compliance risk, a **Big Bang with a verified rollback script** is likely the only viable option, but this must be confirmed now.
2.  **Data Consistency Model:** Decide if the new system requires strong consistency (blocking during migration) or eventual consistency. For financial claims, **strong consistency** is mandatory to prevent double-paying or losing claim history.
3.  **Audit Scope Definition:** Define exactly what artifacts the external auditor needs on Day 8. Is it code access, log files, or a specific report? Ambiguity here will waste Day 8.

**Note:** The single biggest failure point is the Day 6 dry run; if the data mirror does not match production perfectly, the project fails.
Prioritize the "read-only mirror" setup above all other coding tasks in the first 48 hours.
