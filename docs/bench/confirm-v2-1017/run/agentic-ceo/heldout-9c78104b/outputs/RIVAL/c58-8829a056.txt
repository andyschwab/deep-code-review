**Deliverable: 20-Day Critical Path Plan for National Park Reservation System**

**Phase 1: Architecture & Schema Lock (Days 1–5)**
*   **Action:** Conduct immediate architectural review focusing on the irreversible database schema change.
*   **Protocol:** Implement a "Shadow Schema" strategy. Do not alter the live production schema directly. Instead, build the new zoning rules in a parallel schema or separate database instance and migrate data via dual-write mechanisms during low-traffic windows.
*   **First Action Item (Guaranteed Stability):** **Freeze all non-critical code commits and initiate a full-state backup of the current production database to an immutable, off-site storage location.** While you noted "no rollback option" for the schema logic, having a byte-for-byte restore point is the only absolute guarantee against total data loss corruption. If the migration script fails catastrophically, the only recovery path is a full restore to a previous point in time, even if it means losing the last few hours of bookings.

**Phase 2: Infrastructure Scaling & Load Testing (Days 6–14)**
*   **Infrastructure:** Deploy auto-scaling groups for the application layer immediately. Configure the load balancer to handle 10,000 daily visitors (approx. 7 requests/second average, but spike capacity must hit 200+ req/min easily).
*   **Load Testing Lead:** Assign your **most senior backend engineer with specific experience in database contention** to initiate the load testing protocol. This individual must understand locking mechanisms and transaction isolation levels, as the bottleneck will likely be database row locks during the schema transition, not just raw throughput.
*   **Testing Scope:** Simulate 15,000 daily visitors (150% of target) to identify breaking points before Day 20.

**Phase 3: Deployment & Contingency (Days 15–20)**
*   **Deployment Strategy:** Use a Blue-Green deployment model. Spin up the new infrastructure with the new schema alongside the old system. Route internal traffic first, then 1% of public traffic, scaling up only after 24 hours of stability.

**Director Approval Required: Contingency Plans**
As the director, you must explicitly approve the following three contingency scenarios before Day 1:
1.  **The "Hard Stop" Protocol:** Define the exact metric (e.g., error rate > 1% or latency > 2s) that triggers an immediate halt to the migration, reverting traffic to the legacy system while engineers diagnose the shadow schema.
2.  **Data Triage Procedure:** If the schema migration corrupts a subset of bookings, approve the protocol for manual reconciliation. This includes identifying affected users within 1 hour and a pre-drafted communication template offering priority re-booking credits.
3.  **Capacity Throttling:** Authorize the implementation of a virtual waiting room (queue system) that activates automatically if requests exceed 180/minute, protecting the database from total collapse even if the scaling efforts fall short.

**Team Member Assignment Summary**
*   **Load Testing Lead:** Senior Backend Engineer (Database specialization).
*   **Schema Migration Lead:** Lead Database Administrator (paired with a second engineer for real-time code review).
*   **Infrastructure Lead:** DevOps Engineer (focused on auto-scaling and load balancer configuration).

**Note:** The "no rollback" constraint makes the pre-migration immutable backup the single most critical safety net; do not proceed without verifying its restorability.
**Note:** Ensure the load testing environment mirrors production data volume exactly, as performance often degrades non-linearly with dataset size.
