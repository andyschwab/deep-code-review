**Decision:** Execute a "Validate-Then-Archive" sequence immediately. Do not archive any historical data until a full dry-run confirms new user profiles link correctly to active checkouts. The single governing number is **9 days**; this timeline allows zero recovery time for data corruption, making data integrity the only constraint that matters.

**Figures:**
*   **Load:** 15,000 registrations / 60 minutes = **250 registrations/minute** (4.2 per second) sustained peak.
*   **Staff:** 6 total personnel (4 librarians + 2 IT).
*   **Budget:** $0 overtime (strict hard cap).
*   **Risk Window:** If archive runs before validation, **100%** of active checkouts become unreturnable.

**Roadmap & Role Split**

**1. Administrative Choices (Elena – Librarian Lead)**
*   **Freeze Policy:** Authorize a 24-hour read-only freeze on the old system during the final migration window to prevent new data entry during the switch.
*   **Communication Draft:** Approve a pre-written notice for patrons explaining potential brief downtime on May 31st.
*   **Rollback Trigger:** Define the specific failure condition (e.g., " >5% profile mismatch") that mandates aborting the launch and reverting to the manual backup process.

**2. Technical Executions (IT Volunteers)**
*   **Environment Staging:** Set up a sandbox copy of the current database today.
*   **Load Simulation:** Run a script simulating 250 requests/minute against the sandbox to identify bottlenecks.
*   **Linkage Verification:** Execute the "Validate-Then-Archive" test: create dummy users with active loans, run the migration script, and verify the link remains intact before touching real data.

**First 30 Minutes: Stability & Readiness Protocol**

*   **Minutes 0–5: Asset Inventory & Freeze.**
    *   Confirm the exact size of the borrowing history database (GB/rows).
    *   Verify the backup from last night is restorable. **Stop all non-essential writes** to the production database immediately to ensure a clean baseline.
*   **Minutes 5–15: The "Dry-Run" Setup.**
    *   IT clones the production database to the staging server.
    *   Librarians identify 50 real-world complex accounts (users with fines, holds, and multiple checkouts) to serve as the "Golden Set" for testing.
*   **Minutes 15–25: Critical Path Test.**
    *   IT runs the migration script on the staging server using the "Golden Set."
    *   **Crucial Step:** Attempt to "return" a book for a migrated user in the new system. If this fails, the archive logic is flawed. Do not proceed to full migration.
*   **Minutes 25–30: Go/No-Go Decision.**
    *   If the Golden Set links hold: Schedule the full archive for May 30th (night before launch).
    *   If links break: Halt. The script requires rewriting; do not attempt to fix logic during the launch window.

**Halt Trigger:** If the staging test shows *any* loss of linkage between a user and an active checkout, the migration is halted indefinitely until the script is patched and re-verified.
**Fallback Trigger:** If system response time exceeds 2 seconds under the 250/min load test, activate the manual paper-registration protocol for the first hour of launch to prevent system crash.

*Note: All testing must occur on cloned data; never test archiving logic on the live production database.*
