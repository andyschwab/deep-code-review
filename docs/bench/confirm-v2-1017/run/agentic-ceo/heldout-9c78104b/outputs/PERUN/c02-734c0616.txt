**Decision: Halt immediate code rewriting. Proceed with a 4-hour "Freeze & Verify" phase before any migration or deployment planning.**

The single number driving this decision is **0**: the current count of verified test cases mapping the legacy interest calculation behavior. Deploying a rewrite on a legacy system with an unfamiliar team, affecting 40,000 accounts, without a behavioral baseline guarantees data corruption. The irreversible nature of the schema migration means a failed deployment results in days of downtime, breaching your SLA far more severely than a planned delay.

**Figures:**
*   **Risk Exposure:** 40,000 accounts × [Unknown Error Rate] = Potential total financial restatement.
*   **Time Budget:** ~96 hours until Monday morning.
*   **Constraint:** 2-hour max downtime window.
*   **Team Velocity:** 5 developers × 0% legacy context = High probability of regression without strict guardrails.

**Order of Operations**

1.  **Phase 1: Behavioral Lockdown (Hours 0–4)**
    *   **Action:** Do not write new code. The team must write integration tests that capture the *current* output of the legacy system for a representative sample of the 40,000 accounts (including edge cases like rate changes mid-cycle).
    *   **Goal:** Create an executable specification of "what the system does now" vs. "what the regulations say it should do."

2.  **Phase 2: Parallel Implementation & Verification (Hours 4–20)**
    *   **Action:** Develop the new calculation module in isolation. Run the new module against the captured test data from Phase 1.
    *   **Constraint:** The new module must match the legacy output exactly *except* where the legacy output is proven non-compliant.

3.  **Phase 3: Dry-Run Migration (Hours 20–30)**
    *   **Action:** Execute the schema migration and data backfill on a full production clone. Measure the exact time required.
    *   **Goal:** Validate the <2-hour downtime constraint. If this exceeds 90 minutes, the plan fails.

4.  **Phase 4: Staged Deployment (Monday Pre-Audit)**
    *   **Action:** Execute the migration during the lowest-traffic window. Keep the legacy binary available for immediate rollback if the new calculations diverge from the verified test suite.
