## Add composite index on orders(customer_id, created_at)

Priya, this touches the schema, so it needs your approval. One open question for you: I haven't measured the index's effect on insert throughput (details below).

### What and why

This adds a composite index on `orders(customer_id, created_at)` in Postgres. The customer order history endpoint currently does a sequential scan, and p95 latency is around 1.8 s for the largest tenants.

### Results on staging

On a staging copy of production data (about 42 million rows), the same query dropped to roughly 35 ms with the index.

### Migration

- Uses `CREATE INDEX CONCURRENTLY`, so there is no table lock.
- It took 11 minutes on staging. Production is about 1.4x bigger, so I expect roughly 15 minutes.
- The index adds about 2.1 GB of disk.

### Not measured: write overhead

I have not measured the effect on insert throughput. Orders peak around 900 writes per second during sales events, and I don't know whether one more index matters at that rate. Do you want a write benchmark on staging before this merges, or are you comfortable with the risk given the rollback below?

### Rollback

Drop the index. No code depends on it yet, so nothing else needs to change.
