**Pre-Launch Safety Plan: Northwind Playground Gate Automation**

**1. Immediate Harm Inventory & Risk Acknowledgement**
The current failure mode (gates locking but failing to unlock) constitutes an unsafe high-stakes automation causing physical entrapment. This is a critical safety violation. No feature causing irreversible or dangerous physical confinement can ship with full autonomy. The "worst realistic case" is injury or panic due to inability to exit during an emergency.

**2. Mandatory Human-in-the-Loop (HITL) Gate**
Since physical override buttons are prohibited, the software architecture must introduce a digital human gate before any "Lock" command executes and, crucially, a guaranteed "Unlock" fail-safe.
*   **Locking Logic:** Rain detection triggers an *alert* to a remote monitoring dashboard, not an immediate lock. A human operator must confirm the lock command within a defined window.
*   **Unlocking Logic:** Unlocking must be the default state upon any system ambiguity, sensor dropout, or timeout. If the system cannot verify "safe to unlock" conditions within 30 seconds of a lock event, it must automatically revert to "Unlocked."
*   **Remote Override:** Implement a 24/7 remote operations center (even if staffed by an on-call developer rotation) with immediate digital override capabilities. This satisfies the "human gate" requirement without physical infrastructure.

**3. Measurement & Evaluation Plan (Runnable Tests)**
Do not assert safety; measure it. Execute the following test rows before launch:
*   **Probe Set A (Sensor Failure):** Simulate rain sensor dropout mid-lock cycle.
    *   *Pass Condition:* Gate unlocks automatically within 10 seconds of signal loss.
    *   *Stop Condition:* Any test where the gate remains locked >15 seconds after signal loss blocks launch.
*   **Probe Set B (Communication Latency):** Simulate high latency between detection and actuation.
    *   *Pass Condition:* System defaults to "Unlocked" if round-trip verification exceeds 5 seconds.
*   **Probe Set C (Adversarial/Edge Case):** Input contradictory weather data (e.g., rain sensor active, temperature sensor indicating freezing/snow where rules differ).
    *   *Pass Condition:* System defaults to the safest state (Unlocked) and alerts human review.

**4. Transparency & Uncertainty Artifacts**
*   **Confidence Tiers:** Do not display raw sensor percentages to operators. Use defined tiers: "Confirmed Precipitation" (multiple sensors agree), "Single-Source Alert" (requires human verification), or "System Uncertain" (auto-unlock).
*   **Model/Data Card:** Publish a versioned artifact detailing:
    *   *Intended Use:* Weather-based access control only; not a security or emergency egress system.
    *   *Limitations:* Explicitly state known failure modes (sensor occlusion, network latency).
    *   *Performance:* Report unlock success rates by weather subtype (drizzle vs. storm) based on the evaluation above. Mark unmeasured scenarios as `UNVERIFIED`.

**5. Governance & Legal Routing**
*   **Owner Assignment:** Name a specific individual responsible for the "Unlock" logic integrity.
*   **Regulatory Routing:** The entrapment risk likely triggers strict liability under local German safety regulations and potentially the EU AI Act (high-risk physical safety application). **Route immediately to legal counsel** to determine mandatory disclosure requirements and liability frameworks. Do not assume the current design is compliant.
*   **Launch Decision:** If the automatic unlock fail-safe cannot be proven 100% reliable in testing, the feature must not launch in autonomous mode. The fallback is a "Warning Only" mode until reliability is verified.

**Note:** This plan treats the entrapment bug as a fundamental architectural flaw requiring a process control fix, not just a code patch.
