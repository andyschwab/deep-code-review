### Lightweight Offline Triage Validation Strategy

**1. Construct the "Golden Set" of Simulated Records**
Before deployment, your seven doctors must curate a fixed dataset of 50–100 simulated patient records on a local USB drive or tablet. This set must be heavily weighted toward edge cases:
*   **Positive Controls (Critical):** 20 cases that *must* trigger an emergency specialist referral (e.g., chest pain with diaphoresis, stroke symptoms, severe trauma). If the system routes any of these to a general practitioner, it is a critical failure.
*   **Negative Controls (Routine):** 20 cases that *must* route to general practitioners (e.g., mild fever, routine check-up).
*   **Ambiguous/Edge Cases:** 10–20 records with missing data or conflicting symptoms to test how the system handles uncertainty.

**2. Execute the "Blind Dry Run" Protocol**
Local clinic staff will run these simulated records through the scheduler on the offline device without knowing the expected outcome beforehand.
*   **Input:** Staff enters the symptom data exactly as they would for a real patient.
*   **Output Recording:** Staff records the system's recommended routing on a simple paper checklist next to the case ID.
*   **Comparison:** Once the batch is complete, the lead doctor compares the system's outputs against the pre-defined "Golden Set" answers.

**3. Define the Stop Condition (The Human Gate)**
Establish a zero-tolerance threshold for high-stakes errors before any real patient data is processed:
*   **Fail Condition:** If *any* Positive Control (critical case) is misrouted to a general practitioner, the system **must not** be used for live triage. The model requires immediate retraining or rule adjustment.
*   **Pass Condition:** 100% accuracy on critical cases is required. Routine case errors are noted for improvement but do not necessarily block launch if critical safety is preserved.

**4. Implement Uncertainty Tiers, Not Percentages**
Since connectivity prevents real-time cloud validation, the offline system must display its confidence using defined text tiers rather than raw numbers. Configure the output to show:
*   **"EMERGENCY – Confirm Immediately"** (High confidence in criticality)
*   **"Urgent Review Needed"** (Mixed signals)
*   **"Routine"** (Clear non-critical presentation)
*   **"Unverified – Human Review Required"** (Low confidence or missing data)
Never display a percentage (e.g., "87% urgent") as this implies a calibration the offline model cannot guarantee. Force a human review for any case falling into the "Unverified" or "Urgent Review" tiers.

**5. Documentation and Ownership**
Create a one-page "Model Card" stored locally on the device. It must list:
*   **Intended Use:** Rural triage support only; not a replacement for clinical judgment.
*   **Known Limitations:** Specific symptoms or demographics where performance was not verified.
*   **Owner:** Name the lead doctor responsible for reviewing any misrouted cases.
*   **Validation Status:** Mark the metrics as "Locally Verified via Golden Set [Date]" rather than claiming global safety.

**Note:** This strategy measures output behavior locally without cloud dependency. Legal requirements for AI disclosure in medical settings must be routed to counsel; this plan treats disclosure as a safety control regardless of legal mandate.
