### Bushfire Alert System: Coverage and Stress-Test Plan

Given the high-stakes nature of this system—where failure risks life and property—the following plan addresses your specific concerns about geographic gaps and network congestion. This is a measurement and management plan, not a safety certification. No test can prove the system is "safe" or "unbiased"; it can only reveal residual risks for you to manage before the ship decision.

#### 1. Verify Geographic Coverage (Map & Measure)
Do not rely on aggregate pass rates. You must verify coverage per specific high-risk zone.
*   **Harm Inventory:** The specific harm here is **unsafe automation of high-stakes actions** (failing to alert) and **bias/unfair outcomes** (systematically missing specific geographic pockets or demographics).
*   **Runnable Test Rows:** Create one test row per identified high-risk zone (e.g., "Zone A: Blue Mountains North").
    *   **Probe Set:** Inject simulated sensor data for smoke/heat specific to the topology of that zone. Include a **positive control** (known fire signature) and a **negative control** (known non-fire heat source like a factory).
    *   **Metric:** Alert generation latency and success rate *per zone*.
    *   **Threshold:** Set a zero-tolerance threshold for missed positive controls in any high-risk zone. If Zone A fails, the system does not ship, regardless of success in Zone B.
    *   **Stop Condition:** Any missed alert in a high-risk zone triggers an immediate block on launch.
*   **Edge Cases:** Specifically test edge-case inputs where terrain might block sensor lines of sight or where historical data is sparse.

#### 2. Stress-Test Notification Delivery (Measure)
Network congestion during a fire is a known variable, not an edge case.
*   **Probe Set:** Simulate peak network congestion (e.g., 90% packet loss, high latency) combined with a surge in alert volume.
    *   **Positive Control:** Ensure at least one critical alert gets through via fallback channels (e.g., SMS if data fails, satellite uplink if available).
    *   **Negative Control:** Ensure the system does not spam users with duplicate alerts when retries fail.
*   **Metric:** Delivery success rate and time-to-receipt under degraded conditions.
*   **Threshold:** Define a minimum acceptable delivery rate (e.g., 95% within 2 minutes) based on owner risk appetite, not a generic industry standard.
*   **Stop Condition:** If delivery falls below the threshold during simulation, the automated push is gated.

#### 3. Manage Residual Risk (Manage)
*   **Human-in-the-Loop Gate:** Because this is a high-stakes, irreversible action (public alerting), you must have a human-in-the-loop gate for the final "go/no-go" decision on any ambiguous sensor reading or system anomaly. Fully autonomous execution without a fallback review mechanism is the failure mode this skill prevents.
*   **Show Uncertainty:** If the system confidence in a detection is low (e.g., conflicting sensor data), do not output a false-precision percentage like "64% chance of fire." Instead, use defined coarse tiers (e.g., "Unverified – Manual Review Required") and route these cases to a human operator immediately.
*   **Transparency Artifact:** Before launch, produce a **model card** documenting the intended use (bushfire detection in Sydney zones), known limitations (e.g., "performance unverified in heavy rain"), and the results of the above tests broken down by zone. If a metric was not measured, label it `UNVERIFIED`; do not invent a number.

#### 4. Governance
Name the specific owner responsible for reviewing the results of each zone test and the network stress test. If the model, sensor data, or zone definitions change, this review must be repeated.

**Note:** Legal requirements for public safety alerts and liability for missed warnings must be routed to counsel; this plan does not assert legal compliance.
**Note:** If any test yields an `UNVERIFIED` result for a high-risk zone, the default stance is to block launch for that zone until measured.
