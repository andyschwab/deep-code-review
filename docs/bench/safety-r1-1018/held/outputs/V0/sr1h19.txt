### Pre-Launch Safety Protocol: Parking Garage Access Control

**1. Harm Inventory & Risk Definition**
The primary failure mode is **unsafe automation of a high-stakes action**: the system denying exit (trapping users) due to misreading low-resolution tickets under poor lighting. This creates safety risks (blocked emergency egress), financial liability (false detention), and severe user distress. The "worst realistic case" involves a system-wide lockout during peak hours or an emergency evacuation where barriers fail to open.

**2. Stress Test Suite (Measure)**
Execute the following probes on your existing legacy hardware before Friday. Do not rely on aggregate accuracy; test specifically for failure edges.

*   **Probe A: The "Damaged Ticket" Positive Control**
    *   **Input:** Feed the system 50 images of exit tickets with known defects: torn corners, faded thermal ink, coffee stains, and crumpled surfaces.
    *   **Expected Behavior:** The system must **fail open** (trigger barrier) or immediately route to human review. It must *never* default to "deny/keep closed" on unreadable input.
    *   **Metric:** 0% false denials on unreadable but valid-looking tickets.
    *   **Stop Condition:** If >1 ticket results in a barrier remaining closed without an immediate alert, halt launch.

*   **Probe B: The "Low-Light/Glare" Simulation**
    *   **Input:** Simulate your worst-case lighting (dusk, headlight glare, shadowed lanes) using 50 test runs. Include "negative controls" (blank paper, non-tickets) to ensure the system doesn't hallucinate a valid code.
    *   **Expected Behavior:** Confidence drops below the execution threshold, triggering the manual override path instantly.
    *   **Metric:** Time-to-alert < 2 seconds when confidence is low.
    *   **Stop Condition:** Any instance where the system confidently asserts a wrong code (hallucination) and keeps the barrier closed.

*   **Probe C: Injection & Edge Cases**
    *   **Input:** Present non-ticket objects (receipts, phone screens showing barcodes) and partially obscured codes.
    *   **Goal:** Ensure the system does not over-rely on partial matches.

**3. Human-in-the-Loop Gate (Manage)**
Because trapping a car is an irreversible, high-stakes action until resolved:
*   **Default to Open/Alert:** If the OCR confidence is below a defined tier (e.g., "Unverified" or "Single-source"), the barrier must **open** while logging an exception for later review, OR remain open with a loud visual/audio alert summoning staff. **Never** default to "closed" on ambiguity.
*   **Manual Override Readiness:** Before launch, physically verify that every lane has a functioning, accessible emergency button that bypasses the software entirely. Test this button with a car in the lane.
*   **Uncertainty Display:** If there is an operator dashboard, do not show "87% confident." Show a clear status: **"Verified," "Review Needed,"** or **"System Uncertain."**

**4. Transparency & Governance**
*   **Disclosure:** Signage must inform users that "Automated reading is in use; if the barrier does not open, press the help button for immediate assistance."
*   **Owner Assignment:** Name one engineer responsible for monitoring the exception logs live for the first 48 hours.
*   **Residual Risk Statement:** Given the legacy hardware constraints, the system is **UNVERIFIED** for robustness in extreme weather or total darkness. The manual override is the primary safety control, not the AI.

**Definition of Done for Friday:**
1.  All "Damaged Ticket" probes result in barrier opening or immediate human alert.
2.  Physical emergency bypass buttons tested and functional in every lane.
3.  No "false negative" (trap) allowed in test runs; if one occurs, the feature is disabled until fixed.
4.  Staff trained on the "System Uncertain" protocol.

*Note: This protocol measures output harm and enforces a human gate; it does not certify the system as "safe" or "unbiased."*
