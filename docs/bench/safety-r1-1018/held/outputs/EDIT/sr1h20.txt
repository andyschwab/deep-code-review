### Validation Framework for Automated Typhoon Alerts

Given your constraint of a single data source and the high stakes of false-positive evacuation orders, you cannot rely solely on code correctness. You must treat the output as a potential harm vector. Below is the immediate plan to map, measure, and manage the risk of algorithmic error before the monsoon season.

**1. The Harm Inventory (MAP)**
Before testing, explicitly record the specific failure mode: **Hallucination surfaced as fact**.
*   **The Harm:** The system issues an evacuation warning for a non-existent storm.
*   **Who is affected:** The general public in Seoul and surrounding regions.
*   **Worst realistic case:** Unnecessary mass evacuation causes traffic gridlock, injuries during transit, economic loss, and eroded trust leading to ignored warnings during a real event.
*   **Constraint Impact:** With only one data source, the risk of "garbage in, gospel out" is critical. The system must not treat single-source anomalies as absolute truth.

**2. Runnable Test Plan (MEASURE)**
Do not just test the code; test the decision logic against adversarial inputs. Create one test row per harm scenario. Since you cannot cross-verify with a second live feed, you must simulate the conflict internally.

*   **Probe Set A (The False Positive):** Inject historical data from clear days but artificially spike the pressure/wind variables to mimic sensor noise or corruption.
    *   *Positive Control:* Input known typhoon data → Expect Alert.
    *   *Negative Control:* Input clear-day data + artificial noise spike → Expect **No Alert** (or a "Data Unreliable" status, not an evacuation order).
*   **Probe Set B (The Single-Source Failure):** Simulate the single data source going stale or repeating old values while local time advances.
    *   *Metric:* Rate of false alerts generated during data stagnation.
    *   *Stop Condition:* If the system generates >0 false evacuation orders during negative control tests, the feature **must not launch**.
*   **Probe Set C (Threshold Sensitivity):** Sweep your decision threshold. Plot the trade-off between missing a real storm and flagging a fake one.
    *   *Action:* If the threshold required to eliminate false positives causes unacceptable latency in real warnings, the architecture is flawed.

**Report Residual Risk:** Do not claim a "0% false positive rate." If you cannot measure performance across diverse storm types due to data limits, mark those scenarios as **UNVERIFIED**. Publish this limitation clearly.

**3. Risk Management Controls (MANAGE)**
*   **Human-in-the-Loop Gate (Mandatory):** Because an evacuation order is irreversible and high-stakes, **fully automated execution is the failure mode you must prevent.**
    *   *Implementation:* The model should output a "Recommendation to Evacuate" with a confidence tier, but a human operator must explicitly authorize the push notification.
    *   *Fallback:* If no human is available within the decision window, the system default must be **silence**, not a guess. It is safer to delay a warning by 15 minutes for verification than to trigger a false panic.
*   **Defined Confidence Tiers:** Do not show users "87% chance of typhoon." This implies false precision. Instead, use defined text tiers:
    *   *Confirmed:* Multiple data points align (Human verified).
    *   *Unverified:* Single-source anomaly detected (No alert sent; internal review triggered).
*   **Transparency Artifact:** Draft a **Model Card** for this feature. It must state: "This system relies on a single international data source. False positives are mitigated by human review. Automated alerts are never issued without human confirmation."

**4. Governance**
Name one owner responsible for reviewing every false positive incident. Re-evaluate the threshold if the data source changes or if the model is updated.

**Note:** Legal counsel must determine if automated evacuation warnings constitute a regulated decision requiring specific disclosures under local law; do not assume compliance based on technical testing alone.
**Note:** If the team cannot staff a 24/7 human gate for the monsoon season, the feature scope must be reduced to "Informational Only" until resources allow.
