### Simulation Plan: Allergen Safety & Recommendation Logic

**1. Construct the Synthetic Harm Inventory**
Before generating data, define the specific failure modes to test. For your allergen constraint, the inventory must include:
*   **False Negative (Critical):** The system recommends a product containing a known allergen for a user profile explicitly flagged with that allergy.
*   **False Positive (Exclusion):** The system incorrectly blocks safe products for a user, limiting utility.
*   **Hallucinated Ingredient:** The system invents an ingredient list or misattributes an allergen to a safe product.
*   **Over-reliance:** The interface presents recommendations as medical facts without uncertainty markers or disclaimers.

**2. Build the Adversarial Synthetic Dataset**
Since real-world trials are not possible, your synthetic dataset must be more rigorous than typical training data.
*   **Profile Generation:** Create 5,000+ synthetic user profiles. Ensure 30% represent edge cases: severe multiple allergies, rare skin conditions, and conflicting constraints (e.g., oily skin but severe sensitivity to common oil-control agents).
*   **Product Catalog:** Map your entire inventory with verified ingredient lists. Tag every known allergen (fragrances, preservatives, botanical extracts) based on global standards (e.g., EU Annex III).
*   **Control Sets:**
    *   *Positive Controls (Must Fail):* Profiles with specific allergies paired with products containing those allergens. The system **must not** recommend these.
    *   *Negative Controls (Must Pass):* Profiles with allergies paired with verified safe products. The system **must** recommend these where appropriate.

**3. Execute the "Red-Team" Simulation**
Run the recommendation engine against this dataset using automated scripts.
*   **The Allergen Sweep:** For every synthetic user, force the engine to generate top-10 recommendations. Automatically cross-reference every recommended product's ingredient list against the user's allergy profile.
*   **Injection Testing:** Feed the system malformed inputs (e.g., "I am allergic to everything except water") to ensure the logic degrades gracefully rather than hallucinating a solution.
*   **Metric Definition:**
    *   *Pass Threshold:* **Zero tolerance** for False Negatives (recommending an allergen). Even one instance is a critical failure requiring a code stop.
    *   *Acceptable Variance:* Define an acceptable rate for False Positives (over-caution), but aim for <5% to maintain user trust.

**4. Implement the Human-in-the-Loop Gate**
Because this involves potential physical harm (allergic reactions), fully automated high-stakes decisions are unsafe.
*   **Uncertainty Tiering:** If the model's confidence in an ingredient match is below a defined threshold, the output must default to "Unverified – Consult a Dermatologist" rather than a definitive recommendation.
*   **Kill Switch:** Establish a manual override protocol. If the simulation detects *any* critical failure, the launch is halted automatically.

**5. Documentation for Compliance (The Transparency Artifact)**
Do not claim the system is "safe" or "0% biased." Instead, produce a **Model Card** containing:
*   **Intended Use:** Personalized skincare suggestions, explicitly *not* medical diagnosis.
*   **Limitations:** "Tested against synthetic data; real-world variance in skin conditions may yield different results."
*   **Measured Results:** Report the exact number of synthetic profiles tested and the count of failures (e.g., "0 critical allergen failures out of 5,000 simulated scenarios").
*   **Residual Risk:** Clearly state that unknown allergens or untagged ingredients in the database remain an `UNVERIFIED` risk.
*   **Owner:** Name the specific engineer responsible for the allergen logic.

**Note:** Legal requirements for AI disclosure in health-adjacent apps vary by jurisdiction; route the final compliance sign-off to legal counsel. Never fabricate a "100% safe" metric; report only the measured simulation results.
