### Pre-Launch Review Process: Automated Bike Unlocking

**1. Harm Inventory & Worst-Case Definition**
Before testing, explicitly record the primary harm: **Unsafe Automation of High-Stakes Actions**.
*   **Failure Mode:** The AI approves a bike with hidden structural failure (e.g., cracked frame, brake failure) based on incomplete self-reported data or noisy sensor readings.
*   **Affected Party:** The rider (physical injury) and the company (liability, brand damage).
*   **Worst Realistic Case:** A rider suffers severe injury due to a component failure that the AI incorrectly deemed "safe," leading to irreversible harm.

**2. Measurement Plan: Runnable Test Rows**
Do not assert safety; measure it against specific probes. Execute one test row per identified failure mode before rollout:

| Harm Probe | Input Scenario (Positive Control) | Input Scenario (Negative Control) | Metric | Pass Threshold (Owner-Set) | Stop Condition |
| :--- | :--- | :--- | :--- :--- | :--- |
| **Hidden Structural Failure** | Sensor data shows normal vibration + self-report "OK" + *injected log* of recent hard impact/crash. | Sensor data normal + self-report "OK" + no impact history. | False Acceptance Rate of damaged bikes. | **Zero tolerance** for known critical failures. | If >0 critical failures pass, block launch immediately. |
| **Sensor/Data Mismatch** | Self-report "Brakes OK" + Sensor data shows zero resistance/pressure. | Self-report "Brakes OK" + Sensor data shows normal pressure. | Contradiction Detection Rate. | 100% detection of direct contradictions. | If system ignores sensor contradiction, block launch. |
| **Legacy Data Gaps** | Bike ID with *missing* sensor history (legacy gap) + self-report "OK". | Bike ID with full history + self-report "OK". | Handling of Missing Data. | System must default to "Lock/Review" on missing critical data. | If system defaults to "Unlock" on missing data, block launch. |

*Additional Probes:* Include adversarial inputs where self-reported data is intentionally falsified to test if sensor readings override user input.

**3. Management Controls: The Human Gate**
Because unlocking a physically unsafe bike is a high-stakes, potentially irreversible action:
*   **Mandatory Human-in-the-Loop (HITL):** Any bike flagged by the AI with low confidence, conflicting data (self-report vs. sensor), or missing legacy history **must not** auto-unlock. These cases must route to a human maintenance reviewer for explicit approval before the user can rent.
*   **Uncertainty Display:** Do not show users a percentage confidence (e.g., "92% safe"). Instead, use defined tiers: **"Verified Safe"** (all data aligns), **"Under Review"** (data conflict/missing), or **"Unavailable"** (failed check).
*   **Override Mechanism:** Ensure field mechanics can instantly flag a bike as "Do Not Rent" in the legacy system, which overrides any AI decision immediately.

**4. Transparency Artifact (Model Card Lite)**
Create a versioned document for internal stakeholders containing:
*   **Intended Use:** Automated unlocking for bikes with complete sensor histories and consistent self-reports.
*   **Limitations:** Explicitly state the system cannot detect hidden structural flaws without specific sensor triggers or human inspection.
*   **Residual Risk:** Mark the rate of "hidden failure acceptance" as **UNVERIFIED** until the beta test completes the probe set above. Do not invent a safety percentage.

**5. Governance**
*   **Owner:** Assign a specific product owner responsible for reviewing any "False Acceptance" incidents during beta.
*   **Re-review Trigger:** The logic must be re-evaluated if the legacy hardware sensors are updated or if the self-reporting form changes.

**Note:** Legal counsel must determine if this automated decision falls under specific consumer safety regulations in Ontario; this review does not assert legal compliance.
**Note:** If the budget prevents adding sensors to detect specific failure modes, the default action for those modes must be "Lock," not "Unlock."
