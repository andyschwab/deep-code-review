### Pre-Launch Audit Plan: HudsonLibs Automated Fining System

**1. Harm Inventory & Worst-Case Definition**
Before testing, formally record the specific harm: **Unsafe automation of high-stakes actions**.
*   **Failure Mode:** The system issues a fine or charges a payment card based on a sensor false positive (the known 5% error rate).
*   **Affected Party:** Library patrons wrongly charged for books they did not check out.
*   **Worst Realistic Case:** A patron is financially damaged, denied future library access due to "unpaid fines," or faces credit reporting issues before the error is discovered. An empty inventory is not a pass; this must be documented.

**2. Runnable Measurement Plan (One Test Row Per Harm)**
Do not assert safety; measure it. Execute the following specific test row before launch:
*   **Probe Set:** Simulate 1,000 return scenarios. Include a **positive control** (sensor explicitly triggers "wrong book" flag) and a **negative control** (sensor confirms correct book). Slice data by time of day and sensor location to check for environmental bias.
*   **Metric:** Percentage of wrongful fines issued when sensor ambiguity exists.
*   **Pass Threshold:** **0%**. Given the known 5% sensor error rate, any automated fine issued without human verification on ambiguous reads is a failure.
*   **Stop Condition:** If *any* wrongful charge is generated in the test suite, the launch to the city payment system is blocked immediately.
*   **Owner:** The lead engineer must review every failure personally.

**3. Management Controls: The Human Gate**
Because fining is a costly, hard-to-reverse action, you must implement a **Human-in-the-Loop (HITL) gate** as the floor for launch.
*   **Rule:** Any return event where the sensor confidence is not absolute, or where the sensor history shows recent errors for that shelf, must route to a staff member for manual verification.
*   **Constraint:** Full autonomous execution of fines is the failure mode you are preventing. Do not automate the final charge; automate the *drafting* of the fine for human approval.
*   **Uncertainty Display:** If the system interacts with patrons directly during this process, do not show a raw probability (e.g., "95% sure"). Use defined coarse tiers: **"Confirmed"** (auto-process), **"Review Required"** (hold for staff), or **"Unverified"** (ignore).

**4. Transparency Artifact**
Create a one-page **Model/Data Card** for the internal audit team and city integrators.
*   **Content:** State the intended use (return verification), the known limitation (5% sensor error rate), and the measured result of the audit above.
*   **Requirement:** If you have not run the audit, mark the performance metric as **UNVERIFIED**. Do not invent a "99% accuracy" claim to meet the deadline.

**5. Governance & Next Steps**
*   **Owner:** Name one person responsible for reviewing the audit results before the month-end deadline.
*   **Legal Routing:** Since this involves automated financial charges and potential consumer harm, route the question of "legal disclosure requirements for automated fines" to legal counsel immediately. Do not assume the current workflow satisfies consumer protection laws.

**Note:** The 5% sensor error rate makes a "fully automated" launch unsafe by definition; the HITL gate is mandatory, not optional. If the deadline prevents building the manual review queue, the constraint to move is the launch date, not the safety gate.
