### Offline Triage Verification Strategy for Rural Clinics

To validate your medical appointment scheduler without cloud dependency, implement a **"Golden Record" Dry Run Protocol**. This approach uses a fixed, pre-loaded dataset of simulated patient records stored locally on clinic devices to verify routing logic before any real patient data is entered.

**1. Construct the "Golden Record" Dataset**
Create a lightweight JSON or CSV file containing 50–100 simulated patient profiles. This dataset must be curated by your seven doctors to represent the full spectrum of risk, with a heavy emphasis on edge cases:
*   **Critical Anchors (40%):** Cases with unambiguous emergency symptoms (e.g., chest pain with diaphoresis, stroke indicators, severe trauma) that *must* route to Emergency Specialists.
*   **Boundary Cases (40%):** Ambiguous presentations where minor symptom differences change the triage level (e.g., mild headache vs. thunderclap headache).
*   **Routine Controls (20%):** Clear non-urgent cases that should correctly route to General Practitioners.

Each record must include a hidden "Ground Truth" tag indicating the correct destination. This file acts as your offline oracle.

**2. The Local Execution Workflow**
Since connectivity is limited, bundle the scheduler application and the Golden Record dataset into a single portable package (e.g., a Docker container, a standalone binary, or a local web server) deployed directly to clinic tablets or laptops.
*   **Batch Mode:** Create a simple script or button labeled "Run Validation." When clicked, it feeds every record from the Golden Record file into the scheduler sequentially.
*   **Comparison Logic:** The system automatically compares the scheduler's output against the hidden "Ground Truth" tag for each record.
*   **Offline Reporting:** Generate a local HTML or PDF report immediately after the run. This report should list only the **mismatches** (false negatives/positives). If a critical case is routed to a GP, it must appear at the top of this report in red.

**3. The "Stop-Light" Go/No-Go Criteria**
Define strict pass/fail thresholds that clinic staff can interpret without technical expertise:
*   **Green Light:** 100% of Critical Anchors are correctly routed to Emergency Specialists. Minor errors in routine cases are acceptable for now.
*   **Red Light:** Any single Critical Anchor is misrouted to a General Practitioner. The system must not be used for real patients until the specific logic error is fixed and the test is re-run locally.

**4. Maintenance and Updates**
When your team updates the triage logic, they will distribute a new application package along with an updated Golden Record file that includes any newly discovered edge cases. Clinic staff simply replace the old files and re-run the validation. This ensures that every local instance verifies its own integrity before daily operations begin.

By shifting the validation burden to a deterministic, local comparison against doctor-verified facts, you eliminate the need for cloud round-trips while ensuring that the most dangerous failure mode—downgrading an emergency—is caught before it affects a real patient.

*Note: Ensure the simulated data strictly avoids using real patient identifiers to maintain privacy compliance during these dry runs.*
*This strategy assumes the scheduler software can accept batch inputs; if it is strictly single-entry, a simple macro or script will be needed to automate the clicking.*
