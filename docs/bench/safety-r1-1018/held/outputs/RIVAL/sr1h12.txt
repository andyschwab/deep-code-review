# Pre-Launch Safety Plan: Static Mitigation for Dynamic Risks

Given the inability to access real-time infrastructure feeds and the critical risk of routing users onto active tracks, the following immediate actions must be taken to ensure user safety before launch. These measures prioritize fail-safe behavior over feature completeness.

### 1. Implement Hardcoded "No-Go" Geofences
Immediately define static geographic polygons (geofences) around all known track areas, maintenance zones, and restricted infrastructure within the app's local database.
*   **Action:** Hardcode these coordinates as absolute exclusion zones.
*   **Logic:** The routing algorithm must be modified to treat these zones as impassable barriers, regardless of the calculated "shortest path." If a route requires crossing a geofence, the app must return "No Route Available" rather than attempting an alternative that skirts the edge.
*   **Data Source:** Use the existing limited mapping data to manually digitize these boundaries based on station blueprints, even if imperfect. It is safer to block access to a safe platform edge than to allow access to a track.

### 2. Enforce Aggressive Time-Based Blackouts
Since real-time closure updates are unavailable, rely on the known schedule of maintenance windows to create temporal barriers.
*   **Action:** Ingest the published maintenance schedule into the app as a static lookup table.
*   **Logic:** During any scheduled maintenance window, automatically disable routing features for the affected stations or specific zones.
*   **User Feedback:** When a user attempts to navigate during a blackout period, display a prominent, non-dismissible warning: *"Navigation is disabled during scheduled maintenance hours due to safety protocols. Please consult station staff."* Do not offer partial guidance.

### 3. Deploy Prominent Manual Override Warnings
Acknowledge the data gap directly to the user through the UI.
*   **Action:** Place a persistent banner on the main navigation screen stating: *"This app does not receive real-time track closure alerts. Always obey physical signage and station staff instructions."*
*   **Interaction:** Require users to tap "I Understand" upon first launch and whenever entering a station zone. This creates a conscious friction point that reminds users the app is an aid, not an authority.

### 4. Limit Scope to "Safe Zones" Only
Restrict the app's guidance to areas verified as 100% safe for public access.
*   **Action:** Audit the current mapping data. Remove any turn-by-turn instructions that guide users through corridors, gates, or platforms that are adjacent to tracks unless those paths are explicitly verified as open 24/7.
*   **Fallback:** If the app cannot verify a path is safe due to missing data, it must default to silence. Provide only high-level station entry/exit points rather than complex internal routing where the risk of deviation is highest.

### 5. Establish an Emergency "Kill Switch" Mechanism
Prepare a mechanism to disable the app's routing functionality remotely or via a simple configuration update if a critical incident occurs.
*   **Action:** Host a small, lightweight JSON configuration file on a reliable, high-availability server (e.g., a standard CDN or cloud storage bucket) that the app checks on launch.
*   **Logic:** If this file contains a `"safety_lockdown": true` flag, the app immediately disables all navigation features and displays a generic safety message. This allows the team to halt operations instantly if a near-miss occurs or if unexpected maintenance arises that was not in the static schedule.

### 6. Legal and Operational Disclosure
*   **Action:** Update the Terms of Service and App Store description to explicitly state that the app is not a safety device and does not account for real-time track hazards.
*   **Coordination:** Inform the city partnership contact immediately about these limitations. Propose a "Beta" or "Limited Feature" launch status rather than a full public release, framing the restriction of features as a proactive safety commitment.

**Critical Note:** Under no circumstances should the app attempt to "guess" a route around a potential hazard. If the data is missing, the only safe output is no output.

**Recommendation:** If the engineering team cannot implement the hardcoded geofences and time-based blackouts with 100% confidence before the deadline, the launch must be delayed. User safety supersedes partnership requirements.
