### Simulation Plan for Emergency Transport Edge Cases

Given the four-week deadline and the lack of real-world emergency data, you must shift from training-based validation to **rule-based stress testing** using synthetic scenarios. Since you cannot wait for rare events to occur naturally, you will artificially construct them to verify the scheduler's decision logic.

**1. Construct Synthetic "Golden" Scenarios**
Create a library of 50–100 deterministic test cases representing high-stakes medical emergencies. Since your dataset lacks these, manually define them based on medical logistics standards:
*   **Scenario A (Direct Conflict):** An emergency medical train and a high-volume commuter train require the same single-track segment simultaneously.
*   **Scenario B (Cascading Delay):** An emergency request arrives when the network is already at 95% capacity due to monsoon-like congestion.
*   **Scenario C (False Positive):** A non-critical freight train is mislabeled or mimics an emergency signature to test if the system blindly prioritizes flags without verification.
*   **Variables:** Vary the lead time (immediate vs. 30-minute warning), distance to destination, and number of patients onboard.

**2. Define the "Hard Constraint" Oracle**
Before running simulations, codify the non-negotiable policy into a simple script (an "oracle") that acts as the ground truth. This oracle does not optimize; it only checks violations.
*   *Rule:* If `cargo_type == "medical_emergency"`, then `delay_minutes` must be 0 unless physical track blockage makes movement impossible.
*   *Rule:* If `delay_minutes > 0` for emergency cargo, the system must provide a verifiable reason (e.g., "track occupied by higher priority asset" or "physical obstruction").
*   Any simulation where the AI delays an emergency train without a physical impossibility justification is an automatic failure.

**3. Execute Adversarial Stress Tests**
Run your beta system against the synthetic scenarios in a sandboxed environment. Do not use historical data; inject the synthetic scenarios into the live beta logic.
*   **Volume Spike Test:** Inject 10 simultaneous emergency requests across different zones to see if the optimizer degrades into a "first-come-first-served" mode that unfairly penalizes later requests.
*   **Trade-off Analysis:** Measure the "Commute Penalty." Calculate the total additional delay imposed on daily commuters to save the specific time for the medical train. Ensure the system isn't causing gridlock for thousands to save minutes for one, unless explicitly permitted by your ethics board.

**4. Human-in-the-Loop Verification**
For the first two weeks, run the AI in "Shadow Mode" for these specific scenarios. The AI suggests a route, but a human dispatcher validates it against the Oracle rules before execution. Log every instance where the human overrides the AI. If the override rate for medical emergencies exceeds 5%, the model is not ready for live deployment.

**5. Fallback Mechanism Validation**
Test the "Kill Switch." Simulate a scenario where the AI produces an unsafe or illogical schedule for an emergency train. Verify that the system instantly reverts to a static, pre-defined priority protocol that guarantees medical trains right-of-way, bypassing the AI entirely.

By focusing on deterministic, manually crafted edge cases rather than probabilistic training data, you can mathematically prove whether the system respects medical priorities before the monsoon season begins.
