**VineGuard Paris Climate Control Bot: Sensor Failure Testing Protocol**

**1. Test Environment & Baseline Establishment**
*   **Simulation Chamber:** Construct a controlled thermal chamber mimicking the specific thermal mass and insulation properties of the target high-end cellars. Do not test solely in ambient office conditions.
*   **Legacy Interface Emulator:** Build a hardware-in-the-loop (HIL) simulator that replicates the electrical characteristics and communication latency of the existing legacy thermostats. This ensures the bot's compatibility layer is stressed exactly as it will be in production.
*   **Golden Standard:** Install independent, calibrated reference sensors (unconnected to the control loop) to record ground-truth temperature and humidity. This distinguishes between actual environmental shifts and sensor reading errors.

**2. Sensor Failure Mode Injection Scenarios**
Execute the following specific fault injections while the bot is in "automatic calibration" mode:
*   **Stuck-At Faults:** Force sensor inputs to remain static at critical thresholds (e.g., 2°C or 25°C) regardless of actual chamber conditions. Verify the bot detects the lack of variance and triggers a "Sensor Stuck" alarm rather than attempting to heat/cool indefinitely.
*   **Drift Simulation:** Program the emulator to introduce a slow, linear drift (e.g., +0.5°C per hour) to mimic aging sensors. Confirm the bot's cross-validation logic flags discrepancies between the drifting sensor and the internal thermal model before the wine reaches danger zones.
*   **Noise & Spike Injection:** Introduce high-frequency noise and sudden step-function spikes (simulating electrical interference). The protocol must verify that the bot applies appropriate filtering (e.g., moving average or median filter) and does not react to transient outliers by activating cooling/heating elements.
*   **Communication Loss:** Simulate intermittent packet loss and total signal dropout. The bot must default to a "Safe Hold" state (maintaining last known good settings or a conservative default) rather than freezing or guessing.
*   **Cross-Sensor Contradiction:** Feed conflicting data (e.g., humidity sensor reads 90% while temperature suggests dry air). Verify the system prioritizes the most critical safety parameter and requests human intervention rather than executing a contradictory adjustment.

**3. Stability & Recovery Metrics**
For each scenario, measure and log:
*   **Time-to-Detect:** Seconds elapsed between fault injection and system alert generation.
*   **Max Deviation:** The maximum temperature/humidity deviation from the setpoint during the fault event. This must remain within the safe preservation range for the specific vintages listed in your contracts.
*   **Recovery Time:** Time taken to return to stable setpoints after the fault is cleared.
*   **Actuator Cycling:** Count the number of on/off cycles for heating/cooling units during the fault to prevent mechanical wear or thermal shock to the wine.

**4. Validation Gate for Handover**
Before client handover, the system must pass a continuous 72-hour stress test combining random failure modes without a single instance of uncommanded freezing or overheating. Any failure requires a code freeze and root cause analysis before re-testing.

**Note:** Prioritize the "Stuck-At" and "Drift" scenarios immediately, as these most closely resemble the recent glitch. Ensure all test data is logged immutably for liability protection with the vineyard clients.
