# Synthetic Safety Simulation Plan for Skincare Recommendation Engine

## Phase 1: Construct the Synthetic "Adversarial" Dataset
Since real-world trials are not possible, you must construct a high-fidelity synthetic dataset that explicitly targets edge cases and known failure modes. Do not rely on random distribution; instead, engineer specific profiles:
*   **The "High-Risk" Profile:** Create 50+ user profiles with documented severe allergies (e.g., nickel, specific preservatives like parabens, fragrances, lanolin). Tag these profiles with explicit "hard block" rules in your test schema.
*   **The "Mimic" Profile:** Generate profiles with skin conditions that visually resemble allergies but have different contraindications (e.g., rosacea vs. allergic contact dermatitis) to test if the image scanner distinguishes between visual similarity and medical history.
*   **The "Poly-Allergen" Profile:** Users with 5+ concurrent allergies to test the engine's logic when multiple exclusion filters trigger simultaneously.
*   **Data Structure:** Ensure every synthetic user record includes a `blocked_ingredients` array and a `severity_level` flag. Every product in your catalog must have a machine-readable `ingredient_list` and `known_allergen_tags`.

## Phase 2: Define and Execute Logic Stress Tests
Run your recommendation engine against this dataset using a "Red Team" approach where the goal is to force a failure. Execute the following specific test suites:
1.  **The Absolute Block Test:** Input a user profile with a severe allergy to Ingredient X. Feed the engine a database where 90% of top-rated products contain Ingredient X.
    *   *Success Criterion:* The system returns zero products containing Ingredient X. Any single match is a critical failure.
2.  **The Cross-Contamination Logic Test:** Test products that do not list an allergen as a primary ingredient but contain it as a sub-component or trace element (e.g., "May contain traces of...").
    *   *Success Criterion:* The system flags and excludes products with precautionary labeling matching the user's severity level.
3.  **The Image-to-Data Mismatch Test:** Upload synthetic skin photos indicating severe sensitivity while the text profile is left blank or contradictory.
    *   *Success Criterion:* The system defaults to the safest possible recommendation path or halts with a "Consult a Dermatologist" warning rather than guessing.
4.  **Ranking Override Test:** Verify that high user ratings or "trending" status never override a safety block. A product with 5,000 reviews containing a user's allergen must be ranked lower than a niche product with no allergens.

## Phase 3: Compliance Documentation & Safety Audit Trail
To satisfy internal compliance without real-user data, generate a "Safety Validation Report" containing:
*   **Test Matrix Log:** A table listing every synthetic profile ID, the specific allergens tested, the total products scanned, and the count of blocked items.
*   **Failure Mode Analysis:** Document any instance where the system hesitated or required multiple logic checks to block an item. Explain the mitigation implemented.
*   **Confidence Scoring:** For every recommendation generated in the simulation, record the "Safety Confidence Score." Set a hard threshold (e.g., <99% safety confidence = No Recommendation).
*   **Disclaimer Verification:** Confirm that every output in the simulation included the mandatory medical disclaimer: *"This tool does not replace professional medical advice. Users with severe conditions should consult a dermatologist."*

## Phase 4: The "Human-in-the-Loop" Gate
Before launch, institute a manual review gate. Any recommendation generated by the engine for a synthetic profile marked "Severe/High Risk" must be visually inspected by a qualified formulator or dermatologist on your team. If the human reviewer identifies a potential risk the engine missed, retrain the exclusion logic immediately.

**Note:** This simulation validates logic, not biological reaction; ensure your launch terms of service clearly reflect that this is an advisory tool.
**Note:** Retain all synthetic datasets and test logs as immutable records for future liability protection.
