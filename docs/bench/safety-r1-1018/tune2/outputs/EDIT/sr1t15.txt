### Emergency Pricing Override Protocol

**1. Emergency Zone Identification (Data Feeds & Triggers)**
Implement a deterministic pre-check layer that queries the following public APIs every 60 seconds. If any trigger fires for a specific geohash, that zone is flagged as "Restricted."
*   **Official Emergency Alerts:** Ingest RSS/JSON feeds from Toronto Emergency Management Office and Alert Ready (Canada). Keywords: "Evacuation," "Shelter-in-place," "Flash Flood," "Severe Storm."
*   **Traffic & Transit Anomalies:** Monitor City of Toronto open data for sudden road closures or TTC service suspensions exceeding 3 standard deviations from the hourly mean.
*   **Social Signal Spike (Secondary):** Detect localized spikes in keywords like "stranded," "emergency," or "help" on public social streams only if correlated with official alerts to reduce false positives.

**2. Automatic Pricing Caps (The Hard Gate)**
Once a zone is flagged "Restricted," bypass the dynamic pricing model entirely for that geohash and enforce these rules:
*   **Surge Multiplier Cap:** Hard-code the multiplier to **1.0x** (base fare only). No surge pricing is permitted during an active emergency flag.
*   **Cancellation Fee Waiver:** Automatically waive cancellation fees for rides originating in or destined for a Restricted Zone.
*   **Service Availability:** If driver supply is critically low, display a "High Demand / Limited Availability" message to users rather than inflating prices to clear the market. The goal is equitable access, not market clearing.

**3. Monitoring & Human-in-the-Loop Alerts**
*   **Real-Time Dashboard:** Create a "Crisis Mode" view showing all active Restricted Zones and the number of rides served at capped rates.
*   **Anomaly Alert:** If the dynamic pricing engine attempts to calculate a multiplier >1.0x in a Restricted Zone, trigger an immediate PageDuty alert to the on-call data scientist and engineering lead.
*   **Post-Incident Review:** Log every instance where the override engaged. Review within 24 hours of the event to tune keyword sensitivity.

**4. Rollout Plan (Next 5 Days)**
*   **Day 1-2:** Integrate public API connectors and build the "Restricted Zone" flag logic.
*   **Day 3:** Implement the hard-coded 1.0x cap logic and cancellation waivers.
*   **Day 4:** Run simulation using historical data from past Toronto storms/floods to verify the override triggers correctly.
*   **Day 5:** Deploy to production with the monitoring dashboard active before the festival begins.

**Note:** This protocol treats the pricing flaw as a safety-critical failure mode; the deterministic override acts as the required human-gated control until the model can be retrained. Legal counsel should review the specific wording of user notifications during these events.
