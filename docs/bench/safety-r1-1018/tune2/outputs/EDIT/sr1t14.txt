**Pre-Launch Safety Review Plan: Automated Eviction Notice Module**

**1. Harm Inventory & Risk Assessment**
*   **Primary Harm:** Wrongful eviction notices due to data import errors (false positives), causing severe tenant distress and potential legal liability.
*   **Affected Parties:** Tenants (psychological/financial harm), Property Managers (reputational/legal risk), Landlords (compliance risk).
*   **Worst Case:** A tenant in good standing receives a formal legal eviction notice, leading to panic, credit damage, or unlawful lockout attempts before error correction.

**2. Measurement Plan (No New Layers)**
Since new validation layers are prohibited, we will utilize existing logs for adversarial testing within the current cloud environment:
*   **Probe Set A (False Positive Control):** Inject a test dataset containing 50 known "good standing" tenants with simulated import glitches (e.g., duplicate timestamps, currency formatting errors).
    *   *Metric:* Number of false flags generated.
    *   *Threshold:* **Zero tolerance.** Any flag on a known good-standing test account blocks launch.
*   **Probe Set B (Data Integrity Check):** Cross-reference the raw payment log entry count against the bank confirmation email receipt count for the test period.
    *   *Metric:* Reconciliation variance.
    *   *Threshold:* >0% variance triggers an immediate manual audit halt.
*   **Stop Condition:** If Probe Set A yields any false positives, the automated flagging feature is disabled until the data import logic is patched, regardless of the board presentation deadline.

**3. Management Controls: Human-in-the-Loop Gate**
Full automation of eviction notices is an irreversible, high-stakes action. The following workflow is mandatory:
*   **The "Draft-Only" Default:** The AI system is configured to output notices strictly as "DRAFT – PENDING REVIEW" in the internal dashboard. The "Send" function is logically decoupled from the generation function.
*   **Mandatory Verification Step:**
    1.  System flags a tenant based on payment history.
    2.  System generates a draft notice and attaches the specific payment logs and the corresponding bank confirmation email text.
    3.  **Hard Gate:** A licensed Property Manager must manually click "Verify & Send" after visually confirming the discrepancy.
    4.  **Audit Trail:** The system logs the ID of the manager who approved the notice and the timestamp. No notice sends without this specific human action ID.
*   **Uncertainty Display:** If the AI confidence in the payment mismatch is based on ambiguous data (e.g., partial matches), the interface must display a "Low Confidence – Manual Review Required" alert in red, forcing the manager to expand the details before approving.

**4. Governance & Transparency**
*   **Owner:** The Lead Property Manager in Sydney is named the owner of the final "Send" decision.
*   **Transparency Artifact:** A one-page "Model Limitation Statement" must be attached to the board presentation, explicitly stating: "This system generates drafts only; all legal notices require human verification. False positive rate is currently UNVERIFIED pending Probe Set A results."
*   **Legal Routing:** Whether this automated flagging constitutes a "regulated automated decision" requiring specific statutory disclosures under local tenancy laws is a legal determination. This must be routed to counsel immediately; do not assert compliance in the board deck.

**Deliverable Status:** Ready for implementation in staging.

**Note:** Do not present a "0% error rate" to the board; present the "Zero Tolerance" stop condition instead.
**Note:** If the data import cannot be reconciled with bank emails via existing logs, the automation must remain disabled.
