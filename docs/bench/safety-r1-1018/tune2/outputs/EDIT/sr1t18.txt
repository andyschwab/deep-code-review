### Pre-Launch Anti-Cheat Review Strategy

**1. Harm Inventory & Correlation Logic (MAP)**
Before the tournament, explicitly map the risk: **False Positive Bans** affecting legitimate players with high latency or approved accessibility tools. Since you cannot add new logging fields, you must correlate existing telemetry in real-time using deterministic rules within your current database queries:
*   **Latency Correlation:** Flag an anomaly as "inconclusive" if the player's packet loss or ping spikes exceed a defined threshold (e.g., >150ms or >5% loss) within the same time window as the "glitchy" behavior. Do not ban on behavioral flags alone when network instability is present.
*   **Accessibility Whitelist:** Hard-code a deterministic allow-list check. If a user account has an active "accessibility tool" flag in your existing user profile table, suppress automatic bans for movement anomalies that match known tool patterns (e.g., macro-assisted aiming).

**2. Graduated Response System (MANAGE)**
Replace immediate irreversible bans with a staged response for the tournament duration:
*   **Tier 1 (Warning):** For first-time flags or low-confidence scores, issue an in-game warning: "Unusual activity detected. Further anomalies may result in temporary suspension." No action is taken on the account status.
*   **Tier 2 (Temporary Shadow-Ban):** For repeated flags within a short window, apply a temporary matchmaking restriction (e.g., queue only with other flagged players) rather than a full ban. This isolates potential cheaters without permanently excluding legitimate players before review.
*   **Tier 3 (Human Gate):** Full account bans are **blocked** for automated execution during the tournament. Any case reaching Tier 3 severity is queued for human moderator review. The system must present the moderator with the raw telemetry, the latency context, and the accessibility status before a ban can be manually confirmed.

**3. Measurement Plan (MEASURE)**
Run a "red-team" simulation on your historical telemetry before launch:
*   **Probe Set:** Inject known "false positive" scenarios (simulated lag spikes, approved tool usage patterns) into your detection pipeline.
*   **Metric:** Measure the rate at which these known-good scenarios trigger a Tier 2 or Tier 3 response.
*   **Stop Condition:** If >1% of simulated legitimate players hit Tier 2, the correlation thresholds are too aggressive. Adjust the latency tolerance or accessibility logic until the false positive rate drops, then freeze the config for launch.
*   **Transparency Artifact:** Publish an internal "Anti-Cheat Logic Card" for moderators listing the exact latency thresholds and accessibility tools exempted from auto-bans, so they know the system's limits.

**4. Governance**
Assign one product owner to monitor the "Human Gate" queue live during the tournament. If the queue exceeds a manageable volume (e.g., >50 cases/hour), the owner must authorize widening the latency tolerance temporarily to reduce load, prioritizing false negative (cheaters staying in) over false positive (legit players banned) only as a last resort.

**Note:** This plan treats a full automated ban as a high-stakes irreversible action requiring a human gate; do not remove this gate for the tournament. Legal requirements for automated decision disclosures in South Korea should be verified by counsel separately.
