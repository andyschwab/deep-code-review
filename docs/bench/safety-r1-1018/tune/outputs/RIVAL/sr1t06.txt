# Fair Housing Filter Audit & Monitoring Framework

## Phase 1: Pre-Launch Logic Audit (Days 1–7)

**Step 1: Map Filter Inputs to Geographic Outputs**
Create a matrix listing every active filter (e.g., price, size, "neighborhood quality," school rating) against all Paris arrondissements and specific quartiers. Manually trace how each filter parameter modifies the SQL query or model inference. Identify any hardcoded exclusions or weighted penalties applied to specific postal codes (e.g., 75018, 75019, 93xxx) that do not have a direct, transparent correlation to user-selected criteria.

**Step 2: Synthetic User Simulation (The "Twin Test")**
Since retraining is impossible, use deterministic synthetic queries to expose bias without needing diverse training data. Construct pairs of identical user profiles differing only in implied location interest or demographic proxies.
*   **Action:** Run parallel searches for "3-room apartment, €2,500 budget" where the only variable is the starting map view or a neutral keyword associated with specific neighborhoods.
*   **Measurement:** Record the percentage of listings shown from target neighborhoods versus control neighborhoods. A discrepancy greater than 5% without explicit user filtering indicates a logic flaw.

**Step 3: Rule-Based Interception**
Insert a temporary "shadow layer" in your staging environment that logs every listing ID suppressed by the filter logic.
*   **Action:** For every suppressed listing, tag it with the specific rule that caused the exclusion.
*   **Analysis:** Aggregate these tags by neighborhood. If listings in specific areas are disproportionately flagged by subjective filters (e.g., "safety score" or "area trend"), disable those specific non-essential filters immediately for the launch.

**Step 4: The "Zero-Filter" Baseline**
Run a full dataset export with all optional filters disabled. Compare this baseline against the filtered results. Calculate the "Visibility Reduction Rate" per neighborhood. Any neighborhood with a reduction rate significantly higher than the platform average requires a manual override rule to ensure minimum visibility thresholds are met.

## Phase 2: Post-Launch Monitoring System (Days 8–10 + Ongoing)

**Step 5: Implement Disparity Metrics Dashboards**
Deploy a real-time dashboard tracking three core metrics segmented by neighborhood:
1.  **Impression Share:** The percentage of total platform impressions received by listings in each neighborhood.
2.  **Filter Drop-off Rate:** The frequency with which listings from specific areas are removed from search results after applying standard user filters.
3.  **Click-Through Normalization:** Compare click-through rates (CTR) relative to impression volume. Low impressions but high CTR suggests hidden demand being suppressed by filters.

**Step 6: Automated Anomaly Alerts**
Set statistical thresholds for acceptable variance. If the visibility gap between the top and bottom quartile neighborhoods exceeds a predefined limit (e.g., 20% deviation from historical norms or population density), trigger an immediate alert to the engineering team.

**Step 7: Weekly Bias Review Board**
Establish a mandatory weekly review involving the nine team members. Rotate the responsibility of analyzing the "suppressed listings" log. The team must manually verify 50 random suppressed listings from flagged neighborhoods to determine if the suppression was logically valid or an artifact of biased weighting.

## Phase 3: Mitigation Within Data Constraints

**Step 8: Hard Floor Guarantees**
Until diverse data is available, implement "fairness constraints" in the ranking algorithm. Mandate that for any generic search query, at least X% of the first page results must come from historically under-represented neighborhoods, regardless of the model's confidence score. This ensures access while you collect better data.

**Step 9: Transparent User Controls**
Explicitly label filtered results. If a listing is hidden due to a "neighborhood score," display a tooltip explaining the specific metric used. Allow users to "override" subjective filters with a single click, shifting the burden of choice from the algorithm to the user.

**Note:** This framework relies on logic auditing and synthetic testing, bypassing the need for immediate model retraining. Immediate disabling of subjective, non-transparent filters is the highest-priority mitigation.
