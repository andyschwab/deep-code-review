### Pre-Launch Anti-Cheat Review Strategy

**1. Harm Inventory & Risk Mapping**
Before launch, explicitly record the primary risk: **False Positive Bans** affecting legitimate players with high latency or approved accessibility tools. The worst-case scenario is the disqualification of a tournament participant due to an automated error, causing reputational damage and competitive unfairness. Acknowledge that without new logging fields, you must derive network stability proxies from existing telemetry (e.g., packet arrival variance, action timestamp gaps) rather than direct ping logs.

**2. Measurement Plan (Runnable Tests)**
Do not assert the system is "fair." Instead, execute these specific tests using your current database:
*   **Probe Set A (Latency Simulation):** Inject synthetic telemetry mimicking high-jitter connections into your test environment. Verify if the anomaly detector flags these as "glitchy behavior."
*   **Probe Set B (Accessibility Baseline):** Run telemetry from known approved accessibility tool users. Confirm these patterns do not trigger "unauthorized software" heuristics.
*   **Control Metrics:** Define a "False Positive Rate" threshold. If the system flags >0% of known legitimate latency/accessibility cases as cheats, the automatic ban function must remain disabled for those segments.
*   **Stop Condition:** If the test reveals any false positives in the tournament seed group, automatic banning is blocked; only warnings are permitted until manual review clears the logic.

**3. Graduated Response & Human Gate**
Implement a strict **Human-in-the-Loop** gate for all high-stakes actions (tournament bans).
*   **Tier 1 (Borderline/Uncertain):** If the AI confidence is not absolute or if network instability markers (derived from existing data) correlate with the anomaly, issue an **in-game warning** only. Do not ban. Log the event for review.
*   **Tier 2 (High Confidence + Stable Network):** Only consider automatic action if the behavior is egregious AND network metrics indicate stability. However, for the tournament launch, **override this to require human moderator confirmation** for every ban.
*   **Uncertainty Display:** Do not show players a percentage score (e.g., "87% cheat likelihood"). Instead, use defined internal tiers: "Confirmed Anomaly," "Corroborated," or "Unverified/Latency Likely."

**4. Transparency & Governance**
*   **Model Card Lite:** Create a one-page internal document stating the system's intended use (anti-cheat), limitations (cannot distinguish latency from glitches without new fields), and the owner of the ban decision. Mark any unmeasured metric as `UNVERIFIED`.
*   **Owner Assignment:** Name the specific product lead responsible for reviewing every ban during the tournament. No automated ban executes without this owner's implicit or explicit protocol approval.
*   **Legal Routing:** If players appeal based on disability/accessibility tools, route immediately to counsel regarding accommodation duties; do not let the AI override these claims.

**Definition of Done for Launch:**
The automatic ban switch is effectively off for the tournament; the system operates in "Warn & Queue for Human Review" mode. A harm inventory is signed off, and the test results against latency/accessibility probes are documented. No metric claims "zero false positives"; instead, the documentation states the residual risk and the human review process managing it.

*Note: This strategy prioritizes preventing irreversible harm (unfair bans) over immediate automation efficiency, adhering to the constraint that high-stakes decisions require human oversight.*
*Infrastructure limits prevent perfect detection; therefore, the default posture must be "innocent until proven guilty by a human."*
