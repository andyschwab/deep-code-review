### Immediate Action Plan: Isolate, Validate, Communicate

**1. Data Points to Request (Technical vs. Behavioral)**
Do not ask for "all logs." Request these specific events to distinguish a broken interface from a confusing one:
*   **`document_upload_started`**: Count of users clicking the new upload button.
    *   *Diagnosis:* If this is low compared to `verification_step_viewed`, the CTA is invisible or confusing (Behavioral).
*   **`document_upload_error`**: Count of failed API responses or client-side validation errors, tagged by error code (e.g., `file_too_large`, `format_invalid`, `timeout`).
    *   *Diagnosis:* A spike in specific error codes post-March 12 indicates a technical regression. If errors are flat but drop-off increased, the issue is behavioral (UX confusion).
*   **`document_upload_abandoned`**: Users who started the upload but closed the window or navigated away before `document_upload_success`.
    *   *Diagnosis:* High abandonment with low error rates suggests the process is too complex or slow (Behavioral/Friction).
*   **`time_to_complete_upload`**: Duration between `started` and `success`.
    *   *Diagnosis:* A significant increase in median time suggests the new interface is harder to use, even if it technically works.

**2. Quick Validation Test Structure**
Do not roll back entirely yet; you need causal proof. Run a **50/50 A/B test** immediately:
*   **Control Group (50%):** Serves the pre-March 12 interface (or a simplified known-good version).
*   **Treatment Group (50%):** Serves the current March 12 interface.
*   **Primary Metric:** `vehicle_verification_completion_rate`.
*   **Guardrail Metric:** `document_upload_error_rate` (ensure the fix doesn't break technical stability).
*   **Design Rule:** Pre-commit to a sample size (e.g., 2,000 users per arm) or a fixed duration (48–72 hours given your volume). **Do not peek** at results after 100 users to declare a winner; this inflates false positives. Read the result once at the end. If the Control group significantly outperforms Treatment with no difference in error rates, the issue is UX confusion, confirming the need for a redesign rather than a code fix.

**3. Communicating Revenue Impact to the CFO**
Avoid vanity metrics like "14% drop." Frame the impact in **throughput and lag**:
*   **The Leak:** "We are losing 590 verified drivers weekly (1,470 projected vs. 890 actual) due to this funnel step."
*   **The Lag Cost:** Calculate the *delay* in fleet availability. If onboarding takes 3 days longer due to re-attempts or support tickets caused by the UI, that delays revenue generation by 3 days per driver.
*   **The Projection:** "Restoring the 35% baseline recovers 590 drivers/week. At an average driver lifetime value (LTV) of $X and weekly active rate of Y%, this equals $Z in recovered monthly gross booking value. Every day we wait at 21% costs us $[Daily Loss Amount]."
*   **The Ask:** "Approve the 48-hour A/B test. If the Control wins, we authorize the UX patch immediately. If results are inconclusive, we investigate backend latency."
