**Prioritized Event Taxonomy for NexusAI Beta (5 Events Max)**

To distinguish user confusion from genuine disinterest and enable a valid go/no-go decision by January 30th, instrument these five events. This selection prioritizes **retention of the core action** over vanity metrics or system health, adhering to the MVP stage requirement of measuring only what answers a named question.

1.  **`session_started`** (Properties: `user_id`, `timestamp`)
    *   **Question Answered:** Did the user successfully enter the product?
    *   **Rationale:** This establishes the denominator for all activation rates. Without a stable session start, you cannot calculate drop-off between opening the app and creating a document. It differentiates users who never loaded the beta (distribution issue) from those who loaded but didn't act (value issue).

2.  **`document_created`** (Properties: `user_id`, `document_type`, `time_to_create`)
    *   **Question Answered:** Did the user complete the core "activation" action?
    *   **Rationale:** This is your primary activation metric. In an writing assistant, value cannot be delivered without a document. Tracking `time_to_create` here acts as a proxy for initial friction; a long duration suggests confusion in the UI, while immediate creation suggests clear intent. Do not track "signups"; track this specific value-delivering action.

3.  **`suggestion_accepted`** (Properties: `user_id`, `suggestion_type`, `document_id`)
    *   **Question Answered:** Did the user receive and validate the core value proposition?
    *   **Rationale:** This is your "Aha!" moment indicator. A user who creates a document but accepts zero suggestions is likely confused by the interface or disappointed by the output quality (disinterest). High creation but low acceptance signals a product failure, not a distribution failure. This distinguishes confusion (they can't find how to accept) from disinterest (they see it and ignore it).

4.  **`session_returned`** (Properties: `user_id`, `days_since_first_session`)
    *   **Question Answered:** Is the user retaining? (The most critical metric for PMF).
    *   **Rationale:** You explicitly asked to gauge product-market fit. PMF is defined by retention, not initial usage. This event allows you to build a cohort analysis (e.g., "Of users who created a doc on Day 1, how many returned by Day 3?"). If this metric is flat, no amount of "suggestions accepted" matters. It is the bottom-up diagnostic required before looking at acquisition.

5.  **`help_triggered`** (Properties: `user_id`, `context_screen`, `search_query`)
    *   **Question Answered:** Where specifically are users confused?
    *   **Rationale:** To separate confusion from disinterest, you need a negative signal that implies *effort* to understand. A user who struggles and clicks "Help" is confused but interested. A user who struggles and leaves is either deeply confused or disinterested. This event provides the qualitative signal needed to debug the "confusion" variable without engineering overhead for full session replay tools.

**Exclusions & Notes:**
*   **Error Rates:** Do not instrument custom error events for this beta; rely on existing system observability (logs/traces) for stability. Product behavior (what users do) is distinct from system health.
*   **Time-to-First-Value:** Captured implicitly via the delta between `session_started` and `suggestion_accepted` in your analytics tool; no separate event needed.

**Immediate Next Step:** Define the exact property schema for these five events and hand off to engineering tomorrow. Do not add "just in case" events; any metric not tied to these specific questions is noise at this stage.
