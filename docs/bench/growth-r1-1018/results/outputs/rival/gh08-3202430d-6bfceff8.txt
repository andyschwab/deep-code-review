### Data Reconciliation & Validation Plan for DataPure

**Phase 1: Immediate Triage & Scope Definition (Days 1-2)**
1.  **Isolate the Drop:** Segment the 18% decline by platform (iOS, Android, Web), browser, and geographic region. If the drop is uniform across all segments, it suggests a global tagging failure (e.g., container not firing). If isolated to one platform, the issue is likely SDK-specific.
2.  **Verify Implementation Load:** Confirm the new tracking snippet/container ID is actually present on the live production site/app post-November 5th. Use browser developer tools or a tag assistant to verify the network requests are being sent to the new vendor endpoint.
3.  **Check Data Latency:** Contact the new vendor to confirm their SLA for data processing. Some enterprise platforms have a 24-48 hour delay for full dataset availability, though a multi-day gap is unusual.

**Phase 2: Event Prioritization & Validation (Days 3-4)**
Prioritize checking these event types in this order to determine if the drop is structural or functional:
1.  **Session Start / Page View:** These are usually automatic. If these are missing, the base installation is broken.
2.  **Authentication Events (Login/Signup):** Critical for user counting. If these are firing but page views aren't, your user counts might be artificially low due to ID resolution issues.
3.  **Core Feature Events:** Check high-volume actions specific to DataPure's value prop. If these are present but session starts are missing, you may have a duplicate-filtering issue where the new vendor is aggressively deduplicating events.

**Phase 3: Reconciliation & Estimation (Days 5-7)**
Since server logs are incomplete, use a **Ratio-Based Estimation** for the board presentation:
1.  **Establish a Baseline Ratio:** Calculate the ratio of *Logged Actions* (e.g., database writes, API calls) to *Tracked Events* for the period of October 1–31 using the legacy system.
    *   *Formula:* `Legacy Events / Legacy Server Logs = Baseline Ratio`
2.  **Apply to Current Period:** Apply this ratio to the available (incomplete) server logs from November 6–19.
    *   *Formula:* `Current Server Logs × Baseline Ratio = Estimated True Events`
3.  **Present a Range:** Do not present a single corrected number. Present a "Confirmed Floor" (what the new tool shows) and an "Estimated Ceiling" (based on the server log ratio). Explicitly label the gap period data as "Unverified – Pending Full Log Recovery."

**Phase 4: Historical Trend Integrity (Board Prep)**
*   **Do Not Merge Datasets:** Do not simply append the new data to the old. The definitions likely differ.
*   **Create a "Break" in the Chart:** Visually indicate the migration date on all board charts. Annotate the drop as "Tracking Migration – Data Under Validation."
*   **Parallel Run Proposal:** Recommend running both systems in parallel for 14 days once the fix is identified to build a conversion factor for historical normalization.

**Deliverable for Board:** A memo stating the 18% drop is attributed to a tracking implementation error, not user churn, supported by the segmented analysis and the ratio-based estimation model.

**Note:** Prioritize verifying the "Session Start" event first; if this is missing, all downstream user metrics are invalid. Ensure no PII was accidentally sent to the new vendor during the migration debug phase, as this can cause data rejection.
