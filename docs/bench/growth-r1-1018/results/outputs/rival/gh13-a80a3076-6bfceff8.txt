# GreenCart London Launch: Essential Tracking Plan

## 1. Acquisition & Onboarding
**Business Question:** Which channels drive high-intent users versus window shoppers in specific London boroughs?

| Event | Essential Properties | Decision Impact |
| :--- | :--- | :--- |
| `landing_page_view` | `borough_detected`, `utm_source`, `utm_medium`, `device_type` | Validates if marketing spend aligns with delivery zone coverage. |
| `signup_started` | `method` (email/social), `borough_selected` | Identifies friction in account creation by location. |
| `signup_completed` | `user_id`, `borough`, `time_to_complete` | Measures conversion efficiency of the onboarding flow. |

## 2. Browse & Search (Availability Hypothesis)
**Business Question:** Is item availability causing silent drop-offs before users even attempt to checkout?

| Event | Essential Properties | Decision Impact |
| :--- | :--- | :--- |
| `search_performed` | `search_term`, `result_count`, `borough` | Detects demand for items we don't stock in specific zones. |
| `product_view` | `product_id`, `category`, `in_stock_status`, `borough` | Correlates views of out-of-stock items with session abandonment. |
| `out_of_stock_viewed` | `product_id`, `category`, `user_id` | **Critical:** Quantifies the "hidden friction" of unavailable items. |
| `filter_applied` | `filter_type` (e.g., "in stock only"), `results_count` | Shows if users are forced to narrow choices due to lack of availability. |

## 3. Cart & Checkout
**Business Question:** Where do users abandon the funnel, and does basket size correlate with completion?

| Event | Essential Properties | Decision Impact |
| :--- | :--- | :--- |
| `add_to_cart` | `product_id`, `quantity`, `price`, `in_stock_status` | Tracks intent vs. actual inventory success at the moment of selection. |
| `cart_view` | `cart_value`, `item_count`, `estimated_delivery_time` | Analyzes if delivery estimates or basket size deter progression. |
| `checkout_started` | `cart_value`, `delivery_slot_selected`, `borough` | Measures commitment level before payment entry. |
| `payment_failed` | `error_code`, `payment_method`, `cart_value` | Identifies technical or financial friction points. |
| `order_placed` | `order_id`, `total_value`, `item_count`, `delivery_slot`, `borough` | The primary conversion metric; baseline for all funnel rates. |

## 4. Fulfillment & Delivery (Satisfaction Hypothesis)
**Business Question:** Does actual delivery performance match promises, and how does it drive satisfaction?

| Event | Essential Properties | Decision Impact |
| :--- | :--- | :--- |
| `order_confirmed_by_store` | `order_id`, `time_to_confirm`, `items_substituted_count` | Measures operational lag and initial availability issues. |
| `driver_assigned` | `order_id`, `time_to_assign`, `estimated_duration` | Tracks logistics efficiency. |
| `delivery_started` | `order_id`, `actual_start_time` | Begins the true delivery timer. |
| `delivery_completed` | `order_id`, `actual_duration`, `promised_duration`, `on_time_status` | **Critical:** Validates the "delivery time" satisfaction assumption. |
| `order_substituted` | `order_id`, `original_item_id`, `replacement_item_id`, `user_accepted` | Directly measures the impact of availability friction on the final order. |

## 5. Post-Order & Retention
**Business Question:** What drives repeat usage and churn in the first 30 days?

| Event | Essential Properties | Decision Impact |
| :--- | :--- | :--- |
| `rating_submitted` | `order_id`, `rating_score`, `rating_category` (speed/quality), `comment` | Direct feedback loop to correlate specific orders with satisfaction. |
| `support_ticket_created` | `order_id`, `issue_type` (missing item, late delivery), `borough` | Qualitative data to triangulate with quantitative drop-offs. |
| `second_order_placed` | `user_id`, `days_since_first_order`, `borough` | The ultimate measure of product-market fit in each borough. |

## Implementation Notes for Engineering
*   **Consistency:** Ensure `borough` and `user_id` are attached to every single event above to enable cohort analysis by location.
*   **Timing:** Capture timestamps for both the user action and the server response to distinguish between UI lag and backend processing delays.
