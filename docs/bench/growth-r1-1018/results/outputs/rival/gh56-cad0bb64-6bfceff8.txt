**Recommended North Star Metric: Weekly Active Reporting Cycles Completed**

**Definition:** The count of distinct city planning agencies per week that successfully generate, export, or submit a mandated environmental report using GreenCity Dashboard data, where the session duration indicates a ≥30% time reduction compared to the manual baseline.

**Why This Metric:**
Current login frequency is a vanity metric; a planner can log in twice a week and still fail to achieve the 30% efficiency gain required for adoption. "Reporting Cycles Completed" shifts the focus from software access to civic outcome. It directly validates your core assumption: if the dashboard reduces reporting time, planners will use it to finish their actual jobs. This aligns the technical team (who must ensure data latency is low enough for real-time report generation) with civic stakeholders (who care about completed compliance tasks, not dashboard visits). For mayors and the Regional Climate Council, this metric translates technical uptime into verified administrative labor savings, justifying continued investment through tangible operational efficiency rather than hypothetical engagement.

**Validation Strategy Against Data Gaps:**
You currently track sensor ingestion and logins, but lack the link between usage and outcome. To validate this metric before June without building new features:

1.  **Establish the Manual Baseline Immediately:** Survey the 3 agencies to document the average time spent manually compiling air quality and energy reports pre-GreenCity. If historical data is missing, use current staff estimates for a "manual mock-up" task to set the 100% baseline time.
2.  **Instrument the "Finish" Event:** Work with developers to tag the specific action that signifies report completion (e.g., clicking "Export PDF," "Submit to State," or viewing the final summary page for >2 minutes). Do not rely on session end times.
3.  **Calculate Efficiency Per Cycle:** For every completed report event, capture the session duration. Compare this against the manual baseline. Only count a cycle as "Active" if the time taken is ≤70% of the manual baseline.
4.  **Bridge the Latency Gap:** Correlate failed or abandoned report sessions with sensor data timestamps. If users start reports but don't finish when data latency exceeds a specific threshold (e.g., 4 hours), you have isolated latency as the blocker. If they finish but take too long, the issue is UX/insights.

This approach converts your current ambiguous "low login" problem into a binary success/failure signal on actual work completed, providing the funding partners with a clear ROI story based on labor hours saved.

*Note: Ensure user consent is obtained before measuring specific task durations to comply with municipal privacy standards.*
*Note: If "reporting" varies too much between cities, substitute with "Decision Events Verified," where a planner flags a specific sensor anomaly for action within the tool.*
