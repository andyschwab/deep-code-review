### Delivery Plan: Historical Donation Migration

**1. Lanes & Parallelism**
*   **Lane A (Data Engineering):** Two engineers develop the migration script in isolation. They must implement batch processing with per-batch checksum validation and dual-stream logging (application logs + compliance bucket). This lane works against a local snapshot of the legacy data.
*   **Lane B (Infrastructure & Safety):** One engineer prepares the rollback mechanism and verifies the integrity of the latest database backup. Since backups take six hours, this lane must start immediately to ensure a valid restore point exists before any schema interaction. They also prepare a "read-only" fallback mode for the portal to ensure uptime if the migration locks resources unexpectedly.
*   **Lane C (Audit & Compliance):** The fourth engineer drafts the regulator notification template and defines the exact log schema required for the compliance bucket, ensuring the script in Lane A matches these requirements exactly.

**Parallel Execution:** Lanes A, B, and C run simultaneously. Lane A cannot merge until Lane B confirms the backup strategy and Lane C confirms the log schema.

**2. Gates & Checks**
*   **Gate 1 (Code Freeze):** All code must be committed to a feature branch `feat/donation-migration` by Wednesday 18:00. No changes allowed after this point.
*   **Gate 2 (Staging Dry-Run):** Thursday 06:00 (outside business hours). Run the migration script against the staging environment using a full data subset.
    *   *Check:* Verify checksums match source vs. destination.
    *   *Check:* Confirm zero downtime on the staging portal during the run.
    *   *Check:* Validate logs appear in the compliance bucket.
    *   *Constraint:* If the CI pipeline fails due to flaky network checks, manually verify the specific migration job logs rather than re-running the full 55-minute suite immediately.
*   **Gate 3 (Schema Lock):** Confirm no schema changes are attempted between 08:00 and 18:00 local time. The migration job must pause or queue if it detects this window.

**3. Review Process**
*   **Independent Review:** The migration script and rollback plan must be reviewed by an engineer *not* involved in Lane A (preferably the Lane C engineer).
*   **Approval Authority:** Jane Smith is the sole approver for production deployment. She must review the dry-run results and the rollback verification report before signing off.
*   **Audit Review:** The compliance log format must be signed off by the compliance officer (external to the dev team) before the final run.

**4. Landing Strategy**
*   **Execution Window:** Friday 20:00 to Saturday 06:00. This avoids the 08:00–18:00 schema lock and minimizes traffic risk, though the portal must remain live.
*   **Deployment:**
    1.  Trigger the backup verification (Lane B) one last time.
    2.  Deploy the migration job to production.
    3.  Execute the job in batches. If any batch checksum fails, the script must halt immediately and trigger the rollback.
*   **Human Decision Points:**
    *   If the dry-run reveals >1% data discrepancy, Jane Smith must decide whether to delay the launch or authorize a manual patch.
    *   If the irreversible audit log is triggered prematurely, the team lead must immediately contact the regulator.
*   **Rollback:** If the migration fails mid-stream:
    1.  Halt the script.
    2.  Restore the database from the verified backup (6-hour window).
    3.  Revert the code deployment.
    4.  Notify sponsors of a "scheduled maintenance extension" if portal latency spikes, but avoid admitting data failure unless unavoidable.
*   **Final Merge:** Only merge `feat/donation-migration` to `main` after successful completion and verification of the full 20-year dataset. Do not merge partially.
