### Delivery Plan: Course Search Latency Optimization

**1. Lanes and Parallelism**
Work is divided into three lanes to maximize parallel execution while respecting serialization constraints.

*   **Lane A (Database Engineering):** Responsible for schema analysis, index strategy, and query refactoring. This lane must serialize before any load testing.
    *   *Task:* Analyze slow query logs from the read-replica to identify missing indexes or N+1 patterns in course retrieval.
    *   *Task:* Draft migration scripts for new composite indexes.
*   **Lane B (Application Logic):** Responsible for optimizing the retrieval layer and caching strategies.
    *   *Task:* Refactor the catalog service to implement aggressive read-through caching for popular search terms.
    *   *Task:* Implement circuit breakers to prevent cascade failures during peak load.
*   **Lane C (Infrastructure & Observability):** Responsible for synthetic load generation and monitoring.
    *   *Task:* Configure a high-fidelity load test script that mimics "spring rush" concurrency, bypassing the unreliable staging data by injecting production-like traffic patterns.
    *   *Task:* Set up real-time latency dashboards specifically for the search endpoint.

*Parallel Execution:* Lanes A and B can work simultaneously once the initial log analysis is complete. Lane C runs in parallel to prepare the testing harness.
*Serialization:* Lane A's index migrations must be applied and verified before Lane B's caching logic is finalized, as caching depends on the new query performance baseline. The irreversible search index rebuild must be the final database operation before the final load test.

**2. Gates and Checks**
All checks run on a dedicated feature branch derived from the current production revision (`prod-main`).

*   **Gate 1: Static Analysis & Unit Tests (Local/Dev):** Runs on every commit. Must pass before merging to the integration branch.
*   **Gate 2: Integration Test (CI Pipeline):** Triggers manually to conserve credits. Runs only twice daily (08:00 and 14:00 UTC).
    *   *Constraint:* Code must be frozen 30 minutes prior to the window.
    *   *Check:* Verify no regression in billing system latency (shared DB constraint).
*   **Gate 3: Performance Validation (Pre-Prod):** Runs on the integration branch after the CI pass.
    *   *Criterion:* Search results must render <2s under 150% of projected peak concurrency.
    *   *Check:* Verify zero lock contention on the user profile table during the index rebuild simulation.

**3. Review Process**
Reviews are independent and mandatory before approval requests.

*   **Code Review:** Conducted by a Senior Backend Engineer not involved in Lanes A or B. Focus: Query efficiency, cache invalidation logic, and thread safety.
*   **Database Review:** Conducted by the Database Administrator (DBA). Focus: Index impact on write performance, replication lag, and the safety of the irreversible rebuild job.
*   **Product Review:** Conducted by the Product Lead. Focus: Verification that the <2s target is met in the load test reports and that no search relevance was sacrificed for speed.

**4. Landing Strategy**
Deployment is a phased rollout requiring strict human coordination.

*   **Step 1: Approval Gathering:** Once Gates 1-3 pass, the Tech Lead compiles the performance report and submits written requests to the DBA and Product Lead. No deployment occurs without both signatures.
*   **Step 2: Off-Peak Deployment:** Merge to `prod-main` and deploy during the lowest traffic window (02:00–04:00 local time).
    *   *Action:* Apply database migrations first.
    *   *Action:* Trigger the search index rebuild (monitoring for user profile locks).
    *   *Action:* Roll out application changes to 10% of instances.
*   **Step 3: Canary Verification:** Monitor latency and error rates for 30 minutes. If latency exceeds 1.8s or error rates rise >0.1%, trigger immediate rollback.
*   **Step 4: Full Rollout:** Gradually increase traffic to 100% over 2 hours.

**Rollback Plan:**
If performance degrades or billing latency spikes:
1.  Revert the application deployment to the previous stable revision immediately.
2.  The DBA will assess if index drops are required (do not attempt to reverse the index rebuild job if it caused corruption; restore from pre-maintenance snapshot if necessary).
3.  Post-mortem to be conducted within 24 hours.

**Human Decisions Required:**
*   Final go/no-go based on CI credit usage timing.
*   Authorization for the irreversible index rebuild.
*   Approval to proceed if load tests show marginal pass (1.9s–2.0s) under extreme edge cases.
