### Delivery Plan: Q3 Ledger Aggregation Acceleration

**Lanes & Parallelism**
*   **Lane A (Optimization - Platform Stability):** Refactor data retrieval and processing logic to target the 60% reduction. Work occurs on feature branch `feat/q3-perf-opt`. Strict constraint: Zero modifications to calculation formulas, rounding methods, or `global-audit-config`.
*   **Lane B (Validation Harness - QA Automation):** Develop an independent comparison script outside the main build pipeline. This tool will ingest output from both the current production version and the optimized candidate to verify bit-for-bit identity.
*   **Serialization Point:** Lane B cannot execute full validation until Lane A produces the first stable candidate build. However, Lane B may build the harness infrastructure immediately.

**Gates & Checks**
*   **Gate 1: Local Integrity Check (Pre-Commit).** Before pushing code, the developer must run a local subset comparison against a cached production dataset. Failure to match bit-for-bit blocks the commit.
*   **Gate 2: CI Performance Budget.** The pull request triggers the CI pipeline on commit `$HASH`.
    *   *Constraint:* Pipeline must complete under 70 minutes to avoid auto-termination.
    *   *Action:* If the network flake occurs in staging, a manual retry is authorized once per commit. Repeated failures require a pause for infrastructure diagnosis.
    *   *Success Criteria:* Build passes + Execution time simulation shows >60% improvement.
*   **Gate 3: Parallel Run Validation (Staging).** Deploy candidate to a isolated staging environment alongside the current stable version.
    *   *Process:* Run both aggregators against the same Q3 snapshot.
    *   *Check:* Lane B's harness compares outputs. Any byte-level divergence fails the gate immediately.
    *   *Timing:* Must not be scheduled during Tuesday 02:00–04:00 UTC (DB read-only window).

**Review Process**
*   **Code Review:** Conducted by a Senior Engineer from the Platform Stability team *excluding* the author. Focus strictly on retrieval logic and concurrency; calculation lines are excluded from modification review since they must remain untouched.
*   **Audit Logic Verification:** An independent review by the Head of Compliance (or delegate) confirming that no formulas were altered. This is a visual diff check limited to math modules to ensure "no-op" status on logic.
*   **Data Integrity Sign-off:** The QA Lead must sign off on the Parallel Run Validation report generated by Lane B's harness.

**Landing Strategy**
*   **Merge Protocol:**
    1.  Merge `feat/q3-perf-opt` to `main` only after Gate 3 success.
    2.  **Approval Requirement:** Dual approval mandatory before merge button becomes active: Chief Architect (performance verification) + Head of Compliance (audit logic verification).
*   **Deployment Window:**
    *   Deploy to production immediately following merge, provided the current time is *not* within the Tuesday 02:00–04:00 UTC maintenance window.
    *   If the merge completes during the forbidden window, the deployment artifact is staged but held until 04:01 UTC.
*   **Rollback Plan:**
    *   Since calculation logic is unchanged, the primary risk is system instability or timeout persistence.
    *   If timeouts persist or errors arise post-deploy, immediate reversion to the previous `main` commit is authorized by the Chief Architect alone to restore SLA.
    *   If data discrepancies are discovered post-launch (despite validation), trigger an emergency freeze, revert, and notify external auditors of a potential recalculation need.

**Human Decisions Required**
1.  **Chief Architect:** Final approval on performance metrics and rollback authorization.
2.  **Head of Compliance:** Final approval confirming zero audit logic drift.
3.  **QA Lead:** Sign-off on the bit-for-bit validation report.
