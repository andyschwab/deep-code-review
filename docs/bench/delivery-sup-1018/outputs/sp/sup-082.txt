**Delivery Plan: Cross-Factory Device Grouping**

**1. Lanes & Parallelism**
*   **Lane A (Fleet Ops - Backend Logic):** Develop the additive routing layer in `LogisticsCore`. This includes parsing the new `regional-cluster` header and implementing the timeout logic to fallback to local caching. This work is serialized after the interface definition but can proceed independently of Platform Security's freeze.
*   **Lane B (Platform Security - Config Only):** Since code changes are frozen, this lane is limited to pre-authorizing the specific route entry in `global-routes.json` that points to the Shared Identity Service. This must happen *before* Lane A merges code to ensure the route exists when the code goes live.
*   **Lane C (QA/Validation):** Prepare the production canary verification script. Staging is bypassed for auth checks; therefore, QA focuses solely on defining the success metrics for the production canary run.

**Serialization Constraint:** Lane B (Route Pre-approval) must complete before Lane A attempts to merge. Lane A's code deployment must wait for Lane C's canary validation script to be ready.

**2. Gates & Checks**
*   **Gate 1 (Code Freeze Compliance):** Before any commit, verify that no changes touch the existing factory-level permission schema files. Any modification here triggers an immediate revert.
*   **Gate 2 (Dual Approval):** The edit to `global-routes.json` requires explicit written approval from both the Fleet Operations Lead and the Platform Security Lead. This check runs on the specific commit hash introducing the route change.
*   **Gate 3 (CI Optimization):** Trigger the CI pipeline only on the final merge commit to the release branch. Do not run full regression suites on intermediate commits; rely on unit tests for the new routing logic only to save compute credits and time.
*   **Gate 4 (Canary Verification):** The deployment halts automatically if the production canary (5% traffic) reports any identity validation failures or timeout fallback errors exceeding 1%.

**3. Review Strategy**
*   **Code Review:** An independent senior engineer from the Inventory Team (neutral party) reviews Lane A's code. They must verify the "additive only" constraint and the correctness of the timeout-to-cache fallback. They cannot be from Fleet Ops or Platform Security to ensure neutrality.
*   **Config Review:** The `global-routes.json` change is reviewed jointly by both Team Leads as per protocol.
*   **Security Review:** Since Platform Security is frozen, the security implication of the new header parsing is reviewed against the existing security spec by the Inventory Team reviewer, focusing strictly on injection risks in the header parsing logic.

**4. Landing & Rollback**
*   **Merge Strategy:** Merge Lane A into the release branch only after Gate 2 (Dual Approval) is satisfied. The merge triggers the CI pipeline (Gate 3).
*   **Deployment:** Deploy to the production canary immediately after CI passes. Monitor for 30 minutes. If stable, expand to 50%, then 100%.
*   **Human Decision Point:** If the canary shows flaky auth (inherited from staging issues) or high latency, the Fleet Ops Lead must decide whether to proceed or roll back. No automatic promotion past 5% without this explicit go-ahead.
*   **Rollback Plan:** If the central service times out excessively or data loss is detected, revert the `global-routes.json` change immediately (dual approval waived for emergency revert, post-facto sign-off required). Reverting the code commit disables the header parsing, forcing all traffic back to the legacy factory-siloed path, preserving data integrity via local caching.

**Timeline:** All code work must conclude by Thursday EOD to allow Friday for the dual-approval process and Monday morning for the canary launch before the Q3 audit begins.
