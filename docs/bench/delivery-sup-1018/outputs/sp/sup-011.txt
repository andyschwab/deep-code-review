# Delivery Plan: Real-Time Overheat Alerts

## Lanes and Parallelism
**Lane A: Core Monitoring Service (Serialized)**
*   **Owner:** Senior Engineer 1
*   **Work:** Develop the independent monitoring service that ingests the PLC data stream. This service must be strictly read-only regarding the PLC interface.
*   **Constraint:** Development occurs on a feature branch isolated from `main`. No changes to `global_io_map.json` are permitted during business hours; all configuration updates must be staged outside 08:00–18:00 local time.

**Lane B: Dashboard Integration (Parallel to Lane A)**
*   **Owner:** Senior Engineer 2
*   **Work:** Implement the frontend alert components and WebSocket listeners on the internal dashboard.
*   **Dependency:** Requires only the defined JSON payload schema from Lane A, not the running service.

**Lane C: Validation Harness (Parallel to Lane A & B)**
*   **Owner:** QA Automation
*   **Work:** Create a simulated data stream injector to bypass the 45-minute hardware-in-the-loop CI for unit testing. The full 45-minute CI run is reserved strictly for the final pre-deploy gate.

## Gates and Checks
**Gate 1: Architecture Review (Pre-Code)**
*   **Reviewer:** Jane Smith (Independent of implementers)
*   **Target:** Design document on revision `HEAD` of `main`.
*   **Check:** Verify strict isolation of the new service from the core control loop. Confirm no write-back logic exists in the PLC interface code.

**Gate 2: Integration Dry-Run (Post-Unit Test)**
*   **Runner:** CI Pipeline
*   **Target:** Merge commit of Lane A and Lane B in a staging worktree.
*   **Check:** Run the simulated data stream. If the flaky network check fails, one manual retry is authorized. If it fails twice, the build is rejected for infrastructure investigation, not code changes.

**Gate 3: Full Hardware Simulation (Final Pre-Deploy)**
*   **Runner:** CI Pipeline
*   **Target:** Release Candidate branch.
*   **Check:** Full 45-minute hardware-in-the-loop simulation. This must pass green before any deploy ticket is raised.

## Review Process
*   **Code Review:** Conducted by the senior engineer *not* owning the lane (Engineer 1 reviews Lane B; Engineer 2 reviews Lane A).
*   **Safety Audit:** Jane Smith performs a final logic audit specifically on the "read-only" enforcement and failure modes. She verifies that a crash in the alerting service results in a silent fail, not a control loop halt.
*   **Independence:** Reviewers must pull the specific commit hash generated by Gate 2; they do not review live branches.

## Landing Strategy
**Merge Window:** 02:00 UTC – 04:00 UTC.
*   **Reasoning:** This window provides a 2-hour buffer before the irreversible 06:00 UTC shift handover and state purge. It also avoids business hours, allowing unrestricted access to `global_io_map.json` if a configuration tweak is urgently needed.

**Deployment Steps:**
1.  Deploy Lane A (Monitoring Service) to a canary instance.
2.  Verify data ingestion without latency spikes in the core loop.
3.  Deploy Lane B (Dashboard) and enable alert routing.
4.  Monitor for 30 minutes.

**Human Decision Points:**
*   **Go/No-Go:** Jane Smith must explicitly approve the deployment ticket after Gate 3 passes.
*   **Rollback Trigger:** Any latency increase in the core control loop >5ms or a single false negative alert during the canary phase.

**Rollback Plan:**
*   **Mechanism:** Immediate termination of the new monitoring service containers. Dashboard features are toggled off via feature flag.
*   **Constraint:** If the issue is detected after 06:00 UTC, rollback is limited to service termination; state data lost during the shift handover cannot be recovered. Therefore, the "No-Go" decision is critical before 06:00 UTC.
*   **Post-Rollback:** If a rollback occurs, the branch is frozen. A new design review is mandated before re-attempting.
