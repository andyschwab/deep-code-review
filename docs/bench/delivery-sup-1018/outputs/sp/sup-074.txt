### Delivery Plan: Oakwood Legacy Data Backfill

#### 1. Lanes & Parallelism
*   **Lane A (Data Prep - Isolated):** Extract 2021 PDF logs locally. Parse into structured JSON. Apply the "Billing Cap" logic (min(calculated, archived)) and flag discrepancies. **Output:** `oakwood_backfill_candidate.json`.
*   **Lane B (Audit Schema):** Define the metadata schema to tag records as `source: legacy_import` vs. `source: live_sensor`. Update the local ingestion script to apply these tags.
*   **Lane C (Compliance Coordination):** Request the Tuesday change window for `billing-rates.json` if rate alignment is needed. If no rate changes are required, this lane is inactive.
*   **Serialization Point:** Lane A and B must complete and merge before any CI trigger. Lane C must clear before final production deploy if rates are touched.

#### 2. Gates & Checks
*   **Gate 1: Local Verification (Pre-CI):**
    *   **Revision:** Run on the local branch containing Lane A+B changes.
    *   **Check:** Manually verify 5 random accounts where `calculated > archived` to ensure the cap logic applied correctly and flags were raised.
    *   **Constraint:** Do **not** run full integration tests locally (missing parser library causes flaky failures). Rely on unit logic verification only.
*   **Gate 2: Staging Dry-Run (CI Trigger #1):**
    *   **Revision:** Commit `oakwood_backfill_candidate.json` + ingestion script updates.
    *   **Action:** Trigger CI pipeline against the **Staging** ledger (non-production).
    *   **Check:** Verify audit tags appear correctly in the staging ledger. Confirm no tax filings were triggered in the staging environment.
    *   **Cost Control:** This is the only allowed CI run before production.
*   **Gate 3: Compliance Sign-off:**
    *   If `billing-rates.json` was modified, verify the Tuesday window is active and Compliance has approved the diff.

#### 3. Review Strategy
*   **Technical Review:** Performed by a Senior Engineer from the **Urban Infrastructure team** (owners of `legacy-bridge`). They must verify the parsing logic and the "min()" cap implementation.
*   **Business Review:** Performed by the **Director of Resident Services**. They must validate the list of "flagged accounts" generated by Lane A to ensure manual review protocols are clear.
*   **Independence:** The Technical Reviewer cannot be the author of the ingestion script. The Business Reviewer must not rely solely on the Technical Reviewer's summary; they must see the raw flag list.

#### 4. Landing & Rollback
*   **Pre-Landing:**
    *   Ensure the branch is rebased on the latest `main`.
    *   Confirm the "Tuesday Window" status if applicable.
*   **Approval Chain:**
    1.  Lead Architect approval (Technical safety).
    2.  Director of Resident Services approval (Business safety/flags).
*   **Execution:**
    *   Merge to `main`.
    *   Trigger Production CI pipeline (**Cost:** $45, **Time:** 50 mins).
    *   **Critical:** Monitor the pipeline for the specific step that commits to the ledger.
*   **Rollback Strategy:**
    *   **Constraint:** Production ledger transactions are **irreversible** and trigger tax filings.
    *   **Mitigation:** There is no code-based rollback. If data is corrupt, the "rollback" is a manual financial reversal process initiated by Finance.
    *   **Stop Condition:** If the Staging Dry-Run (Gate 2) shows any untagged records or failed caps, **do not proceed** to production. The risk of irreversible tax filing errors outweighs the urgency.

#### 5. Human Decisions Required
1.  **Director of Resident Services:** Must explicitly approve the list of flagged accounts before the merge.
2.  **Lead Architect:** Must confirm the audit tag schema prevents double-counting during month-end close.
3.  **Compliance Team:** Must grant access to `billing-rates.json` if the Tuesday window is required.
