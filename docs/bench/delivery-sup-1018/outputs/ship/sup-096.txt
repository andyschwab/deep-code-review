**Delivery Plan: Rollback Cosmetic Shader Update v4.2**

**Objective:** Revert 'Neon Glow' asset bundle references to the previous stable version on staging, verifying visual correction without disrupting active user sessions or touching the inventory database.

### 1. Lanes & Serialization

*   **Lane A: Asset Reversion (Builder)**
    *   **Task:** Identify the previous stable commit SHA for the 'Neon Glow' asset bundle. Modify only the asset bundle references in the client configuration.
    *   **Constraint:** Do not modify user inventory schemas or equip-state logic.
    *   **Serialization:** Must complete before Lane B. Cannot run during business hours if shared material config files are locked.
*   **Lane B: Session Integrity Verification (QA)**
    *   **Task:** Simulate active sessions in the customization lounge. Verify that reverting assets does not force deselection or crash menus. Confirm visuals revert to the stable state.
    *   **Constraint:** Must run against the exact SHA produced by Lane A.
*   **Lane C: Pipeline Optimization (Conductor)**
    *   **Task:** Configure the CI run to skip the known flaky "lighting validation" check for this specific metadata-only change to save compute credits and time, documenting the justification.

**Parallelism:** Lane C runs parallel to Lane A. Lane B must wait for Lane A's output.

### 2. Gates & Checks

*   **G0/G1 (Intake/Spec):** Confirm scope is strictly client-side asset reversion. Explicitly state: "No database writes; no equip-state logic changes."
*   **G2 (Plan):** Define the specific previous stable SHA. Set a hard budget cap for the CI run (avoiding full 45-minute suite if possible via targeted testing).
*   **G3 (Design):** Verify the rollback strategy ensures cache propagation safety. Confirm the "irreversible" nature is understood; staging is the only safe testbed.
*   **G4 (Implement):** Lane A commits the reference change. Commit message must cite the ticket and the target stable SHA.
*   **G5 (Verify):**
    *   **Environment:** Staging only.
    *   **Check 1:** Visual confirmation of 'Neon Glow' reverting to stable textures on mid-range device profiles.
    *   **Check 2:** Stress test customization lounge with active sessions; assert zero crashes and zero forced deselections.
    *   **CI Run:** Execute optimized pipeline (Lane C). If "lighting validation" triggers despite skips, treat as known flake and proceed if other gates pass (documented).
*   **G6 (Review):**
    *   **Reviewer 1 (Independent):** Visuals Squad Lead (confirms asset integrity).
    *   **Reviewer 2 (Independent):** Site Reliability Engineer (confirms no side effects on session stability).
    *   **Constraint:** Neither reviewer can be the Builder from Lane A.

### 3. Landing & Human Decisions

*   **Merge Strategy:**
    *   Merge to staging branch only after G6 approval.
    *   **Human Gate 1:** Dual approval required from Lead Artist and Site Reliability before merging to staging.
    *   **Human Gate 2:** Final "Go/No-Go" for production deployment after staging verification receipts are reviewed.
*   **Deployment:**
    *   Triggered only by the automated deployment bot (engineers have no write access to prod equip states).
    *   **Rollback Plan:** Since cache propagation is irreversible, the "rollback" of this rollback requires a new forward deploy. If staging fails, halt immediately; do not attempt hotfixes on the broken v4.2 in prod.
*   **Post-Deploy Verification:**
    *   Monitor support ticket volume for "texture tearing" keywords.
    *   Confirm no spike in "session crash" logs from the customization lounge.

### 4. Risk & Constraints Summary

*   **Irreversibility:** Once cached, the revert cannot be undone quickly. Staging verification is the single point of failure prevention.
*   **Cost Control:** CI optimization (Lane C) is mandatory to prevent wasted credits on flaky checks.
*   **Data Safety:** Strict prohibition on touching the production database. Equip state preservation is validated via simulation, not database manipulation.
*   **Timing:** Execution must avoid business hours if shared config locks are active.
