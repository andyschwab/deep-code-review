### First-Time Documentation Contribution Checklist

**1. Verify Front-Matter Headers**
Open your edited markdown files and locate the top section enclosed by `---`. Ensure these exact fields exist and are valid:
*   `author`: Add your name or GitHub handle (e.g., `author: your-name`). Do not leave this empty.
*   `last-reviewed`: Update this to today's date in the format the project uses (typically `YYYY-MM-DD`).
*   **Crucial:** Ensure there are no trailing spaces after the colons and that the closing `---` is on its own line. A missing dash or extra space often causes the "build fails" error you mentioned.

**2. Run the Local Build Command**
Do not rely on visual inspection alone. Run the specific build command defined in the project's `package.json`, `Makefile`, or `CONTRIBUTING.md` (common examples: `npm run build`, `hugo`, or `mkdocs build`).
*   **Success:** The command finishes without errors and generates a `dist/` or `public/` folder.
*   **Failure:** If it stops with an error like "Front-matter missing" or "YAML parse error," re-check Step 1 for syntax typos.

**3. Validate the Fixed Content**
Once the build succeeds, open the generated HTML file in your browser corresponding to your changes.
*   Confirm the typo is gone.
*   Copy the code snippet from the rendered page and test it locally to ensure the fix actually works, not just that it looks right.

**4. Check for Unintended Changes**
Run `git diff` in your terminal.
*   Verify you only changed the intended text, code snippet, and the two front-matter lines (`author` and `last-reviewed`).
*   If you see changes to whitespace, indentation, or other files you didn't touch, revert those immediately. Maintainers reject PRs that reformat unrelated lines.

**5. Commit with Conventional Messages**
Create your commit using a clear message format.
*   Example: `docs: fix typo and update code example in [filename]`
*   Avoid vague messages like "fixed stuff" or "updated docs."

**6. Final Pre-Push Sanity Check**
Before pushing, run the build command one last time on a clean branch state to ensure no cached artifacts are hiding an error. If it passes, you are ready to push and open your Pull Request.

*Note: If the build fails locally, do not open the PR; the automated system will reject it immediately. If you are unsure about the date format, check three other recent files in the same folder and copy their style exactly.*
