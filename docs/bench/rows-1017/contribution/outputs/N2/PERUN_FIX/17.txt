### Back-Porting Plan for Messaging Queue Race Condition Fix

**1. Isolate the Core Logic Change**
Extract the specific code modifications required to fix the race condition from your main branch commit. Separate the functional fix (logic changes to prevent duplication) from any refactoring, style changes, or new infrastructure dependencies introduced in the main branch. The goal is a minimal patch containing only the essential logic repair.

**2. Adaptation Strategy for Deprecated Testing Frameworks**
Since the older branches use an incompatible testing framework, do not attempt to port the new test suite directly. Instead, adopt one of the following approaches:
*   **Native Translation:** Rewrite the *intent* of your new tests using the syntax and capabilities of the deprecated framework present in the older branches. Focus on verifying the specific invariant (no duplicate messages under load) rather than replicating the exact test structure.
*   **Integration Verification:** If the deprecated framework lacks robust concurrency testing tools, propose adding a lightweight, standalone integration script (e.g., a shell script or simple Python runner) that simulates high load and asserts message counts. This script should live alongside the existing tests but not depend on the deprecated framework's internal APIs.
*   **Manual Verification Protocol:** If automated testing is impossible without significant risk of flakiness, draft a rigorous manual verification procedure. This should include specific load parameters, duration, and success criteria (e.g., "Run X producer/consumer pairs for Y hours; zero duplicates observed in logs"). Present this as a temporary measure until the branch is upgraded or EOL.

**3. Branch-Specific Implementation**
*   **Branch A (Newer Legacy):** Apply the isolated logic patch. Attempt to translate the primary test case into the legacy framework. Run the existing CI pipeline to ensure no regressions in unrelated areas.
*   **Branch B (Older Legacy):** Apply the isolated logic patch. If the testing framework is too restrictive, implement the standalone integration script or manual verification protocol. Ensure the build environment for this branch is stable before introducing new verification steps.

**4. Proposal to Maintainers**
Prepare a single pull request (or three, if preferred by the project) containing:
*   The back-ported fix for each branch.
*   A clear explanation in the commit message linking to the original main branch fix.
*   A "Verification" section in the PR description explicitly stating:
    *   How the fix was validated on the latest version.
    *   The specific adaptation made for the older branch's test environment (translated test, new script, or manual protocol).
    *   Any limitations of the older verification method and why it was chosen over risking flaky tests.
*   A request for guidance if the maintainers prefer a different verification strategy for the EOL branches.

**5. Consistency Check**
Ensure the fix logic is identical across all three branches, even if the surrounding test code differs. Document any minor deviations necessitated by older language features or library versions in the PR comments to maintain an audit trail.

*Note: Do not claim tests pass on older branches until you have actually run them in those specific environments.*
*If the deprecated framework causes build failures, isolate the test changes in a separate commit to make review easier.*
