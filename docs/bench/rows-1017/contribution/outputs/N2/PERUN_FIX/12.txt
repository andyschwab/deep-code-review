**Step-by-Step Plan for Secure Secret Removal**

1.  **Verify Rotation Completeness:** Before touching the repository, confirm with your security team that the rotated token invalidates *all* previous instances of the leaked secret across every environment (test, staging, production). Ensure no active services rely on the old value.

2.  **Prepare the Replacement Commit:**
    *   Create a new branch (e.g., `fix/leaked-token-scrub`).
    *   Apply your prepared change: replace the hardcoded token in the sample settings file with a clear placeholder (e.g., `<ACME_LOGISTICS_TEST_TOKEN>`).
    *   Add a prominent warning comment in the file explaining why the placeholder exists and where developers can obtain a valid test token.
    *   Commit this change with a message like: `security: scrub leaked access token from sample config; replace with placeholder`.

3.  **Address Git History (The Critical Constraint):**
    *   **Do not rewrite history.** Since you cannot break existing forks or downstream tutorials relying on specific commit hashes, tools like `git filter-repo` or `bfg-repo-cleaner` are unsafe here. Rewriting history would invalidate all existing clones and links.
    *   **Accept the trade-off:** The secret will remain in the *history* of the repository. This is acceptable **only if** the token is definitively revoked and useless to attackers. The goal is to prevent *future* accidental usage, not to erase the past record of the mistake (which is often required for audit trails anyway).
    *   **Mitigation:** By rotating the token, you have rendered the historical data harmless. The priority is stopping new clones from picking up the active secret.

4.  **Submit the Change:**
    *   Push your branch to the remote.
    *   Open a Pull Request (PR) targeting the main branch.
    *   In the PR description, explicitly state: "This change removes an active secret from the current tree. The token has been rotated and invalidated. We are NOT rewriting history to preserve fork compatibility; the historical commit remains but contains only a revoked credential."

5.  **Post-Merge Actions:**
    *   Once merged, tag the release immediately so users pulling the latest version get the clean file.
    *   Update any associated documentation or tutorials to reference the new placeholder variable instead of the old hardcoded value.
    *   Monitor the repository for any accidental re-introduction of the secret via automated scanning tools if available.

**Note:** Never attempt to "clean" history in a public, forked project without explicit consensus from all major stakeholders, as it causes widespread breakage.
**Note:** If the token was not fully rotated, do not proceed; treat this as an active incident and contact the project maintainers directly via a private channel before opening a public PR.
