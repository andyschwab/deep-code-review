You can safely skip opening a separate issue for this fix. For trivial documentation corrections like broken links, creating a standalone ticket is often considered noise unless the project explicitly mandates "issue-first" for *all* changes. Your pull request (PR) itself will serve as the necessary record.

Here is your step-by-step plan to ensure your contribution is accepted without process errors:

**1. Verify the "Issue-First" Rule Nuance**
Re-read the `CONTRIBUTING.md` section on issues. If it says "Features and bug fixes require an issue," you are clear to proceed. If it strictly says "All changes require an issue," open one anyway, but title it clearly: `docs: Update broken governance link in README`. In 95% of projects, a direct PR for a dead link is preferred.

**2. Branch Correctly**
Do not work on your fork's `main` branch. Run these commands in your terminal:
```bash
git fetch origin
git switch -c fix-readme-link origin/main
```
This ensures your change is isolated and based on the latest project state.

**3. Make the Change**
Edit the `README.md` file to update the URL. Do not fix other typos or reformat lines nearby; keep the diff strictly to the broken link.

**4. Craft the Commit Message**
Since the project requires a ticket reference but none exists, the standard convention is to reference the PR itself (which you will create next) or use a generic documentation tag if allowed. However, to satisfy strict linters that demand a ticket number, you often have to create the PR first, get the number, and then amend your commit.

*Scenario A: The linter allows "no-issue" markers.*
Try this commit message first:
```text
docs(readme): fix broken governance link

Updates the governance document URL to the new location.
No issue opened per trivial docs-change convention.
```

*Scenario B: The linter strictly demands a `#123` format.*
If the CI fails on Scenario A, you must push the PR first to get a number.
1. Commit with a temporary placeholder: `docs(readme): fix broken link (see PR)`
2. Push and open the Draft PR.
3. Once you have the PR number (e.g., #402), amend your commit locally:
   ```bash
   git commit --amend -m "docs(readme): fix broken governance link (#402)"
   git push --force-with-lease
   ```

**5. Write the PR Description**
Keep it brief but evidence-based. Use this template:
```markdown
## Summary
Fixes a 404 error in the README where the governance link pointed to a moved document.

## Change
- Updated `[Governance](old-url)` to `[Governance](new-url)` in README.md.

## Verification
- Verified new URL resolves correctly.
- No other files affected.
```

**6. Submit and Monitor**
Mark the PR as "Ready for Review." If a bot comments about a missing issue, reply politely: "Given this is a trivial dead-link fix, I skipped the issue phase to avoid clutter. Happy to retroactively open one if strictly required."

**Note:** Always use `--force-with-lease` instead of `--force` if you need to update your commit after pushing; it prevents accidentally overwriting changes if you are working on a shared branch.
