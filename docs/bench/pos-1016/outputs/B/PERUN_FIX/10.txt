**Bottom line:** Don't aim to make all six languages fully automatic by flu season. Aim to publish automatically only what you can verify without a fluent reader, gate everything else on a human, and ship narrower in any language without a reviewer. I can't certify any language as "safe" or "accurate", and nothing here has been run. The Spanish pilot tells you nothing measured about the other six.

**Harm inventory (who is hurt, worst case)**
- Critical facts wrong, such as a flipped negation ("do not drink"), dates, times, addresses or phone numbers. Worst case: residents drink contaminated water or miss care.
- Fluent-sounding fabrication or omission that nobody can detect.
- Wrong dialect, script or reading level, so the text is technically correct but unusable.
- SMS encoding failures, such as garbled or truncated non-Latin scripts and split messages.
- Wrong language sent to the wrong recipients.
- Staff over-reliance: department staff can't read the output, so "it was translated" becomes assumed correctness.
- Missing disclosure that the text is machine-translated.
- Autonomous publishing of an urgent, irreversible message. A sent text alert can't be recalled.

**What gets published automatically**
- **Auto-publish:** only reviewed templates per language (clinic hours, routine reminders) where code fills the slots (date, time, address). Each template is reviewed once per language, which is far less reviewer time than reviewing every notice.
- **Human gate, always:** outbreak alerts, water advisories and any free-text notice. A named reviewer approves before publishing.
- **No reviewer available:** don't publish machine text as if it were vetted. Publish English plus a link or phone number for interpreter help, or a clearly labelled machine translation only if the health department's owner signs off knowingly. That is their decision, not ours.
- **Urgent alerts:** pre-translate and pre-review templates for likely scenarios (boil-water, do-not-drink, clinic closure) before the season, so the urgent path doesn't need a live review.

**Test plan, one row per harm**

Each row needs a probe set, a seeded known-bad positive control (so you know the test can catch the error), a known-good negative control, a metric, an owner-set threshold, and a stop condition. Propose zero tolerance for critical-fact errors. Don't invent a "typical" rate.

- **Critical facts:** a deterministic check in code that every number, date, time, address and phone number in the English source appears correctly in the output, plus negation and "do not" probes. This works in every language with no fluent reader. Failure blocks publish.
- **Fabrication or omission:** a reviewer compares against the source, and a back-translation or second-engine disagreement flags items for review. Disagreement is a flag only, never a clearance.
- **Dialect and literacy:** community reviewers rate comprehension on a short rubric.
- **SMS rendering:** send test messages to real handsets and carriers using fixture numbers, never residents.
- **Routing:** test language-to-recipient mapping and the fallback path.
- **Staff over-reliance:** show staff a status label per message (Reviewed / Template / Unreviewed machine translation, each defined) rather than a score.

Limits live in code, not in the model: the publish function rejects unreviewed free-text in gated categories regardless of what the model says.

**Statistics caveats:** zero failures in n probes only bounds the failure rate at about 3/n at 95%. One hundred probes is roughly 3%, which is too loose for critical facts, so rely on templates and code checks there. Reviewer ground truth from a backlog is selection-biased. Re-run probes for non-deterministic output.

**Reviewers with no paid translators**
Try health department bilingual staff, community health workers, partner community organizations, and university language programs. Two reviewers per language is ideal, though one may be all you get. Ask counsel about volunteer liability and compensation. If a language has no reviewer by week 5, it ships template-only or not at all.

**Timeline (about 8 weeks, four people)**
- **Week 1:** finalize the inventory, send counsel their questions, and recruit reviewers. Assign owners.
- **Weeks 2–3:** build the code checks, publish gate, status labels and kill switch, and draft the templates.
- **Weeks 3–5:** reviewer sessions, template approvals, and shadow mode (translations logged, not shown or sent).
- **Weeks 6–7:** staged rollout, one or two counties per language, with monitoring under a named owner.
- **Week 8:** kill-switch drill and buffer. Treat this as slack, not a feature window.

If time runs short, cut languages, not gates.

**Legal routing (counsel's call, not mine)**
Ask counsel whether language-access or civil-rights obligations apply to health departments, whether machine-translation disclosure is required, how public-records or emergency-communication rules treat these notices, and what privacy rules cover phone numbers. Bring: the counties, message types, languages, and the human-review design. Time-sensitive: anything that must be settled before the first staged rollout. Name the EU AI Act and ISO/IEC 42001 only if counsel says they're relevant to you.

**Artifacts**
Write a model card (intended use, out-of-scope uses, per-language results, limits, owner, model version). Any unmeasured metric is marked UNVERIFIED, not filled in. Recommend a visible "machine-translated" disclosure as a control. Re-review whenever the model, a language or the message types change.
