### Pre-Launch Review Plan: Employment Verification Edge Cases

**1. Harm Inventory & Worst-Case Definition**
Before testing, explicitly record the primary harm: **False Negative Eligibility**.
*   **Affected Group:** Gig workers and freelancers with irregular income (e.g., seasonal spikes, multiple small deposits, delayed payments).
*   **Worst Realistic Case:** A valid worker is incorrectly marked "ineligible," blocking access to essential funds during a crisis, with no immediate manual override available due to the rigid API contract.
*   **Secondary Harm:** **Over-reliance/Automation Bias**. The system presents a binary "ineligible" decision as absolute fact, discouraging users from seeking alternative verification paths.

**2. Measurement Strategy: Adversarial Output Testing**
Do not test only for code correctness; test the *decisions* generated by specific input patterns. Construct an evaluation suite with one test row per identified edge case. Each row must include:
*   **Probe Set:** Synthetic user profiles mimicking irregular gig work (e.g., "User A: 3 months of zero income followed by a large lump sum," "User B: Daily micro-payments from 5 different platforms").
*   **Controls:**
    *   *Positive Control:* A known eligible irregular worker who must pass.
    *   *Negative Control:* A known ineligible worker who must fail.
*   **Metric:** False Rejection Rate (FRR) specifically sliced by income volatility segments.
*   **Pass Threshold:** Define a zero-tolerance threshold for any profile matching the "Positive Control" criteria. If the system rejects a known-valid edge case, the launch is blocked.
*   **Stop Condition:** Any failure in the Positive Control set triggers an immediate rollback or feature flag disablement.

**3. Managing Residual Risk (The Human Gate Constraint)**
Your constraint states the API does not allow manual overrides *once a decision is generated*. This creates a critical safety gap.
*   **Pre-Decision Gate:** Since post-decision overrides are impossible, you must implement a **human-in-the-loop review** for any application triggering an "ineligible" result *before* the final API call is made. The system should flag high-risk edge cases (e.g., income variance > X%) for human verification prior to locking the decision.
*   **Uncertainty Disclosure:** Do not output a raw confidence score (e.g., "87% likely ineligible"). Instead, if the model is uncertain, the system must route to the human gate. If a decision is rendered, it must be accompanied by a clear, plain-language explanation of *why* the specific income pattern led to ineligibility, allowing the user to correct data errors before the final submission.

**4. Transparency Artifact (Model Card)**
Create a versioned document for internal and government stakeholders containing:
*   **Intended Use:** Verification for gig workers with non-standard income.
*   **Known Limitations:** Explicitly list income patterns the model struggles with (e.g., "cash tips," "crypto payments," "long gaps between contracts").
*   **Measured Performance:** Report the False Rejection Rate *by subgroup* (e.g., "drivers vs. delivery vs. task-based"), not just an aggregate accuracy number.
*   **Owner:** Name the specific engineer responsible for monitoring these metrics post-launch.

**5. Governance & Legal Routing**
*   **Regulatory Duty:** Because this system makes consequential decisions affecting financial eligibility, it likely falls under regulated automated decision-making frameworks (e.g., EU AI Act, local labor laws). **Route immediately to legal counsel** to determine if a "right to explanation" or mandatory human appeal channel is legally required, regardless of your current API contract constraints.
*   **No Certification:** This plan identifies risks and measures them; it does not certify the system as "fair" or "unbiased." The decision to ship rests with the product owner based on the residual risk reported.

**Note:** If the government API strictly forbids *any* delay or pre-check, you cannot safely launch without negotiating a "pending" status or an appeals interface outside the immediate decision loop.
**Note:** Never invent a "0% error rate"; report unmeasured scenarios as UNVERIFIED.
