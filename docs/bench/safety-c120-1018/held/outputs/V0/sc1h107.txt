### Pre-Launch Safety Audit Strategy

**1. Harm Inventory & Targeted Testing**
Before launch, explicitly record the primary harm: **false-positive revocations** causing financial loss and reputational damage to legitimate fishermen. Given your server budget constraints, do not attempt to reprocess all historical data. Instead, execute a **targeted adversarial eval**:
*   **Probe Set:** Curate a small, high-value dataset containing only the "similar-looking species" pairs known to cause errors (e.g., protected vs. non-protected lookalikes).
*   **Controls:** Include known "bad" inputs (clear protected species) and known "good" inputs (clear non-protected species) to verify the model hasn't broken basic recognition while tuning for edge cases.
*   **Metric & Threshold:** Measure the false-positive rate specifically on the lookalike subset. Set a **zero-tolerance stop condition** for automatic revocation on these ambiguous cases. If the model cannot distinguish them with near-perfect certainty, it must not trigger an auto-revocation.
*   **Reporting:** Report the residual risk as **UNVERIFIED** for any species pair not included in this specific test set. Do not invent a global "accuracy rate" based on limited data.

**2. Human-in-the-Loop Gate (The Floor)**
Because permit revocation is a **high-stakes, irreversible action** with immediate economic consequences, fully automated execution is unsafe.
*   **Confidence Tiers:** Do not display raw confidence percentages (e.g., "87% sure") to users or internal staff, as this implies false precision. Instead, define coarse tiers:
    *   **Confirmed:** High certainty, distinct features.
    *   **Unverified/Ambiguous:** Low certainty, similar features detected.
*   **Workflow Change:** Configure the system so that **only** "Confirmed" cases proceed to automatic revocation. Any detection falling into the "Unverified" tier (including all lookalike scenarios) must be routed to a **human reviewer** for manual validation before any penalty is issued. This satisfies the requirement for a human gate on high-stakes actions.

**3. Dispute Resolution & Transparency**
*   **Disclosure:** Clearly inform fishermen that an AI system assisted in the scan, but that a human reviews ambiguous cases.
*   **Appeals Process:** Establish a fast-track appeals workflow for disputed revocations. Since the system admits uncertainty via the "Unverified" tier, users flagged in this category should have a simplified path to submit counter-evidence (e.g., higher resolution photos) for immediate human re-evaluation.
*   **Documentation:** Create a simple **Model Card** for internal and regulatory use. It must state the intended use (Oslo fishing license validation), list the known limitations (specific lookalike species), and document the human-review gate for ambiguous detections. Absence of this card is a transparency failure.

**4. Governance**
Assign a specific owner responsible for reviewing the error logs post-launch. If the model or the list of protected species changes, the harm inventory and targeted tests must be re-run.

***

**Note:** Legal requirements for automated administrative decisions in Norway/EU (such as specific disclosure mandates) must be verified by counsel; this plan recommends disclosure as a safety control but does not assert legal duty.
**Note:** Do not claim the system is "bias-free" or "safe"; the audit measures residual risk and manages it via human oversight.
