### Validation Workflow: Common Name & False Positive Mitigation

**1. Pre-Processing Harm Inventory**
Before processing any real data, document the specific risk: "False Positive Match."
*   **Affected Party:** Eligible volunteers wrongly flagged as having a criminal record.
*   **Worst Case:** A qualified volunteer is rejected, the nonprofit loses critical staffing, and the individual suffers reputational harm.
*   **Constraint Acknowledgement:** Explicitly record that without unique identifiers (e.g., SIN, specific ID numbers), the system cannot achieve 100% certainty. The output must be treated as a "potential match requiring review," not a "confirmed hit."

**2. Synthetic "Common Name" Stress Test (The Measure)**
Do not wait for real volunteers to find errors. Create a synthetic test set immediately:
*   **Positive Controls (Known Matches):** Create 10 fake profiles where the Name + Birth Date exactly matches a known public record entry you have manually verified. The system *must* flag these.
*   **Negative Controls (Known Non-Matches):** Create 20 fake profiles using very common names (e.g., "John Smith," "Maria Garcia") paired with birth dates that *do not* match the specific record entry for those names in your source data.
    *   *Crucial Step:* Include variations in spelling and formatting (e.g., "J. Smith" vs. "John Smith").
*   **The Metric:** The system must have a **0% false positive rate** on the Negative Controls before touching real data. If "John Smith (DOB: 01/01/1990)" is flagged when the record belongs to "John Smith (DOB: 01/02/1990)," the matching logic is too loose.

**3. The Human-in-the-Loop Gate (The Manage)**
Given the high stakes (rejecting a person) and low confidence (name/DOB only), **fully automated rejection is prohibited.**
*   **Tiered Output:** The system must not output "Clear" or "Fail." It must output:
    *   *Green:* No match found.
    *   *Amber:* Potential match detected (Name matches, DOB matches exactly). **Action:** Requires manual review by two team members.
    *   *Red:* Exact match on Name + DOB + additional context (if available). **Action:** Requires manual review + secondary source verification.
*   **Uncertainty Disclosure:** Any "Amber" or "Red" result presented to the final decision-maker must include a visible warning: "Match based on Name and DOB only. Identity not uniquely verified. Risk of false positive exists."

**4. Operational "Stop Condition"**
Define a hard stop for the pilot:
*   If the synthetic test set yields even **one** false positive (flagging a known innocent profile), the matching algorithm must be tightened or the manual review threshold lowered before processing real volunteers.
*   Do not process the first batch of real volunteers until the synthetic test passes 100%.

**5. Transparency Artifact (Model Card Lite)**
Create a one-page document for your team and the nonprofit leadership stating:
*   **Intended Use:** Preliminary screening only.
*   **Limitations:** High risk of false positives for common names; cannot distinguish between individuals with identical names and birth dates.
*   **Verification Method:** All potential matches require manual adjudication; no candidate is rejected by the algorithm alone.

**Note:** This workflow treats the algorithm as a suggestion engine, not a decision maker, which is the only safe approach given your data constraints. Ensure your legal counsel reviews the "potential match" language to ensure it meets Ontario privacy and human rights standards before deployment.
