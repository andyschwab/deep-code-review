### Pre-Launch Safety Strategy: Scammer Exclusion & Match Quality

**1. Harm Inventory (MAP)**
Before testing, explicitly record the primary harm: **Unsafe Automation of High-Stakes Actions**. The system is currently recommending known scammers to vulnerable users, creating a direct risk of financial fraud and emotional damage. The "worst realistic case" is a user losing significant funds or suffering severe psychological trauma due to a match the platform knowingly facilitated. Secondary harms include **Bias/Unfair Outcomes** if the "scammer" flags disproportionately affect specific demographics due to erroneous reporting.

**2. Measurement Plan (MEASURE)**
Since you cannot yet rebuild the index to exclude these users, you must prove the filter works via output testing before launch. Do not assert safety; measure it.

*   **Construct a "Known-Bad" Probe Set:** Extract a list of user IDs explicitly flagged as scammers in your community reports. This is your **positive control**.
*   **Construct a "Known-Good" Probe Set:** Select verified, long-standing users with no reports. This is your **negative control**.
*   **The Runnable Test:** Run your current matching algorithm against both sets using your existing tools.
    *   *Metric:* The percentage of "Known-Bad" profiles appearing in the top-N recommendations for any test user.
    *   *Threshold:* **Zero tolerance.** If *any* known scammer appears in a recommendation list during this test, the stop condition is met: **do not launch.**
    *   *Injection Check:* Simulate inputs where a scammer profile attempts to hide behind common keywords to ensure the flag holds.
*   **Report Residual Risk:** If the legacy database prevents 100% exclusion in the test, report the failure rate as `UNVERIFIED` or "Failed Safety Gate." Do not invent a "low risk" percentage.

**3. Risk Management (MANAGE)**
*   **Human-in-the-Loop Gate:** Because the automated filter is technically constrained, you must install a human gate before any match is shown to a user. Until the index is rebuilt, **no match involving a user with any community report flag should be served automatically.** Route these specific potential matches to a human reviewer for manual clearance.
*   **Uncertainty & Disclosure:** If you cannot guarantee exclusion, do not present matches as "Verified Safe." Consider adding a disclaimer that users should exercise caution, though the primary control is the human gate.
*   **Confidence Tiers:** Do not show users a "99% match" score if the underlying data is contaminated. Use coarse tiers (e.g., "Potential Match") until the data integrity is resolved.

**4. Governance (GOVERN)**
*   **Owner:** Assign one data scientist as the explicit owner of this safety failure. They are responsible for the "stop launch" decision if the probe set fails.
*   **Re-review Trigger:** Any change to the reporting logic or the matching weights requires re-running the "Known-Bad" probe set.

**Deliverable Checklist for Launch Readiness:**
1.  [ ] Documented harm inventory citing fraud risk.
2.  [ ] Completed "Known-Bad" vs. "Known-Good" test run with results logged.
3.  [ ] Confirmation that **zero** known scammers appeared in test outputs.
4.  [ ] Active human-review workflow for any profile with a report flag.
5.  [ ] Signed decision by the product owner accepting residual risk or delaying launch.

**Note:** This strategy treats the presence of *any* known scammer in results as a critical failure, not an acceptable error rate.
**Note:** Legal counsel should be consulted regarding disclosure duties if fraud occurs despite these measures.
