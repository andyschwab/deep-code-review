### Fairness Audit and Mitigation Workflow for Automated Valuation Model

**1. Harm Inventory & Scope Definition**
Before testing, formally record the specific risk: **Bias/Unfair Outcomes** where historical discriminatory lending data causes systematic undervaluation in minority communities, leading to financial harm for sellers in protected classes. Acknowledge that an "empty inventory" is not a pass; this specific risk must be tracked from design through launch.

**2. Measurement Strategy: Output-Focused Evaluation**
Do not test only the code; test the outputs against real-world scenarios. Construct an evaluation set with the following components:
*   **Probe Set:** Create synthetic property profiles that are identical in physical characteristics (square footage, age, condition) and neighborhood amenities, varying only by the demographic composition of the block or census tract (using proxy variables if direct demographic data is restricted).
*   **Controls:** Include "known-good" cases (properties in diverse areas with verified fair market values) and "known-bad" positive controls (historical examples of undervaluation) to validate the test's sensitivity.
*   **Metric & Threshold:** Define a disparate impact ratio (e.g., valuation in Group A vs. Group B). Set a strict stop condition: if the valuation gap exceeds a pre-defined tolerance (e.g., 5%) for any protected segment, the launch is blocked. Do not invent a "safe" rate; the threshold must be set by product owners based on risk appetite, with zero tolerance for irreversible financial harm without a human gate.
*   **Adversarial Testing:** Run red-team probes to check if the model amplifies biases when presented with edge-case neighborhood descriptors or mixed-demographic boundaries.

**3. Management & Human-in-the-Loop Gate**
*   **High-Stakes Gate:** Since an automated valuation directly influences a homeowner's financial outcome and is hard to reverse once a listing is priced too low, you must implement a **human-in-the-loop gate** for any valuation that falls into a "low confidence" tier or triggers a bias flag. Do not allow fully autonomous execution for these high-stakes decisions.
*   **Uncertainty Disclosure:** Do not display a precise percentage (e.g., "98% accurate") which implies false precision. Instead, show a defined coarse tier (e.g., "Corroborated by recent sales" vs. "Single-source estimate") and provide an easy override mechanism for users to request a human review.
*   **Recalibration Workflow:** If bias is detected:
    1.  **Halt:** Trigger the stop condition immediately; do not launch.
    2.  **Isolate:** Identify which historical features are driving the disparity.
    3.  **Adjust:** Retrain with re-weighted data or remove proxy variables that correlate too strongly with protected classes.
    4.  **Re-test:** Run the full probe set again. Only proceed when the disparate impact ratio meets the threshold.

**4. Transparency Artifact (Model Card)**
Ship a **Model Card** with the feature. This document must state the intended use, the data provenance (acknowledging the historical lending data limitation), the measured performance **by subgroup** (not just aggregate), and the known limitations. If a metric was not measured, label it `UNVERIFIED`—never fabricate a clearance number.

**5. Governance & Legal Routing**
Name a specific owner responsible for this output harm. Because this involves potential fair housing violations and automated decisions with financial consequences, **route the question of legal disclosure requirements and regulatory compliance (e.g., fair housing laws) to legal counsel immediately.** Do not assert whether you are legally required to disclose the AI nature of the tool; let counsel determine the duty.

**Note:** This plan measures residual risk; it does not certify the model as "unbiased" or "safe." The decision to ship rests with the product owner after reviewing the evidence.
Ensure the Model Card is versioned and updated if the data or model changes post-launch.
