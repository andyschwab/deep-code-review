### 1. Harm Inventory (MAP)
Before testing, we define the specific risks to families in Cairo:
*   **Unsafe Automation:** The algorithm prioritizes energy savings over health, causing overheating (>30°C) or freezing (<16°C) conditions.
*   **Vulnerable Populations:** Infants and the elderly suffer heatstroke or hypothermia due to narrow safe temperature margins.
*   **Over-reliance:** Users trust the "smart" setting and ignore manual overrides until it is too late.
*   **Edge Case Failure:** Extreme weather spikes or unusual usage patterns (e.g., a family gathering) confuse the model, triggering dangerous shifts.

### 2. Measurement Plan (MEASURE)
You must run adversarial tests against the algorithm before shipment. Do not just test "normal" usage.
*   **Probe Set A (Extreme Weather):** Simulate Cairo heatwaves (+45°C) and rare cold snaps. Inject sensor noise to mimic faulty hardware.
    *   *Metric:* Does the thermostat ever command a temperature outside the 18°C–28°C safe band?
    *   *Stop Condition:* **Any** instance of commanding <16°C or >30°C blocks launch.
*   **Probe Set B (Unusual Usage):** Simulate zero occupancy for 48 hours followed by sudden full occupancy; simulate windows left open while AC runs.
    *   *Metric:* Time-to-recovery to safe zone.
    *   *Stop Condition:* Recovery time >30 minutes blocks launch.
*   **Probe Set C (Adversarial Inputs):** Feed impossible weather forecasts or corrupted user behavior logs.
    *   *Metric:* System stability and fallback behavior.
    *   *Stop Condition:* System crash or unbounded temperature adjustment blocks launch.

**Reporting:** Report residual risk as "UNVERIFIED" for any scenario not explicitly tested. Do not invent a "99.9% safe" metric.

### 3. Management & Fail-Safes (MANAGE)
Since you cannot update firmware, you must hard-code strict boundaries:
*   **Hard Limits (The Floor):** Implement absolute min/max temperature clamps in the firmware (e.g., never below 18°C, never above 28°C) that the AI logic **cannot** override. This is your primary human-in-the-loop proxy.
*   **Uncertainty Handling:** If the weather forecast confidence is low or sensor data conflicts, the system must revert to a conservative "safe default" mode, not guess.
*   **Manual Override:** Ensure a physical or app-based override is always available and clearly visible, preventing "automation bias."
*   **Disclosure:** Clearly inform users that the device is automated and provide instructions on how to disable it immediately.

*   **Transparency Artifact:** Create a "Model Card" for this feature documenting the intended use (energy saving within safe bounds), the tested edge cases, and the known limitations (e.g., "fails safe if sensor data is lost"). Ship this with the device documentation.
