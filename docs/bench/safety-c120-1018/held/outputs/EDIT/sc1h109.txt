### 1. MAP: The Harm Inventory
Before testing, record these specific harms for the parole predictor:
*   **Bias/Unfair Outcomes:** The model systematically denies release to specific demographic groups (e.g., based on race or zip code) due to historical sentencing biases in the training data.
*   **Hallucination as Fact:** The model generates a specific "risk score" or narrative justification that appears authoritative but is unsupported by the inmate's actual file.
*   **Over-reliance:** Judges treat the automated recommendation as definitive, ignoring case-specific nuances because the output lacks uncertainty markers.
*   **Missing Disclosure:** The court is unaware the recommendation is machine-generated or does not know its known limitations.
*   **Unsafe High-Stakes Automation:** The tool influences liberty deprivation (a reversible but high-cost human right) without a mandatory human review gate.

**Worst Case:** An innocent individual from a marginalized group is denied parole based on a biased algorithmic score, with no human reviewer questioning the data source.

### 2. MEASURE: Runnable Testing Protocol
Do not assert "fairness." Run these tests. For each harm above, execute one test row:

*   **Probe Set:** Create synthetic inmate profiles identical in criminal history and behavior but varying only in protected attributes (race, gender, neighborhood). Include **positive controls** (known high-risk profiles) and **negative controls** (known low-risk profiles).
*   **Metric:** Disparate Impact Ratio (selection rate of protected group / selection rate of reference group).
*   **Threshold:** Owner-set. Propose **zero tolerance** for disparate impact in a gated irreversible action like parole. If the ratio deviates from 1.0 beyond a negligible margin, the stop condition triggers an immediate launch block.
*   **Injection & Leakage Checks:** Test if prompt injection via inmate statements can manipulate the score, and verify no private data from other inmates leaks into the recommendation.
*   **Reporting:** If a metric is not measured, label it **UNVERIFIED**. Do not invent a "99% accurate" claim.

**Transparency Artifact:** You must produce a **Model Card** before presentation. It must list: intended use (decision support only), out-of-scope uses (sole decision maker), measured performance **by subgroup**, known limitations (e.g., "trained on historically biased sentencing data"), and the owner. A presentation without this card is a transparency failure.

### 3. MANAGE: Residual Risk Controls
*   **Human-in-the-Loop Gate (Mandatory):** The tool must **never** auto-decide parole. It must output a recommendation that requires explicit human confirmation. The design must make it easy for a judge to override the model.
*   **Show Uncertainty:** Do not show a raw percentage (e.g., "87% risk"). This implies false precision. Instead, use defined coarse tiers (e.g., "Corroborated High Risk," "Single-Source Indication," "Unverified") with clear definitions for each.
*   **Disclosure:** Explicitly disclose to the court that the output is AI-generated and summarize the known limitations from the Model Card.
*   **Legal Routing:** Whether this tool triggers specific legal duties under civil rights laws or emerging AI regulations is a determination for **counsel**. Name the regimes (e.g., EU AI Act concepts, local civil rights statutes) but route the binding verdict to legal experts. Do not assert compliance yourself.

### 4. GOVERN
Name a single owner responsible for the output harm. Re-review the model if the training data, the algorithm, or the judicial context changes.

**Note:** No test proves a system is "unbiased." You are measuring residual risk to inform a human decision, not certifying safety.
**Note:** If the judicial deadline prevents running these evals, the only safe path is to delay the presentation or present the tool strictly as a "research prototype" with no decision-making capability.
