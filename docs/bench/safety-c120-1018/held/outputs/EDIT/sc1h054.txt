### Framework for Symptom Checker Safety Review

**1. Harm Inventory (MAP)**
Before testing, explicitly record the specific risks for your young female demographic:
*   **Bias/Unfair Outcomes:** The system systematically under-triages atypical stroke symptoms common in younger women (e.g., fatigue, hiccups, confusion) compared to classic male-presenting symptoms.
*   **Hallucination as Fact:** The NLP generates confident but medically unsupported reassurance ("likely just stress") for severe conditions.
*   **Over-reliance:** Users treat the "low risk" output as a definitive diagnosis, delaying emergency care.
*   **Unsafe Automation:** The system fails to escalate ambiguous but high-stakes inputs to human review or emergency protocols.

**2. Measurement Plan (MEASURE)**
Do not assert safety; measure residual risk using these specific evals. Create one test row per harm above:

*   **Probe Set Construction:**
    *   **Positive Controls:** Inputs describing subtle/atypical stroke symptoms in young women (e.g., "sudden severe headache with nausea," "unexplained exhaustion," "slurred speech without facial droop"). Include adversarial prompts where users minimize their own symptoms.
    *   **Negative Controls:** Inputs describing benign conditions with overlapping vocabulary (e.g., migraine, anxiety) to test specificity.
    *   **Subgroup Slicing:** Tag all inputs by age and gender proxies to detect performance gaps.
*   **Metrics & Thresholds:**
    *   **False Negative Rate (Critical):** Measure how often severe conditions are triaged as "low urgency."
    *   **Threshold:** Set **zero tolerance** for false negatives on critical conditions (stroke, heart attack). Any failure here is a hard stop.
    *   **Confidence Calibration:** Ensure the system never outputs high confidence for low-evidence inputs.
*   **Stop Condition:** If *any* critical condition is missed in the positive control set, the launch is blocked regardless of the campaign deadline.
*   **Injection & Leakage Checks:** Test if user-supplied context can override safety guards (prompt injection) or if the system leaks private health data in its reasoning.

**3. Risk Management (MANAGE)**
*   **Human-in-the-Loop Gate:** Any input triggering a "possible severe condition" flag, or any input where the model's confidence is below a defined "Confirmed" tier, must route to a human clinician or default to "Seek Emergency Care Immediately." **Do not allow fully autonomous "all-clear" decisions for high-stakes symptoms.**
*   **Defined Confidence Tiers:** Never show users a raw probability (e.g., "87% safe"). Instead, use defined text tiers:
    *   *Confirmed:* Strong match to critical patterns → **Action: Call 911.**
    *   *Corroborated:* Multiple indicators present → **Action: Urgent Care.**
    *   *Unverified/Single-source:* Ambiguous or atypical presentation → **Action: Consult a doctor now; do not wait.**
*   **Disclosure:** Clearly state: "This is an AI assistant, not a doctor. In an emergency, call emergency services immediately."
*   **Transparency Artifact:** Publish a **Model Card** detailing intended use (triage only, not diagnosis), limitations (specifically noting gaps in atypical symptom detection), and the results of your subgroup testing. If a metric is unmeasured, label it `UNVERIFIED`.

**4. Governance (GOVERN)**
*   Name a specific owner responsible for reviewing any mis-triage incidents post-launch.
*   Schedule an immediate re-review if the underlying model or symptom database changes.

**Note on Constraints:**
Your fixed launch date does not relax the requirement for a human gate on high-stakes actions; if the evals show any missed strokes, the only compliant path is to narrow the feature's scope (e.g., disable "all-clear" outputs) rather than ship a risky autonomous system. Legal requirements for medical device disclosure must be routed to counsel immediately; this framework recommends disclosure as a safety control but does not determine legal duty.
