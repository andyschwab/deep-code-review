### Risk Assessment and Human-Gate Plan for School-Bus Route Optimizer

**1. Harm Inventory: Outdated Map Data Risks**
Before deployment, we must explicitly name the failures caused by static data:
*   **Unsafe Automation:** The system assigns routes traversing unmarked construction zones, high-risk intersections, or temporary road closures, directly exposing children to traffic hazards.
*   **Over-Reliance:** Drivers or dispatchers may trust the "optimized" path without questioning it, assuming the algorithm accounts for all known risks.
*   **Missing Context:** The optimizer minimizes fuel/time but lacks the variable for "current safety," potentially routing buses through areas deemed unsafe by local authorities that day.

**2. Measurement Strategy: Adversarial Route Probing**
Do not assume the system is safe because the code works. You must test the outputs against known bad conditions.
*   **Probe Set:** Create a list of 10–20 known current hazards in Cairo (e.g., specific streets under construction this week, reported accident hotspots).
*   **Test Execution:** Run the optimizer with these locations in the map zone.
*   **Pass/Fail Criteria:** If the generator proposes a route through *any* of these known hazards without flagging them, the system **fails** the safety gate.
*   **Stop Condition:** If the failure rate is >0% for known high-severity hazards, do not automate assignment. The system must remain in "Draft Only" mode until the human gate proves effective.
*   **Residual Risk Statement:** Since real-time data is unavailable, the residual risk of encountering an *unknown* temporary hazard is **UNVERIFIED**. This cannot be calculated as a percentage; it must be managed via the human process below.

**3. Management Control: The Human-in-the-Loop Gate**
Because routing children is a high-stakes action with irreversible consequences if an accident occurs, **full autonomous assignment is prohibited.** You must implement a mandatory human review step every morning before routes reach drivers.

**Proposed Manual Cross-Reference Workflow:**
*   **Step A (Generation):** The system generates draft routes based on static data. Status: *Pending Review*.
*   **Step B (Intelligence Gathering):** An operations lead collects daily municipal reports, police traffic updates, and community alerts (e.g., WhatsApp groups for local schools) regarding road closures or dangers.
*   **Step C (The Gate):** The operations lead visually compares the draft routes against the daily hazard list.
    *   *Check:* Does any route intersect a reported hazard?
    *   *Action:* If yes, manually reroute that specific bus and mark the segment as "Avoid" in the system for the next run.
*   **Step D (Release):** Only after the lead signs off (digital checkbox or physical log) are routes sent to drivers.
*   **Uncertainty Display:** The driver's app/interface must display a warning: *"Route optimized for fuel/time based on static maps. Driver must exercise caution for unmarked temporary changes."* Do not show a false "100% Safe" score.

**4. Governance and Transparency**
*   **Owner:** Assign one specific person (e.g., Head of Operations) as the owner of the "Daily Safety Gate." This cannot be a shared abstract responsibility.
*   **Documentation:** Create a simple "Route Safety Card" for the school administration. It must state:
    *   *Intended Use:* Draft planning only; not for direct execution without review.
    *   *Limitations:* Relies on static open-source data; does not know real-time closures.
    *   *Known Gaps:* Temporary construction and emergency roadblocks.
*   **Re-review:** If the data source changes or the city expands significantly, repeat the harm inventory.

**Note:** This plan treats the optimizer as a decision-support tool, not an autonomous agent. The "human gate" is the primary safety control, not the algorithm.
**Note:** Legal requirements for automated decision-making involving minors vary by jurisdiction; consult local counsel to determine if additional disclosures to parents are legally mandated.
