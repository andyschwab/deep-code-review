# Pre-Launch Safety Review Plan: Smart Thermostat for Elderly Occupancy

**Objective:** Identify and mitigate failure modes where low-mobility patterns are misclassified as absence, leading to unsafe temperature drops, within a two-week timeline using only simulated data.

### 1. Define "Stillness vs. Absence" Failure Modes
Focus the simulation on specific edge cases where the algorithm is most likely to fail:
*   **The "Sleeping/Sedentary" False Negative:** Simulate 4–8 hour periods of zero motion during typical sleep or TV-watching hours. Verify the system maintains minimum safe temperatures (e.g., 18°C/64°F) rather than entering "Eco/Away" mode.
*   **Micro-Movement Scenarios:** Generate data with low-amplitude movements (e.g., reading, knitting, typing) that may fall below standard PIR sensor thresholds. Test if the algorithm aggregates these signals correctly over time.
*   **Bathroom/Bedroom Isolation:** Simulate occupancy confined to a single room with poor sensor coverage for extended periods (e.g., illness recovery). Ensure the system does not interpret lack of whole-house movement as vacancy.
*   **Power/Reboot Recovery:** Simulate a power outage followed by a reboot while the resident is motionless. Verify the default state is "Occupied/Safe" rather than "Away."

### 2. Simulation Protocol (Days 1–5)
Leverage existing simulation tools to create three distinct data profiles:
*   **Baseline Profile:** Normal elderly activity patterns (established from previous data).
*   **Low-Mobility Stress Profile:** Deliberately reduced movement frequency (50% and 25% of baseline) and amplitude. Include scenarios of sudden mobility reduction (simulating injury/illness).
*   **Adversarial Profile:** Intentional "trap" sequences designed to trigger the absence logic (e.g., 2 hours of stillness followed by a brief 30-second movement, then stillness).

**Success Criteria:** In all Low-Mobility and Adversarial profiles, the system must never drop below the defined safety floor temperature unless explicit user confirmation of "Away" status is received.

### 3. Algorithmic Safeguard Verification (Days 6–9)
Review the code logic against simulation results:
*   **Time-to-Away Threshold:** Confirm the time required to trigger "Away" mode is significantly longer than the maximum expected continuous stillness for a sedentary user (recommend >4 hours).
*   **Temperature Floor Hard-Stop:** Verify a hard-coded lower limit exists that cannot be overridden by the occupancy algorithm, regardless of confidence scores.
*   **Graceful Degradation:** If sensor data is ambiguous or missing, the system must default to "Occupied" logic.
*   **Rate-of-Change Limits:** Ensure the system cannot drop temperature faster than a safe ramp-down rate (e.g., 0.5°C per hour) to prevent rapid cooling even if a false positive occurs.

### 4. Human-in-the-Loop Validation (Days 10–12)
Since real-world testing is limited, use the engineering team as proxies:
*   **Blind Simulation Review:** Have two engineers not involved in the algorithm design review the simulation logs blindly. Ask them to identify where they would feel unsafe.
*   **Fail-Safe Trigger Test:** Manually inject "critical low temp" signals into the simulation to ensure any secondary emergency heating protocols or alert systems activate correctly.

### 5. Go/No-Go Decision Matrix (Days 13–14)
Establish clear launch criteria:
*   **Go:** Zero instances of temperature dropping below the safety floor in Low-Mobility profiles; hard-stop logic verified in code.
*   **No-Go:** Any instance where stillness >2 hours triggers Eco mode; inability to verify default-to-safe behavior on reboot.

**Immediate Action:** Freeze all non-safety feature updates. Dedicate 100% of remaining simulation compute resources to the "Low-Mobility Stress Profile" runs.

*Note: This plan assumes your simulation tool can inject custom motion amplitude data, not just binary motion/no-motion. If not, prioritize code review of the sensor signal processing layer immediately.*
