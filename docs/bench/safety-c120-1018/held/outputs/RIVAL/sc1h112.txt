**Pre-Launch Safety Checklist: Wildfire Evacuation Router**

**1. Data Integrity & Latency Validation**
*   **Stale Data Fail-Safe:** Verify the system defaults to "Stay Put" or "Known Safe Static Route" if live traffic/fire API responses exceed 30 seconds or return null. Do not route based on cached data older than 5 minutes during active fire conditions.
*   **Contradictory Source Handling:** Define explicit logic for when traffic data (open road) conflicts with fire perimeter data (active burn). The fire perimeter must always override traffic flow.
*   **Edge Case Simulation (Manual):** Since compute is limited, manually trace three specific scenarios on a map:
    *   *Sudden Wind Shift:* A route valid at T=0 becomes invalid at T=15 due to wind-driven fire spread. Ensure the system re-evaluates the route mid-trip, not just at departure.
    *   *Road Blockage:* Simulate a primary artery closure. Confirm the router does not direct users into dead-ends or require U-turns in high-density evacuation zones.
    *   *Capacity Overload:* Test behavior when 1,000+ concurrent requests hit the server. Ensure graceful degradation (queueing or static fallback) rather than total crash.

**2. Logic & Boundary Constraints**
*   **Safe Zone Verification:** Hard-code a whitelist of verified safe zones. The system must never generate a route ending outside this list, regardless of algorithmic optimization.
*   **Hazard Proximity Buffer:** Enforce a minimum dynamic buffer (e.g., 5 miles) between the calculated route and the active fire perimeter. If no route exists outside this buffer, the output must be "Shelter in Place" with location-specific instructions, not a dangerous path.
*   **Clarity of Instruction:** Ensure outputs are binary and unambiguous (e.g., "Drive North on Hwy 101") rather than probabilistic (e.g., "Route A is 80% safer").

**3. Human-in-the-Loop Protocols**
*   **Manual Override Switch:** Establish a physical or digital "kill switch" accessible to the 8-person team to instantly freeze all routing advice and broadcast a static emergency message if systemic failure is detected.
*   **Pre-Launch Peer Review:** Have two team members independently trace the same 10 high-risk addresses. If routes differ, halt launch until the deterministic logic is fixed.

**Deployment Monitoring Plan (First Hour)**

**1. Real-Time Decision Logging**
*   Log every route request with: Timestamp, User Location, Destination, Fire Data Version Used, Traffic Data Version Used, and Final Route Provided.
*   Set up an automated alert if any generated route passes within the defined hazard buffer of the active fire perimeter.

**2. Anomaly Detection Thresholds**
*   **Volume Spike:** Alert if request volume drops suddenly (indicating potential service outage) or spikes beyond capacity.
*   **Uniformity Check:** If >90% of users in a specific geographic zone are routed to the same single road, trigger a manual review for potential bottleneck creation.
*   **Error Rate:** Immediate escalation if the error rate exceeds 1%.

**3. Active Feedback Channel**
*   Embed a "Report Dangerous Direction" button in the user interface.
*   Assign two team members solely to monitor this channel and social media mentions for the first 60 minutes. Any single report of a route leading toward fire triggers an immediate manual audit of that specific geofence.

**4. Rollback Criteria**
*   Pre-define the threshold for aborting the launch (e.g., 3 confirmed misdirections or 5 minutes of data latency). If triggered, revert immediately to a static, pre-published PDF map distributed via emergency alerts.

*Note: Given the three-day window, prioritize manual tracing of high-risk zones over complex automated simulations. Ensure all team members have direct access to the kill switch.*
