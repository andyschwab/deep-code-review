# Allergy Restriction Verification Checklist for EduFood Services

## 1. Data Ingestion & Mapping Validation
*   **Format Stress Test:** Upload allergy lists in every supported format (CSV, JSON, manual entry) containing edge cases: empty fields, special characters in allergen names (e.g., "Peanut (Arachis)"), and duplicate entries for the same student.
*   **Synonym Matching:** Verify the system recognizes common synonyms and scientific names. Test inputs like "milk" vs. "casein," "peanut" vs. "arachis hypogaea," and "gluten" vs. "wheat protein."
*   **Severity Levels:** If your system tracks severity, confirm that "life-threatening" flags trigger stricter filtering than "preference" flags. If no severity levels exist, ensure *all* listed allergens are treated as absolute hard stops.
*   **Student ID Integrity:** Upload a list where student IDs are missing, duplicated, or mismatched with names. Ensure the system rejects the file or flags errors rather than assigning allergies to the wrong child or skipping the record.

## 2. Menu Generation Logic (The "Hard Stop" Test)
*   **Direct Contamination:** Generate a menu for a student with a specific allergy (e.g., shellfish). Manually inspect 50+ generated meals to confirm zero instances of the allergen appear in the main dish, side, or garnish.
*   **Cross-Contact Scenarios:** Test meals where the allergen isn't an ingredient but a risk (e.g., "fried in shared oil" or "processed in a facility with nuts"). If your inventory data includes these warnings, verify the planner excludes these items for sensitive profiles.
*   **Ingredient Decomposition:** Input complex recipes (e.g., "Caesar Dressing") where the allergen is a sub-component (e.g., "anchovies" or "wheat-based soy sauce"). Confirm the system breaks down composite ingredients before checking against allergy lists.
*   **The "Safe Default" Check:** Simulate a system error where an allergy file fails to load for a specific student. Verify the system defaults to the most restrictive menu (allergen-free) or halts generation entirely, rather than serving a standard menu.

## 3. Edge Case & Boundary Simulation
*   **Multiple Allergies:** Create profiles for students with 5+ simultaneous severe allergies. Ensure the generator can still construct a nutritionally viable menu without accidentally slipping in a forbidden item due to logic overload.
*   **Last-Minute Changes:** Simulate updating a student's allergy status *after* a menu has been generated but *before* final approval. Verify the system forces a re-scan of existing plans and flags conflicts immediately.
*   **Inventory Substitution:** Force a scenario where the primary safe ingredient is out of stock. Check if the automated substitution engine suggests an alternative that contains the student's allergen.
*   **Batch Consistency:** Run the generator for a hypothetical district of 5,000 students with randomized allergy profiles. Spot-check 100 random students to ensure the restriction logic holds at scale and doesn't degrade under load.

## 4. Output & Human Review Safeguards
*   **Allergen Highlighting:** Ensure the final printed/digital menu explicitly highlights potential allergens for every dish, even if the system claims it's "safe," to aid human verification.
*   **Conflict Reporting:** Verify that if *no* safe meal can be generated for a specific day due to inventory constraints, the system throws a critical alert rather than outputting a risky default.
*   **Audit Trail:** Confirm the system logs *why* a meal was selected and *which* allergy rules were applied, creating a traceable path for every decision.

## 5. Manual "Red Team" Exercise
*   **The "Trick" Input:** Have a team member try to bypass filters by entering allergens with typos, extra spaces, or in all-caps to see if the matcher fails.
*   **Recipe Loophole Search:** Review the recipe database for items labeled "vegetarian" or "vegan" that might still contain hidden allergens (like dairy in a "creamy" soup) and ensure the planner catches them.

**Immediate Action:** Before Monday, run the "Hard Stop" and "Safe Default" tests manually on your pilot data; these represent the highest risk to student safety.
**Note:** Since you cannot audit code, treat any untested edge case as a potential failure point and require human sign-off on all generated menus for the first month.
