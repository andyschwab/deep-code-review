### Synthetic Concurrency Test Design

To expose the race condition without revealing proprietary traffic patterns, you must isolate the **concurrency primitive** (the simultaneous write) from the **load profile** (the Black Friday volume). The bug exists because the locking mechanism fails under contention, not because of the specific data shape or network topology.

Replace your massive stress test with a focused unit test using Go's `testing` package and the `-race` detector. This test artificially creates high contention on a single key using many goroutines, which mathematically guarantees the race condition if the lock is flawed, regardless of total throughput.

**1. The Synthetic Test (`cache_test.go`)**

```go
func TestConcurrentWriteRace(t *testing.T) {
    // Initialize a fresh client instance
    c := NewClient()
    key := "contention-key"
    iterations := 1000
    goroutines := 50 // High contention on a single resource

    var wg sync.WaitGroup
    wg.Add(goroutines)

    // Launch concurrent writers
    for i := 0; i < goroutines; i++ {
        go func(id int) {
            defer wg.Done()
            for j := 0; j < iterations; j++ {
                // Attempt to update the same key simultaneously
                // If the lock fails, data inconsistency occurs here
                err := c.Set(key, fmt.Sprintf("value-%d-%d", id, j))
                if err != nil {
                    t.Errorf("Set failed: %v", err)
                }
            }
        }(i)
    }

    wg.Wait()

    // Optional: Verify final state consistency if your logic dictates a specific outcome

}
```
