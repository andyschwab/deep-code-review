You cannot upstream a fix that relies on your private CA certificates, nor can you generalize a solution that only works because of your specific internal infrastructure. The maintainers' stance is correct: open-source libraries must not contain logic that implicitly or explicitly favors a single organization's private security assets.

However, you **can** contribute a generalizable improvement: **enhancing the configurability of the trust store injection mechanism**. If the current library makes it difficult for *any* user (not just you) to inject a custom root CA or intermediate chain at runtime without code changes, that is a legitimate upstream defect. The fix is not "add Omni Consumer Products certs"; the fix is "make the API ergonomic and secure for injecting arbitrary custom trust anchors."

### Direct Answer to Your Uncertainty
The standard pattern is **Configuration, not Code**. Do not try to make the library "know" about your CA. Instead, make the library *easier to configure* with any CA. Your contribution is the improved API/ergonomics, not the certificate data. Users (including your team) will supply the actual cert bytes via environment variables or config files at runtime, keeping them out of the source tree entirely.

### Fallback
If maintainers reject the API change as "out of scope," do not argue. Instead, publish a blog post or gist titled "How to use [Library Name] with Private PKI" containing the boilerplate code your team uses. This shares the lesson without requiring an upstream merge.
