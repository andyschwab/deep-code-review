Open a feature request (issue) first; do not submit the code as-is.

Your implementation relies on undocumented internal APIs that the maintainers explicitly reserve the right to change. Submitting a PR dependent on these endpoints violates the project's stability guarantees and will likely be rejected immediately. Furthermore, because your current solution cannot function without access to non-public data, the core problem is not the plugin hook itself, but the lack of a stable interface to provide the necessary build context.

The correct approach is to propose an extension to the public API. Draft an issue that:
1.  **Describes the Use Case:** Explain the need to inject custom analytics with build-specific metadata (e.g., build ID, timestamp, environment) without revealing your company's proprietary logic.
2.  **Identifies the Gap:** State clearly that current public interfaces do not expose this context, forcing reliance on unstable internal endpoints.
3.  **Proposes a Solution:** Suggest a specific, stable mechanism (e.g., a new public interface `BuildMetadataProvider` or a structured context object passed to plugins) that would solve this for you and potentially other users.
4.  **Offers Collaboration:** Mention that you have a working prototype using internal calls that validates the feasibility, and you are eager to refactor it against a public API once defined.

This approach respects the maintainers' architecture, invites design discussion, and creates a path for your contribution to be accepted once the public interface is established.

Note: Never include code snippets referencing internal endpoints in the public issue; describe only the data requirements. If the maintainers agree to the API change, you can then refactor your local code to use the new public interface before submitting a PR.
