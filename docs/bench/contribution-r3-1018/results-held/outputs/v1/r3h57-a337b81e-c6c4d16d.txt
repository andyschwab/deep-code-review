**Discussion Post Draft: Proposal to Address Leap Second Handling in CoreUtils Date Formatting**

**Subject:** [Discussion] Handling Leap Seconds in `formatDate`: Breaking Change vs. Workaround

Hi CoreUtils Maintainers,

I am writing to propose a discussion regarding a limitation in the current `formatDate` function: its inability to correctly handle leap seconds. This edge case causes timestamp mismatches in high-precision domains, particularly financial applications where sub-second accuracy during leap events is critical.

**The Problem**
The current implementation assumes a standard 60-second minute. During a leap second event, this leads to a one-second drift in calculated timestamps. While rare, this drift violates correctness guarantees required by downstream users in regulated industries.

**Proposed Solution**
I have explored two paths:
1.  **Non-Breaking Workaround:** Injecting logic to detect and adjust for leap seconds internally. This approach requires maintaining an external lookup table within the library and adds significant complexity to the parsing logic, potentially impacting performance and maintainability without fully resolving the semantic ambiguity.
2.  **Configuration Object (Breaking Change):** Modifying the function signature to accept an optional configuration object (e.g., `formatDate(date, { handleLeapSeconds: true })`). This allows explicit opt-in behavior, keeping the default path fast and unchanged for existing users while providing a clean, correct mechanism for those who need it.

**Why This Matters**
While I understand the project's preference for small, incremental patches and the hesitation toward breaking changes, the "workaround" approach introduces technical debt and hidden complexity that contradicts CoreUtils' reputation for reliability. A clean, explicit API ensures that:
*   Correctness is guaranteed for users who need it.
*   Existing users remain unaffected unless they explicitly opt in.
*   The codebase remains maintainable without fragile heuristics.

**Next Steps**
Before drafting any code or formal RFC, I wanted to gauge the community's interest in this direction. Would the maintainers be open to discussing a major version strategy that includes this fix, or is there a preferred alternative pattern for handling such edge cases without altering the signature?

I am happy to provide benchmarks, proof-of-concept snippets, or a detailed migration guide if there is interest in exploring the configuration-based approach.

Looking forward to your thoughts.

---

*Note: This draft frames the breaking change as an opt-in enhancement to mitigate backlash, directly addressing the maintainers' historical preferences while highlighting the risk of the alternative.*
*Do not submit code until maintainers respond; this post is designed to test the waters for a major version discussion.*
