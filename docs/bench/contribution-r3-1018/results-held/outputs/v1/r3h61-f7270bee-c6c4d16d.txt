### Refactored Design Overview: Generic Plugin System

**Core Concept**
The proposed plugin system introduces a standardized extension interface that allows third-party developers to hook into the editor's lifecycle events (e.g., `onLoad`, `onSave`, `onRender`) without modifying the core codebase. Instead of coupling with specific external services, the system defines a generic "Resource Provider" abstraction. This abstraction allows plugins to fetch, parse, and store data from *any* source defined by the user at runtime, rather than hardcoding connections to specific internal infrastructure.

**Architecture Changes**
1.  **Event Bus:** A central pub/sub mechanism within the editor core where plugins can subscribe to document state changes.
2.  **Generic Adapter Interface:** A new TypeScript/JavaScript interface `IExternalAdapter` requiring methods like `fetchResource(id: string)` and `pushResource(data: object)`. The core editor provides no implementations; plugins supply them.
3.  **Configuration Schema:** A JSON-based manifest where users map specific file types or actions to installed plugins, ensuring the core remains agnostic of the data's origin.

**Example Usage (Generic)**
*Before:* A plugin explicitly calls `acmeCms.fetchDocument(id)`.
*After:* A plugin implements `IExternalAdapter`. The user configures the adapter in `settings.json`:
```json
{
  "adapter": "custom-cms-connector",
  "endpoint": "https://user-defined-url.com/api",
  "authMethod": "bearer-token"
}
```
The editor simply invokes `adapter.fetchResource(id)`, unaware of whether the backend is a proprietary CMS, a local file server, or a public cloud service.
