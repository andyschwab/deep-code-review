**Proposed Issue Title:**
RFC: Renaming `RiskCalcV1` to `ModernRiskEngine` – Exploring Deprecation Strategy and Community Impact

**Issue Body:**

### Summary
The current class name `RiskCalcV1` no longer accurately reflects the extensive capabilities of the component, which has evolved into a comprehensive solution for modern risk metrics. This proposal suggests renaming the class to `ModernRiskEngine` to improve code readability and semantic clarity for new users.

### Problem Statement
While the functionality has grown, the legacy name `RiskCalcV1` implies a limited, version-specific calculator rather than the robust engine it currently is. This mismatch causes confusion during onboarding and leads to misuse in complex integration scenarios. However, we recognize that this class is heavily relied upon in production environments across the ecosystem.

### Proposed Solution
We propose introducing `ModernRiskEngine` as the primary class name while maintaining `RiskCalcV1` as a deprecated alias. The transition would follow a structured deprecation cycle:
1.  **Introduction:** Add `ModernRiskEngine` as the canonical class.
2.  **Alias & Warning:** Keep `RiskCalcV1` functional but issue a clear deprecation warning in logs/documentation, pointing users to the new name.
3.  **Sunset (Future):** After a defined period (e.g., 2 major releases), consider removing the alias, contingent on community adoption metrics.

### Risks and Mitigation
*   **Breaking Changes:** A direct rename would break existing implementations. *Mitigation:* The alias approach ensures zero immediate breakage.
*   **Migration Overhead:** Large organizations may face challenges updating internal codebases. *Mitigation:* A long deprecation window and automated refactoring tools (if feasible) would be provided.
*   **Fragmentation:** Temporary coexistence of two names might confuse documentation. *Mitigation:* Documentation will immediately prioritize the new name while clearly marking the legacy alias.

### Request for Feedback
Before drafting any implementation, we seek community input on:
1.  Is the confusion caused by the current name significant enough to warrant this change?
2.  What is an acceptable deprecation timeline for your organization?
3.  Are there specific technical hurdles in your stack that an alias strategy would not resolve?

This is currently an exploratory discussion to gauge interest and identify potential pitfalls. No code changes are proposed at this stage.
