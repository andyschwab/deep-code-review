**Title:** Feature: Configurable health check intervals based on latency zones

**Problem**
Current health check logic assumes uniform network conditions across all backend targets. In heterogeneous environments (e.g., hybrid cloud, edge deployments, or clusters spanning distinct availability zones with variable routing), a single global health check interval is suboptimal.
- **Too aggressive:** Causes false positives in high-latency zones, triggering unnecessary failovers.
- **Too conservative:** Delays detection of actual failures in low-latency zones, increasing error rates for end users.

**Proposed Change**
Introduce a configuration option to define health check intervals mapped to logical latency zones or geographic proximity groups.
- Allow users to group backends by expected latency profile.
- Enable per-group interval configuration (e.g., `interval_ms: 500` for local, `interval_ms: 2000` for remote).

**General Utility**
This addresses a broader class of deployment scenarios beyond uniform data centers:
1.  **Edge Computing:** Nodes at the edge often have higher, more variable latency to the control plane than core nodes.
2.  **Multi-Cloud/Hybrid:** Inter-provider links often exhibit higher jitter than intra-datacenter links.
3.  **Legacy Integration:** Environments integrating modern microservices with older infrastructure often face asymmetric routing delays.

By allowing interval tuning per zone, the load balancer can maintain high availability without sacrificing detection speed, adapting to the physical reality of the deployment rather than forcing a one-size-fits-all policy.

**Testing Plan**
- Unit tests simulating variable network delay profiles.
- Integration test demonstrating stable state maintenance under high-latency simulation with adjusted intervals vs. oscillation with default intervals.
