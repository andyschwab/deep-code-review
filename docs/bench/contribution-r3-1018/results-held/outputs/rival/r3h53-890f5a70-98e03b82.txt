### Testing Strategy: Protocol Simulation and Contract Verification

Since direct connection to the production read-replica is forbidden, you must shift your validation strategy from **integration testing** (connecting to the real DB) to **protocol conformance testing** and **contract verification**.

1.  **Implement a "Wire-Level" Mock Server:**
    Instead of mocking the Java interface, build a lightweight TCP server (using a library like Netty or standard Java Sockets) that sits on `localhost`. This server should not implement full database logic; it only needs to replay the specific byte-level handshake and protocol frames your driver expects from the mainframe.
    *   **Action:** Capture a sanitized packet trace (if available) or strictly follow the legacy protocol specification to hard-code the server's responses.
    *   **Benefit:** This validates your driver's parsing logic, timeout handling, and state machine transitions against the *actual protocol structure* without touching real data or risking table locks.

2.  **Define a Strict Interface Contract:**
    Since you cannot test against real data volume, you must prove your code adheres to the `DataBridge` abstraction contract.
    *   **Action:** Write unit tests that inject your "Wire-Level" mock. Assert that your driver correctly translates the legacy protocol's specific error codes, null representations, and transaction boundaries into the standard exceptions and data types expected by `DataBridge`.
    *   **Evidence:** Include a matrix in your PR showing exactly which protocol states (e.g., "Handshake Success," "Auth Failure," "Timeout," "Malformed Packet") are covered by your mock tests.

3.  **Security & Safety Audit:**
    Explicitly document that your code contains *no* hardcoded production endpoints. Verify via static analysis that connection strings are purely configuration-driven. This assures maintainers that merging the code cannot accidentally trigger a production connection.
