### Solution Strategy: Pluggable Trust Store Injection

Do not submit code containing your private certificates or logic specific to "Omni Consumer Products." Instead, implement a **pluggable trust store interface** that allows *any* user to inject custom Root CAs via environment variables or configuration files, without altering the library's default behavior. This shifts the burden of trust management from the library maintainer to the end-user deployment environment, which is the standard enterprise pattern for Rust TLS stacks (e.g., `rustls` or `native-tls`).

#### 1. Code Changes (Conceptual)

Modify the server initialization to accept an optional `RootCertStore` populated from an external source, falling back to the system default if none is provided.

**Before (Hardcoded/Failing):**
```rust
// Fails for private CAs because it only uses system roots
let mut root_store = RootCertStore::empty();
root_store.add_trust_anchors(webpki_roots::TLS_SERVER_ROOTS.iter().map(|ta| {
    OwnedTrustAnchor::from_subject_spki_name_constraints(
        ta.subject, ta.spki, ta.name_constraints,
    )
}));
```

**After (Pluggable Injection):**
```rust
use std::env;
use std::fs;
use rustls::RootCertStore;

fn build_root_store() -> Result<RootCertStore, Box<dyn std::error::Error>> {
    let mut root_store = RootCertStore::empty();

    // 1. Load standard public roots first
    root_store.add_trust_anchors(webpki_roots::TLS_SERVER_ROOTS.iter().map(|ta| {
        OwnedTrustAnchor::from_subject_spki_name_constraints(
            ta.subject, ta.spki, ta.name_constraints,
        )
    }));

    // 2. Inject custom CA path via Environment Variable (Standard Pattern)
    if let Ok(ca_path) = env::var("EXTRA_TLS_ROOT_CA_FILE") {
        let cert_data = fs::read(&ca_path)?;
        let certs = rustls_pemfile::certs(&mut &cert_data[..])?;
        for cert in certs {
            root_store.add(&rustls::Certificate(cert))?;
        }
        eprintln!("Loaded extra root CA from: {}", ca_path);
    }

    Ok(root_store)
}
```

#### 2. PR Description Draft

**Title:** `feat(tls): support custom root CA injection via EXTRA_TLS_ROOT_CA_FILE`

**Summary:**
Adds support for injecting additional root Certificate Authorities via the `EXTRA_TLS_ROOT_CA_FILE` environment variable. This enables deployment in enterprise environments with private PKI infrastructures without hardcoding specific certificates or altering default security posture.

**Motivation:**
Standard system trust stores often lack intermediate CAs required for internal enterprise services. Previously, users had to modify system roots or fork the project. This change allows users to point the application to a local PEM file containing their private chain.

**Implementation Details:**
- Introduces no new dependencies.
- Defaults to standard `webpki-roots` behavior if the env var is unset.
- Validates that the provided file contains valid PEM-encoded certificates before loading.
- No private certificates are included in this repository.

**Usage for Enterprise Users:**
1. Export your private intermediate/root chain to a local file (e.g., `company-ca.pem`).
2. Set the environment variable: `export EXTRA_TLS_ROOT_CA_FILE=/path/to/company-ca.pem`.
3. Run the server; it will now trust chains signed by your private CA alongside public CAs.

**Security Considerations:**
- The application only trusts certificates explicitly pointed to by the user via the environment variable.
- No network requests are made to fetch certificates.
- Maintainers do not need to review or approve specific private CAs.

**Test Plan:**
- Verified server starts successfully without the env var (uses system roots).
- Verified server accepts connections signed by a custom test CA when the env var points to that CA's PEM file.
- Verified server rejects invalid PEM files with a clear error message.
