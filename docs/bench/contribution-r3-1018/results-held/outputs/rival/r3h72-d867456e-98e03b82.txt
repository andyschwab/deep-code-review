Do not upload the screenshot. Instead, submit a text-only bug report that replaces the visual evidence with a sanitized stack trace and a minimal, reproducible code example.

**1. Extract the Stack Trace (Critical)**
Since this is a C++ segmentation fault, the debug screen almost certainly displayed a stack trace. Copy the text of the stack trace exactly. This is far more valuable to C++ maintainers than a screenshot. It tells them the exact function call chain that caused the crash.
*   **Action:** If you can still access the debug screen, transcribe the function names and line numbers. If the application logged this to a file (e.g., `stderr` or a `.log` file), extract those lines.
*   **Sanitization:** Text logs rarely contain internal IPs unless explicitly printed by your application logic. If the IP appears in a log line (e.g., `Connecting to 192.168.x.x...`), redact the IP and port, replacing them with placeholders like `[REDACTED_INTERNAL_IP]` and `[PORT]`. The crash location (function name) is what matters, not the network address.

**2. Create a Minimal Reproducible Example (MRE)**
Maintainers need to reproduce the crash without your specific network context.
*   **Action:** Write a small, standalone C++ snippet (5–20 lines) that calls the OpenMap routing function with the specific coordinates that triggered the crash.
*   **Mock the Network:** If the crash depends on network data being returned, mock the response. Hardcode the data structure that would have been received from your internal server directly into the test code. This removes the need to show *where* the data came from (your internal IP) and focuses solely on *what* data caused the parser to fail.

**3. Draft the Issue Description**
Structure your report as follows:

*   **Title:** `Segfault in [Function Name] when processing coordinates [Lat, Long]`
*   **Environment:** OpenMap version, OS, Compiler version.
*   **Description:** "Triggering the routing engine with coordinates X,Y causes a segmentation fault."
*   **Stack Trace:** Paste the sanitized text stack trace here.
*   **Reproduction Steps:**
    1. Compile the attached MRE (provide the code block).
    2. Run the binary.
    3. Observe the segfault.
*   **Note on Screenshots:** Explicitly state: "Original debug output contained sensitive internal infrastructure details. A screenshot was withheld to comply with security policies, but the full stack trace and a minimal reproducer are provided above."

**Why this works:**
C++ developers prioritize stack traces and reproducible code over GUI screenshots. By providing an MRE, you remove the dependency on your internal network entirely, making the bug easier for them to fix while guaranteeing zero data leakage. Acknowledging that you *withheld* a screenshot for security reasons demonstrates professionalism and aligns with their safety guidelines, rather than raising suspicion.

*If you cannot extract a stack trace, describe the exact coordinate inputs and the specific routing function called; this may allow them to guess the failure point, though it is less ideal.*
*Never attempt to "blur" sensitive text in images for open-source reports; forensic recovery of blurred text is trivial and the risk is not worth it.*
