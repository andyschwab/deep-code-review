## Issue Title: [Discussion] Proposal: Deprecate `RiskCalcV1` in favor of `ModernRiskEngine` to improve clarity

### Summary
This issue proposes a discussion on renaming the public class `RiskCalcV1` to `ModernRiskEngine` to better reflect its current capabilities. Given the widespread adoption of this library, **this is not a proposal for an immediate breaking change**. Instead, we seek community consensus on introducing a deprecation cycle that allows users to migrate gradually while maintaining backward compatibility for a defined period.

### Motivation
The name `RiskCalcV1` currently creates confusion:
1.  **Misleading Versioning:** The "V1" suffix implies the existence of a "V2" or suggests the class is legacy/outdated, despite it being the primary, actively maintained engine.
2.  **Lack of Descriptiveness:** The name does not convey the modern risk metrics and expanded functionality the class currently supports.
3.  **Onboarding Friction:** New users often hesitate to use a class named "V1," assuming it is deprecated or unstable.

Renaming to `ModernRiskEngine` would align the API with its actual value proposition and improve long-term maintainability.

### Proposed Transition Strategy (Draft)
To mitigate disruption for thousands of downstream users (including critical internal systems at Northwind Traders and others), we propose a **multi-release deprecation cycle** rather than an immediate rename:

1.  **Introduction Phase:** Add `ModernRiskEngine` as an alias or subclass of `RiskCalcV1`. Both names function identically.
2.  **Deprecation Phase:** Mark `RiskCalcV1` as `@deprecated` with clear documentation pointing to `ModernRiskEngine`. This phase would last for X major releases (e.g., 12–18 months).
3.  **Removal Phase:** Only after the deprecation period and sufficient community feedback would `RiskCalcV1` be considered for removal in a future major version (e.g., v3.0).

### Risks & Concerns
We acknowledge significant risks:
*   **Migration Overhead:** Large enterprises may have hard-coded dependencies on `RiskCalcV1`.
*   **Tooling Breakage:** Static analysis tools, IDEs, and internal linters may flag the new name or miss the alias.
*   **Community Fragmentation:** Tutorials and StackOverflow answers may become outdated during the transition.

### Questions for the Community
Before any code is written, we need to gauge interest and feasibility:
1.  Does the community agree that the current naming causes confusion?
2.  Is a 12–18 month deprecation window sufficient for most organizations to plan a migration?
3.  Are there specific technical constraints (e.g., serialization formats, pickled objects) that would make an alias approach difficult?
4.  Would maintainers be open to a PR that implements the alias + deprecation warning, contingent on this discussion's outcome?

### Next Steps
If there is general agreement on the need for a rename and the proposed timeline, we can draft a formal RFC (Request for Comments) detailing the implementation specifics. If the consensus is that the disruption outweighs the benefits, we will close this proposal and explore non-breaking alternatives (e.g., documentation improvements only).

Looking forward to your thoughts.
