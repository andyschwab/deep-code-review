### Validation Plan: Isolated Binary + Maintainer-Supplied Credentials

Do not attempt to run integration tests using your employer's credentials, even locally, if there is any risk of those binaries or logs being committed or shared. Instead, propose a **"Verified Binary"** workflow. This shifts the trust burden from "believing your word" to "verifying your artifact," without exposing secrets.

**Step 1: Prepare the "Dry-Run" Artifacts**
Ensure your code includes a specific `make test-integration-dryrun` target or a CLI flag (e.g., `--integration-test-mode=record`) that exercises the CloudNexus logic but fails gracefully when credentials are missing, outputting exactly *what* it would call (URLs, payloads, expected headers) without sending them. This proves the code path exists and is structured correctly.

**Step 2: Build a Reproducible Binary**
Compile your branch into a static binary for the standard CI platform (usually Linux/amd64). Generate a SHA256 checksum of this binary. This binary contains your logic but no secrets.

**Step 3: The Maintainer Verification Loop**
Propose that a maintainer (or a trusted community member with CloudNexus access) downloads your binary, supplies *their own* test credentials in their private environment, and runs the integration suite. Since the binary is built from your public commit hash, they can verify the source matches the executable.

**Step 4: Evidence for the PR**
In your PR description, include:
1.  The SHA256 hash of the verified binary.
2.  A transcript of the "dry-run" mode showing the exact API calls your code constructs.
3.  A statement that the binary is ready for maintainer verification against their own sandbox.
