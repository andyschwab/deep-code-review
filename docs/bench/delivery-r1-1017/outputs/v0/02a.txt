### Delivery Plan: Seasonal Trend Filter (Merchant Analytics)

**Objective:** Implement a "Seasonal View" toggle overlaying last year's data on the revenue chart with persistent state, verified by headed-browser video evidence.

#### 1. Lanes & Parallelism
*   **Lane A (Product Spec & Data Contract):** Define the exact date-mapping logic for "corresponding dates" (handling leap years) and the persistence schema (localStorage key). *Owner: Product Analyst.*
*   **Lane B (UI Implementation):** Build the toggle component, integrate the overlay into the existing chart (respecting the frozen viz library v2.4 constraint), and implement state persistence. *Owner: Builder (Frontend Guild).*
*   **Lane C (Accessibility & UX):** Verify color contrast for the overlay, keyboard navigation for the toggle, and screen reader announcements. *Owner: Accessibility Champion (Independent).*
*   **Lane D (Evidence Capture):** Script a headed-browser session to record the interaction on a lower-resolution viewport, capturing the overlay render and refresh persistence. *Owner: QA.*

**Parallelism:** Lanes A, B, and C start simultaneously once the spec (A) defines the data contract. Lane D waits for Lane B's build.
**Serialization:** Lane B must complete before Lane D. Lane C must approve before merge.

#### 2. Gates & Checks
*   **G1 (Spec):** Product Lead approves the date-mapping logic and persistence strategy.
*   **G3 (Design):** Confirm no changes to the frozen visualization library; overlay implemented via wrapper or configuration only.
*   **G4 (Implement):** Builder commits code with unit tests for date logic and storage hooks.
*   **G5 (Verify):**
    *   **Functional:** Headed browser test on exact revision. Must prove overlay renders and persists after refresh.
    *   **Evidence:** Video artifact (`.mp4`) captured at 1280x720 showing the full interaction.
    *   **Constraint:** Skip flaky screenshot comparison checks; rely on video evidence and functional DOM assertions.
*   **G6 (Review):**
    *   **Code Review:** Senior Frontend Engineer (independent of Builder).
    *   **Accessibility:** Accessibility Champion sign-off (mandatory).
    *   **Product:** Product Lead sign-off (mandatory).

#### 3. Review Strategy
*   **Independence:** The Builder cannot self-approve. The Accessibility Champion and Product Lead must review the running staging deployment, not just the diff.
*   **Scope:** Review focuses on the overlay logic, persistence mechanism, and a11y compliance. No changes to the core viz library are permitted.

#### 4. Landing & Human Decisions
*   **Integration:** Merge to `main` via a merge train only after G6 approvals are recorded.
*   **Staging:** Auto-deploy to staging upon merge. QA verifies the video evidence against the staging URL.
*   **Production Gate (Human):**
    *   **Approver:** VP of Engineering.
    *   **Condition:** Manual sign-off required during business hours.
    *   **Trigger:** Deployment script is ready but paused pending explicit approval.
*   **Rollback:** If the overlay causes performance regression or rendering errors in production, revert the merge immediately. The persistence schema is backward compatible (graceful degradation if key missing), minimizing data risk.

#### 5. Cost & Efficiency
*   **CI Optimization:** Trigger full CI ($45, 55m) only once on the final integration SHA. Use incremental lint/type checks for intermediate commits to avoid costly re-runs.
*   **Flake Mitigation:** Explicitly disable the flaky screenshot check for this PR; substitute with the required video evidence.

**Deliverable:** Merged code, accessibility report, product sign-off, and a video file proving the feature works on low-res screens with persistence.
