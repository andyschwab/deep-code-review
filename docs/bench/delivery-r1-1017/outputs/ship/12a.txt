**Delivery Plan: Parallel Run Migration (Cron → Queue)**

**Strategy:** Implement a "Shadow Mode" queue consumer that processes events alongside the existing cron job without writing to the production ledger until verification is complete. The migration is gated by a 7-day parallel execution window starting next Monday.

### Lanes & Serialization

1.  **Lane A: Shadow Consumer Implementation (Builder)**
    *   **Work:** Develop the queue consumer logic to read from the new distributed queue and write output to a *staging* directory (`/tmp/claims-shadow/`), not the production ledger. Include a feature flag `CLAIMS_SHADOW_MODE=true` to toggle this behavior.
    *   **Parallelism:** Can run immediately.
    *   **Constraint:** Must not modify `global-rates.json` during business hours (8 AM–6 PM EST).

2.  **Lane B: Comparison Harness & Alerting (QA/Builder)**
    *   **Work:** Create a nightly comparison script that diffs the cron-generated file against the shadow consumer's output. It must flag any byte-level drift or record count mismatch. Integrate an alert if the queue consumer fails, ensuring the cron job's continuity is verified.
    *   **Serialization:** Depends on Lane A's interface definition.

3.  **Lane C: Deployment Configuration (Release)**
    *   **Work:** Prepare the deployment manifest to enable the shadow consumer alongside the cron job. Configure the 7-day timer logic to auto-disable shadow mode after the window, pending manual decommissioning of the cron.
    *   **Serialization:** Must wait for Lane A and B to be verified locally.

### Gates & Checks

*   **G1 Spec:** Confirm acceptance criteria: "Zero data drift" means exact file checksum match or semantic equivalence validated by the comparison harness.
*   **G2 Plan:** Verify the 7-day start date (next Monday) is hardcoded or configurable in the deployment manifest. Ensure the flaky staging network check is isolated to prevent false negatives from blocking the build.
*   **G4 Implement:**
    *   **Base SHA:** Pin to the current `main` head before branching.
    *   **Local Check:** Run unit tests for the comparison harness locally. Do not trigger the full 45-minute CI pipeline for every commit; run it only on the final candidate SHA for Lane A and B.
    *   **Constraint Check:** Verify no writes to `global-rates.json` occur in the code path during restricted hours.
*   **G5 Verify (Shadow Run):**
    *   **Environment:** Staging.
    *   **Action:** Deploy the shadow consumer. Simulate queue events.
    *   **Check:** Confirm the cron job still runs successfully if the shadow consumer is artificially failed (chaos test).
    *   **CI Strategy:** Trigger the full CI pipeline *once* on the merged candidate SHA. If the flaky network check fails, retry only that specific check once; do not rerun the whole suite unless the SHA changes.
*   **G6 Review:**
    *   **Reviewer:** Senior Lead (Settlements team) + Independent Security Review.
    *   **Scope:** Review the irreversibility of ledger writes. Confirm the shadow mode strictly prevents production writes.
    *   **Independence:** Reviewer must not be the Builder from Lane A.

### Landing & Human Decisions

*   **Merge Strategy:**
    1.  Merge Lane A and B into a feature branch.
    2.  **Human Gate:** Two senior leads must approve the PR before merging to `main`.
    3.  Deploy to production with `CLAIMS_SHADOW_MODE=true` effective next Monday 00:00 UTC.
*   **The 7-Day Window:**
    *   The system will automatically collect comparison receipts nightly.
    *   **Human Gate:** After 7 days, the business owner must review the "Zero Drift" report generated by Lane B. Only upon explicit approval can the cron job be decommissioned (future ticket).
*   **Rollback:**
    *   **Trigger:** Any data drift detected or queue consumer crash affecting cron stability.
    *   **Action:** Toggle `CLAIMS_SHADOW_MODE=false` via config update (no code rollback needed).
    *   **Database:** Since the shadow mode does not write to the production ledger, no database rollback is required unless the flag was erroneously set to false during the test. If production writes occurred prematurely, a manual database rollback request is mandatory.

**Risk Mitigation:** The flaky network check is marked as "non-blocking" for the shadow deployment but must pass for the final cron decommissioning. The `global-rates.json` lock is respected by scheduling config updates outside 8 AM–6 PM EST.
