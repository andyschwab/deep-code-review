### Delivery Plan: Seasonal Trend Filter

**Scope & Constraints**
*   **Goal:** Add "Seasonal View" toggle to overlay last year's data; persist state via URL/local storage.
*   **Constraints:** Visualization library frozen (v2.4); CI costs $45/55m (optimize); screenshot check flaky (Linux/animations); requires Product Lead + Accessibility Champion approval; VP Engineering sign-off for Prod.
*   **Evidence:** Headed-browser video required (unit tests insufficient).

#### 1. Lanes & Parallelism
*   **Lane A (Implementation):** Builder implements toggle UI, data-fetching logic for prior-year dates, and chart overlay using existing frozen library APIs. Implements state persistence.
    *   *Worktree:* Isolated `feature/seasonal-toggle`.
    *   *Parallel:* Yes.
*   **Lane B (Accessibility & Design Review):** Accessibility Champion reviews contrast, focus states, and screen reader announcements for the new toggle. Product Lead validates the "last year" calculation logic and UI placement.
    *   *Trigger:* Ready when Lane A pushes initial draft.
    *   *Parallel:* Yes (after draft).
*   **Lane C (Verification & Evidence):** QA executes manual integration test on staging. Records headed-browser video on a low-resolution viewport proving overlay rendering and state persistence after refresh.
    *   *Constraint:* Skips flaky automated screenshot check; relies on manual video evidence.
    *   *Serialized:* Must wait for Lane A merge to staging.

#### 2. Gates & Checks
*   **G1 Spec (Now):** Confirm "last year" date logic (e.g., handling leap years) and persistence mechanism (URL param vs. local storage) with Product Lead.
*   **G4 Implement:** Builder commits code.
    *   *Check:* Local lint/type check only. **Do not run full CI suite** locally or on every commit to save $45/55m.
*   **G5 Verify (Staging):**
    *   Deploy to staging (automated).
    *   **Action:** QA runs Lane C. Record video. Verify persistence.
    *   **Flake Handling:** Explicitly mark automated screenshot gate as `SKIPPED_FLAKY` in PR body; cite manual video as replacement evidence.
*   **G6 Review:**
    *   **Independent Reviewers:** Accessibility Champion (a11y), Product Lead (logic), Senior Engineer (code safety).
    *   **Base:** Exact SHA of the staging deployment verified in G5.
*   **G7 Integrate:** Merge to `main` (or release branch) only after all three approvals are recorded.

#### 3. Review Strategy
*   **Builder** never self-approves.
*   **Accessibility Champion** must explicitly approve UI interactions.
*   **Product Lead** must explicitly approve the business logic of the date overlay.
*   **Security/Privacy:** No new data sources introduced; standard review suffices.

#### 4. Landing & Human Gates
*   **Merge:** Automated merge train allowed *only* after G6 approvals are present.
*   **Production Deploy (G8):**
    *   **Gate:** Manual sign-off required from **VP of Engineering**.
    *   **Timing:** Business hours only.
    *   **Action:** Conductor requests approval with link to staging video and approval trail.
*   **Rollback Plan:**
    1.  **Code:** Revert merge commit (instant).
    2.  **Flag:** If implemented behind a feature flag, toggle off (preferred).
    3.  **Data:** No database changes expected; no data repair needed.

#### 5. Cost & Risk Controls
*   **CI Optimization:** Full suite runs exactly once: on the final PR head before merge. No runs on intermediate commits.
*   **Flaky Test:** The Linux screenshot check is bypassed via manual video evidence to prevent false blocking.
*   **Library Freeze:** Strictly no updates to visualization library; usage confined to existing v2.4 APIs.

**Next Step:** Awaiting confirmation on date-logic edge cases (leap years) to finalize G1 Spec.
