### Delivery Plan: PolicyViewer Keyboard Trap Fix

**Lanes & Parallelism**
*   **Lane A (Core Logic):** Refactor `PolicyViewer` focus management. Remove the modal trap logic and implement standard Escape key handling. This lane is serialized; it must complete before Lane B begins.
*   **Lane B (Integration Check):** Verify `focus-lock` utility usage. Since the signature cannot change, this lane runs in parallel with Lane A’s initial analysis but must merge before final testing to ensure the shared utility remains intact for the other twelve components.
*   **Lane C (Manual Verification):** Prepare the staging environment and assistive technology suite. This runs parallel to development but gates the final merge.

**Gates & Checks**
*   **Gate 1 (Local Build):** Before any remote push, the developer must run a local build against the specific commit hash of the `nexus-ui` main branch. This confirms the `focus-lock` signature remains unchanged and the build passes locally, bypassing the 25-minute CI cost for iteration.
*   **Gate 2 (Visual Regression):** A strict check ensuring no CSS or animation timing files were modified. Any diff in style assets triggers an immediate revert of those specific changes.
*   **Gate 3 (Staging Validation):** Deploy to staging only after local build success. Manual testing using the standard assistive technology suite is the primary acceptance criterion. The flaky CI accessibility check on mobile viewports is ignored for pass/fail status; a manual "Pass" ticket from the tester is required.

**Review Process**
*   **Independent Code Review:** A senior engineer not involved in the `nexus-ui` library’s recent changes must review the pull request. They will specifically audit the focus management logic and verify that `focus-lock` imports remain backward compatible.
*   **Accessibility Audit:** A separate QA specialist, distinct from the developer, must perform the manual staging test. They will sign off on the "Escape key exits modal" and "Screen reader navigation flows correctly" criteria.

**Landing Strategy**
*   **Merge Conditions:** The pull request merges only when:
    1.  Local build passes on the target revision.
    2.  Independent code review is approved.
    3.  QA sign-off on staging manual tests is attached.
    4.  Visual diff shows zero styling changes.
*   **Human Decisions:** Explicit approval is required from both the **Security Lead** (confirming no new attack vectors via focus manipulation) and the **Product Owner** (confirming the interaction change meets compliance needs) before the production deploy button is enabled.
*   **Rollback Plan:** If production monitoring shows increased error rates or user reports of focus issues within 2 hours of deploy, immediately revert the merge using the pre-deploy commit hash. Do not attempt hotfixes; revert first, investigate later. The `focus-lock` utility’s broad usage makes rapid reversion safer than patching live.

**Timeline Constraint**
All lanes must conclude testing and review 48 hours before the month-end deadline to allow buffer time for the required human approvals and potential rollback/retry cycles.
