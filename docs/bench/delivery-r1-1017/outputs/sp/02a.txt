### Delivery Plan: Seasonal Trend Filter

#### 1. Work Lanes & Parallelism
*   **Lane A (Frontend Guild - Core Logic):** Implement the "Seasonal View" toggle state management and the data transformation layer to fetch/overlay last year's revenue data. This lane works strictly within the frozen visualization library constraints (v2.4), manipulating input data rather than library code.
*   **Lane B (Frontend Guild - UI/UX):** Build the toggle component, ensure responsive rendering on lower-resolution screens, and implement local storage persistence for the chart state.
*   **Lane C (QA/Video):** Once Lane A and B merge to a feature branch, execute the manual browser session recording on a low-resolution viewport to verify the overlay rendering. This cannot start until the code is deployed to a preview environment.

**Parallel Execution:** Lanes A and B run in parallel. Lane C is serialized after A and B are integrated and deployed to staging.

#### 2. Gates & Checks
*   **Gate 1 (Local Pre-Flight):** Before pushing, developers must run unit tests locally. Do not trigger the full CI pipeline ($45/55m) for text edits or minor style tweaks. Only trigger CI when the data overlay logic and persistence are both present.
*   **Gate 2 (CI Pipeline):** Trigger the full suite only on the commit tagged `ready-for-review`.
    *   *Constraint:* If the screenshot comparison check fails, manually verify if the failure is an animation frame false positive (known Linux runner issue). If it is a false positive, bypass this specific check with a documented comment; do not re-run the whole suite unnecessarily.
*   **Gate 3 (Staging Deployment):** Automated deployment occurs immediately after CI passes. Verification of the "Seasonal View" persistence (refresh test) happens here.

#### 3. Review Process
*   **Independent Reviewers:**
    1.  **Product Lead:** Reviews the functional correctness (does the overlay match the spec?) and the video deliverable from Lane C.
    2.  **Accessibility Champion:** Reviews the toggle's keyboard navigation, screen reader announcements, and color contrast for the overlay.
*   **Rule:** These reviews happen in parallel but both must approve before merge. Neither reviewer should be the author of the code.

#### 4. Landing Strategy
*   **Merge Condition:** Code merges to `main` only after:
    1.  CI passes (with documented bypass of flaky screenshot check if applicable).
    2.  Product Lead and Accessibility Champion approvals are recorded.
    3.  The video deliverable is attached to the ticket.
*   **Production Push:** Requires manual sign-off from the VP of Engineering.
    *   *Constraint:* This sign-off can only be requested during business hours. Prepare the release candidate early to ensure the VP is available.
*   **Rollback Plan:** If the overlay causes performance degradation or data mismatches in production:
    1.  Revert the merge commit immediately.
    2.  Disable the feature flag (if implemented) or redeploy the previous stable tag.
    3.  Notify the three enterprise clients who filed the urgent tickets with an updated ETA.

#### 5. Critical Constraints Summary
*   **Library:** Do not upgrade the visualization library; work around v2.4 limitations.
*   **Cost:** Minimize CI runs; verify locally first.
*   **Proof:** Unit tests are insufficient; the low-res video recording is a mandatory definition of done.
