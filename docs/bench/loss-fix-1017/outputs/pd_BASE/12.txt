**Decision Recommendation: Do not build a native app yet. Prioritize fixing the mobile web experience first.**

**Evidence & Reasoning**
Your current data validates a **usability problem**, not necessarily a **platform demand**.
*   **The Signal:** 38% of sessions are mobile, but completion rates are 22% lower. This indicates users are *trying* to work on mobile but are blocked by a "clunky" interface.
*   **The Riskiest Assumption:** You are assuming mobile users want a *native app* (download, install, login) rather than just a *functional mobile website*.
*   **The Cost of Being Wrong:** Building a native app requires 3 months of engineering time (18 engineer-months). If users only wanted a better browser experience, you have wasted a quarter of capacity on a solution they won't adopt, while the core friction remains unresolved.

**Required Next Step: The "Cheap Test" (Before Any Build)**
Do not start coding. Run a **Fake-Door Test** on your existing mobile web traffic to measure actual intent to download.
1.  **Action:** Add a non-intrusive banner to the mobile web experience for 2 weeks: *"Want a faster, offline-ready experience? Join the waitlist for our iOS/Android app."*
2.  **Metric:** Click-through rate (CTR) on the banner and email sign-ups.
3.  **Kill Threshold:** Set a specific number now. Example: *"If fewer than 5% of mobile users click the banner, or we get fewer than 200 sign-ups, we assume demand for a native app is too low to justify 3 months of dev time."*
4.  **Outcome:**
    *   **If test fails:** Invest the 3 months into fixing the mobile web completion rate. This directly addresses the 22% drop-off you already see.
    *   **If test passes:** You have validated demand. Proceed to scoping the native app with confidence.

**Immediate Action Plan**
1.  **Fix Mobile Web:** Allocate 1–2 engineers immediately to address the top 3 friction points causing the 22% completion drop. This is a high-confidence win based on existing data.
2.  **Run the Fake-Door Test:** Implement the banner this week to gather the missing evidence on native app demand.
3.  **Re-evaluate in 2 Weeks:** Make the final build/no-build decision based on the test results, not assumptions.

**Note:** This approach protects your team from building the wrong thing faster. It solves the known problem (web friction) immediately while cheaply validating the unknown (app demand).
