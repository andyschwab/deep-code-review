### BrightHome Accessibility Audit Work Session Plan

**Phase 1: Triage & Backlog Organization (Days 1–2)**
1.  **Categorize the 12 Failures:** Split the list into "Blocking" (prevents task completion, e.g., unlabeled buttons, broken focus order) and "Non-Blocking" (annoyances, e.g., color contrast on decorative elements). Focus 100% of effort on Blocking items first.
2.  **Assign Ownership:** Pair your two accessibility-experienced developers with the three juniors. Each pair takes 2–3 critical items. The experts act as reviewers, not just implementers.
3.  **Freeze Scope:** Declare a code freeze on non-essential features for three weeks. Any new commit must relate directly to these 12 fixes.

**Phase 2: Implementation & Unit Verification (Days 3–10)**
1.  **Fix Implementation:** Developers implement fixes using native accessibility APIs (UIAccessibility for iOS, AccessibilityNodeInfo for Android).
2.  **Automated Regression Check:** Run existing automated test suites to ensure core navigation paths remain intact. If no automated accessibility tests exist, manually record a "happy path" video for screen reader navigation before applying fixes to use as a baseline comparison.
3.  **Peer Review Gate:** No code merges without sign-off from an accessibility-experienced developer. They must verify the fix using a screen reader (VoiceOver/TalkBack) on a physical device, not just a simulator.

**Phase 3: Internal Validation & Pre-Audit (Days 11–18)**
1.  **The "Blind" Test:** Have team members who did *not* write the code attempt core user flows (login, booking, payment) with screen readers enabled and displays off. Document any failures immediately.
2.  **Regression Audit:** Specifically test the areas surrounding the fixes. Did fixing the "Submit" button label break the form submission logic?
3.  **Pre-Audit Mock Run:** Simulate the auditor's process. Attempt to fail the app. If you cannot find the original 12 errors, you are ready.

**Phase 4: Final Polish & Submission Prep (Days 19–21)**
1.  **Documentation:** Prepare a remediation report listing the 12 items, the fix applied, and the date verified.
2.  **Store Metadata:** Update app store listings if required to reflect new accessibility features.

### Decision Matrix: Product Owner vs. Developers

**Requires Product Owner Input (UX Trade-offs):**
*   **Alternative Text Strategy:** Deciding how much context to provide for complex charts or images. Too little is useless; too much is noisy. You must define the "user intent" for each image.
*   **Focus Order Logic:** If the visual layout differs from the logical reading order, you must decide the priority of information for a non-visual user.
*   **Error Messaging:** Defining clear, actionable language for form errors that screen readers will announce.

**Handled by Developers (Technical Implementation):**
*   **Labeling Controls:** Ensuring every button, switch, and input has a programmatic label.
*   **Focus Management:** Ensuring focus moves logically when screens change or modals open.
*   **Color Contrast Adjustments:** Tweaking hex codes to meet WCAG AA/AAA standards without altering brand identity significantly.
*   **Touch Target Sizing:** Expanding clickable areas to meet minimum size requirements without breaking the visual layout.
