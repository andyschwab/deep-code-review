### Immediate Action Plan: CryptoCore Open-Source Release

**1. Execute Automated Secret Scanning and Sanitization (Owner Action)**
You must personally run a multi-tool secret scan on the current codebase before any other step. Use tools like `truffleHog`, `gitleaks`, or your IDE's built-in security linter to search the entire commit history, not just the current head. Look specifically for hardcoded API keys, database credentials, internal hostnames, and proprietary algorithm constants.
*   **Deliverable:** A sanitized Git repository where all identified secrets are removed via `git filter-branch` or `BFG Repo-Cleaner`, and the local history is rewritten. Verify that no internal hostnames remain in configuration files or comments.
*   **Why you must do this:** Automated tools miss context-specific leaks (e.g., a variable named `salt` that contains a real value). Only you know the specific internal patterns of CryptoCore. Delegating this risks a false negative from an external party unfamiliar with your internal naming conventions.

**2. Establish the "Clean Room" Contribution Boundary (Engineering Team Delegation)**
Delegate the creation of a public-facing contribution workflow to your engineering lead, but with a strict constraint: they must set up a *new, empty* public repository and a separate internal staging repository.
*   **Deliverable:** A documented workflow where external Pull Requests land in the public repo, are reviewed by an internal maintainer, and then manually cherry-picked or mirrored to the internal staging repo for integration. Never allow direct push access from the public repo to your internal microservices' dependency chain.
*   **Why delegate:** This is standard infrastructure setup. However, you must define the rule: "No internal CI/CD pipelines may trigger on public PRs until the code is explicitly merged to the internal staging branch by a trusted maintainer." This prevents supply chain attacks via malicious PRs triggering internal build secrets.

**3. Initiate Legal Licensing and IP Audit (Legal Team Delegation)**
Engage legal immediately to select an open-source license (e.g., MIT, Apache 2.0) and perform an IP clearance check.
*   **Deliverable:** A signed `LICENSE` file and a `NOTICE` file listing any third-party dependencies included in CryptoCore. Legal must confirm that no internal patents are inadvertently disclosed and that the code does not contain any copied snippets from other proprietary systems you don't own.
*   **Why delegate:** This requires specific legal expertise regarding liability and patent grants. Your role is to provide the list of all third-party libraries used; their role is to verify compatibility and risk.

---
**Note:** Do not push *any* code to GitHub until Steps 1 and 3 are complete and verified. The risk of accidental leakage outweighs the schedule pressure; a delayed release is preferable to a compromised infrastructure.
