### Session Plan: Legacy Inventory Repository Safe Release

**Objective:** Execute a critical security patch within five days without triggering a production lockout due to expired credentials.

#### Phase 1: Knowledge Recovery & Non-Intrusive Audit (Days 1-2)
**Goal:** Understand the system state without executing any code or pipelines.

*   **Owner (You):**
    *   **Static Code Analysis:** Manually inspect the build configuration files (e.g., `Jenkinsfile`, `.github/workflows`, `build.gradle`, `pom.xml`) to locate hardcoded credential patterns. Do not run the build yet.
    *   **Dependency Mapping:** Identify the specific library requiring the security patch and trace its usage across the codebase to assess breaking change risks.
    *   **Infrastructure Inventory:** Locate documentation or comments regarding the production environment access levels and the specific consequences of a failed authentication attempt (e.g., account lockout policies).
*   **Junior Developer (Review/Support):**
    *   **History Excavation:** Scrape commit messages and old pull requests from the last 18 months to find clues about previous deployment successes/failures or credential rotation events.
    *   **Environment Parity Check:** Compare the local development environment setup scripts against the production build scripts to identify discrepancies without connecting to production.

#### Phase 2: Credential Verification Strategy (Day 3)
**Goal:** Validate access without risking the production lockout.

*   **Owner (You):**
    *   **Sandbox Simulation:** If a staging or lower-level environment exists, attempt a dry-run deployment there using the suspected credentials.
    *   **Manual Validation:** If no sandbox exists, contact the infrastructure/security team directly to verify the status of the hardcoded credentials. **Do not guess.** Request a temporary, scoped token for testing if possible.
    *   **Rollback Planning:** Define the exact manual steps to revert the deployment if the patch fails or if the pipeline behaves unexpectedly.
*   **Junior Developer (Review/Support):**
    *   **Script Preparation:** Draft the scripts needed to rotate the credentials in the build pipeline once the new valid credentials are secured, ready for your review.

#### Phase 3: Controlled Execution (Days 4-5)
**Goal:** Apply the patch and deploy safely.

*   **Owner (You):**
    *   **Patch Application:** Apply the security update and run local integration tests.
    *   **Final Gate Review:** Conduct a line-by-line review of the changes with the junior developer, focusing specifically on interaction points with the build pipeline.
    *   **Supervised Deployment:** Trigger the deployment pipeline during a low-traffic window while monitoring logs in real-time. Be prepared to abort immediately upon any authentication error.
*   **Junior Developer (Review/Support):**
    *   **Live Monitoring:** Watch the deployment logs for anomalies and confirm the application health checks post-deployment.

---

#### Immediate First Steps (Do These Now)

1.  **Freeze All Activity:** Do not run any build commands, scripts, or deployment tools. Any execution could trigger the lockout mechanism if credentials are invalid.
2.  **Locate Build Config:** Open the primary build configuration file and search for strings like `password`, `token`, `secret`, or `key`. Screenshot these sections for analysis.
3.  **Contact Infrastructure:** Send an urgent message to the infrastructure or security team stating: "Taking over legacy repo; need to verify status of build credentials before attempting any access to avoid lockout."

**Note:** Under no circumstances should you attempt a "test" deployment to production to check credentials. The risk of total lockout outweighs the value of a quick check.
**Note:** If the infrastructure team cannot verify credentials immediately, the timeline must shift to credential recovery before any code changes are merged.
