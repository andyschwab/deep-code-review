### BrightHome Accessibility Audit Work Session Plan

**Phase 1: Triage and Prioritization (Days 1–3)**
1.  **Categorize the 12 Failures:** Map failures to WCAG 2.1 levels. Immediate focus must be on Level A (critical blockers like missing labels, no keyboard focus) before Level AA (contrast, spacing).
2.  **Risk-Based Sequencing:** Order fixes by "Navigation Impact." Any failure blocking screen reader navigation (e.g., VoiceOver/TalkBack getting stuck) takes precedence over visual issues.
3.  **Team Allocation:** Pair the two accessibility-experienced developers with the three novices. Experts define the pattern; novices implement across iOS/Android.

**Phase 2: Execution and Product Decisions (Days 4–14)**
*   **Developer-Only Tasks:** Technical implementations such as adding accessibility labels, defining focus order, ensuring dynamic type scaling, and correcting contrast ratios where brand colors allow flexibility.
*   **Product Owner Decisions Required:**
    *   **Visual Trade-offs:** If meeting contrast ratios requires altering primary brand colors in key buttons, you must approve the visual deviation.
    *   **Content Descriptions:** For complex custom graphics or icons, you must define the *intent* of the element so developers can write accurate screen reader descriptions.
    *   **Interaction Patterns:** If a standard accessible gesture conflicts with a unique BrightHome feature, you must decide whether to adapt the feature or the gesture.

**Phase 3: Robust Verification (Days 15–21)**
1.  **Automated Re-scan:** Run the preliminary scan tool again to confirm technical resolution.
2.  **Manual Screen Reader Audit:** Developers must test every fixed flow using VoiceOver (iOS) and TalkBack (Android) with the screen turned off. This is non-negotiable for preventing navigation traps.
3.  **Regression Check:** Verify core user journeys (login, home navigation, primary task completion) to ensure fixes did not break existing functionality for the 500k user base.
4.  **Pre-Audit Mock Review:** Conduct a internal "mock audit" simulating the external auditor's path.

**Immediate Next Actions**
1.  **Backlog Organization:** Create a dedicated "Accessibility Sprint" board. Tag each of the 12 items with "iOS," "Android," or "Both," and assign a severity score (High/Medium).
2.  **Testing Protocol Setup:** Establish a mandatory checklist for every Pull Request: (a) Automated scan pass, (b) VoiceOver test pass, (c) TalkBack test pass. No code merges without all three checked.
3.  **Kickoff Meeting:** Convene the team to review the 12 failures, assign pairs, and distribute the testing checklist.

**Note:** Do not deploy to production until the "Mock Review" is signed off by the two experienced developers.
**Note:** Document every decision regarding visual trade-offs to demonstrate "good faith" efforts to auditors if minor issues persist.
