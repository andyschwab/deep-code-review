### CryptoCore Open-Source Release Plan

**Session Sequence:**
1.  **Sanitization & Security Audit (Days 1–5):** Automated scanning followed by manual verification of the codebase.
2.  **Legal & IP Review (Days 6–10):** Parallel review of licenses, contributor agreements, and export control classifications once the code is sanitized.
3.  **Release Preparation & Workflow Setup (Days 11–20):** Repository configuration, documentation finalization, and CI/CD pipeline adjustment for public contributions.
4.  **Final Sign-off & Publication (Days 21–30):** Executive approval and GitHub release.

**Responsibility Matrix:**

*   **Your Personal Responsibilities (Non-Delegable):**
    *   **Final Sanitization Verification:** You must personally run the final grep/search checks for internal hostnames, IP addresses, and hardcoded keys on the sanitized candidate. Automated tools can miss context-specific secrets; human verification of the "clean" commit is the last line of defense.
    *   **Architecture Boundary Definition:** You must explicitly define which internal modules are stripped out entirely versus which are abstracted. Legal and engineering cannot decide what constitutes "core proprietary logic" without your architectural context.
    *   **Emergency Rollback Authority:** You must hold the sole authority to halt the release if any doubt arises during the final review.

*   **Engineering Team Delegations:**
    *   **Automated Scanning:** Configure and run secret-scanning tools (e.g., TruffleHog, GitLeaks) across the entire history, not just the head commit.
    *   **Build Pipeline Refactoring:** Modify CI/CD to remove dependencies on internal artifact repositories and secret managers, replacing them with public equivalents or environment variable placeholders.
    *   **Test Data Sanitization:** Replace all integration test fixtures containing realistic data with synthetic, public-safe datasets.

*   **Legal Team Delegations:**
    *   **License Selection & Header Injection:** Select the appropriate open-source license (e.g., Apache 2.0, MIT) and ensure all file headers are updated accordingly.
    *   **Contributor License Agreement (CLA):** Draft and integrate a CLA bot workflow to manage external contributions legally.
    *   **Export Control Classification:** Verify the encryption strength complies with export regulations (e.g., EAR in the US) for public distribution.

**First Three Concrete Actions:**

1.  **Create a Dedicated "Sanitization Branch":** Immediately branch off the current mainline. Do not work on the active development branch. Run a full history rewrite tool (like `git filter-repo`) to purge any known secret patterns found in the commit history, as deleting them from the current file is insufficient if they exist in previous commits.
2.  **Execute a "Dry-Run" Build in an Isolated Environment:** Clone the sanitized branch onto a machine with *no* access to internal networks or secret vaults. Attempt to build and run tests. If the build fails due to missing internal resources, you have identified a hidden dependency that must be abstracted before release.
3.  **Draft the "Security Policy" and "Contributing Guidelines":** Before accepting any code, publish a `SECURITY.md` detailing how to report vulnerabilities privately (preventing public disclosure of bugs) and a `CONTRIBUTING.md` that explicitly forbids submitting internal configurations or data. This sets the governance perimeter before the gate is opened.

Note: Do not push any code to GitHub until the "Dry-Run" build succeeds in total isolation.
Ensure the legal team reviews the specific encryption algorithms used for any patent encumbrances before the license is finalized.
