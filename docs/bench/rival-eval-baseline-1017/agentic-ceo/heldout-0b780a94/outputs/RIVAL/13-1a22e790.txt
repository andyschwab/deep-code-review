### Vertex Logistics Postmortem Session Agenda & Action Plan

**Objective:** Produce a finalized report with agreed action items within 72 hours via a blame-free, fact-driven investigation.

#### Phase 1: Data Gathering (Hours 0–12)
*Before the joint session, secure objective data to neutralize subjective blaming.*
1.  **Distribute Data Request:** Send immediate requests to Network, Database, and App Engineering leads for:
    *   Exact timestamps of anomalies (latency spikes, error rates, connection drops).
    *   Recent change logs (deployments, config updates, schema changes) from the last 7 days.
    *   Resource utilization graphs (CPU, memory, I/O, network throughput) during the outage window.
2.  **Consolidate Timeline:** Merge the initial event timeline with the technical metrics above into a single "Master Chronology" document. Highlight gaps where data is missing.
3.  **Schedule Alignment:** Book three 45-minute pre-meetings (one per team) to review their specific data contributions, followed by one 90-minute joint working session.

#### Phase 2: The Joint Working Session (Hours 12–24)
**Agenda Sequence:**
1.  **Prime Directive (5 mins):** Read the standard postmortem prime directive: "We are here to improve the system, not to judge individuals. We assume everyone did their best with the information they had."
2.  **Fact Walkthrough (20 mins):** Present the Master Chronology. Ask teams only to confirm or correct timestamps based on logs. No "why" questions yet.
3.  **Contributing Factor Mapping (40 mins):** Use a whiteboard to map events to system layers. Ask: "What condition allowed this event to impact the shipment flow?" Focus on systemic gaps (e.g., lack of circuit breakers, insufficient monitoring) rather than "who pushed the button."
4.  **Root Cause Hypothesis (15 mins):** Identify the chain of failures. Distinguish between the *trigger* (the change) and the *vulnerability* (why the system couldn't absorb the change).

#### Phase 3: Remedy Planning & Ownership (Hours 24–48)
1.  **Draft Action Items:** Categorize fixes into "Immediate Mitigation," "Systemic Repair," and "Process Improvement."
2.  **Ownership Assignment Strategy:**
    *   **Assign to Technical Leads:** Specific code fixes, config rollbacks, and tool implementation. They decide *how* to fix it.
    *   **Manager Decision Required (You):** Assign ownership when the issue spans multiple domains (e.g., an API gateway timeout affecting both Network and App). You must decide which team owns the *integration contract* and the *end-to-end reliability metric*. Do not let teams negotiate this; assign based on which team controls the failure boundary.
3.  **Consensus Check:** Review action items with leads. If deadlock occurs on a systemic issue, invoke the "Bus Factor" rule: assign to the team with the most context, but require a joint design review before implementation.

#### Phase 4: Finalization (Hours 48–72)
1.  **Draft Report:** Compile findings, root cause, and action items with owners and deadlines.
2.  **Stakeholder Review:** Circulate to department heads for sign-off.
3.  **Client Delivery:** Submit the finalized report to enterprise clients.

**Critical Decisions for You to Make:**
*   **Integration Boundaries:** When Network and App blame each other on interface failures, you must assign the "Integration Owner" responsible for the end-to-end handshake.
*   **Resource Allocation:** If a systemic fix requires pausing feature work, you must authorize the trade-off.
*   **Timeline Enforcement:** If consensus isn't reached in the joint session, you must unilaterally assign tentative owners with a 24-hour appeal window to keep the 72-hour clock moving.

**Next Concrete Steps:**

2.  Draft the Master Chronology template and populate it with your known timeline.
3.  Send calendar invites for the pre-meetings and the joint session.
