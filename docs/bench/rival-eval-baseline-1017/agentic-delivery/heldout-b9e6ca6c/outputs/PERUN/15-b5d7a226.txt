### Implementation Plan: ISO 8601 Date Migration with Mitigation

**Strategy:** Feature-flagged dual-format output with per-customer override, phased rollout, and automated parser validation.

#### 1. Implementation Approach
*   **Feature Flag:** Introduce a configuration flag `export.date.format.iso8601` (default: `false`) in `src/export_generator.java`.
*   **Dual-Format Logic:**
    *   If flag is `false`: Output `MM/DD/YYYY` (legacy).
    *   If flag is `true`: Output `YYYY-MM-DD` (ISO 8601).
*   **Customer Override:** Add a `date_format` column to the customer configuration table. Values: `legacy`, `iso`, or `auto`.
    *   `auto`: Uses the global flag (for gradual migration).
    *   `legacy`/`iso`: Forces specific format regardless of global flag.
*   **Code Changes:**
    *   Modify `src/export_generator.java` to read customer config and apply formatting logic.
    *   Ensure no hardcoded date strings remain; all formatting goes through a dedicated `DateFormatter` utility class.

#### 2. Verification Plan (Linda's Requirement)
*   **Test Harness:** Create `src/test/resources/parser-samples/` containing 50 realistic CSV snippets representing the diverse parser logic of active customers.
*   **Validation Suite:**
    *   Write a JUnit test `CustomerParserValidationTest.java` that:
        1.  Generates exports in both formats.
        2.  Feeds each format into the 50 sample parsers (simulated via regex/substring checks or actual parser stubs).
        3.  Flags any parser that fails to extract a valid date from the ISO format.
    *   **Gate:** The build fails (`mvn test`) if >0 parsers break on ISO format without an explicit override mapping.
*   **Manual Review:** Customer Success validates the 200 at-risk customers against the test results to assign `legacy` overrides where needed.

#### 3. Monitoring & Detection
*   **Server-Side Logging:** Log a `WARN` event whenever a customer downloads a CSV with `date_format=auto` while the global flag is `true`. Include `customer_id` and `format_used`.
*   **Client-Side Feedback Loop:**
    *   Add a hidden "validation endpoint" or email hook: Customers can upload a sample parsed row; our system confirms if dates were interpreted correctly.
    *   Monitor support tickets for keywords "date error", "import failed", "CSV parse" post-deployment.
*   **Automated Alert:** If error rate on import-related support tickets spikes >5% above baseline within 24 hours of a phase change, trigger an PagerDuty alert.

#### 4. Rollout Schedule (2 Weeks)
*   **Days 1-3:** Implement feature flag, dual-format logic, and test harness. Run `mvn test` to identify breaking parsers.
*   **Days 4-5:** Customer Success assigns `legacy` overrides to the ~200 at-risk customers based on test results.
*   **Day 6:** Deploy code (flag remains `false`). Verify no regression in legacy exports.
*   **Day 7:** Enable ISO format for 5% of low-risk customers (those with `auto` and passing tests). Monitor for 48 hours.
*   **Day 10:** Expand to 50% of remaining `auto` customers.
*   **Day 12:** Expand to 100% of `auto` customers.
*   **Day 14:** Deadline. If no critical incidents, keep global flag `true`. If issues persist, revert flag to `false` immediately.

#### 5. Rollback Procedure
*   **Immediate Action:** Set `export.date.format.iso8601` to `false` in production config. All `auto` customers instantly revert to `MM/DD/YYYY`.
*   **Communication:** Notify affected customers of temporary reversion and revised timeline.
*   **Post-Mortem:** Analyze logs to identify uncaught parser failures; update override list before retrying.

This plan ensures zero breaking changes for known at-risk customers while enabling a safe, measurable migration for the rest.

*Note: Requires database migration script for the new `date_format` column. Ensure config service supports hot-reloading the feature flag.*
