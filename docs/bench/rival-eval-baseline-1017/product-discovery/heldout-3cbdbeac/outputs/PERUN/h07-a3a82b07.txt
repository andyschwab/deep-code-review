### Q3 Discovery Roadmap Draft: Employee Directory

**Objective:** Validate whether high-frequency support tickets represent critical workflow blockers or minor annoyances before committing engineering resources.

**Priority 1: Search Functionality (40 Tickets)**
*   **Hypothesis:** Search failures are preventing users from completing core tasks (e.g., contacting colleagues, finding org charts), not just causing frustration.
*   **Discovery Action:** Conduct 5 "Switch Interviews" with users who filed search tickets.
    *   *Ask:* "Walk me through the last time you used search. What specific task were you trying to finish? What did you do when search failed?"
    *   *Metric to Define:* % of search failures that force a manual workaround (e.g., calling IT, asking a manager).
*   **Decision Rule:** If >60% of interviewed users abandoned their task or required a manual workaround, prioritize a full search refactor. If <20%, treat as a UI polish item.

**Priority 2: Profile Photo Uploads (30 Tickets)**
*   **Hypothesis:** Upload failures are blocking new hire onboarding or compliance requirements, creating high anxiety despite low "urgent" tagging.
*   **Discovery Action:** Analyze the *timing* and *user role* of the 30 tickets.
    *   *Ask:* Correlate tickets with new hire start dates. Interview 3 users who failed to upload. "What happens if your photo isn't up by Friday? Who notices?"
    *   *Metric to Define:* Correlation between upload failure and onboarding delay days.
*   **Decision Rule:** If failures delay official badge issuance or system access by >24 hours, this is a viability risk. If it only affects aesthetic completeness, deprioritize.

**Priority 3: Minor UI Glitches (80 Tickets)**
*   **Hypothesis:** These 80 scattered tickets may indicate a systemic usability debt that erodes trust, even if no single glitch is a blocker.
*   **Discovery Action:** Cluster the 80 tickets by specific component (e.g., mobile view, specific browser, filter menu).
    *   *Ask:* Do these glitches occur in the same user journey step?
    *   *Metric to Define:* Frequency of glitches per active user session.
*   **Decision Rule:** If glitches cluster in one high-traffic flow (e.g., mobile directory view), bundle them into a "Stability Sprint." If truly scattered, log as known issues but do not build a dedicated fix yet.

**Immediate Next Steps (Before Engineering Starts):**
1.  **Run the Riskiest Assumption Test:** Assume Search is the biggest problem. The cheapest test is to observe 5 users attempting the top 3 search tasks recorded in tickets. If they succeed via workarounds without stopping work, the assumption is false.
2.  **Define "Urgent":** The lack of "urgent" tags suggests users have adapted. Discovery must reveal if they have adapted *well* (workarounds) or *poorly* (giving up).

**Non-Goals for This Quarter:**
*   Refactoring the entire directory backend until a specific behavioral blocker is proven.
*   Fixing all 80 UI glitches individually; they will be addressed only if clustered into a single high-impact pattern.

---
*Note: This plan relies on behavioral evidence (what users did) rather than stated intent. Do not proceed to build until the "Decision Rules" above are met with real data.*
*Engineering effort is withheld until the "Riskiest Assumption Test" confirms that fixing search actually moves the needle on task completion.*
