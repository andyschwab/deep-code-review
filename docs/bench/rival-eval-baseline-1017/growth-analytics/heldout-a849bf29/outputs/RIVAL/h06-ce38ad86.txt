# FitPulse Launch Instrumentation Plan (v1.0)

**Objective:** Capture critical behavioral data for the core loop and social friction points to inform immediate post-launch optimization without requiring a code update.

**Priority 1: Day One Essentials (Must Ship)**
These events answer the highest-risk unknowns regarding engagement and social friction. Implement these immediately.

| Event Name | Trigger Point | Essential Properties | Decision Informing |
| :--- | :--- | :--- | :|
| `app_opened` | App comes to foreground | `source` (utm), `user_type` (new/returning) | Acquisition quality & retention baseline |
| `onboarding_step_viewed` | Screen appears | `step_name`, `step_number` | Identify drop-off in setup flow |
| `onboarding_step_completed` | Step finished | `step_name`, `time_spent` | Friction in initial configuration |
| `workout_started` | "Start" button tapped | `workout_type`, `entry_point` | Feature adoption & entry paths |
| `workout_completed` | "Finish" button tapped | `workout_type`, `duration_sec`, `calories` | Core loop completion rate |
| `workout_abandoned` | Exit before finish | `workout_type`, `progress_percent` | **Critical:** Where users quit logging |
| `progress_viewed` | Dashboard/Stats screen loaded | `view_type` (daily/weekly), `has_data` (bool) | Value realization frequency |
| `share_initiated` | Share button tapped | `platform` (iOS/Android native), `context` (post-workout/profile) | **Critical:** Intent to share social features |
| `share_completed` | OS share sheet confirms send | `platform`, `context` | **Critical:** Actual social conversion vs. intent |
| `error_encountered` | App catch-all for non-crash errors | `error_code`, `screen_name`, `action_attempted` | Hidden friction points not causing crashes |

**Priority 2: Deferred (Post-Launch Release)**
These provide nuance but are not required to answer "Is the product working?" or "Where is the bleeding?" in week one. Add these in the v1.1 update.

*   `button_clicked` (Generic): Too noisy; track specific CTAs instead.
*   `scroll_depth`: Low priority for a widget-focused app initially.
*   `settings_changed`: Unless it breaks the flow, analyze later.
*   `notification_permission_requested`: Can be inferred from system logs initially.
*   `social_feed_viewed`: Secondary to the act of sharing; validate if users even reach the feed later.

**Implementation Notes for Engineering:**
*   **Naming Convention:** Use `object_action` format (lowercase, underscores) as shown above.
*   **User Identity:** Ensure `user_id` is attached to every event immediately upon login/signup to enable cohort analysis.
*   **Timing:** Log timestamps in UTC. Calculate `time_spent` client-side where possible to reduce payload size.
*   **Validation:** Use DebugView (GA4) or equivalent to verify `share_initiated` vs. `share_completed` fires correctly on both iOS and Android before April 10.

**Why This Mix?**
Your assumption to focus only on the core loop is risky; the `share_initiated` vs. `share_completed` delta is the only way to detect if the social feature is broken or just unappealing without waiting for user complaints. The `workout_abandoned` event is equally critical to distinguish between users who skip logging versus those who try and fail.
