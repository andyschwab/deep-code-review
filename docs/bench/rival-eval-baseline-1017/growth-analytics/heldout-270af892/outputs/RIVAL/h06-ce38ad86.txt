# FitPulse Launch Instrumentation Plan (v1.0)

**Objective:** Capture critical behavioral data for the core loop and social friction points before the April 10 launch to enable immediate engagement analysis without waiting for code updates.

## 1. Core Loop Events (Priority: Critical)
*These events validate the primary value proposition. Without them, retention and engagement cannot be measured.*

| Event Name | Trigger Point | Essential Properties |
| :--- | :--- | :--- |
| `workout_started` | User initiates a new workout session | `workout_type` (e.g., running, lifting), `source` (home_screen, notification) |
| `workout_completed` | User finishes and saves a workout | `duration_seconds`, `workout_type`, `calories_estimated`, `has_gps_data` |
| `workout_abandoned` | User exits active workout screen without saving | `step_reached` (e.g., warmup, main_set), `duration_elapsed_seconds` |
| `progress_viewed` | User opens the progress/dashboard screen | `view_type` (weekly, monthly, all_time), `time_on_screen_seconds` |

**Why these matter:** Your assumption to focus only on "logging and viewing" is partially correct but incomplete without capturing *abandonment*. Tracking `workout_abandoned` is the only way to identify if users are struggling with the interface mid-workout. Distinguishing between `started` and `completed` allows you to calculate the core completion rate immediately.

## 2. Social & Friction Events (Priority: High)
*Your concern about missing social friction is valid. These events determine if social features are a growth lever or a distraction.*

| Event Name | Trigger Point | Essential Properties |
| :--- | :--- | :--- |
| `share_initiated` | User taps any "Share" button | `share_target` (instagram, stories, copy_link), `context` (post_workout, progress_milestone) |
| `share_completed` | OS share sheet confirms successful handoff | `share_target`, `time_to_complete_seconds` |
| `share_cancelled` | User closes the share sheet without action | `share_target`, `step_cancelled` (e.g., permission_denied, manual_close) |
| `invite_sent` | User successfully invites a friend | `method` (sms, email, link), `batch_size` (number of recipients) |

**Why these matter:** Tracking only `share_completed` hides friction. If you see high `share_initiated` but low `share_completed`, you have a UX or permission issue. If `share_cancelled` spikes at "permission_denied," you know exactly where the block is. This data is impossible to retroactively infer.

## 3. User Identity & Context (Priority: Critical)
*Ensure these properties attach to every event above.*

- `user_id`: Persistent unique ID (not email/PII).
- `account_status`: `free`, `trial`, `premium`.
- `app_version`: Crucial for debugging if issues arise post-launch.
- `device_os` & `os_version`: To isolate iOS vs. Android specific bugs.
- `days_since_install`: To segment new vs. returning behavior.

## Implementation Timeline & Phasing

### Phase 1: Must-Have for April 10 Launch
Implement the 8 events listed above. This covers the "unknowns" regarding core loop completion rates and social sharing friction. This set is small enough to be tested and approved within your one-week deployment window.

### Phase 2: Post-Launch (v1.1+)
Defer these until you have initial data and can prioritize based on actual usage patterns:
- Granular UI clicks (e.g., `button_clicked` on non-critical settings).
- Deep dive into specific workout sub-types unless they are distinct products.
- A/B test variant tracking (unless you are launching with an immediate experiment).
- Passive background sync events (unless critical for billing).

**Note:** Ensure your analytics tool (e.g., Mixpanel, Amplitude, GA4) is configured to treat `user_id` as the primary identifier before day one to avoid fragmented user profiles. Validate the `share_cancelled` event specifically, as OS-level share sheets often require custom implementation to detect cancellation.
