**Decision:** Proceed with a **Design-First, Data-Safe** strategy. Do not write automation code until the data migration path is proven safe. The single number driving this plan is **0% data loss tolerance**; any approach risking the 10-year archive is rejected regardless of the December 1st deadline.

**Figures:** 3,000 returns/week × 8 weeks (holiday surge) = 24,000 returns. Current staff (12) × ~250 returns/person/week (max sustainable manual rate) = 3,000 capacity. Gap: 21,000 returns unprocessed without automation. 48-hour window × 24 hours/day = 2 days max latency.

**Order of Operations**

**Phase 1: Design & Validation (Weeks 1–3)**
1.  **Data Integrity Proof:** Execute the immediate first step (detailed below) on a full copy of the archive.
2.  **Process Mapping:** Map the "happy path" and top 5 exception cases for returns against the new 48-hour policy.
3.  **Architecture Sign-off:** Define the integration points between the new automation engine and the legacy archive.
4.  **Pilot Simulation:** Run a shadow test processing last month's returns manually vs. the proposed logic to verify refund timing.

**Phase 2: Execution & Migration (Weeks 4–7)**
1.  **Safe Migration Build:** Develop the migration script with built-in checksums and rollback triggers.
2.  **Automation Development:** Code the workflow engine only after data safety is certified.
3.  **Parallel Run:** Process live returns manually while the system processes them in shadow mode for 7 days.
4.  **Cutover:** Switch to automated processing with a manual override team on standby.

**Required Approvals (Before Any Code Is Written)**
*   **Data Custodian Sign-off:** Formal acceptance of the data migration risk assessment and the specific rollback procedure.
*   **Compliance/Legal Sign-off:** Confirmation that the proposed 48-hour workflow logic meets the exact wording of the new consumer policy.
*   **Architecture Board Sign-off:** Approval of the technical design ensuring the legacy archive is read-only during the transition.

**Immediate First Step: The Data Integrity "Fire Drill"**
Do not touch the production archive yet. Immediately execute a **full binary copy** of the 10-year historical database to an isolated sandbox environment. Run a validation script that calculates a cryptographic hash (SHA-256) for every customer record and transaction ID in both the source and the copy. Compare the hashes. If even one bit differs, the migration tool or process is flawed. Only when the hash match is 100% do you proceed to test migration logic on this sandbox copy. This validates that your *method* of moving data is safe before you risk the actual asset.

**Halt Trigger:** If the sandbox hash comparison shows >0% mismatch, stop all planning and engage a specialized data recovery vendor before proceeding.
**Fallback Trigger:** If the design phase exceeds 3 weeks without a signed data safety certificate, revert to a temporary manual overtime plan for the holiday surge to ensure compliance, delaying full automation to Q1.

*Note: This plan prioritizes audit survival over speed; a fine for late refunds is recoverable, lost tax audit proofs are not.*
