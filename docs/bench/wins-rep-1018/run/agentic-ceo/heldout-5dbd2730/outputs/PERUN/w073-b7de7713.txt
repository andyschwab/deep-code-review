**Decision:** Halt all migration scripting immediately. The first and only action is to execute a full, immutable backup of the legacy system to write-once storage before any data movement logic is written or tested.

**Figures:** 12,000 files × ~2MB (estimated average record size with history) = ~24GB minimum data volume; Deadline: November 30th; Team: 6 personnel (4 data, 2 clinical). No mismatch detected in stated totals, but the timeline creates a high-risk compression for a 6-year data history migration.

**Safest Sequence of Operations:**
1.  **Immutable Backup:** Create a bit-for-bit copy of the legacy database to offline/write-once media. Verify checksums. This is the only recovery point if the "overwrite" risk materializes.
2.  **Staging Environment Clone:** Restore the backup to an isolated staging server that mirrors the new database schema. No production data is touched here.
3.  **Dry-Run Migration:** Execute the migration script against the staging clone. Intentionally test the "conflicting ID" scenario to verify the script *rejects* or *flags* conflicts rather than overwriting.
4.  **Automated Integrity Check:** Run a row-count comparison and hash validation between legacy and staging.
5.  **Clinical Liaison Sampling:** Your two liaisons manually verify a statistically significant sample of complex acupuncture records (e.g., multi-visit histories) in staging.
6.  **Medical Director Sign-off:** Only after steps 1–5 are successful does the Medical Director review the integrity report and grant access approval.
7.  **Production Cutover:** Execute the verified script on the live system during a maintenance window.

**Rationale for First Action:**
The stated risk is permanent overwrite without backup. No script can be considered "safe" until a restorable, immutable copy exists. If the migration script fails catastrophically at step 7, the project dies without the step 1 backup. All other planning is theoretical until the data is secured.

**Halt Trigger:** If the checksum of the immutable backup does not match the source legacy system exactly, stop. Do not proceed to staging.
**Fallback Trigger:** If the dry-run migration shows *any* overwritten records (instead of rejections/flags) on November 25th, revert to the legacy system and engage a professional data forensics team; do not attempt to patch the script again internally.

*Note: This plan assumes the legacy system allows for full export/backup capabilities which must be verified immediately. Legal compliance regarding patient data transfer should be confirmed by counsel before the final cutover.*
