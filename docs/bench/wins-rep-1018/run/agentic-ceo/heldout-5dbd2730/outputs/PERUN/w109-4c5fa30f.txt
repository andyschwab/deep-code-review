**Decision:** Start with a **read-only integration sandbox and fallback dry-run** before any data mapping or UI work; this is the only path that de-risks the October 20 migration without endangering live manifests. The single number driving this is **12 hours**: the maximum allowable outage window, which dictates that zero live writes occur until the fallback mechanism is proven.

**Figures:** 45 days total minus 20 days for stabilization/testing leaves 25 days for build; 6 engineers divided into 2 teams (Integration vs. Product) yields 3 engineers per lane; 1 bad update could cost 20 clients × 12 hours = 240 client-hours of delay, valued at approximately $120k–$500k depending on SLA penalties (assumed $5k–$20k/hr impact).

**Phase Sequence & Delegation:**
1.  **Days 1–5 (Critical Path): Integration Safety & Fallback.**
    *   *Action:* Build a read-only adapter against a cloned terminal OS environment. Implement the "circuit breaker" that instantly reverts to the legacy manual/CSV process if latency >2s or error rate >1%.
    *   *Owner:* Senior Backend Engineer (Lead).
    *   *Deliverable:* A verified "kill switch" demo.
2.  **Days 6–20: Core Data Pipeline & Mapping.**
    *   *Action:* Map terminal data fields to dashboard metrics. Ingest historical data only.
    *   *Owner:* 2 Backend Engineers + 1 Data Engineer.
    *   *Deliverable:* Clean data stream in staging.
3.  **Days 10–30: Dashboard UI & Alerting.**
    *   *Action:* Build visualization layers and threshold alerts.
    *   *Owner:* 2 Frontend Engineers + 1 Full-stack.
    *   *Deliverable:* Internal beta dashboard.
4.  **Days 31–40: User Acceptance Testing (UAT) & Dry Runs.**
    *   *Action:* Top 5 clients validate data accuracy; run full migration simulation including forced failure.
    *   *Owner:* Product Lead + QA.
    *   *Deliverable:* Signed UAT and "Go/No-Go" report.
5.  **Days 41–45: Hardening & Launch Prep.**
    *   *Action:* Freeze code, load test, prepare rollback scripts.
    *   *Owner:* All Hands.
    *   *Deliverable:* Production release candidate.

**Decisions Required From You (Owner):**
1.  **Fallback Trigger Threshold:** Define the exact metric that triggers the revert (e.g., "If 3 consecutive API calls fail" or "If data freshness lag exceeds 15 minutes"). Do not leave this to engineering judgment during a crisis.
2.  **Manual Process Owner:** Name the specific individual responsible for executing the manual CSV entry fallback if the system locks. This must be a person, not a team.
3.  **Scope Cut Line:** Identify the one non-essential feature (e.g., "predictive analytics" or "mobile view") you will cut immediately if the integration takes longer than 10 days.

**Immediate Kickoff Actions (Day 1):**
*   **Engineering Lead:** Spin up an isolated sandbox environment mirroring the terminal OS; do not connect to production.
*   **Product Lead:** Draft the "Failure Protocol" document detailing the manual fallback steps for the top 20 clients.
*   **You:** Send a written mandate to the team stating: "No code touches the live terminal OS until the fallback dry-run succeeds on October 10."

**Halt Trigger:** If the sandbox integration cannot achieve 99.9% read stability by October 1, halt all UI work and shift 100% of engineering to stabilizing the data pipe.
**Fallback Trigger:** If the live migration on October 20 shows >1% error rate within the first hour, execute the manual fallback immediately; do not attempt to "fix live."

*Note: This plan assumes the terminal OS provides a documented sandbox API; if not, the timeline must extend or scope must reduce. Budget constraints require strict adherence to the scope cut line defined above.*
