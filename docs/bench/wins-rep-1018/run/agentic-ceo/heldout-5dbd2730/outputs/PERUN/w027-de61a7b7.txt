**Decision:** Pilot the update with ten providers immediately; defer the user communication plan until pilot data confirms risk levels; build the rollback script in parallel with the pilot setup. The single number driving this is **zero tolerance for simultaneous lockout** across 1,200 daily sessions.

**Figures:** 45 days remaining; 3,000 devices total; 10-device pilot (0.3% fleet); 1,200 daily sessions at risk if failed broadly. No mismatch detected; the pilot size is conservative enough to contain failure to <1% of daily volume.

### Sequence of Operations

**1. Immediate Build (Start Now, No Sign-off Required)**
*   **Action:** Engineering squad splits into two pairs. Pair A constructs the **real-time rollback script** capable of reverting keys within 60 seconds of a failed handshake. Pair B provisions the **isolated pilot environment** for the ten closed providers.
*   **Constraint:** The rollback script must be tested against a simulated "bad key" injection before the pilot begins.
*   **Rationale:** You cannot pilot safely without a verified escape hatch. This is the technical floor.

**2. Strategic Sign-off (Required from CTO Before Pilot Launch)**
*   **Action:** You must approve the **Pilot Success/Fail Criteria**. Specifically: Define the exact error rate threshold (e.g., >0% lockout) that triggers an immediate global halt versus a script fix.
*   **Action:** You must authorize the **List of Ten Pilot Providers**. These must be internal staff or highly resilient partners who can tolerate a scheduled 1-hour downtime for a physical reset if the script fails.
*   **Rationale:** This transfers the "go/no-go" decision from an emotional moment during the crisis to a pre-agreed logical gate.

**3. Execution Phase 1: The Pilot (Days 1–5)**
*   **Action:** Deploy encryption layer to the ten providers. Monitor handshake latency and key rotation success in real-time.
*   **Contingency:** If a lockout occurs, execute the rollback script. If the script fails, perform physical reset on the ten devices.
*   **Output:** A binary result: "Mechanism Stable" or "Mechanism Flawed."

**4. Execution Phase 2: Scaled Rollout or Pivot (Day 6+)**
*   **If Stable:** Begin phased rollout (10% of fleet per week). *Now* draft the user communication plan for scheduled maintenance windows.
*   **If Flawed:** Halt all deployment. Re-architect the key delivery mechanism. Communicate delay to stakeholders immediately.

### Why This Sequence?
Starting with the communication plan is premature optimism; you do not yet know if the update is safe to send. Starting with a broad rollout ignores the catastrophic failure mode of locking out hundreds of patients simultaneously. The pilot provides the evidence needed to write an honest communication plan and validates the rollback script under real network conditions.

**Halt Trigger:** If the pilot results in >0 permanent lockouts requiring physical reset, stop all deployment immediately. Date: End of Day 5. Action: Re-architect key delivery.
**Fallback Trigger:** If the rollback script takes >5 minutes to execute during pilot testing, halt deployment. Date: End of Day 3. Action: Manual intervention protocol required before any further automation.

*Note: Do not draft general downtime notices until the pilot proves the update mechanism's stability. Your sign-off on the specific pilot participants is the only bottleneck before engineering starts.*
