### Session Roadmap: Green Valley Hospital AI Scheduler Migration

**Phase 1: Data Audit & Cleansing (Immediate Start)**
Before any migration or training, the current manual data must be audited. This is the only phase where you (the stakeholder) must make direct decisions regarding rule exceptions.
**Phase 2: Constraint Definition & Algorithm Configuration**
Once data is clean, architects configure the AI optimizer with hard constraints (rooms, times) and soft constraints (preferences).
**Phase 3: Dry-Run Migration & Validation**
Architects execute a non-destructive import of cleaned data into a sandbox environment to verify constraint logic.
**Phase 4: User Acceptance Testing (UAT)**
Surgeons and schedulers validate the optimized output against real-world scenarios.
**Phase 5: Final Migration & Cutover**
Execution of the irreversible live migration, scheduled to complete well before the Monday 8 AM deadline.

---

### Decision Matrix: Stakeholder vs. Architects

**Requires Your Direct Decision:**
*   **Conflict Resolution Rules:** Define priority when two surgeons request the same room (e.g., emergency vs. elective, seniority, or procedure duration).
*   **Exception Handling:** Determine how to handle historical data anomalies (e.g., past double-bookings that were manually resolved but not recorded).
*   **Optimization Weighting:** Decide the balance between maximizing room utilization (targeting 50 procedures) versus minimizing surgeon idle time.
*   **Fallback Protocols:** Approve the manual revert plan if the AI output fails UAT validation.

**Executable by System Architects:**
*   **Data Extraction:** Pulling raw calendar logs and surgeon availability records from the legacy system.
*   **Schema Mapping:** Translating legacy data fields to the new AI optimizer's input format.
*   **Algorithm Training:** Feeding cleaned historical data into the model to learn typical procedure durations and turnover times.
*   **Integration Scripting:** Building the API connectors between the AI optimizer and the hospital's notification system.
*   **Sandbox Deployment:** Setting up the test environment for the dry-run migration.

---

### Immediate Actions: Data Audit Protocol

To prevent irreversible double-booking risks, perform these specific actions immediately to audit the current calendar data:

1.  **Cross-Reference Surgeon Rosters:** Compare the current manual surgeon availability list against HR duty rosters for the upcoming week. Flag any discrepancies where a surgeon is marked "available" in the schedule but "on leave" in HR records.
2.  **Operating Room Block Verification:** Manually verify every blocked time slot in the current system against physical room maintenance logs. Ensure no blocks exist for rooms scheduled for repair or deep cleaning.
3.  **Procedure Duration Variance Analysis:** Extract the last three months of procedure data. Calculate the variance between *scheduled* duration and *actual* duration for each procedure type. Identify outliers where manual scheduling consistently underestimates time, as these are high-risk candidates for AI misinterpretation.
4.  **Ghost Booking Scan:** Run a query to identify any time slots marked as "occupied" without an associated patient ID or procedure code. These orphaned blocks must be cleared or validated before import.
5.  **Constraint Logic Stress Test:** Select a single day with maximum historical load (40+ procedures) and manually map the constraints. Attempt to fit these into the proposed 50-procedure model logically to identify immediate physical impossibilities before algorithmic training begins.

**Note:** Do not proceed to algorithm training until the "Ghost Booking Scan" and "Cross-Reference" steps yield zero unresolved conflicts.
**Note:** The 8 AM Monday deadline requires the Final Migration to be completed by Sunday 6 PM to allow a 14-hour buffer for emergency manual overrides.
