### IronRail Intermodal Migration Planning Session Flow

**Phase 1: Data Baseline & Shadow Mode (Weeks 1–4)**
1.  **Extract Legacy Snapshot:** Immediately trigger the single daily export from the legacy interface. Store this as the "Golden Record" for Day 0.
2.  **Parallel Ingestion:** Load the Day 0 snapshot into the new platform in read-only mode.
3.  **Shadow Calculation:** For the next 21 days, run the new platform's scheduling engine in parallel with the live legacy system using daily exports. Do not execute schedules; only compare slot availability calculations.
4.  **Discrepancy Logging:** Automate a report highlighting any variance between legacy and new platform slot calculations. Zero variance is the mandatory gate to proceed.

**Phase 2: Dry-Run & Stress Testing (Weeks 5–7)**
1.  **Historical Replay:** Ingest data from peak traffic days in the previous year to test system load against the 400-train daily volume.
2.  **Failure Simulation:** Manually inject data errors to verify if the new platform fails safely (blocking bad data) or calculates incorrectly (the irreversible risk).
3.  **Rollback Rehearsal:** Execute a mock cutover and immediate rollback using a non-production environment to measure the time required to revert to the legacy state.

**Phase 3: The Cutover Window (Weeks 8–9)**
1.  **Final Baseline:** Take the final daily export 48 hours before the August 10th hard stop.
2.  **Freeze Window:** Halt all manual schedule changes in the legacy system.
3.  **Validation Gate:** Confirm the final data load matches the shadow mode results exactly.
4.  **Go/No-Go Decision:** Based on the validation gate, authorize the switch.
5.  **Live Activation:** Enable the new platform for live scheduling.
6.  **Hyper-Care Monitoring:** Assign all ten engineering members to monitor the first 24 hours of live calculations against manual spot-checks.

**Critical Decisions Required: Rollback Strategy**
You must define the "Point of No Return" and the specific mechanism for reversion. Since you cannot easily roll back without canceling shipments, you must decide:
*   **The Trigger Threshold:** What specific error rate (e.g., >0% slot miscalculation) immediately triggers a rollback?
*   **The Fallback State:** If the new platform fails, do you revert to the last known good legacy snapshot (losing up to 24 hours of manual adjustments) or attempt a manual patch? Given the risk, the strategy must prioritize reverting to the legacy system immediately upon any critical calculation failure, accepting the loss of recent manual tweaks to prevent cascading network delays.

**First Concrete Step**
Initiate the first daily data export from the legacy interface today and load it into the new platform's isolated staging environment to establish the initial baseline for shadow comparison. Do not alter any live schedules until this data pipeline is verified.

*Note: This plan assumes the 24-hour export limitation is the primary bottleneck; any delay in starting the shadow phase directly reduces your validation window before the August 10th deadline.*
