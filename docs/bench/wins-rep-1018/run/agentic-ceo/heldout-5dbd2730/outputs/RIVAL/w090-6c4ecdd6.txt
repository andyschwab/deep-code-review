**SwiftRide Transport Migration Strategy Workflow**

**Phase 1: Sandbox Validation (Immediate – Feb 10)**
1.  **Data Extraction & Conversion:** Run the custom conversion script on a full copy of the production database within an isolated sandbox environment.
2.  **Automated Integrity Check:** Execute a script to compare record counts and total shift hours between the legacy export and the new platform's imported data.
3.  **Conflict Simulation:** Deliberately introduce known edge cases (e.g., split shifts, overtime overlaps) to verify the new system's handling logic.
4.  **Parallel Dry Run:** Generate a mock roster for a single day in the new system and compare it manually against the legacy output for 10 randomly selected drivers.

**Phase 2: Contingency Planning & Approval (Feb 11 – Feb 14)**
*CEO Approval Required:*
*   **The "Hard Stop" Rollback Plan:** A definitive procedure to revert to the legacy system within 30 minutes if critical errors appear post-migration. This includes maintaining the legacy server in read/write mode until Feb 25.
*   **Manual Override Protocol:** Authorization for dispatch managers to manually assign shifts via a temporary spreadsheet interface if the new platform experiences latency or data visibility issues during the first 48 hours.
*   **Communication Cascade:** Pre-drafted notifications to drivers regarding potential app downtime or schedule refresh delays.

*IT Lead Authority (No CEO Approval Needed):*
*   **Script Logic Adjustments:** Modifying the conversion script to fix formatting errors discovered during sandbox testing.
*   **Database Indexing:** Optimizing the new database for query speed prior to go-live.
*   **Access Control Configuration:** Setting up user permissions for drivers and dispatchers in the new environment.

**Phase 3: Pre-Live Verification (Feb 15 – Feb 19)**
1.  **Final Data Freeze:** Lock the legacy system to prevent new schedule changes.
2.  **Final Conversion Run:** Execute the conversion script on the frozen data set.
3.  **The Golden Record Audit:** A line-by-line verification of a statistically significant sample (5% of drivers, ensuring coverage of all shift types).
4.  **Sign-off:** IT Lead and Operations Director sign off on the "Golden Record" audit results.

**Phase 4: Live Implementation (Feb 20)**
1.  **Final Backup:** Create a full snapshot of the legacy database immediately before the swap.
2.  **Data Swap:** Import the verified converted data into the production instance of the new platform.
3.  **Real-Time Monitoring:** IT team monitors system logs for import errors while Operations verifies the dashboard displays the correct total shift count.
4.  **Go/No-Go Decision:** Based on the real-time monitor, either open the system to drivers or execute the CEO-approved Rollback Plan.

**First Specific Verification Task**
Before touching the live environment, the first specific verification task is to perform a **cryptographic hash comparison of the total shift minutes and unique shift IDs** between the raw legacy export file and the output of the conversion script. This mathematical proof ensures that not a single minute of labor has been lost or duplicated during the format translation, serving as the foundational gate before any visual or functional testing occurs.

*Note: Ensure the legacy system remains accessible in read-only mode for at least five days post-migration for dispute resolution.*
*The success of this migration relies entirely on the rigidity of the "Hard Stop" rollback timeline.*
