**Emergency Work Session Structure: Northwind Trading Exchange Connector**

**Strategic Direction**
Do **not** begin with root cause analysis (RCA) yet, and do **not** jump straight to writing the rollback script in isolation. The immediate priority is **Stabilization and Safe-Recovery Preparation**. You must first secure the "undo" capability before attempting any diagnostic deep-dive or code changes. If the patch fails, the rollback script is your only lifeline to meet the 08:00 UTC deadline. Therefore, the sequence starts with validating the rollback path, followed by a time-boxed RCA, then the fix, and finally a rigorous review.

**Operational Sequence**

1.  **Phase 1: Safety Net Construction (Hours 0–1)**
    *   **Action:** Three Site Reliability Engineers (SREs) must immediately verify the current production state and draft/validate the rollback script to revert the connector to the last known stable version.
    *   **Goal:** Ensure that if the patch deployment fails, you can restore operations within minutes, not hours.
    *   **Sign-off Required:** You must approve the rollback script logic and the specific trigger conditions for its execution before any patch code is touched.

2.  **Phase 2: Time-Boxed Root Cause Analysis (Hours 1–3)**
    *   **Action:** Four Quantitative Developers, aided by one SRE, perform a focused RCA on the latency bug. This is strictly limited to identifying the specific code path causing slippage.
    *   **Constraint:** If the cause is not identified within 2 hours, escalate to a "blind" revert to the previous stable version and reassess (sacrificing the fix to save the deadline).
    *   **Sign-off Required:** You must approve the identified root cause and the proposed code fix strategy before coding begins.

3.  **Phase 3: Patch Development & Isolated Testing (Hours 3–6)**
    *   **Action:** Developers implement the fix in an isolated environment. SREs simulate the load to verify latency is resolved and no new regressions exist.
    *   **Goal:** A verified binary/package ready for deployment.

4.  **Phase 4: Staged Review & Deployment Prep (Hours 6–7)**
    *   **Action:** Joint review of the patch and the final deployment runbook. Dry-run the deployment steps in a staging environment.
    *   **Sign-off Required:** **Final Go/No-Go Decision.** You must explicitly authorize the production deployment based on the test results and the verified rollback plan.

5.  **Phase 5: Deployment & Monitoring (Hours 7–8)**
    *   **Action:** Deploy patch during the pre-market window. Monitor closely. If anomalies occur, execute the pre-approved rollback immediately.
    *   **Goal:** Algorithms unfrozen and operational by 08:00 UTC.

**Decision Matrix for Lead Engineer Sign-off**
You are required to provide explicit approval at these three critical gates:
1.  **Rollback Validity:** Confirmation that the rollback script is tested and ready to execute.
2.  **Fix Strategy:** Confirmation that the proposed code change addresses the RCA findings without introducing high-risk side effects.
3.  **Final Deployment:** The absolute "Go" command to push to production.

**First Immediate Task**
**Assign the three SREs to validate and finalize the rollback script immediately.** Do not allow developers to start debugging until the SREs confirm that a safe, tested path exists to revert the system to its pre-freeze state. This ensures that even if the patch introduces a catastrophic error triggering the circuit breaker, you can bypass the lockout by reverting quickly, securing your ability to trade at 08:00 UTC.

*Note: Strict time-boxing of the RCA phase is essential to prevent missing the market open.*
*Note: Communication channels should be restricted to war-room only to prevent distraction.*
