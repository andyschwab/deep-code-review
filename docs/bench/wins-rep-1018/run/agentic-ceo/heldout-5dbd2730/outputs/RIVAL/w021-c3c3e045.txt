### Work Session Structure: Metro City EMS Dispatch Transition

**Objective:** Safely activate the new routing algorithm between 4 PM and 7 PM to reduce response times from 18 minutes, utilizing three senior developers without the ability to revert easily.

#### 1. Precise Sequence of Validation Steps (Pre-4 PM Deadline)
To mitigate the critical risk of irreversible activation, execute these validations in strict order:
1.  **Static Logic Verification:** Confirm the new algorithm correctly prioritizes traffic density data against historical maps without live input.
2.  **Shadow Mode Simulation:** Run the new algorithm in parallel with the current live system for 2 hours (e.g., 1 PM–3 PM) using real-time data feeds but *without* sending commands to vehicles. Compare proposed routes against actual dispatched routes.
3.  **Fail-Safe Trigger Test:** Manually simulate a "critical failure" in the test environment to verify the team can halt the deployment script before it commits destination changes to the vehicle fleet.
4.  **Staged Rollout Dry-Run:** Execute a deployment to a single, isolated test vehicle (or a digital twin representing one unit) to confirm the manual reset procedure works as documented, ensuring the "chaos" scenario is theoretically preventable.
5.  **Go/No-Go Gate:** At 3:45 PM, review Shadow Mode discrepancy reports. If variance in route efficiency is >5% or safety flags exist, abort immediately.

#### 2. Data Analysis Responsibilities
**You (Requester) Must Review:**
*   **The "Chaos" Threshold Metrics:** Define the specific KPIs (e.g., maximum allowable route deviation, minimum safety buffer) that constitute a failed deployment. You must sign off on the risk tolerance level.
*   **Shadow Mode Discrepancy Report:** A high-level summary comparing the old vs. new system's proposed routes during the simulation window. Look for outliers where the new system suggests dangerously long or illogical paths.

**Developers Must Handle:**
*   **Raw Traffic Data Ingestion:** Verifying the integrity of the live traffic feed inputs.
*   **Algorithm Performance Logs:** Analyzing latency and computational load to ensure the system doesn't crash under peak load.
*   **Route Calculation Deltas:** Detailed statistical comparison of every proposed route in the shadow simulation to identify edge cases.

#### 3. First Three Concrete Actions (Execute Immediately)
1.  **Isolate the Downtown Sector Digital Twin:** Instantiate a virtual environment mirroring current downtown traffic conditions. Load the new routing logic into this sandbox and inject a simulated surge of 50 concurrent dispatch requests to observe if the algorithm creates circular routing or gridlock patterns.
2.  **Hard-Code the "Kill Switch" Protocol:** Before writing any new deployment code, the three developers must jointly write and test the specific command sequence that freezes all outgoing dispatch updates. This ensures that if the new logic causes gridlock, the team can stop the bleed instantly, even if they cannot revert routes.
3.  **Execute a "Paper" Walkthrough of the Manual Reset:** Since technical reversion is impossible, physically walk through the manual reset protocol with the team. Assign one developer to draft the exact communication script and step-by-step instructions that field operators would need to manually reset vehicle destinations should the system fail, ensuring this contingency plan is ready before code is touched.

**Note:** The inability to revert technically makes the "Kill Switch" (Action #2) your primary safety mechanism; prioritize its reliability over feature completeness.
**Note:** Ensure the Shadow Mode (Validation Step #2) uses actual live data from the current peak hour to ensure simulation fidelity.
