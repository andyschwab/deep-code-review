### Freight Bill Automation Work Session Plan

**Session Objective:** Define the safe path to automated auditing and payment to eliminate the $50k/month overpayment loss and prevent future close delays.

**1. Strategic Starting Point: Exception Rules First**
We must begin by **mapping exception rules**, not cleaning vendor master data.
*   **Reasoning:** You cannot effectively clean 3,000 historical bills or define "clean" status without first establishing the logic that defines an error. Cleaning vendor data in a vacuum risks fixing fields that the automation won't even use. By defining the exception rules (e.g., rate mismatches, duplicate bills, weight discrepancies) first, we identify exactly which data fields are critical. This creates a targeted filter for the subsequent data cleaning effort, ensuring the accountants only fix data that impacts the algorithm's decision-making.

**2. Critical Auto-Payment Thresholds for Your Decision**
To mitigate the risk of irreversible incorrect payments, you must define these three thresholds before any code is finalized:
*   **The "Zero-Touch" Dollar Limit:** What is the maximum invoice amount eligible for instant auto-payment? (e.g., Any invoice under $500 with a perfect match score).
*   **The Confidence Score Floor:** What algorithmic confidence percentage is required to bypass human review? (e.g., 98% match certainty based on historical data).
*   **The Carrier Trust Tier:** Which carriers are eligible for auto-payment immediately? (Recommendation: Start only with carriers who have had zero disputes in the last 12 months, excluding all others from the initial auto-pay wave).

**3. Data Validation Tasks for the Accounting Team**
While engineers build the rule engine, the five accountants will execute the following validation tasks on the 3,000-item backlog:
*   **Ground Truth Labeling:** Manually audit a statistically significant sample (e.g., 300 bills) to label them as "True Positive," "False Positive," or "Exception." This dataset becomes the test bed for the algorithm.
*   **Exception Taxonomy Definition:** Categorize the root causes of the current 12% error rate into specific rules (e.g., "Fuel surcharge calculation error" vs. "Wrong mileage band").
*   **Vendor Master Spot-Check:** Validate only the specific data fields identified in the exception rule mapping phase (e.g., if the rule checks "Rate per Mile," accountants verify only that field for top 20 vendors).

**4. The Very First Action to Validate the Algorithm**
Before the next closing cycle, the immediate first action is to **run a "Shadow Mode" simulation on the 3,000 unmatched bills.**

In this mode, the algorithm processes the backlog and flags invoices as "Pay" or "Hold," but **no money moves**. The output is then compared line-by-line against the manual "Ground Truth" labels created by the accountants. We will calculate the simulated error rate. If the shadow run shows an error rate higher than 1%, the auto-payment feature remains disabled, and we refine the rules. Only when the shadow mode achieves a 0% error rate on the historical backlog do we enable auto-payment for new, incoming invoices under the defined thresholds.

***

*Note: This approach prioritizes risk mitigation by proving the logic on historical data before exposing live funds.*
*Ensure the data engineers prepare the sandbox environment for the shadow run immediately upon rule definition.*
