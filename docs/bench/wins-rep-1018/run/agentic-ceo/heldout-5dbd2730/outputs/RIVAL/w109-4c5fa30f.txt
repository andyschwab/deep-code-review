### Port Congestion Dashboard: Critical Path Plan

**Phase Sequence & Timeline (45 Days)**
1.  **Days 1–10: Architecture & Risk Mitigation (Current Priority)** – Define data schemas, establish fallback protocols, and build the "shadow" integration layer.
2.  **Days 11–25: Core Development** – Build the dashboard UI, real-time data ingestion pipeline, and internal testing harnesses.
3.  **Days 26–35: Integration & Staging** – Connect to the Terminal Operating System (TOS) in a isolated staging environment; simulate live traffic.
4.  **Days 36–40: User Acceptance Testing (UAT)** – Validate with key stakeholders from the top twenty clients' accounts.
5.  **Days 41–45: Hardening & Go-Live Prep** – Final security audit, load testing, and deployment rehearsal before the October 20 migration window.

**Immediate First Step: The "Shadow" Integration Layer**
To mitigate the risk of locking out shipping manifests, the team must first build a **read-only "shadow" connector** that mirrors data from the main TOS without writing back or altering state. This allows the team to validate data mapping and latency requirements against live feeds without any possibility of disrupting current operations. No code touching the write-API of the TOS should be written until this shadow layer proves stable.

**Decisions Required from You (Data Fallback Strategy)**
You must personally decide on the **trigger threshold and manual override protocol** for the fallback strategy. Specifically:
*   At what exact latency or error rate does the system automatically switch from the live TOS feed to the cached/static fallback data?
*   Who holds the authority to manually initiate the fallback during the October 20 migration, and what is the communication chain to notify the top twenty clients if this occurs?
*   Define the acceptable data "freshness" lag for the fallback mode (e.g., is 15-minute-old data acceptable, or must it be real-time?).

**Immediate Kickoff Actions for the Team**
*   **Engineers A & B (Integration Leads):** Map the TOS API schema against internal data requirements. Identify exactly which endpoints pose write-risks and flag them for strict access control.
*   **Engineers C & D (Backend):** Set up the isolated staging environment that mimics the production TOS response patterns. Begin constructing the shadow reader service.
*   **Engineers E & F (Frontend/UX):** Draft the dashboard wireframes focusing on "degraded mode" visualization, ensuring users clearly see when data is coming from the fallback source rather than live feeds.
*   **All Hands:** Conduct a "pre-mortem" workshop specifically focused on the October 20 migration scenario to list every possible failure point in the handover process.

**Delegation & Critical Path**
The critical path is strictly tied to the **TOS integration stability**. If the shadow layer fails to parse data correctly by Day 10, the entire timeline slips. Therefore, Engineers A and B are on the critical path; their output unblocks all other development. Engineers C and D support them by providing the test harness. Engineers E and F can work in parallel on UI components but must align their data models with the integration team daily.

Your role is to remove blockers for the integration leads and finalize the fallback policy within the first 48 hours so the team can code the logic immediately.

***

*Note: This plan assumes the current staff possesses the necessary domain knowledge of the specific TOS API; if not, documentation review must happen concurrently with Day 1 tasks.*
*Ensure the October 20 migration window has a confirmed "rollback" time agreed upon with the TOS provider before any code is deployed.*
