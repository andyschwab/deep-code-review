### Critical Work Session Structure (Next 8 Hours)

**Immediate Decision: Run a Pilot First**
Do **not** begin full extraction immediately. Given the high risk of corrupting historical trends via pain scale code mapping and the inability to roll back after the second batch, you must execute a pilot on 100 records first. This pilot will validate the mapping logic without jeopardizing the entire dataset.

**Timeline & Batch Strategy**
With an 8-hour window and a 90-minute cycle per batch, you can realistically complete **five full batches** (7.5 hours), leaving 30 minutes for final verification.
*   **Hour 0–1.5:** Pilot execution (100 records) and validation.
*   **Hour 1.5–7.5:** Five full production batches (~9,000 records each).
*   **Hour 7.5–8.0:** Final integrity check.

*Note: 45,000 records across 5 batches means ~9,000 records per batch. If the pilot reveals mapping errors, you must pause full extraction until the lead researcher returns at 4 PM, even if it risks the deadline. Data integrity is paramount for grant compliance.*

**Decisions You Must Make Right Now**
Before the pilot starts, define these two validation thresholds:
1.  **Pain Scale Mapping Tolerance:** What percentage of mismatched or unmapped pain codes in the pilot triggers a full stop? (Recommendation: >0% discrepancy requires immediate halt).
2.  **Record Completeness Threshold:** What percentage of missing fields in a batch is acceptable before rejecting the whole batch? (Recommendation: >1% missing critical fields requires rejection).

**Task Assignments for Junior Staff (While You Wait for the Researcher)**
Assign your two data analysts to the following parallel tasks:

*   **Analyst A (Preparation & Sanitization):**
    *   Isolate the 100-record pilot set ensuring it covers all known variations of legacy pain scale codes.
    *   Pre-scan the full 45,000 records for null values in critical fields (Patient ID, Date of Service, Outcome Score) to flag potential extraction failures.
    *   Prepare the logging template to track batch success/failure rates and specific error codes during migration.

*   **Analyst B (Documentation & Monitoring):**
    *   Draft the "Rollback Contingency Plan" detailing exactly which database tables would need manual truncation if the first batch fails (even though full rollback is impossible, partial cleanup may be needed).
    *   Set up the monitoring dashboard to track the 90-minute batch windows and alert you 5 minutes before each cycle completes.
    *   Compile a list of all unique legacy pain scale codes found in the dataset to present to the lead researcher upon their return at 4 PM.

**Execution Flow**
1.  **Start Pilot:** Run the 100-record batch immediately.
2.  **Validate:** Compare pilot output against your defined thresholds.
3.  **Branch:**
    *   *If Pass:* Begin Batch 1 immediately.
    *   *If Fail:* Halt all extraction. Use the remaining time to document errors for the lead researcher. Do not guess the mapping logic.

This approach maximizes your throughput while strictly mitigating the risk of irreversible data corruption.
