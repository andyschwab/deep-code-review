### Customs Automation Cutover Work Session Plan

**Session Objective:** Define testing phases, assign liability authority, and identify the critical pre-migration check to ensure zero-downtime cutover by next Friday at 5 PM.

**1. Testing Phases (48-Hour Window Strategy)**
Given the bottleneck (3 connections/minute) and volume (2,000/week), testing must be phased to validate throughput without triggering API bans or data corruption.
*   **Phase A: Connectivity & Rate Limit Validation (Hours 0–4):** Verify the application strictly adheres to the 3-requests-per-minute limit using a dummy account. Confirm error handling for "429 Too Many Requests" responses.
*   **Phase B: Data Integrity Sandbox (Hours 4–24):** Run a subset of 50 historical declarations (mixed complexity) for France, Germany, and Italy against the government sandbox. Validate that the API response matches expected clearance codes exactly.
*   **Phase C: Throughput Stress Test (Hours 24–36):** Simulate peak load (approx. 300 declarations) using the rate-limited queue. Measure total processing time to ensure the 2,000 weekly volume can be cleared within operational windows.
*   **Phase D: Rollback & Failover Drill (Hours 36–42):** Since manual submission is blocked post-switch, this phase verifies the *emergency pause* procedure. If the automator fails mid-stream, how do we stop the bleed immediately? (Note: True rollback to manual is impossible; the drill confirms we can halt the automated bleeder).
*   **Phase E: Final Go/No-Go Review (Hours 42–48):** Review logs from Phases A-D. Sign off required here.

**2. Liability Waivers & Authority Matrix**
*   **Requires Your Direct Sign-off (Executive Liability):**
    *   **The "Point of No Return" Authorization:** Formal approval to switch the live environment, acknowledging that manual submission will be permanently blocked for these shipments.
    *   **Financial Risk Acceptance:** Waiver accepting potential fines (€10k/day) should the automation fail post-cutover due to logic errors not caught in testing.
    *   **Data Sovereignty Confirmation:** Certification that the automation tool complies with GDPR when transmitting shipment data to the new government APIs.
*   **Team Handling (Operational Liability):**
    *   **Test Data Accuracy:** The compliance team certifies that the 50 sample declarations used in Phase B are error-free.
    *   **Monitoring Protocols:** The team owns the setup of alerts for failed submissions during the first 24 hours of live operation.
    *   **API Credential Management:** Secure storage and rotation of the three allowed connection tokens.

**3. The Single Most Critical Preliminary Check**
Before writing a single migration script, you must perform a **Live API Handshake Verification with a "Poison Pill" Test**.

You must execute a real-time connection to the *live* government API (not just the sandbox) using one valid credential to submit a deliberately malformed declaration designed to be rejected instantly.
*   **Why:** Sandboxes often differ from production in rate-limit enforcement, authentication token validity, and error code structures.
*   **Goal:** Confirm three things simultaneously: (1) Your network credentials actually work in production today; (2) The API returns the specific error code you expect for bad data (ensuring your parser won't crash); and (3) The 3-requests-per-minute limit is enforced exactly as documented on the live endpoint.
*   **Risk Mitigation:** If this check fails, no amount of script optimization will save the deadline. It prevents building a complex engine for a lock that has changed its shape.

**Note:** Schedule the session immediately to maximize the 48-hour window; any delay compresses the stress-testing phase. Ensure legal counsel reviews the "Point of No Return" waiver before the session ends.
