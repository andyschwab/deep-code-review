### Warehouse Robot Migration Work Session Plan

**Strategy: Limited Pilot First**
We will bypass shadow mode simulation. Given the irreversible schema change and the critical "no fallback" constraint, shadow mode cannot validate the actual database migration or the failure recovery path. We must execute a **Limited Pilot on five robots** in an isolated network segment that mirrors production data structures. This provides the only valid proof of the cutover procedure and rollback limits (even if rollback is impossible, we must prove we can safely halt without corrupting the remaining 45 robots).

**Phase 1: Preparation & Delegation (Days 1–10)**
*   **Junior Engineers (Delegated):**
    1.  **Data Sanitization Script:** Create a script to clone the production database, strip active order IDs, and generate a realistic "frozen" dataset for the pilot environment.
    2.  **Isolation Harness:** Build the network sandbox ensuring the 5 pilot robots cannot communicate with the 45 production robots or the live inventory system.
    3.  **Telemetry Dashboard:** Configure monitoring to track robot heartbeat, database lock times, and error rates specifically during the schema write phase.
*   **Senior Engineers (Legacy Experts):**
    1.  Define the exact "Point of No Return" in the migration script.
    2.  Document the manual override procedures to physically stop robots if software halts mid-cycle.

**Phase 2: The Limited Pilot (Days 11–17)**
*   Execute the full migration sequence on the 5-robot cluster.
*   **Success Criteria:** The schema change completes within 45 minutes (leaving buffer in the 4-hour window), and robots resume normal operation without data loss.
*   **Failure Protocol:** If the pilot fails, the team analyzes logs. No further attempts are made until a code fix is verified in the sandbox.

**Phase 3: Staging Rehearsal (Days 18–22)**
*   Run a "dry run" of the cutover script on the sandbox using the exact timing planned for October 25th.
*   Validate that the 8-person team can execute their specific roles within the time limit.

**Phase 4: Final Cutover (October 25th)**
*   **Hour 0–0.5:** Halt incoming orders; allow robots to finish current tasks.
*   **Hour 0.5–2.5:** Execute irreversible schema migration and software update on all 50 robots (staggered batches of 10 to manage network load).
*   **Hour 2.5–3.5:** System validation and sanity checks.
*   **Hour 3.5–4.0:** Decision gate: Go/No-Go for resuming operations.

**Contingency Plans Requiring Your Sign-off**
1.  **The "Hard Stop" Protocol:** Authorization to physically power down the entire fleet if the migration exceeds 3 hours, accepting a total operational halt for the day rather than risking data corruption.
2.  **Manual Operations Mode:** Approval to switch to 100% manual packing for 48 hours if the software migrates successfully but exhibits instability, requiring a patch deployment post-Q4 rush.
3.  **Data Loss Acceptance:** Explicit sign-off on the maximum acceptable number of "in-flight" orders that may be lost if the schema change aborts mid-transaction (must be defined as zero or a specific recoverable number).

**First Immediate Task**
Instruct the three legacy experts to map the exact database dependencies and calculate the precise write-time for the schema change on the current data volume. We must mathematically confirm the migration takes less than 3 hours before planning any further steps; if the write time exceeds this, the 4-hour window is impossible, and the strategy must change immediately.

*Note: This plan assumes the isolated pilot environment can be stood up within 48 hours. Any delay in sandbox preparation directly threatens the October 25th deadline.*
