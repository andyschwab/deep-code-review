### Assumption Evaluation: Rail Car Tracking Dashboard vs. Demurrage Reduction

**Core Hypothesis:** Building a real-time rail car tracking dashboard will reduce demurrage penalties by enabling proactive re-routing before fines are incurred.

**Critical Unknown:** The root cause of the six-hour average delay is unverified. It is unclear whether delays stem from external track congestion (uninfluencable by software) or internal communication gaps with rail providers (potentially solvable via better data).

#### Risk & Assumption Analysis

**1. Value Risk (High Uncertainty)**
*   **Assumption:** Better visibility directly translates to the ability to re-route cars and avoid fines.
*   **Challenge:** If the primary driver of the $45,000 in penalties is external track congestion rather than internal reaction time, a dashboard provides visibility but no lever for action. You cannot re-route a car stuck in a congested yard regardless of how accurately you predict its arrival.
*   **Verdict:** The link between "seeing the delay" and "fixing the delay" is broken if the bottleneck is external infrastructure.

**2. Feasibility & Data Risk (Medium Uncertainty)**
*   **Assumption:** Real-time data accurate enough to predict arrival windows is available from rail providers or third parties.
*   **Challenge:** Rail data is often delayed or proprietary. If the dashboard relies on the same phone calls and manual updates currently used by dispatchers, it merely digitizes existing noise without improving accuracy.
*   **Verdict:** Without a verified data feed superior to current phone/spreadsheet methods, the tool adds cost without improving prediction fidelity.

**3. Usability & Process Risk (Medium Uncertainty)**
*   **Assumption:** Dispatchers will use predictive data to change behavior (re-routing) faster than they currently react to phone calls.
*   **Challenge:** Even with perfect data, if the operational process for re-routing requires rail provider approval that takes longer than the delay window, the tool is useless.
*   **Verdict:** The bottleneck may be the negotiation process with rail providers, not the detection of the problem.

#### Strategic Recommendation for the Board

Do not approve the full Q3 budget for development yet. The assumption that "visibility equals control" is unproven and carries high financial risk if the root cause is external congestion.

**Immediate Next Steps (Low Cost/High Learning):**
1.  **Root Cause Audit:** Manually analyze the last five demurrage complaints. Categorize each delay as either "External Congestion" (track full, rail provider delay) or "Internal Reaction" (late notification, missed call).
    *   *If >70% are External:* The dashboard will not solve the problem. Focus efforts on negotiating service level agreements (SLAs) or alternative routing contracts.
    *   *If >70% are Internal:* Proceed with a lightweight prototype using existing data sources to test if earlier notification reduces the six-hour average.
2.  **Data Feasibility Check:** Before building, confirm with rail providers if real-time API access exists. If not, the "real-time" promise is technically infeasible without expensive third-party integrations.

**Conclusion:** Building the dashboard now assumes the problem is internal ignorance. If the problem is external incapacity, the build effort will add noise and cost without reducing the $45,000 penalty burden. Validate the source of delays before writing code.

*Note: This analysis relies strictly on the provided context of 200 weekly cars, six-hour delays, and recent complaint history. No external rail industry benchmarks were applied.*
