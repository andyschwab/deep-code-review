**Strategic Recommendation: Do Not Build Yet**

**Verdict:** Pause development of the specialist directory. Proceeding now violates the riskiest-assumption gate. You are proposing to build a solution dependent on an untested, high-effort operational assumption (manual data accuracy) to solve a problem where the root cause and user behavior are not yet verified.

**1. The Riskiest Assumption & Required Test**
*   **Assumption:** "We can maintain up-to-date provider availability manually without exceeding current administrative capacity, and patients primarily need a *searchable list* rather than direct booking or triage."
*   **Impact:** High (core value prop). **Uncertainty:** High (no data on admin load or user preference).
*   **The Cheap Test (Concierge/Wizard-of-Oz):** Before writing code, run a manual simulation for 5 days.
    *   **Action:** When a ticket arrives about finding a specialist, have a human manually find the match and reply within 1 hour. Log the time spent per ticket.
    *   **Metric:** Administrative minutes per successful match.
    *   **Kill Threshold:** If the average time per match exceeds 15 minutes, or if you cannot fulfill 90% of requests within 2 hours using current staff, **drop the manual approach**. The feature is not viable until automation exists.
    *   **Decision Rule:** If the test fails the threshold, building the directory now creates a "data accuracy problem" that erodes trust faster than having no directory at all.

**2. Resource Requirements (Estimated via Test)**
*   **Administrative Load:** Unknown until the concierge test is run. Do not guess; the test will reveal the true cost per transaction.
*   **Engineering:** Zero until the test passes. If the manual process works but is too slow, *then* the requirement is an automated sync engine, not a frontend directory.
*   **Opportunity Cost:** High. Diverting focus to a directory with stale data distracts from the core telemedicine offering and risks brand damage due to incorrect information.

**3. Potential Risks of Launching with Incomplete Data**
*   **Trust Erosion:** A directory with outdated availability is worse than no directory; it sends patients on wild goose chases, increasing frustration beyond the current state.
*   **False Efficiency:** You assume a 75% ticket reduction. If the directory is inaccurate, tickets may shift from "I can't find a doctor" to "The directory said they were available, but they aren't," potentially increasing total support volume.
*   **Strategic Distraction:** Building a frontend for a broken backend (manual data entry) creates technical debt and operational drag that conflicts with the core telemedicine value proposition.

**4. Immediate Next Steps**
1.  **Run the 5-day Concierge Test** described above.
2.  **Interview 5 recent ticket submitters** (Mom Test style): Ask specifically about the last time they needed a specialist, what they tried, and what they paid for or used instead. Do not pitch the directory; verify if a "searchable list" is actually what they need versus a "guaranteed appointment."
3.  **Re-evaluate:** Only if the manual test proves the value (patients are satisfied with the match) but fails on scale (too much admin time) do you prioritize building the *automation* first, not the directory UI.

**Conclusion:** The evidence required to justify this build is missing. The assumption that manual maintenance is feasible is the single point of failure. Test the operation, not the software.
