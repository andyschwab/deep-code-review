### Initiative Comparison: Drug Shortage Alert vs. Physician Rating Overhaul

**Status:** Both initiatives currently lack the validated evidence required to commit two senior developers for Q3. The following analysis structures your existing data against the critical unknowns that must be resolved before a build decision.

#### 1. Drug Shortage Alert System
*Hypothesis: Reducing medication delays drives higher hospital contract renewals.*

| Dimension | Current Evidence | Critical Unknowns (Must Validate Before Build) | Riskiest Assumption & Test |
| :--- | :--- | :--- | :--- |
| **Desirability** | 40% of pharmacists manually call clinics; 3-hour delay observed. | Do pharmacists *want* an automated alert, or do they prefer the control of a manual call? Will clinics accept automated inbound alerts? | **Assumption:** Hospitals will renew contracts specifically because of this feature.<br>**Test:** Concierge test. Manually simulate the alert for 5 pilot hospitals for 2 weeks. <br>**Kill Threshold:** If <3 of 5 pilots cite the manual simulation as a "must-have" for renewal discussions, drop the idea. |
| **Viability** | Assumed link to contract renewals. | Does the revenue from retained contracts exceed the cost of real-time inventory integration? | **Assumption:** Integration cost < Revenue gain.<br>**Test:** Sales interview with 3 decision-makers showing a mockup. Ask: "Would this specific capability change your renewal decision today?" <br>**Kill Threshold:** If 0 of 3 say "Yes, this changes our decision," the ROI hypothesis fails. |
| **Feasibility** | Requires real-time inventory integration. | Can 2 senior devs build a reliable integration with heterogeneous pharmacy systems by Sept 15? | **Assumption:** Integration is feasible within 6 weeks.<br>**Test:** Spike. One dev spends 3 days attempting connection with one major pharmacy vendor.<br>**Kill Threshold:** If no viable API path is found in 3 days, the scope is too large for Q3. |

#### 2. Physician Rating Overhaul
*Hypothesis: Improving provider discovery increases bookings.*

| Dimension | Current Evidence | Critical Unknowns (Must Validate Before Build) | Riskiest Assumption & Test |
| :--- | :--- | :--- | :--- |
| **Desirability** | 65% of patients check ratings elsewhere; current feature unused. | Why is the current feature unused? Is it trust, visibility, or lack of data? Will patients trust *your* ratings over established third-party sites? | **Assumption:** Patients will switch to using MediFlow for ratings.<br>**Test:** Fake-door test. Add a visible "Check Doctor Ratings" button on the booking flow that leads to a "Coming Soon" page. <br>**Kill Threshold:** If click-through rate is <5% of total booking attempts, interest is insufficient. |
| **Viability** | Assumed link to increased bookings. | Does seeing ratings on MediFlow actually convert to a booking *on MediFlow* vs. bouncing to another site? | **Assumption:** Ratings drive incremental bookings.<br>**Test:** Wizard-of-Oz. Manually send rating summaries to 50 users during their search. Track if they book via your link.<br>**Kill Threshold:** If conversion lift is <2% compared to control group, the feature won't move the needle. |
| **Feasibility** | Overhaul of existing feature. | Can a trustworthy rating system be built without significant moderation overhead? | **Assumption:** We can populate enough ratings to look credible immediately.<br>**Test:** Manual collection. Gather 50 real ratings for 5 doctors manually.<br>**Kill Threshold:** If it takes >4 hours per doctor to get verified ratings, the operational burden is too high for the current team. |

#### Recommendation for August Sprint Planning
**Do not greenlight either full build yet.** With only two senior developers, building the wrong thing is the highest risk.

1.  **Immediate Action (Week 1):** Run the **Concierge Test** for the Drug Shortage Alert and the **Fake-Door Test** for the Rating Overhaul. These require minimal engineering effort (mostly manual work or simple UI tweaks).
2.  **Decision Gate (Week 2):**
    *   If the Alert test meets the kill threshold (3/5 pilots interested) AND the feasibility spike confirms API access → **Greenlight Alert System.**
    *   If the Rating test shows >5% click-through AND >2% conversion lift → **Greenlight Rating Overhaul.**
    *   If both pass, prioritize the one with the clearer path to revenue (likely the Alert system given the direct contract renewal link).
    *   If both fail, you have saved 6 weeks of wasted engineering time.

**Non-Goals for Q3:**
*   Full automated inventory integration (until the concierge test proves value).
*   Complete rating platform rebuild (until fake-door proves demand).
*   Scaling to all hospitals/physicians (focus only on the pilot group).

**Note:** The "operational cost vs. revenue gain" question cannot be answered without the sales interviews proposed in the viability tests above; any number generated now would be a guess.
**Note:** Do not proceed to development until the specific numeric kill thresholds defined above are met or failed.
