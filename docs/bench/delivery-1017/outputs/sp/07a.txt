### Delivery Plan: Hotfix Payment Gateway Timeout

**1. Lanes & Parallelism**
*   **Lane A (Configuration - Serialized):** Modify `global-config` to reset connection pool limits. This must occur **first** and alone, as the file is locked during business hours. No other writes to this file are permitted until Lane B completes.
*   **Lane B (Validation - Parallelizable):** Once Lane A commits, trigger the CI pipeline. The "database-schema-sync" job must be configured with an automatic retry policy (max 2 attempts) due to known network flakiness; this runs in parallel with other sanity checks but blocks the final gate.
*   **Lane C (Observability - Continuous):** The On-Call Manager prepares the rollback script and dashboard filters immediately, independent of code changes.

**2. Gates & Checks**
*   **Gate 1 (Pre-Merge):** Automated sanity checks must pass on the specific commit hash generated by Lane A. If the "database-schema-sync" fails twice, a human must manually retry the job before proceeding.
*   **Gate 2 (Approval):** Dual approval is mandatory before merging to the production branch.
    *   Approver 1: Security Lead (verifies config change scope).
    *   Approver 2: On-Call Manager (verifies operational readiness).
*   **Execution Revision:** The fix deploys strictly from the commit hash that passed Gate 1 and received Gate 2 approvals. No rebasing or force-pushes allowed after approval.

**3. Review Strategy**
*   **Reviewer Independence:** The Security Lead and On-Call Manager act as independent reviewers. Neither may be the author of the configuration change.
*   **Scope:** Review is limited strictly to the `global-config` diff and the CI sanity check logs. No new features or unrelated refactoring are permitted in this hotfix.
*   **Sandbox Verification:** The requester's verification in the disaster-recovery sandbox is accepted as functional proof; the CI pipeline serves as the regression gate only.

**4. Landing & Rollback**
*   **Merge Strategy:** Direct push to the production branch is permitted only after dual approval. The standard two-day freeze is waived for this specific ticket ID.
*   **Human Decision Point:** If latency exceeds 200ms post-deployment, the On-Call Manager must manually authorize the rollback if the automatic trigger fails.
*   **Rollback Protocol:**
    1.  **Trigger:** Automatic if latency > 200ms for 60 consecutive seconds.
    2.  **Action:** Revert to the immediate previous stable commit hash.
    3.  **Constraint:** Do not attempt to re-apply the fix. Reverting restores the previous connection pool state.
*   **Post-Incident:** Once stable (or rolled back), the "database-schema-sync" flakiness must be ticketed separately for investigation, but not fixed within this hotfix window.

**Summary of Constraints:**
*   **Cost:** One CI run ($15) expected; budget for one retry if flaky.
*   **Time:** Total window approx. 45–50 minutes (22m CI + approval + buffer).
*   **Database:** Zero schema changes; immutable production DB respected.
