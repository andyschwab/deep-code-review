**Delivery Plan: Helios Critical Patch Expedite**

**Lanes & Parallelism**
*   **Lane A (Configuration - Serialized):** One engineer drafts the pipeline modification to skip regional simulations for the six specific commit hashes. This lane is blocked until the Lead Engineer provides written delegation for the absent Platform Architect's sign-off. No code changes occur here; only CI config edits.
*   **Lane B (Patch Verification - Parallel):** Six developers simultaneously rebase their patches onto the current `main` head. Each runs the *core security* and *transaction integrity* suites locally against the staging mirror. They must not push yet.
*   **Lane C (Audit Prep - Parallel):** Compliance prepares the audit trail documentation, mapping each patch to the specific regulatory requirement it satisfies.

**Gates & Checks**
*   **Gate 1 (Pre-Flight):** Before any config change, the Lead Engineer must verify the "delegation of authority" in writing. Without this, Lane A halts.
*   **Gate 2 (Dry Run):** Lane A applies the config change to a *feature branch* of the CI config, not `main`. A manual trigger runs the six patches through this modified pipeline in a isolated staging namespace.
    *   *Check:* Verify regional sims are skipped.
    *   *Check:* Verify core security/transaction tests pass.
    *   *Constraint:* If the flaky currency conversion check fails, manual retry is authorized up to 3 times before halting for investigation.
*   **Gate 3 (Integrity Lock):** The Risk Officer reviews the dry-run logs specifically for transaction integrity pass/fail status. No deployment proceeds without their explicit "Approved for Deployment" token.

**Review Protocol**
*   **Config Review:** The CI config change is reviewed by the Lead Engineer (acting for the Architect) and a Senior SRE. They must confirm the bypass logic matches *only* the six specific commit hashes and does not create a permanent loophole.
*   **Code Review:** The six patches undergo a rapid "pair-review" where two senior devs swap patches. They focus strictly on regression risks related to transaction integrity.
*   **Independence:** The Config Reviewers must not be the same individuals who wrote the patches. The Risk Officer acts as the final independent gatekeeper, separate from engineering leadership.

**Landing Strategy**
*   **Merge Window:** Thursday 12:00 PM to 4:00 PM. This allows one full cycle of the daily staging reset (midnight) before the Friday freeze, providing a buffer for unexpected rollback.
*   **Deployment Mechanism:**
    1.  Merge CI config change to `main` (requires Lead + SRE sign-off).
    2.  Merge the six patches sequentially (not in one bulk commit) to isolate failure points.
    3.  Trigger deployment to Staging. Wait for successful smoke tests.
    4.  Trigger deployment to Production (requires Lead Engineer + Risk Officer dual approval).
*   **Human Decisions Required:**
    *   Lead Engineer: Authorization to bypass Architect sign-off.
    *   Risk Officer: Final go/no-go based on integrity test results.
    *   Compliance Lead: Confirmation that skipping regional sims satisfies audit requirements for this specific emergency.
*   **Rollback Plan:**
    *   If production deployment fails integrity checks post-merge: Immediate revert of the specific patch causing failure via automated script.
    *   If the CI config causes broader issues: Revert the config commit to restore the full matrix.
    *   *Constraint:* Since production deploys are irreversible, "rollback" means deploying a corrective patch immediately, not undoing the transaction log. The corrective patch must be pre-drafted for the most likely failure mode (currency conversion flakiness).

*   Do not edit the monolithic config file directly on `main`.
