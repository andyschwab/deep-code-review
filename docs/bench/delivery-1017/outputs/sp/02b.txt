### Delivery Plan: Cargo Weight Filter

**1. Work Lanes & Parallelization**
*   **Lane A (Frontend Implementation):** Develop the numeric range slider component and integrate it into the Fleet Dashboard layout next to the date picker. Implement the event listener to trigger map redraws on value change, ensuring zoom/region state preservation.
    *   *Constraint:* Must not modify `map-config.json` during business hours. If changes are needed, stage them for off-hours application or use a temporary local override.
*   **Lane B (Test Automation):** Write the automated visual snapshot tests specifically targeting the map redraw behavior. Focus on verifying no flickering and state retention across supported desktop browsers.
    *   *Parallel Start:* Can begin immediately using existing staging data; does not wait for Lane A's final UI polish, only the interface signature.
*   **Lane C (Documentation & Compliance):** Prepare the audit trail document linking the new filter logic to the compliance requirements. Draft the release note for Jane Smith.

**Serialization Points:**
*   Lane B's final snapshot validation must wait for Lane A's code commit to ensure the visual target exists.
*   Final merge waits for Lane C's audit confirmation.

**2. Gates & Checks**
*   **Gate 1: Local Verification (Pre-CI):** Before pushing, the developer must manually verify the filter on the legacy browser container locally. This bypasses the known flaky CI visual regression check for the first attempt, saving the $45/22min job if the implementation is fundamentally broken.
*   **Gate 2: CI Pipeline (Revision: `feat/cargo-weight-filter`):**
    *   Trigger the full browser verification suite *once* upon the first stable PR.
    *   *Flake Protocol:* If the visual regression fails on the legacy container, do not re-run immediately. Perform a local manual verification. Only re-trigger CI if the local check passes and the CI failure is deemed a infrastructure glitch. A second CI failure requires a human infrastructure ticket, not a code retry.
*   **Gate 3: Analyst Sign-off:** Lead Analyst Jane Smith must review the live staging deployment and the audit document. No code merge occurs without her explicit written approval.

**3. Review Process**
*   **Code Review:** Conducted by a senior Telemetry Team engineer (peer review). Focus: State management logic (zoom/region preservation) and performance (no render loops).
*   **Functional Review:** Conducted by Jane Smith. Focus: Usability, correct weight isolation, and audit compliance.
*   **Independence:** The peer reviewer cannot be the author of Lane A or Lane B. Jane Smith's review is independent of the code review; she validates behavior, not implementation details.

**4. Landing Strategy**
*   **Merge Window:** Outside business hours to avoid locking `map-config.json` conflicts and to minimize live traffic risk during the initial cutover.
*   **Merge Action:** Squash merge to `main` only after Gate 3 is cleared.
*   **Human Decision Point:** Final "Go/No-Go" rests with Jane Smith after reviewing the staging environment.
*   **Rollback Plan:**
    *   Since production deployments are irreversible without a full database rollback, the feature must be wrapped in a feature flag.
    *   *Immediate Mitigation:* If critical issues arise post-merge, toggle the feature flag to "OFF" via the configuration service (no code revert needed).
    *   *Full Revert:* Only if the flag mechanism fails. This requires a coordinated database rollback procedure, authorized by the Telemetry Team Lead and scheduled for a maintenance window.

**Risk Mitigation Summary:**
*   **Cost Control:** Strict "one CI run" policy unless local verification proves CI wrong.
*   **Audit Safety:** Compliance docs prepared in parallel; feature flag ensures immediate disablement if audit criteria aren't met in production.
*   **State Integrity:** Manual legacy browser check prevents wasting CI resources on known flaky infrastructure.
