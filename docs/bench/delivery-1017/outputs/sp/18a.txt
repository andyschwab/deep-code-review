**Delivery Plan: Patient Intake Flow Update**

**Lanes and Parallelism**
Work is divided into three parallel lanes to maximize speed before serialization is required for integration.
*   **Lane A (UX/UI Design):** Redesigns the insurance verification step specifically for the elderly demographic (larger fonts, simplified language, linear progression). This lane produces static assets and a style guide ensuring consistency with recent branding updates. No code changes occur here.
*   **Lane B (Frontend Logic):** Refactors the client-side intake wizard to implement the new flow. This includes adding client-side validation to prevent incomplete records before submission. This work proceeds against the current `main` branch but does not touch encryption configurations.
*   **Lane C (Backend & Compliance):** Prepares the data capture schema to ensure all fields required for the upcoming regulatory audit are mandatory and correctly typed. This lane also drafts the "Compliance Impact Statement" required for the final approval gate.

**Serialization Point**
Lanes A, B, and C converge at the **Integration Branch**. Lane B cannot finalize until Lane A provides the final assets, and Lane C must verify the data schema before Lane B connects the form to the API.

**Gates and Checks**
All checks run on a dedicated feature branch created from the latest stable `main` revision.
1.  **Static Analysis & Unit Tests:** Runs immediately on push. The known flaky check in the insurance validation module is explicitly configured to be non-blocking; a failure here triggers a manual log review by the Lead Architect but does not halt the pipeline.
2.  **Immutable Config Guard:** A pre-commit hook strictly prevents any modification to the shared patient data encryption file. Any attempt triggers an immediate build failure and security alert.
3.  **Integration Test Suite:** Verifies the end-to-end flow from intake to record creation. This must pass 100% excluding the known flaky test.
4.  **Compliance Gate:** The Compliance Officer reviews the "Compliance Impact Statement" and verifies that the new flow captures all audit-required data points. This is a manual gate performed on the staging environment.

**Review Process**
*   **Code Review:** Conducted by a Senior Engineer not involved in Lanes B or C. They focus on logic correctness and adherence to the immutability constraints.
*   **UX Review:** Conducted by the Product Lead using the staging deployment to verify the elderly-friendly design and branding consistency.
*   **Security & Compliance Review:** Independent review by the Compliance Officer. They do not review code logic but verify data handling and audit readiness.

**Landing Strategy**
*   **Merge Window:** The merge to `main` is scheduled strictly for the next available Tuesday between 02:00 and 04:00 UTC.
*   **Approval Requirement:** Dual approval is mandatory. The Lead Architect must approve the code quality and flaky test mitigation; the Compliance Officer must approve the data integrity. Both approvals must be present in the pull request before the merge button becomes active.
*   **Deployment:** Automated deployment occurs immediately following the merge within the restricted window.
*   **Rollback Protocol:** If critical issues are detected post-deployment, the rollback is a manual process involving a database restore from the nightly snapshot. This operation takes approximately 45 minutes, during which the portal will be in read-only mode. The decision to rollback rests solely with the Lead Architect in consultation with the on-call Clinic Manager.
*   **Post-Launch:** Once live, a notification is sent to the requester to begin front-desk staff training. No further code changes are permitted until after the regulatory audit.
