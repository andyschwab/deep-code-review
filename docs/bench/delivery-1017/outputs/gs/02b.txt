### Delivery Plan: Cargo Weight Filter for Fleet Dashboard

**1. Work Lanes & Serialization**
*   **Lane A (Frontend Implementation):** Develop the numeric range slider component and integrate it with the existing date picker layout. Implement the event listener to trigger map redraws without resetting zoom/region state.
    *   *Constraint:* Must not edit `map-config.json` during business hours.
*   **Lane B (Test Automation):** Write automated visual snapshot tests specifically targeting the map redraw behavior.
    *   *Optimization:* Configure tests to run only on changed visual states to avoid full suite triggers ($45/22min cost). Include a retry logic wrapper to handle the known legacy browser flake (auto-retry once before flagging for manual check).
*   **Lane C (Documentation & Compliance):** Prepare the audit evidence package, including browser compatibility matrices and test result logs.

*Serialization:* Lane A and Lane B can proceed in parallel on the feature branch. Lane C waits for Lane B's successful snapshot generation. All lanes must complete before the Review Gate.

**2. Gates & Checks**
*   **Pre-Merge Gate 1 (Code Review):** Independent review by a senior Telemetry Team engineer (not the author). Focus: State preservation logic (zoom/region) and `map-config.json` access patterns.
*   **Pre-Merge Gate 2 (Product Sign-off):** Mandatory approval from Lead Analyst Jane Smith. She must verify the filter UX and slider placement on a staging deployment.
*   **CI Gate:** Run the targeted visual regression suite on the specific commit hash selected for merge.
    *   *Flake Protocol:* If the legacy browser check fails, automatically retry once. If it fails twice, pause pipeline for manual local verification by the engineer; do not re-trigger the expensive CI job.
*   **Config Lock Gate:** Verify `map-config.json` is not locked before final merge integration.

**3. Review Strategy**
*   **Technical Review:** Performed by a peer engineer independent of the implementation lane. They verify code quality, browser compatibility logic, and test coverage.
*   **Product Review:** Performed exclusively by Jane Smith. She validates the feature against the compliance audit requirements.
*   **Independence:** The technical reviewer cannot be the product approver, and neither can be the primary author of the code.

**4. Landing & Rollback**
*   **Merge Strategy:** Squash merge to `main` only after both Gate 1 and Gate 2 are explicitly cleared.
*   **Human Decision Point:** Final "Go/No-Go" for production deployment requires a verbal or written confirmation from the Telemetry Team Lead, acknowledging the irreversible nature of the deploy.
*   **Deployment Window:** Schedule outside business hours to avoid `map-config.json` lock conflicts and minimize live traffic risk during the critical audit prep week.
*   **Rollback Plan:** Since production deployments are irreversible without database impact, the rollback strategy is an immediate revert commit followed by a full database restore to the pre-deploy snapshot. This process must be rehearsed in staging before the production window opens.

**Summary of Critical Constraints:**
*   Do not touch `map-config.json` during business hours.
*   Limit CI runs to avoid unnecessary $45 charges; rely on targeted testing.
*   Manual verification is required if visual tests flake twice.
*   Jane Smith's sign-off is the hard blocker for merging.
