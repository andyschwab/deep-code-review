### Delivery Plan: Sequential PR Landing for Acme Freight Routing

**Objective:** Land six dependent PRs in strict sequence to prevent documentation checksum conflicts and ensure field tablet readiness before the morning shift.

#### 1. Lanes and Serialization
*   **Serialized Lane (Critical Path):** The six PRs must be merged strictly in order (PR #1 → PR #2 → ... → PR #6). No parallel merging is permitted.
*   **Parallel Lane (Preparation):** While waiting for CI on the current PR, the warehouse integration team can pre-validate the *next* PR locally against the updated `main` branch to anticipate merge conflicts in the shared JSON lockfile.
*   **Human Lane:** Senior Operations Leads must be available for approval windows. Coordinate their availability before starting the sequence.

#### 2. Gates and Checks
*   **Pre-Merge Gate (Every PR):**
    *   **Rebase Check:** Before any merge attempt, rebase the pending PR onto the *current* `main` (which includes the previously merged PR). Resolve any JSON lockfile conflicts locally first.
    *   **CI Validation:** Wait for the full 45-minute CI pipeline to return a **GREEN** status. Do not merge on "pending" or assume success based on previous runs.
    *   **Checksum Verification:** Confirm the automated documentation generator completed without checksum errors in the CI logs.
*   **Environment Gate:**
    *   **Tuesday Block:** Do not initiate or complete any merge during Tuesday's scheduled data syncs due to staging instability.
    *   **Production Approval:** Ensure a Senior Operations Lead approves the specific commit SHA in the production environment before the final merge of the sequence.

#### 3. Review Strategy
*   **Independent Review:** Assign a reviewer who is *not* the author and *not* part of the immediate warehouse integration pair-programming session to ensure objective audit compliance.
*   **Audit Trail Preservation:** Explicitly configure the merge to **"Merge Commit"** or **"Rebase and Merge"** (preserving individual commits). **Squash merging is forbidden** to maintain the required audit trail for shipment logic changes.
*   **Scope Check:** Reviewers must verify that changes are isolated to the intended routing logic and generated assets, ensuring no unintended side effects on the database schema that could complicate a rollback.

#### 4. Landing and Rollback Protocol
*   **Execution Window:** Begin the sequence early enough to accommodate 6 × 45 minutes (4.5 hours) of CI time plus buffer for conflict resolution, ensuring completion well before the morning shift.
*   **The "One-by-One" Rule:**
    1.  Merge PR #1.
    2.  **STOP.** Wait for CI green.
    3.  Update local `main`, rebase PR #2, resolve conflicts, push.
    4.  Repeat until PR #6 is merged.
*   **Final Trigger:** Immediately after PR #6 merges and CI passes, trigger the **manual snapshot job**. Verify the job completes successfully before declaring the ticket closed.
*   **Rollback Plan:**
    *   **Risk:** Reverting requires a full database rollback, which is **irreversible** for tracked shipment events.
    *   **Mitigation:** If a critical failure occurs post-merge (e.g., corrupted routing maps), do *not* attempt a git revert immediately. Engage the Database Administration team to execute the full rollback procedure only after confirming the severity warrants data loss of tracked events.
    *   **Decision Point:** Only the Senior Operations Lead can authorize the database rollback.

**Summary:** Strict serialization, patience with the 45-minute CI gate, and absolute avoidance of squash merges are the non-negotiable constraints. Success is defined by the manual snapshot job completing green before the morning shift.
