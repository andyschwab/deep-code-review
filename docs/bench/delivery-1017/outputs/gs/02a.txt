# Delivery Plan: Seasonal Trend Filter

## Work Lanes & Parallelization

**Lane A: Frontend Implementation (Frontend Guild)**
*   **Task:** Implement "Seasonal View" toggle, overlay logic for last year's data, and local storage persistence for chart state.
*   **Constraint:** Must use the current frozen visualization library; do not attempt to upgrade version 2.4.
*   **Parallel Status:** Can run immediately alongside Lane B.

**Lane B: Data & Backend Verification (Backend/Data Team)**
*   **Task:** Verify API endpoints can efficiently retrieve "corresponding dates from last year" without performance regression. Ensure data shape matches frontend expectations.
*   **Parallel Status:** Runs parallel to Lane A. Must complete before integration testing.

**Lane C: Accessibility & Compliance (Accessibility Champion)**
*   **Task:** Review toggle semantics, keyboard navigation, and screen reader announcements for the new overlay state.
*   **Serialization:** Must complete *after* Lane A's draft implementation is ready but *before* final merge approval.

**Lane D: Evidence Generation (QA/Requester)**
*   **Task:** Record the required video demonstration on a real browser session, specifically testing lower-resolution screens.
*   **Serialization:** Runs after deployment to Staging.

## Gates & Checks

**Gate 1: Local Validation (Pre-CI)**
*   **Who:** Developer (Lane A).
*   **Check:** Run unit tests locally. Verify persistence logic manually.
*   **Revision:** Feature branch head.
*   **Cost Avoidance:** Prevents triggering the $45/55min CI suite for broken builds or minor text errors.

**Gate 2: Continuous Integration (Automated)**
*   **Who:** CI Pipeline.
*   **Check:** Full test suite + Build.
*   **Revision:** Merged feature branch (post-code review).
*   **Exception:** If the screenshot comparison check fails, inspect the diff manually. If the failure is solely due to animation frames on Linux runners, override the check with a written justification from the Tech Lead. Do not re-run indefinitely.

**Gate 3: Dual Approval (Human)**
*   **Who:** Product Lead AND Accessibility Champion.
*   **Check:** Product Lead verifies business logic (holiday data isolation); Accessibility Champion verifies WCAG compliance.
*   **Timing:** Before merging to main. Both signatures required.

**Gate 4: Staging Verification**
*   **Who:** QA/Requester.
*   **Check:** Deploy to automated staging. Execute Lane D (Video Recording). Verify overlay rendering on low-res screens.
*   **Timing:** After merge to main, before Production sign-off.

## Review Strategy

*   **Code Review:** Performed by a Senior Frontend Engineer *not* in the Frontend Guild (to ensure cross-guild objectivity).
*   **Independence:** The reviewer must not be the Product Lead or Accessibility Champion to separate functional/accessibility approval from code quality assurance.
*   **Focus:** Ensure no attempts were made to unfreeze the visualization library and that persistence does not block main thread rendering.

## Landing & Rollback

**Merge Strategy:**
*   Merge to `main` only after Gate 3 (Dual Approval) and Gate 2 (CI Green) are satisfied.
*   The merge triggers the automated Staging deployment.

**Production Promotion:**
*   **Trigger:** Manual sign-off required from VP of Engineering.
*   **Window:** Business hours only (Mon–Fri, 9 AM–5 PM).
*   **Prerequisite:** Submission of the passing video evidence (Lane D) to the VP.

**Rollback Plan:**
*   **Condition:** If critical data mismatch occurs, overlay causes layout shift breaking usability, or persistence corrupts user settings.
*   **Action:** Revert the merge commit immediately.
*   **Communication:** Notify enterprise tier clients who filed the urgent tickets that the feature is temporarily disabled pending a fix.
*   **Post-Mortem:** Required if rollback occurs, specifically analyzing why the staging video evidence did not catch the failure.

**Risk Mitigation:**
*   To avoid CI costs, ensure all linting and unit tests pass locally before pushing.
*   To avoid production issues, the VP sign-off is strictly contingent on viewing the low-resolution video proof, ensuring the specific client pain point is resolved before general release.
