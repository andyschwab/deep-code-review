**Delivery Plan: Winter Sale Banner Update**

**1. Lanes & Parallelism**
*   **Lane A (Content Prep):** Marketing Lead provides the exact final string and confirms the target timezone for the "end date."
*   **Lane B (Implementation):** Engineer edits the homepage content file. This lane is serialized after Lane A completes.
*   **Lane C (Validation):** Shift Lead prepares to override the accessibility checker. This runs in parallel with Lane B but must conclude before merging.
*   **Lane D (Staging Verification):** Marketing Lead verifies formatting on Staging. This is serialized after the build completes.

**2. Gates & Checks**
*   **Gate 1 (Scope Confirmation):** Verify the change is strictly text (under 50 lines) and includes no logic or asset changes. If true, tag commit `docs-only` to bypass senior engineer approval.
*   **Gate 2 (Build Trigger):** Push to the content branch triggers the static generation pipeline.
    *   *Constraint:* Pipeline takes 22 minutes. Cost: $45.
    *   *Revision:* Build must run on the exact commit hash containing only the copy update.
*   **Gate 3 (Accessibility Override):** The automated checker will likely flag the dynamic date string.
    *   *Action:* Shift Lead must manually override the false positive in the CI dashboard before the merge is permitted.
*   **Gate 4 (Staging Visual Check):** Once the build deploys to Staging, Marketing Lead confirms the copy and formatting.
    *   *Constraint:* Staging data lags 4 hours. Marketing must mentally adjust for this lag when verifying dynamic elements, though static copy will be accurate.

**3. Review Strategy**
*   **Reviewer:** Growth Team Lead (independent of the implementing engineer).
*   **Scope:** Review is limited to a diff check ensuring only the banner text changed. No code logic review is required.
*   **Timing:** Review occurs after Gate 1 (tagging) but before Gate 3 (merge).

**4. Landing & Deployment**
*   **Merge Strategy:** Merge to `main` immediately after Staging sign-off and Accessibility override.
*   **Production Deploy:** The merge triggers the production build (another 22-minute window).
*   **Human Decision Point:** The Shift Lead must explicitly authorize the accessibility override. No other human gates are required due to the `docs-only` tag.
*   **Rollback Protocol:**
    *   *Risk:* Production deploys are irreversible without a full snapshot rollback.
    *   *Consequence:* Rolling back resets all analytics counters for the hour of the rollback.
    *   *Procedure:* If the copy is incorrect post-deploy, immediately revert the commit on `main`. Accept the analytics data loss as the cost of correction. Do not attempt hotfixes; use the snapshot revert.

**Timeline Critical Path:**
1.  Receive copy (Lane A).
2.  Commit & Tag (Lane B).
3.  Staging Build (22 mins).
4.  Staging Check (Lane D) + A11y Override (Lane C).
5.  Merge & Prod Build (22 mins).
*Total minimum lead time: ~50 minutes + verification time.*

**Warning:** Ensure the final push occurs no later than 6:00 AM to guarantee visibility before the 8:00 AM email blast, accounting for the two build cycles.
