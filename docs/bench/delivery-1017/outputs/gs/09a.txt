### Delivery Plan: Fix Duplicate Payouts in Vendor Disbursement Loop

**1. Work Lanes & Serialization**
*   **Lane A (Code Fix):** Engineer patches the idempotency check in the `finance-core` disbursement service. This lane is **serialized** before any external testing.
    *   *Constraint:* Must not modify the shared read-only configuration file used by the invoicing engine.
    *   *Validation:* Local validation is mandatory. The engineer must simulate the network blip retry logic locally to verify the token enforcement before touching the CI pipeline.
*   **Lane B (Data Analysis):** Data Analyst extracts last week's failed batch logs and identifies legitimate pending payouts.
    *   *Parallel:* Runs concurrently with Lane A.
    *   *Output:* A whitelist of transaction IDs that must not be blocked by the new logic.
*   **Lane C (Staging Verification):** Once Lane A passes local validation, the code is deployed to the **staging ledger** environment.
    *   *Constraint:* Do not use the standard test environment; its mocked bank simulator incorrectly passes duplicates and is unreliable for this bug.
    *   *Action:* Replay the specific failed scenarios from Lane B against the staging ledger to confirm single execution.

**2. Gates & Checks**
*   **Gate 1 (Local Logic Proof):** Before pushing, the engineer must demonstrate via local logs that a retry token prevents the second transfer execution. Failure here blocks the push.
*   **Gate 2 (CI Pipeline):** Only run after Gate 1 passes.
    *   *Check:* Standard build and unit tests.
    *   *Cost Control:* Limit runs to one final verification commit to avoid unnecessary $45 charges.
*   **Gate 3 (Staging Ledger Integrity):**
    *   *Revision:* The exact commit passing Gate 2.
    *   *Check:* Verify no legitimate pending payouts (from Lane B) are blocked and no duplicate transfers occur during simulated network retries.
*   **Gate 4 (CFO Approval):** Mandatory human gate.
    *   *Approver:* Chief Financial Officer.
    *   *Timing:* Must be scheduled Monday–Thursday. **No production deploys on Fridays.**

**3. Review Strategy**
*   **Code Review:** Performed by a Senior Backend Engineer independent of the author. Focus strictly on the idempotency logic and ensuring the shared config file remains untouched.
*   **Logic Review:** Performed by the Data Analyst (Lane B). They must sign off that the whitelist of legitimate payouts is correctly handled by the new filter.
*   **Independence:** The code reviewer cannot be the same person who wrote the fix. The CFO approval is a separate administrative gate, not a code review.

**4. Landing & Rollback**
*   **Merge Strategy:** Merge to `main` only after Gates 1–3 pass and CFO approval (Gate 4) is secured.
*   **Deployment Window:** Schedule the production deploy for Monday–Thursday to ensure CFO availability for emergency sign-off if needed. Avoid Friday deployment entirely.
*   **Rollback Plan:**
    *   *Trigger:* If staging verification shows blocked legitimate payouts or if the first production batch fails.
    *   *Action:* Immediate revert of the merge commit.
    *   *Fallback:* Re-deploy the previous stable version of the `finance-core` module.
    *   *Communication:* Notify logistics partners immediately if any overpayment occurs during the window; prepare a recovery script to recall funds if the banking rail supports it.

**Summary of Critical Constraints:**
*   **No** changes to shared read-only config.
*   **No** reliance on the mocked test environment; use staging ledger only.
*   **No** CI runs without prior local validation.
*   **No** Friday deploys.
*   **Mandatory** CFO approval for production.
