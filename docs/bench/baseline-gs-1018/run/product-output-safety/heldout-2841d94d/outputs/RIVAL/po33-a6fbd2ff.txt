**Pre-Launch Safety Checklist: Tax Calculation Accuracy**

**1. Construct a Deterministic "Golden Dataset"**
Create a local spreadsheet containing 20–30 manual test cases with known, verified outcomes. Do not rely on the system to generate these.
*   **Base Cases:** Include scenarios with zero income, single income source, and standard deduction only.
*   **Edge Cases:** Specifically target Mexican tax law complexities:
    *   Income exactly at the exemption threshold.
    *   Receipts totaling just above/below specific deduction caps (e.g., medical expenses limits).
    *   Mixed income types (salary + occasional services) with overlapping deductions.
    *   Dependents with partial-year eligibility.
*   **Expected Outputs:** Manually calculate the exact refund/owed amount and the specific form line items for each case using official SAT (Servicio de Administración Tributaria) guidelines.

**2. Execute Isolated Logic Verification**
Run your calculation engine against the Golden Dataset without any network connection or form submission features enabled.
*   **Input Parsing Test:** Feed raw text from scanned receipts that mimic common OCR errors (e.g., confused characters like '0' vs 'O', missing currency symbols, date format variations). Verify the parser rejects invalid data rather than guessing values.
*   **Calculation Comparison:** Compare the system's output line-by-line against your manual Golden Dataset. Any deviation, even by one cent, must be treated as a critical failure.
*   **Rounding Audit:** Verify how the system handles fractional cents at every intermediate step, not just the final total. Mexican tax forms often require specific rounding rules (e.g., rounding down vs. nearest) which, if inconsistent, trigger audits.

**3. Implement "Hard Stop" Validation Rules**
Embed non-negotiable constraints in the code that prevent submission if logical inconsistencies are detected:
*   **Cap Enforcement:** If a calculated deduction exceeds the legal maximum for that category, the system must flag it for human review rather than auto-correcting or submitting.
*   **Negative Value Check:** Ensure no line item results in a negative value where legally impossible.
*   **Summation Integrity:** Verify that the sum of individual deduction categories equals the total claimed deduction before generating the final form.

**4. Manual "Dry Run" Submission Simulation**
Generate the final output files (XML/PDF) for the Golden Dataset and visually inspect them against official SAT format specifications.
*   Check that all required fields for low-income exemptions are populated correctly.
*   Ensure no debug data or internal error messages appear in the user-facing documents.
*   Verify that the digital stamping requirements (if applicable to your specific workflow) are not attempted with invalid data.

**5. Fallback Protocol Definition**
Since you cannot afford third-party compliance tools, define a strict "Human-in-the-Loop" rule for the launch:
*   Any case where the calculated refund exceeds a specific high-risk threshold (e.g., >20% of reported income) must be paused for manual engineer review before submission.
*   Disable automatic re-submission for any return that receives an error code from the government portal; these must be queued for human analysis.

**Note:** Prioritize accuracy over speed; submitting an incorrect form is more harmful to vulnerable users than a delayed filing. If any Golden Dataset case fails, halt the launch until the logic is corrected.
