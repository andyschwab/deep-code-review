### Pre-Launch Date Validation Review Process

**1. Construct a "Poison Pill" Test Dataset**
Before reviewing code, assemble a dataset of 50+ specific edge cases that intentionally break standard date parsing. This must include:
*   **Ambiguous Formats:** Dates in `MM/DD/YY` vs `DD/MM/YY` conflicts (e.g., 02/03/24).
*   **Leap Year & Month-End Errors:** Feb 29 on non-leap years, or "Day 32" rollovers.
*   **Timezone Drift:** Expiry occurring at midnight UTC vs. local warehouse time.
*   **Malformed Inputs:** Null values, text strings ("TBD"), and partial dates.
*   **The "Expired-Safe" Control:** Explicitly include items known to be expired that your current library historically misreads as valid. If the system accepts any of these for donation, the build fails immediately.

**2. Implement a "Fail-Closed" Logic Gate**
Do not rely on the existing library to correct errors. Wrap the date processing in a strict validation layer with the following rule: **If a date cannot be parsed with 100% certainty into a standardized ISO format, the item is automatically classified as "UNSAFE/DO NOT DONATE."**
*   Hard-code a buffer: Treat any item within 24 hours of expiry as already expired.
*   Ensure the default state for any exception or crash is to block the donation workflow, not to proceed.

**3. Execute Adversarial "Red Team" Simulation**
Have a developer who did not write the code attempt to force an expired item through the system using the poison pill dataset. They should try to manipulate input fields, bypass UI constraints, and inject raw data directly into the API. Record every instance where the system hesitates, guesses, or defaults to "safe."

**4. Mandate Human-in-the-Loop for Ambiguity**
Since you cannot upgrade the library, you must add a manual gate. Any item where the date confidence is not absolute (or where the library returns a warning flag) must be routed to a warehouse staff member for visual verification before a charity pickup is scheduled. Fully automated donation is only permitted for dates that pass the strict parser without any ambiguity.

**5. Document Residual Risk as "UNVERIFIED"**
Do not claim the system is "error-free." Create a transparency note stating: "Due to legacy library constraints, date parsing relies on a fail-closed heuristic. Any unparseable date blocks donation. Specific edge cases regarding [list specific untestable formats] remain UNVERIFIED and are treated as unsafe by default."

**Note:** Given the high stakes of distributing harmful food, fully autonomous execution for final approval is unsafe; the human gate in Step 4 is mandatory regardless of the deadline.
**Note:** If the "poison pill" test reveals that expired items can be flagged as safe, the launch must be blocked until the logic is hardened, even if this misses the integration deadline.
