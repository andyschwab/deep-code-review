# DesignMatch Early-Stage Measurement Framework

## North Star Metric: **Weekly Active Matches**
Define a "Match" as a client accepting a proposal or initiating a contract. Do not prioritize "completed contracts" (too lagging for early iteration) or "message response rates" (too narrow). A Match proves mutual intent and liquidity. Track this weekly to show investors momentum in core value creation.

## Core Health Metrics (The Marketplace Equation)

Track these four metrics to diagnose Liquidity vs. Trust:

| Metric | Formula | Diagnosis |
|--------|---------|-----------|
| **Supply Liquidity** | Proposals Sent / Jobs Posted (Target: >3) | <3 indicates designers aren't seeing or trusting jobs. |
| **Demand Conversion** | Matches / Proposals Sent (Target: >10%) | Low % indicates pricing mismatch or poor profile quality. |
| **Time-to-First-Bid** | Avg. hours from Job Post → First Proposal | >24 hours suggests low supply engagement or notification failures. |
| **Completion Rate** | Completed Projects / Matches | <50% indicates trust/pricing friction *after* the match. |

## Essential Event Tracking Plan

Implement only these 7 events to avoid team overload. All events must include `user_type` (client/designer) and `timestamp`.

| Event Name | Trigger | Critical Properties |
|------------|---------|---------------------|
| `job_posted` | Client submits job | `budget_range`, `category`, `urgency` |
| `proposal_sent` | Designer submits bid | `bid_amount`, `job_id`, `designer_tenure` |
| `proposal_viewed` | Client opens proposal | `job_id`, `time_since_post` |
| `match_created` | Client accepts proposal OR hires directly | `job_id`, `agreed_price`, `match_method` |
| `contract_started` | Funds escrowed/contract signed | `job_id`, `start_date` |
| `project_completed` | Work approved & closed | `job_id`, `duration_days`, `final_payout` |
| `chat_initiated` | First message exchanged | `job_id`, `initiator_type` |

## Diagnostic Logic: Liquidity vs. Trust

Use your data to answer the founders' specific hypothesis:

**Scenario A: Liquidity Problem (Not enough activity)**
*   **Signals:** Low `proposals_sent` per `job_posted`; High `time_to_first_bid`.
*   **Interpretation:** Designers aren't applying. The issue is awareness, job feed relevance, or incentive to bid.
*   **Fix:** Improve job matching algorithms, send push notifications, or subsidize initial bids.

**Scenario B: Trust/Price Problem (Activity exists, no conversion)**
*   **Signals:** High `proposals_sent`, but low `match_created`; High `proposal_viewed` but no action.
*   **Interpretation:** Clients see bids but reject them. Your hypothesis on pricing mismatch is likely correct here.
*   **Fix:** Introduce price guidance ranges, highlight designer portfolios better, or add escrow trust badges.

**Scenario C: Fulfillment Problem (Matches happen, no completion)**
*   **Signals:** High `match_created`, low `project_completed`.
*   **Interpretation:** Deals fall apart during execution due to scope creep, payment disputes, or quality issues.
*   **Fix:** Improve contract templates, milestone tracking, or dispute resolution.

## Dashboard Proposal for Investors

Structure the weekly dashboard into three sections:

1.  **Growth Velocity:** Weekly Active Matches (trend line), Total GMV (Gross Merchandise Value).
2.  **Marketplace Health:** Supply Liquidity Ratio, Time-to-First-Bid (avg hours).
3.  **Quality & Retention:** Completion Rate %, Repeat Client Rate.

**Immediate Action:** Before the dashboard is built, run a manual SQL query on existing data to calculate the current `Time-to-First-Bid` and `Proposals per Job`. If proposals per job is <2, you have a supply liquidity crisis, not a pricing one. If it is >5 but matches are low, the pricing/trust hypothesis holds.

*Note: Ensure `budget_range` is captured as a standardized category (e.g., "$0-250", "$250-500") rather than raw text to enable quick aggregation.*
*Do not track individual message counts yet; focus on whether a conversation started (`chat_initiated`) as a proxy for interest.*
