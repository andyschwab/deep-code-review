### Measurement Strategy: PulseBand Gen 2 Pilot

**1. The North Star Metric (Value, Not Vanity)**
Reject "Daily Active Users" or "Total Sleep Hours Tracked" as your primary metric; these are vanity metrics that rise even if the product fails to deliver value.
**Adopt: "Weekly Actionable Sleep Interventions Completed."**
This metric only rises when a user not only receives a sleep insight (e.g., "Your deep sleep was low due to late caffeine") but also performs a linked behavior change (e.g., logs an earlier bedtime or completes a wind-down routine) and returns the following week. If users view the data but do not act, the North Star remains flat, signaling a novelty feature rather than a habit.

**2. Input Metrics & Event Taxonomy (Instrument Only What Answers a Question)**
Do not instrument "everything." Define events strictly by the question they answer to avoid noise and battery drain.

| Event Name | Question Answered | Properties to Log |
| :--- | :--- | :--- |
| `sleep_insight_viewed` | Did the user notice the new data? | `insight_type`, `time_since_sync` |
| `intervention_accepted` | Did the user agree to try a change? | `recommendation_id`, `difficulty_level` |
| `behavior_logged` | Did the user actually change behavior? | `action_type`, `timestamp` |
| `device_synced` | Is the friction of syncing too high? | `sync_duration`, `battery_level_at_sync` |

**3. Distinguishing Curiosity from Habit (Retention First)**
Read your funnel bottom-up. Do not analyze acquisition or total views until you confirm retention.
*   **Curiosity Signal:** High `sleep_insight_viewed` counts in Week 1, but `behavior_logged` drops to near zero by Week 2. Retention of the *core action* (logging behavior) is <20%.
*   **Habit Signal:** `behavior_logged` stabilizes into a weekly cohort pattern where users return to log actions even if they skip viewing detailed charts.
*   **The Leak Test:** If `device_synced` frequency drops as app complexity rises, your derived metrics are too heavy. Correlate `sync_duration` against `battery_level_at_sync`. If users only sync when battery >80%, the 48-hour estimate is causing anxiety; simplify the data payload immediately.

**4. Pilot Phase Rules (MVP Stage)**
*   **Pre-commit Experiment Design:** If you A/B test two different sleep insights, define the sample size (N) and duration (e.g., 14 days) *before* looking at the data. Do not stop the test early because one variant looks "significant" on Day 3; this is peeking and will yield false positives.
*   **Guardrail Metric:** Monitor "App Uninstall Rate" or "Support Tickets per 100 Users." If a new "advanced" metric drives up confusion (guardrail breach), kill the feature even if engagement looks high.
*   **Identifier Seam:** Use a stable, pseudonymous User ID to track cohorts across sessions. Do not log raw PII (names, exact locations) in firmware logs; route any consent management to your privacy compliance protocol.

**5. This-Week Steps**
1.  **Define the "Action":** Explicitly list the 3 specific behaviors (e.g., "Set Bedtime Alarm," "Log Caffeine Cut-off") that count toward the North Star. If you cannot name the action, you cannot measure the value.
2.  **Draft the Event Schema:** Finalize the JSON structure for `intervention_accepted` and `behavior_logged` for the firmware team. Ensure these events are lightweight to protect the 48-hour battery target.
3.  **Set the Baseline Query:** Write the SQL/Analytics query now that calculates "Week 4 Retention of Behavior Logging" so you can run it immediately when pilot data arrives.

*Note: Do not fabricate a "good" retention benchmark; compare the Gen 2 pilot results strictly against the Gen 1 baseline of 20%. Any metric without an instrumentation plan is `UNVERIFIED`.*
