### Immediate Diagnostic Plan for CoinVault Verification Drop-off

**Primary Diagnostic Signal:** Measure **Rejection Reason Frequency** first, segmented by error code. While time-to-decision is valuable, a sudden 25% cliff suggests a hard failure (false rejections or broken integration) rather than a gradual friction issue like latency. If the provider changed their model or rules on Nov 22nd, you will see a spike in specific rejection codes immediately.

**Step 1: Instrument the "Black Box" (Event Taxonomy)**
You currently lack visibility into the third-party response. You must immediately instrument the callback or webhook from your verification provider with the following specific events. Do not track generic "errors"; track the specific answer to "Why did this fail?"

*   **Event Name:** `verification_attempt_completed`
    *   **Properties:** `status` (success, rejected, error), `error_code` (e.g., `DOC_BLURRY`, `ID_EXPIRED`, `PROVIDER_TIMEOUT`, `API_500`), `provider_latency_ms`, `document_type`, `user_country`.
    *   **Question Answered:** "Are users failing due to document quality, provider technical errors, or new regulatory blocks?"

*   **Event Name:** `verification_step_abandoned`
    *   **Properties:** `time_on_step_seconds`, `last_action_taken` (e.g., `uploaded_doc`, `viewed_instructions`, `retry_clicked`), `error_message_shown` (if any).
    *   **Question Answered:** "Are users leaving before getting a decision (UX/Timeout) or after receiving a rejection (Trust/Policy)?"

**Step 2: Segment the Data to Isolate Root Cause**
Run these three queries on your last 7 days of data (comparing pre- and post-Nov 22nd):

1.  **The "Hard Fail" Check:** Group `verification_attempt_completed` by `error_code`. If a specific code (e.g., `PROVIDER_SYSTEM_ERROR` or a new strictness flag like `BIOMETRIC_MISMATCH`) spiked from <1% to >20% on Nov 22nd, the issue is **Technical/Provider Configuration**.
2.  **The "Timeout" Check:** Calculate the 95th percentile of `provider_latency_ms`. If this exceeds your frontend timeout threshold (e.g., 30s) starting Nov 22nd, users are abandoning due to **Technical Latency**.
3.  **The "Regulatory/UX" Check:** Filter for `status: rejected`. Compare the rejection rate by `user_country` or `document_type`. If rejections spiked only for specific IDs or regions, the provider may have updated **Regulatory Rules** without notice.

**Step 3: The Decision Framework**
*   **If `error_code` shows high API failures:** Roll back the provider integration or switch to a fallback provider immediately.
*   **If `status: rejected` is high but `error_code` is valid (e.g., "Face Mismatch"):** The provider's algorithm likely tightened. Contact them for a model rollback or adjust your UI to give better pre-upload guidance.
*   **If `verification_step_abandoned` is high with low latency:** The UX of the error message is confusing users, or the process feels too invasive.

**This Week's Action:**
1.  Deploy the `verification_attempt_completed` event with `error_code` capture within 4 hours.
2.  Generate a hourly time-series chart of rejection rates by `error_code` for Nov 20–24.
3.  If `PROVIDER_TIMEOUT` > 5%, enable a "retry" button with a different upload path; if `FALSE_REJECTION` codes dominate, escalate to the provider's emergency support with the specific error logs.

Note: Do not assume the cause is "longer processing times" without the latency data; false rejections are a more common cause of sudden cliffs in verification flows. Ensure all user identifiers in these logs are pseudonymized to comply with privacy standards before sharing with external vendors.
