### Critical Event Taxonomy for Screen Reader Compatibility Launch

To validate inclusivity goals quantitatively without relying on vanity metrics like raw session duration, instrument the following events. Each event answers a specific question about user value and workflow completion.

**1. Core Action Completion (The North Star Input)**
*   **Event Name:** `accessibility_core_action_completed`
*   **Question Answered:** Are users with assistive technology successfully delivering value (creating a project), regardless of how long it takes?
*   **Properties:** `workflow_type` (e.g., "create_project"), `assistive_technology_detected` (e.g., "screen_reader"), `success_boolean`.
*   **Why:** Session duration is ambiguous; a long session could mean deep engagement or a blocked user. This metric isolates successful outcomes.

**2. Navigation Failure & Recovery**
*   **Event Name:** `accessibility_navigation_blocked`
*   **Question Answered:** Where does the screen reader flow break, preventing task completion?
*   **Properties:** `element_id`, `failure_reason` (e.g., "unlabeled_button", "focus_trap"), `recovery_attempted` (boolean).
*   **Why:** Prioritize tracking *blocked* states over generic error rates. A generic 404 is less relevant than a focus trap that makes the UI unusable. This identifies specific fixes needed.

**3. Time-to-Task Completion (Efficiency, not just Duration)**
*   **Event Name:** `accessibility_workflow_duration`
*   **Question Answered:** Is the new update reducing the time required to complete core workflows compared to the pre-launch baseline?
*   **Properties:** `workflow_type`, `duration_seconds`, `step_count`.
*   **Why:** Unlike total session duration, this measures efficiency for a defined goal. It validates if the "compatibility update" actually improves speed or reduces friction.

**4. Feature Adoption by Segment**
*   **Event Name:** `accessibility_feature_utilized`
*   **Question Answered:** Are users actually engaging with the specific compatibility improvements we shipped?
*   **Properties:** `feature_name` (e.g., "skip_to_content", "aria_live_region_triggered"), `user_segment`.
*   **Why:** Confirms the update is being reached and used, distinguishing between "available" and "adopted."

**Implementation Notes for Data Team:**
*   **Identifier Seam:** Ensure these events tie to a **stable, pseudonymous user ID** to track cohorts over time without exposing PII. Do not use raw session IDs alone, as they prevent longitudinal retention analysis.
*   **Baseline Reality:** You currently have **no baseline** for this segment. Any metric measured before April 10th for this specific taxonomy is `UNVERIFIED`. Do not fabricate a "good" completion time; establish the baseline only after data accumulates post-launch.
