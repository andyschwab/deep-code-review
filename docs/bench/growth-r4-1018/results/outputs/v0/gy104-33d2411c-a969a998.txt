# VeriChain ID Pilot Success Framework: April 1st Launch

**North Star Metric:** **Verified Identities per Hour (at Target Fraud Threshold)**.
This metric rises only when real value is delivered (a user is successfully verified) without compromising the bank's risk appetite. It rejects vanity metrics like "total signups" or raw "uptime," which can increase even if the product fails to verify anyone safely.

### Core KPI Structure (Balancing Speed vs. Security)
Do not weigh speed and security as separate competing goals; treat security as a **guardrail** that gates the speed metric.

1.  **Primary Input Metric (Value):** **Median Time-to-Verification (TTV)** for *successful* verifications.
    *   *Target:* < 10 minutes.
    *   *Question:* Are we delivering the promised speed to users who pass?
2.  **Guardrail Metric (Risk):** **False Positive Rate (FPR)** on fraud detection.
    *   *Definition:* Legitimate users incorrectly flagged or rejected by the system.
    *   *Constraint:* Must remain below the bank's agreed tolerance (e.g., < 1.5%). If FPR breaches this threshold, the TTV metric is invalidated regardless of how fast the system is.
3.  **Retention/Quality Metric:** **Day-7 Re-verification Rate**.
    *   *Question:* Do verified users return to use the bank's services, or did the verification fail to enable actual account usage?
4.  **Operational Metric:** **Manual Review Queue Depth**.
    *   *Question:* Is the automation actually reducing bank staff workload, or are edge cases flooding human reviewers?

### Leading Indicators for Month 1
Watch these weekly to detect leaks before they impact the North Star:
*   **Drop-off Rate at Document Upload:** Indicates friction in the user interface before the blockchain check even begins.
*   **Provider-Specific Failure Rates:** Breakdown of failures by ID type (e.g., Estonian ID card vs. Passport) to identify integration gaps.
*   **Average Time in "Pending" Status:** Specifically for cases sent to manual review; ensures the hybrid model isn't creating a new bottleneck.

### Decision Rules & Weighting
*   **The "Stop" Tripwire:** If the False Positive Rate exceeds the agreed threshold for two consecutive days, pause automated approvals and route all traffic to manual review immediately. Speed is irrelevant if fraud leaks through.
*   **The "Optimize" Signal:** If FPR is stable but TTV > 10 minutes, investigate the specific step causing latency (e.g., blockchain confirmation time vs. image processing).
*   **Weighting Logic:** Security is binary (pass/fail against the threshold); Speed is linear (optimization within the safe zone). Never trade a higher FPR for a faster TTV.

### This-Week Steps
1.  **Instrument the "Verification Outcome" event** with properties for `duration_ms`, `fraud_score`, and `decision_type` (auto-approve/auto-reject/manual-review) to calculate the North Star.
2.  **Define the specific FPR threshold** with the Chief Risk Officer in writing before April 1st; without this number, the guardrail is `UNVERIFIED`.
3.  **Build a daily cohort dashboard** showing TTV and FPR side-by-side for the first 100 users to validate the baseline before scaling traffic.

*Note: All fraud benchmarks must come from the bank's historical data, not external estimates. Ensure user identifiers in analytics are pseudonymous to comply with GDPR and privacy standards.*
