# StarDrift Leaderboard Data Strategy & Instrumentation Plan

## 1. Critical Data Points for Integrity
To ensure fairness and prevent double-counting, capture only these verified events. Each answers a specific integrity question.

| Event Name | Question Answered | Required Properties |
| :--- | :--- | :--- |
| `match_started` | Did this session begin with a valid roster? | `match_id` (UUID), `user_id` (pseudonymous), `platform`, `region`, `timestamp_utc` |
| `score_snapshot` | What was the state at the moment of submission? | `match_id`, `user_id`, `score_value`, `game_tick`, `client_version`, `submission_attempt_count` |
| `match_resolved` | Was the final score accepted by the authoritative server? | `match_id`, `winner_id`, `final_scores` (map), `resolution_status` (success/rejected), `server_tick` |
| `connectivity_loss` | Did a drop occur during a critical window? | `user_id`, `match_id`, `timestamp_utc`, `last_known_tick`, `error_code` |

**North Star Metric:** % of `match_resolved` events where `resolution_status` = "success" within 2 seconds of client submission.
**Input Metrics:** Rate of `connectivity_loss` during submission; count of duplicate `match_id` submissions.

## 2. Addressing Your Current Assumptions & Gaps

**Gap A: The "Unique Session ID" Fallacy**
Your assumption that a session ID tied to a user account suffices is **insufficient** for cross-platform integrity.
*   **Risk:** If a player switches devices mid-match, a new session ID is generated. Relying solely on session IDs will split a single match into two incomplete records or create duplicate entries if the handover fails.
*   **Fix:** The `match_id` must be the **immutable primary key** for the leaderboard entry, generated by the authoritative server at `match_started`. The `user_id` links the player to the match, but the `match_id` tracks the game instance across device switches.

**Gap B: Network Drops & Double-Counting**
You lack a strategy for idempotency (preventing double processing) when connectivity drops.
*   **Risk:** A player submits a score, the network drops before the ACK returns, the client retries, and the server records two scores for one match.
*   **Fix:** Implement **idempotent write logic** on the backend. The server must check: "Has `match_id` + `user_id` already been resolved?" If yes, ignore the retry. The client must include a `submission_attempt_count` to help debug retry loops, but the server decides validity.

**Gap C: Authority Verification**
*   **Risk:** Accepting client-side scores allows cheating.
*   **Fix:** The `score_snapshot` is for telemetry only. The leaderboard must only update based on `match_resolved` events calculated by the **authoritative server**. Never trust the client's final score claim for ranking.

## 3. Identifier Seam & Privacy
*   **Stable ID:** Use a pseudonymous `user_id` (hashed account ID) to track players across console, mobile, and PC.
*   **PII Routing:** Do not store raw usernames, IP addresses, or device IDs in the analytics stream used for general leaderboard analysis. Route these to the secure operations database per `privacy-compliance` standards.

## 4. This-Week Steps
1.  **Schema Update:** Modify the backend schema to make `match_id` the unique constraint for leaderboard writes; reject any write where `match_id` already exists with a "resolved" status.
2.  **Client Logic:** Implement an exponential backoff retry mechanism on the client for `score_snapshot` events, ensuring the same `match_id` is reused on retry, not a new session ID.
3.  **Validation Query:** Write a test query to detect any `match_id` appearing with >1 `resolution_status` = "success" in the staging environment before the beta stress test.
