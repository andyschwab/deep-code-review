**Subject:** Mitigation Strategy: Optimizing Delivery Estimates Amid Driver Shortages

**Executive Summary**
To address the driver shortage and rising cancellation rates (4% → 11%), we will test a hypothesis that displaying accurate, extended delivery times reduces cancellations without critically harming revenue. We will move from optimizing for speed (vanity) to optimizing for reliable fulfillment (value).

**1. Primary Metric (North Star): Completed Orders per Session**
We will optimize for **Completed Orders per Session** rather than "Orders Placed" or "Average Delivery Time."
*   **Rationale:** "Orders Placed" is a vanity metric in this context; it rises even when cancellations spike, masking the failure. "Average Delivery Time" is an operational output, not a customer outcome.
*   **Definition:** The number of orders successfully delivered divided by the number of user sessions where a restaurant was viewed.
*   **Goal:** Increase this rate by reducing the gap between promised and actual delivery, thereby stopping the bleed of 11% cancellations.

**2. Guardrail Metrics (Constraints)**
We will monitor these to ensure the solution does not destroy long-term value. If any breach their thresholds, the test pauses.
*   **Guardrail A: Gross Merchandise Value (GMV) per Active User.**
    *   *Threshold:* Must not drop >5% below the 3-month baseline.
    *   *Purpose:** Ensures that while we may lose some impulse orders due to longer times, the remaining users still generate sufficient revenue.
*   **Guardrail B: 7-Day User Retention Rate.**
    *   *Threshold:* Must not drop >2% below baseline.
    *   *Purpose:** Prevents the "abandon app entirely" risk. If users see a 60-minute estimate and never return, GMV looks stable today but collapses next week.
*   **Guardrail C: Customer Satisfaction (CSAT) on Delivered Orders.**
    *   *Threshold:* Must increase or remain flat.
    *   *Purpose:** Validates that accurate expectations improve the experience for those who do order.

**3. Experiment Design & Reading Rules**
*   **Method:** A/B Test. Control group sees current estimates; Variant group sees adjusted estimates (current time + buffer based on real-time driver availability).
*   **Pre-commitment:** We will run this for **14 days** or until we reach **50,000 sessions** (whichever comes first). We will read the results **once** at the end.
    *   *Reasoning:* Checking daily ("peeking") creates false positives. We need to see if users adapt to the new reality over a full cycle.
*   **Decision Rule:**
    *   **Ship:** If *Completed Orders per Session* increases AND both GMV and Retention guardrails hold.
    *   **Stop:** If *Completed Orders per Session* does not improve, OR if Retention drops >2%.
    *   **Extend:** If results are inconclusive but trends look positive, extend to the pre-committed sample size only.

**4. Immediate Next Steps (This Week)**
1.  **Instrumentation Check:** Verify that the event `order_estimate_displayed` includes the `estimated_minutes` property and links to a stable, pseudonymous `user_id` to track retention cohorts.
2.  **Baseline Query:** Run a query on last month's data to establish the exact baseline for *Completed Orders per Session* segmented by delivery time buckets (e.g., 30-40m, 40-50m, 50m+).
3.  **Test Launch:** Deploy the variant to 10% of Milan traffic by Wednesday to ensure data collection begins before the board meeting.

*Note: All metrics compare against GustoSubito's own historical baseline; no external industry benchmarks are used as they do not reflect our current supply constraint.*
