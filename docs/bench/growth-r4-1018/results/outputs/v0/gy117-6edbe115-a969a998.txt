### Offline-First Instrumentation Specification for AgriConnect Pilot

**Objective:** Preserve accurate temporal sequencing of farming activities (planting, irrigation, harvesting) despite connectivity gaps up to 18 hours, ensuring grant reporting validity by January 20.

#### 1. Data Storage Strategy: Local-First with Deferred Sync
Do not attempt to transmit events immediately. All user actions must be captured locally first.
*   **Local Store:** Use an embedded lightweight database (e.g., SQLite or Realm) on the device.
*   **Transmission Trigger:** Sync batches only when a stable connection is detected and the app is in the foreground (to preserve battery).
*   **Data Retention:** Locally store events until a successful server acknowledgment is received. Do not delete local records until confirmed.

#### 2. Critical Metadata Schema (Per Event)
To reconstruct timelines reliably after delayed upload, every event record must include these four specific fields:
1.  **`event_id` (UUID v4):** A unique identifier generated locally at the moment of action. Prevents duplication if a sync retry occurs.
2.  **`occurred_at` (ISO 8601 UTC):** The precise timestamp when the user performed the action, generated by the device clock. **This is your source of truth for farming cycles.**
3.  **`synced_at` (ISO 8601 UTC):** The timestamp when the data actually left the device. Used to calculate latency and diagnose connectivity patterns.
4.  **`device_clock_offset` (Optional but Recommended):** If possible, capture the device's last known NTP offset or network time reference to validate clock drift on low-cost devices.

#### 3. Reconstruction Logic (Server-Side)
Your analytics pipeline must ignore the server receipt time for behavioral analysis.
*   **Sorting:** Always sort and aggregate based on `occurred_at`, never `synced_at`.
*   **Sessionization:** Reconstruct user sessions by grouping events where the gap between `occurred_at` timestamps is less than a defined threshold (e.g., 30 minutes), regardless of when they arrived at the server.
*   **Gap Detection:** Flag days where `synced_at` minus `occurred_at` exceeds 24 hours to monitor extreme connectivity outliers for the grant report.

#### 4. Key Risks & Mitigations
*   **Risk: Device Clock Drift.** Low-end Android devices common in rural Kenya may have incorrect system times, corrupting the `occurred_at` data.
    *   *Mitigation:* On every successful sync, fetch the server time and store a `clock_correction_factor` locally. Apply this factor to future local timestamps until the next sync.
*   **Risk: Data Loss on App Uninstall/Crash.** If the app is removed before syncing, the data is lost forever.
    *   *Mitigation:* Implement a "critical event" flag for high-value actions (e.g., "Harvest Logged"). If these exist in the local queue for >48 hours, trigger a persistent local notification reminding the user to connect.
*   **Risk: Duplicate Events.** Network instability may cause the same batch to be sent twice.
    *   *Mitigation:* Enforce idempotency on the server using the `event_id`. If an `event_id` already exists, discard the duplicate.

#### 5. Immediate Next Steps (This Week)
1.  **Define the Core Event List:** Limit instrumentation to the 5-7 specific actions that prove "real-world usage" for the grant (e.g., `plot_created`, `crop_planted`, `input_applied`). Do not instrument "just in case."
2.  **Prototype the Schema:** Have the lead engineer implement the local schema with the four metadata fields above and verify that a simulated 48-hour offline period reconstructs the correct sequence upon reconnection.
3.  **Baseline Clock Accuracy:** Test 5 target devices to measure average clock drift over 24 hours without internet to determine if the `clock_correction_factor` logic is strictly necessary for the pilot.

*Note: Ensure all locally stored user identifiers are pseudonymous; route any PII handling to your privacy compliance protocol. Do not estimate retention or conversion rates until the pilot generates actual data.*
