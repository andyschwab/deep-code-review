**Experiment Read-Out: TravelGo Booking Flow (Nov 1 – Nov 21)**

**Verdict: UNVERIFIED (Methodology Failure Likely).** Do not abandon the hypothesis yet; the pattern of *all* variants underperforming the control indicates a structural flaw in the test setup or data integrity, not a user preference signal. A true "bad idea" usually results in parity or mixed results, not a uniform collapse across five distinct changes.

**Recomputed Reality Check**
Your baseline is 5.2%. The "best" variant dropped to 4.1% (a ~21% relative decline). If five independent changes all caused significant harm, the probability is near zero. The most probable cause is that the **Control group was contaminated** or the **variants were disadvantaged** by non-experimental factors.

**Primary Diagnoses (in order of likelihood)**

1.  **Selection Bias / Traffic Segmentation Fault:** The most common cause of universal underperformance is that the "Control" group received higher-quality traffic than the test groups.
    *   *Check:* Did the routing logic accidentally send returning users, high-intent organic search traffic, or a specific geographic cohort disproportionately to the Control bucket? If the Control group had inherently higher conversion propensity, the variants appear to fail even if they are neutral.
2.  **Instrumentation Breakage (The "Silent Killer"):** The changes deployed in the variants may have broken the tracking event itself, not the booking flow.
    *   *Check:* If the button click or completion event listener failed to fire in the new layouts, your analytics recorded "no conversion" for users who actually booked. This artificially tanks the metric to ~0% (or significantly lower) without affecting revenue. Compare raw transaction logs (database) against analytics events for each variant.
3.  **Novelty Effect / UI Shock:** If the layout adjustments were drastic, users may have hesitated or abandoned due to confusion, not dislike. However, this rarely causes a 21% drop across *all* variants unless the core affordance (the button) was obscured in every version.
4.  **Peeking / Early Stop Bias:** You mentioned a three-week period. If the decision to declare "significance" was made by watching the dashboard daily and stopping the moment the p-value dipped below 0.05, this is a false positive driven by repeated testing (peeking). The "significant" loss may be statistical noise amplified by early stopping.

**Immediate Actions (This Week)**

1.  **Audit the Data Pipeline (Day 1):** Query the backend database for actual bookings completed during the test window, grouped by variant ID. If the database shows equal conversion rates across all groups while analytics shows a drop, the issue is **broken instrumentation**, not user behavior.
2.  **Validate Randomization (Day 2):** Run an A/A test analysis on pre-exposure metrics (e.g., device type, source/medium, prior visit count) across the six groups. If the Control group has a statistically different mix of traffic sources than the variants, the **segmentation logic is flawed**.
3.  **Recompute Significance (Day 3):** Ignore the daily looks. Recalculate the p-value using *only* the final dataset from the full three-week period. If the significance disappears when analyzed as a fixed-horizon test, the result was **peeking noise**.

**Decision Rule:**
*   **If backend bookings match analytics:** The variants genuinely harmed performance. Pause this specific design direction and return to user research.
*   **If backend bookings are equal but analytics differ:** The test is invalid due to tracking errors. Fix the instrumentation and re-run.
*   **If traffic mix is skewed:** The test is invalid due to bias. Discard results and fix the randomization engine.

Do not declare the hypothesis dead until the instrumentation and randomization are proven clean.
