### Critical Event Taxonomy for Screen Reader Compatibility Launch

To validate inclusivity goals quantitatively without relying on vanity metrics like raw session duration, instrument the following events. Each event answers a specific question about whether users with assistive technologies (AT) are deriving real value from TaskFlow.

**1. Core Action Completion: "Project Created"**
*   **Question Answered:** Can AT users successfully complete the primary value proposition of the tool?
*   **Properties to Capture:** `user_segment` (AT vs. non-AT), `completion_time_seconds`, `error_encountered` (boolean), `error_type` (e.g., "focus_trap", "unlabeled_button", "dynamic_content_missed").
*   **Why:** Session duration is ambiguous; a long session could mean deep engagement or inability to find the "Create" button. Time-to-task completion paired with success/failure status provides a definitive measure of efficiency.

**2. Navigation Efficiency: "View Switched"**
*   **Question Answered:** Can AT users navigate between key views (e.g., Board to List) without getting lost?
*   **Properties to Capture:** `source_view`, `target_view`, `navigation_method` (e.g., "keyboard_tab", "screen_reader_hotkey", "mouse"), `steps_taken` (count of intermediate actions).
*   **Why:** Screen reader users often rely on specific navigation landmarks. An unusually high `steps_taken` count indicates poor landmark implementation or confusing hierarchy.

**3. Error Recovery: "Form Submission Failed"**
*   **Question Answered:** When errors occur, are they perceivable and recoverable for AT users?
*   **Properties to Capture:** `field_name`, `error_message_read` (boolean, inferred if focus moved to error), `retry_success` (boolean), `time_to_retry_seconds`.
*   **Why:** Standard error tracking logs the server response but not the user experience. If an AT user fails to submit and does not retry within a reasonable window, the error message was likely inaccessible.

**4. Feature Discovery: "Help/Shortcut Menu Accessed"**
*   **Question Answered:** Are AT users finding and utilizing accessibility-specific features or shortcuts?
*   **Properties to Capture:** `menu_type`, `items_selected`, `session_count_at_access` (is this a new or returning user?).
*   **Why:** Low access rates may indicate the entry point is invisible to screen readers, not that users don't need help.

**Measurement Strategy & Baselines**
Do not assert a "good" completion time or error rate, as no baseline exists for this segment yet. Instead, establish the **user's own baseline** starting April 10th:
*   **Primary Metric (North Star):** Success Rate of "Project Created" for the AT segment.
*   **Input Metric:** Average `steps_taken` for "View Switched."
*   **Guardrail Metric:** `error_encountered` rate during form submission.

Compare the AT segment's performance directly against the non-AT segment's historical baseline to identify gaps. If the AT success rate is significantly lower or `steps_taken` is significantly higher, the feature is not working as intended. Avoid tracking "page loads" or generic "clicks" for this initiative; they do not distinguish between accessible and inaccessible interactions.
