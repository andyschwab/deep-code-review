### Lean Growth Metrics Plan for TaskFlow
**Audience:** Founder & Co-founder | **Deadline:** Quarterly Planning (March 5) | **Constraint:** 20 dev-hours/week

#### 1. The North Star: Weekly Active Creators
Stop measuring "active users" or "logins." Your North Star is **users who complete one core value action per week** (e.g., creating a task, finishing a workflow, or sending an invite).
*   **Why:** Logins are vanity; a user can log in and leave. Value is only delivered when they *do* something. If this number rises, revenue follows. If it falls, churn is imminent.
*   **Input Metric:** Count of users performing the [Core Action] in the last 7 days.

#### 2. The Funnel: Read Bottom-Up (Retention First)
Do not pour effort into acquisition until you know why users stay or leave. Diagnose in this order:
1.  **Retention (The Leak Check):** Of the users who performed the Core Action in Week 1, what % do it again in Week 2?
    *   *Signal:* If this is low (<20-30% for productivity tools), new features won't fix growth. The core loop is broken.
    *   *Action:* If low, stop building new tools. Fix the onboarding or the primary workflow.
2.  **Activation (The "Aha" Moment):** What % of signups perform the Core Action within their first 24 hours?
    *   *Signal:* If low, users aren't seeing value fast enough.
    *   *Action:* Simplify the first-run experience.
3.  **Adoption (Your Original Question):** Of active users, what % use Feature X?
    *   *Signal:* Only measure this for features already built. If <5% of active users touch a feature after 30 days, mark it for deprecation or redesign. Do not build Feature Y until Feature X is adopted.

#### 3. Event Taxonomy (Instrument Only These 3)
With 20 hours/week, do not "track everything." Implement exactly these three events. Anything else is noise.

| Event Name | Question It Answers | Properties to Capture |
| :--- | :--- | :--- |
| `core_action_completed` | Are users getting value? | `user_id` (pseudonymous), `feature_type`, `timestamp` |
| `feature_used` | Which specific tools drive retention? | `user_id`, `feature_name`, `session_duration` |
| `subscription_renewed` | What behavior precedes payment? | `user_id`, `plan_type`, `days_since_signup` |

*Note on Identity:* You must link these events to a stable, pseudonymous `user_id` across sessions. Server logs often miss this; ensure your app generates/stores this ID locally and sends it with every event.

#### 4. Implementation & Monitoring Strategy
*   **Phase 1 (MVP - Week 1):** Instrument `core_action_completed` and `subscription_renewed`. Build a simple spreadsheet or basic dashboard plotting these two lines over time.
*   **Phase 2 (Diagnosis - Week 2):** Add `feature_used`. Run a cohort analysis: "Do users who use Feature A have higher retention than those who don't?"
*   **The Decision Rule:**
    *   If a feature has <5% adoption among active users AND no correlation to retention: **Stop developing it.**
    *   If a feature has high adoption but low retention impact: **Optimize it.**
    *   If a feature correlates strongly with renewal: **Double down.**

#### This Week's Steps
1.  **Define the Core Action:** Agree internally on the *one* action that equals "value" (e.g., "Task Created").
2.  **Ship the Tracker:** Have the developer instrument the `core_action_completed` event with a stable user ID.
3.  **Baseline Query:** Run a manual query on existing logs (if possible) or wait 7 days for new data to answer: "What % of users who did the Core Action this week did it last week?"

**Note:** Do not invent benchmarks for "good" retention; compare your Week 2 rate only against your own Week 1 rate. If data is missing for any metric above, label it `UNVERIFIED` until the event is shipped.
