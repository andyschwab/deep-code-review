# HealthKeep HIPAA-Compliant Instrumentation Strategy

## Executive Summary
This tracking plan enables measurement of patient engagement and medication adherence proxies without capturing Protected Health Information (PHI). All events are designed with a "zero-trust" data model: if an event *could* identify a patient or reveal specific health conditions, it is not tracked.

## Core Privacy Principles
1.  **No PHI in Events:** Never log medication names, dosages, diagnosis codes, patient names, or specific appointment times.
2.  **Pseudonymization:** User IDs must be hashed, non-reversible tokens generated specifically for analytics, distinct from medical record IDs.
3.  **Aggregation Over Individualization:** Focus on cohort-level trends rather than individual patient journeys where possible.
4.  **Purpose Limitation:** Only track data required to answer specific clinical questions (e.g., "Is the reminder system working?").

## Proposed Event Schema

### 1. Engagement & Retention (Proxy for Adherence)
*Hypothesis: Consistent app interaction correlates with medication compliance.*

| Event Name | Properties (Allowed) | Properties (Forbidden) | Trigger |
| :--- | :--- | :--- | : |
| `session_started` | `time_of_day_bucket` (e.g., "morning", "afternoon"), `device_os` | Exact timestamp, GPS location, IP address | App foregrounded |
| `reminder_viewed` | `reminder_type` (e.g., "medication", "check-in"), `delay_minutes` (since scheduled) | Medication name, specific scheduled time | Notification opened |
| `action_completed` | `action_category` (e.g., "confirm_intake", "log_symptom", "dismiss") | Specific symptom text, medication details | User taps confirmation |
| `streak_maintained` | `streak_length_bucket` (e.g., "1-3 days", "4-7 days", "8+ days") | Exact day count if it reveals specific regimen start dates | Daily goal met |

### 2. Feature Utilization
*Goal: Understand which tools drive retention without knowing *what* they are treating.*

| Event Name | Properties (Allowed) | Properties (Forbidden) | Trigger |
| :--- | :--- | :--- | :--- |
| `feature_accessed` | `feature_id` (e.g., "chart_view", "export_pdf", "caregiver_link") | Content viewed within feature | Navigation event |
| `help_article_read` | `article_category` (e.g., "general_wellness", "app_usage") | Article title if it reveals condition | Page view |

## Data Handling Architecture

### User Identification
-   **Analytics ID:** A randomly generated UUID created at app install, stored locally, and hashed before transmission.
-   **No Cross-Referencing:** The mapping between this Analytics ID and the medical record ID must exist *only* in the secure clinical database, never in the analytics platform (GA4, Mixpanel, etc.).

### Temporal Obfuscation
-   **Time Buckets:** Instead of exact timestamps (which can be quasi-identifiers when combined with other data), round times to 4-hour buckets or general periods (Morning/Afternoon/Evening).
-   **Date Granularity:** Report daily aggregates only; do not enable raw event exploration by date for individual users in the UI.

### Compliance Safeguards
-   **Data Retention:** Set analytics data retention to 14 months maximum; auto-delete raw event logs after 30 days.
-   **Access Control:** Analytics dashboard access restricted to Product and Engineering leads only; Clinical staff view only aggregated reports generated by the system.
-   **Audit Trail:** Enable logging of who accesses the analytics dashboard, though the data within is anonymized.

## Validation for Dr. Arvind & CTO
-   **Risk Assessment:** Even if the analytics database is breached, the attacker sees only "User X opened the app 5 times in the morning" and "clicked confirm." No medical condition, drug name, or identity is recoverable.
-   **Metric Viability:** "Adherence Rate" will be calculated as `(Users with >1 action_completed per day) / (Total Active Users)`. This provides the clinical partner with a statistically valid proxy for adherence without violating HIPAA.
