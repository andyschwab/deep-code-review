# Andes Aid Operational Measurement Framework

**Objective:** Validate operational efficiency to secure donor funding by April 1.
**Primary Hypothesis:** Faster time-to-match correlates with successful supply delivery.
**Constraint:** Metrics must be calculable despite sporadic rural connectivity (offline-first logic).

### 1. Core Success Metrics (The "North Stars")
These metrics directly answer whether the platform is saving lives by moving supplies. Instrument these immediately.

| Metric | Definition | Why It Matters | Data Source |
| :--- | :--- | :--- | : |
| **Confirmed Delivery Rate** | `(Deliveries with Photo Proof) / (Total Matches)` | Distinguishes actual aid from browsing or failed attempts. This is your primary impact metric for donors. | Mobile App (Photo Upload) |
| **Median Time-to-Match** | Time elapsed between `Request Posted` and `Donor Accepted` | Validates your hypothesis that speed drives survival. Median is preferred over average to ignore outliers caused by connectivity blackouts. | Server Timestamps |
| **Sync Success Rate** | `(Successfully Synced Events) / (Total Local Events Attempted)` | Measures the impact of rural connectivity. If this drops below 80%, your data is unreliable, and you need offline UX improvements. | Local Storage vs. Server Log |

### 2. Operational Efficiency Metrics
Use these to diagnose bottlenecks in the coordination workflow.

| Metric | Definition | Actionable Insight |
| :--- | :--- | :--- |
| **Match-to-Delivery Lag** | Time between `Donor Accepted` and `Photo Uploaded` | Identifies if the bottleneck is finding donors (matching) or physical logistics (delivery). |
| **Message Efficiency Ratio** | `(Messages Exchanged) / (Successful Match)` | High ratios indicate friction in coordination. If users exchange >10 messages before matching, the interface is failing. |
| **Volunteer Activation Rate** | `(Volunteers with ≥1 Accepted Match) / (Total Registered Volunteers)` | Currently 1,200 registered. If only 100 are active, your onboarding or alert system is broken. |

### 3. Implementation Priorities (Offline-First)
Given the connectivity constraints, do not rely on real-time streaming analytics.

1.  **Local-First Event Logging:** Store every critical action (`request_created`, `match_accepted`, `delivery_confirmed`) in local device storage immediately. Tag each with a local timestamp and a `synced: boolean` flag.
2.  **Batch Synchronization:** Attempt to sync data only when connectivity is detected. Do not block the user interface waiting for a server response.
3.  **Minimal Payloads:** For the "Confirmed Delivery" event, compress photos before transmission. If the network fails, queue the image but allow the text confirmation to sync first to preserve the count.
4.  **Definition of "Success":** A coordination event is **only** successful when a delivery photo is uploaded and synced. A match without a photo is a "Pending Delivery," not a success.

### 4. Reporting Cadence for Elena (Donor Report)
For next week's report, aggregate data into these three figures:
*   **Total Supplies Delivered:** Count of unique `delivery_confirmed` events with photos.
*   **Average Speed of Aid:** Median time from request to match (in hours).
*   **Network Resilience:** Percentage of attempted deliveries successfully recorded despite connectivity issues.

**Note:** Do not track "Page Views" or "Time on Site"; these are vanity metrics in a crisis context.
**Note:** If Sync Success Rate is low, explicitly state in the donor report that "Recorded deliveries are a conservative floor; actual impact is likely higher due to offline gaps."
