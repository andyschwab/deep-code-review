# DataVista Dashboard Update: Diagnostic Framework

## Immediate Diagnostic Steps (Days 1-2)

**1. Segment the DAU Drop**
Break down the 12% decline by user cohort to isolate the impact:
*   **Power Users vs. Casual Users:** Filter by historical login frequency (e.g., >5x/week vs. <2x/week). If the drop is concentrated in power users, your navigation hypothesis is likely correct.
*   **Entry Point Analysis:** Compare drop-off rates for users landing directly on deep-link reports vs. the homepage. A spike in homepage exits with no subsequent page views indicates navigation failure.
*   **Browser/Device Split:** Rule out technical rendering issues specific to certain environments.

**2. Analyze Support Ticket Content**
Categorize the 40% increase in tickets immediately:
*   **"Can't Find" Tags:** Count tickets mentioning specific missing reports or navigation terms.
*   **Error Reports:** Separate functional bugs (broken links, 404s) from usability confusion.
*   **Time-to-First-Ticket:** Measure the time between login and ticket submission. A sharp decrease suggests immediate blockage.

**3. Session Replay Sampling**
Review 20-30 session recordings of power users who logged in post-launch but did not access a report. Look specifically for:
*   "Rage clicks" on old navigation locations.
*   Sessions ending within 30 seconds of landing on the new dashboard.
*   Repeated failed search queries for standard reports.

## Critical Metrics to Monitor (Days 3-5)

Track these daily to determine the trajectory:

| Metric | Definition | Success Signal | Failure Signal |
|--------|------------|----------------|----------------|
| **Task Completion Rate** | % of sessions where a user opens ≥1 core report | Stabilizing or increasing | Continued decline |
| **Navigation Depth** | Average pages viewed per session | Returning to pre-launch levels | Remains shallow (1-2 pages) |
| **Search-to-Report Ratio** | % of searches that lead to a report view | High conversion | High search volume with zero report views |
| **Support Ticket Velocity** | New tickets per 1,000 DAU | Decreasing trend | Flat or increasing |
| **Power User Retention** | DAU of users with >20 historical logins | Flat or recovery | Continued double-digit drop |

## Decision Matrix for CTO

Use the Day 5 data to make the rollback decision:

**Scenario A: Temporary Learning Curve (Do Not Rollback)**
*   *Indicators:* Task completion rates are recovering daily; support tickets are shifting from "can't find" to "how-to"; power user drop-off stabilizes.
*   *Action:* Deploy targeted in-app tooltips or a "classic view" toggle for 48 hours while users adapt.

**Scenario B: Fundamental Workflow Failure (Rollback Required)**
*   *Indicators:* Power user retention continues to drop >5% day-over-day; >60% of support tickets cite inability to complete core tasks; session depth remains critically low.
*   *Action:* Immediate rollback to previous version for power user segment while fixing navigation for a phased re-release.

**Scenario C: Technical Blocker (Hotfix Required)**
*   *Indicators:* High error rates in logs; specific browser/device cohorts show 100% drop-off; search function returns no results.
*   *Action:* Engineering hotfix for specific broken components without full rollback.

Focus strictly on the **Power User Retention** and **Task Completion Rate** metrics. If these two do not show a positive trend by Thursday, the risk of permanent churn outweighs the cost of a rollback.

*Note: Ensure all data comparisons normalize for day-of-week effects (e.g., compare Tuesday to Tuesday, not Monday to Tuesday).*
