### Delivery Plan: Auto-Updates with Staged Validation

**Lanes & Parallelism**
Work splits into three parallel lanes once the branch is cut:
1.  **Pipeline Configuration (DevOps):** Modify the CI definition to introduce a two-stage test gate. Stage 1 runs only `smoke-tests` (targeting billing calculation integrity). Stage 2 triggers a detached background job for the full regression suite.
2.  **Alerting Integration (SRE):** Configure the background job failure handler to bypass standard ticketing and immediately page the on-call engineer via the primary incident channel.
3.  **Flake Mitigation (Ledger Team):** Isolate the known flaky currency conversion check. Tag it to be excluded from the Stage 1 smoke suite to prevent false-positive blocking, while retaining it in the Stage 2 full suite for trend monitoring.

**Serialization Constraints**
*   The `global-rules.json` update must be the final commit in the PR to minimize merge conflict windows with other teams.
*   Alerting configuration must be verified in staging before the auto-merge policy is activated.

**Gates & Checks**
All checks run on the exact merge commit generated by the update bot, prior to merging.
*   **Gate 1 (Hard Block):** Smoke tests must pass 100%. This suite excludes the flaky currency check but includes all core billing arithmetic assertions. If this fails, the PR is rejected immediately.
*   **Gate 2 (Soft Block):** The `global-rules.json` lint check ensures no schema violations exist.
*   **Background Check:** The full 40-minute suite runs asynchronously post-merge. Its status does not block the initial merge but triggers the "Red" state for the commit hash.

**Review Process**
*   **Code Review:** The Pipeline and Alerting changes require approval from one Senior Ledger Engineer (excluding Jane Smith, to reserve her for deployment approval) AND one SRE.
*   **Independence:** The reviewer must not be the author of the pipeline logic. They must verify that the smoke suite explicitly excludes the flaky test and that the background job failure path guarantees an alert.
*   **Security Scan:** An automated dependency vulnerability scan runs on the PR; high-severity findings block merge regardless of test status.

**Landing Strategy**
*   **Merge Mechanism:** Auto-merge is enabled on the PR once Gate 1 and Gate 2 pass. The bot merges immediately upon green status.
*   **Staging Deployment:** Despite auto-merge, deployment to Staging remains manual. Jane Smith must explicitly approve the promotion of the new commit hash to Staging. This provides a human firewall before any data migration scripts can run.
*   **Production Deployment:** Remains locked to the Tuesday maintenance window. No changes to this constraint.

**Human Decisions & Rollback**
*   **Human Decision Required:** If the background job fails after merge, the on-call engineer must decide within 30 minutes whether to revert the dependency or patch the application code.
*   **Rollback Protocol:** Because data migrations are irreversible, a "revert" commit is only safe if the dependency change did not trigger a migration.
    *   *Scenario A (No Migration):* Standard git revert is executed.
    *   *Scenario B (Migration Executed):* Rolling back the code is forbidden. The team must deploy a forward-fix to maintain compatibility with the new data schema. The on-call engineer must confirm migration status before authorizing any revert action.
*   **Cost Control:** If the background job fails due to the known flaky test, the SRE must update the exclusion list; repeated flaky failures in Stage 2 warrant disabling that specific test until stabilized.

This plan balances speed (smoke tests ~2 mins) with safety (background validation + manual staging approval), ensuring security patches land quickly without risking production billing integrity.
