### Delivery Plan: Unified Core Validator

**Objective:** Consolidate Billing, Logistics, and Identity validation libraries into a single backward-compatible core without halting feature releases.

#### 1. Lanes & Parallelism
Work is divided into three parallel lanes to maximize throughput while managing dependencies.

*   **Lane A (Core Construction):** Extracts common logic from the three source folders into `libs/unified-validator`. This team defines the canonical error messages and business rules. They operate independently of the microservices initially.
*   **Lane B (Adapter & Compatibility):** Creates backward-compatible wrapper layers for each of the three existing libraries. These wrappers redirect calls to the new Unified Core but maintain old function signatures and error formats exactly. This allows existing callers to function without code changes.
*   **Lane C (Adoption & Documentation):** Drafts the adoption guide and prepares migration scripts for each microservice. They also prepare the "rollback switches" in the configuration of each service to toggle between legacy and unified logic.

*Serialization Point:* Lane B cannot finalize until Lane A produces the first stable interface definition. Lane C cannot finalize migration scripts until Lane B validates the adapters.

#### 2. Gates & Checks
Given the $45/22-minute build cost and flaky Tuesday tests, gates are strict and scheduled strategically.

*   **Gate 1: Interface Freeze (Revision `feat/unified-core-v0.1`):** Before full implementation, Lane A and B leads review the proposed function signatures and error schemas. No code is merged until Jane Smith and John Doe provide asynchronous written approval on this design doc (bypassing their leave status via documented async consent).
*   **Gate 2: The "Wednesday" Build:** Full integration builds are scheduled strictly for Wednesdays or Thursdays to avoid the known Tuesday test flakiness. Any build failure on these days triggers an immediate pause; manual retry authorization is reserved for confirmed infrastructure glitches, not code defects.
*   **Gate 3: Dual-Run Verification:** Before merging to main, the Unified Core must run in "shadow mode" alongside legacy libraries in the staging environment for 24 hours. Discrepancies in validation results block promotion.

#### 3. Review Strategy
To ensure independence and quality:

*   **Code Review:** Lane A (Core) code is reviewed by senior engineers from Billing and Logistics (excluding their own authors). Lane B (Adapters) is reviewed by the Identity team lead. This cross-pollination ensures no single team's bias dominates the unified logic.
*   **Architecture Review:** The final merge request requires sign-off from one of the two senior architects. If both remain unavailable, a designated delegate (pre-approved by management) must sign off, referencing the original async approval from Gate 1.
*   **Documentation Review:** The adoption guide is reviewed by a developer from each of the three teams who did *not* write the migration scripts, ensuring clarity for the end-user.

#### 4. Landing & Rollback
The merge strategy prioritizes safety and reversibility.

*   **Phased Rollout:**
    1.  **Merge 1:** The new `libs/unified-validator` and adapters merge to `main` behind a feature flag disabled by default.
    2.  **Pilot:** Enable the new library for 5% of traffic in the Identity service (lowest risk). Monitor error rates.
    3.  **Expansion:** Gradually enable for Logistics, then Billing, waiting 24 hours between each.
*   **Human Decision Points:** Explicit written approval is required before moving from Pilot to Expansion phases. This requires contacting Jane Smith or John Doe (or their delegate) specifically for the go-ahead.
*   **Rollback Protocol:** If regressions occur, the configuration switch in the affected microservice is toggled immediately to revert to the legacy library path. This requires no code revert, only a config change, ensuring the rest of the platform remains unaffected. The unified library remains in `main` but disabled until fixes are applied.

This plan minimizes expensive rebuilds, navigates personnel constraints, and ensures a safe, reversible transition.
