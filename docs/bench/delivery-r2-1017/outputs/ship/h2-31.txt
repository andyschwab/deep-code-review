### 3. Review Strategy

*   **Cross-Language Peer Review:** Prevents team-specific blind spots.
*   **Changelog Verification:** Treated as a functional requirement, not documentation. If the changelog lacks the specific SLA wording, the lane fails G5.
*   **Go Flakiness Mitigation:** The review explicitly accepts the "Flake Evidence Packet" as a substitute for the automated latency check, preventing blockage by known infrastructure noise.

### 4. Landing & Rollback

*   **Merge Strategy:** All three repos merge to their respective release branches on Monday morning. No merging to `main` until Tuesday.
*   **Publishing:** Scripts prepared to publish all three packages in a single atomic operation (or as close as the registry APIs allow) during the Tuesday window.
*   **Human Decisions Required:**
    1.  **David Chen:** Manual override of Go network latency gate (Monday).
    2.  **Security Officer + Product Owner:** Dual approval for production publish (Tuesday).
*   **Rollback Plan:**
    *   **Pre-Publish:** If validation fails at G7, halt. Revert spec update (if possible) or patch spec to revert version.
    *   **Post-Publish:** Reverting is **irreversible** per ticket constraints. If a defect is found post-publish:
        1.  Immediately issue a hotfix version (e.g., x.y.z+1) reverting the timeout to 30s or fixing the root cause.
        2.  Notify enterprise customers of the caching issue and provide the new version coordinates.
        3.  Do not attempt to "unpublish"; the old binary remains cached downstream.

### 5. Risk Mitigation

*   **Spec Build Cost:** The 4-hour build runs once. If it fails, diagnose immediately; do not retry blindly.
*   **Version Drift:** Version numbers are derived programmatically from the spec file in each lane to prevent manual entry errors.
*   **Timing:** All lanes freeze code on Monday. Tuesday is strictly for approval and execution.
