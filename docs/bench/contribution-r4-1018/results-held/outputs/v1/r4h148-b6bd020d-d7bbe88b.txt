### Proposed Pull Request Structure

**Title:** feat: Add pluggable interface for regional holiday providers

**Problem:**
The current holiday lookup module hardcodes federal holidays, causing `InvalidHolidayException` crashes when users in regions with additional statutory observances attempt to schedule deliveries. The existing architecture lacks an extension point for local variations without modifying core logic.

**Proposed Change:**
Refactor the holiday lookup module to support a generic `HolidayProvider` interface. This allows external modules to inject regional logic without altering the core codebase or hardcoding specific dates.

1.  **Define Interface:** Create an abstract base class `HolidayProvider` with a method `get_holidays(year: int) -> List[date]`.
2.  **Refactor Core:** Update the `HolidayService` to accept a list of `HolidayProvider` instances via dependency injection.
3.  **Default Implementation:** Move existing federal holiday logic into `FederalHolidayProvider`.
4.  **Extension Point:** Document how downstream users can implement custom providers (e.g., `QuebecHolidayProvider`) and register them at application startup.

**Code Skeleton (Generic):**
```python
from abc import ABC, abstractmethod
from datetime import date
from typing import List

class HolidayProvider(ABC):
    @abstractmethod
    def get_holidays(self, year: int) -> List[date]:
        pass

class HolidayService:
    def __init__(self, providers: List[HolidayProvider]):
        self.providers = providers

    def is_holiday(self, target: date) -> bool:
        for provider in self.providers:
            if target in provider.get_holidays(target.year):
                return True
        return False
```

**Testing Strategy:**
- Unit tests verifying `HolidayService` aggregates results from multiple mock providers.
- Integration test demonstrating the default `FederalHolidayProvider` behavior remains unchanged.
- Example snippet in documentation showing how to instantiate a custom provider (using synthetic dates like "January 3rd" instead of real policy data).

**Risk:**
Low. The change is additive and backward-compatible if the default provider is registered automatically. No existing logic is removed.
