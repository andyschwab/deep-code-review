**Title:** RFC: Deprecating `processLayout` in favor of `fetchDataAndRender` to resolve critical semantic confusion

**The Problem**
The function `processLayout` currently performs data fetching and rendering, not layout calculation. This semantic mismatch is not merely stylistic; it has directly caused production bugs where developers assumed the function was safe to call during layout passes, leading to re-entrancy issues and UI freezes. The name actively misleads competent engineers, creating a recurring tax on the community.

**The Constraint**
We fully respect the project's policy against breaking changes in minor versions. A direct rename is unacceptable. However, maintaining a dangerously misleading API name also carries a high cost in downstream bugs and support burden.

**The Proposal: A Zero-Breakage Migration Path**
We propose a phased deprecation that introduces clarity without breaking existing code:

1.  **Introduce `fetchDataAndRender`:** Add the new, accurately named function in the next minor release. Its implementation simply calls the existing logic.
2.  **Deprecate `processLayout`:** Mark the old function as `@available(*, deprecated, renamed: "fetchDataAndRender")`. This triggers compiler warnings for all downstream users, guiding them to update at their own pace, but causes no runtime failures.
3.  **Documentation Update:** Immediately update docs to label `processLayout` as "Legacy/Misleading" with a prominent warning box explaining the historical confusion.
4.  **Removal Timeline:** Propose removing `processLayout` only in the next *major* version (e.g., v3.0), giving the community 12+ months to migrate via compiler warnings.

**Why This Works**
*   **No Breaking Changes:** Existing apps compile and run exactly as before.
*   **Active Guidance:** Compiler warnings force the issue into every developer's daily workflow, ensuring gradual migration without manual effort.
*   **Reduced Maintenance:** The alias pattern is trivial to maintain (one line of code) compared to the ongoing cost of debugging confusion-induced bugs.
*   **Community Safety:** It prevents new users from falling into the same trap we encountered at Hooli.
