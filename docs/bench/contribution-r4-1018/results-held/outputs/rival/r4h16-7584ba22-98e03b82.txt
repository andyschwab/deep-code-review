**Title:** `[CRITICAL] Query Planner Memory Corruption on Complex Join with Aggregation`

**Environment:**
- **Engine Version:** [Upstream Version Number, e.g., v2.4.1]
- **OS/Arch:** Linux x86_64 (Kernel 5.15+)
- **Deployment:** Distributed Cluster (3+ nodes)

**Issue Description:**
The database engine crashes with a segmentation fault (SIGSEGV) when executing a specific class of queries involving nested sub-queries, outer joins, and aggregate functions. The crash occurs consistently in the query planner phase during cost estimation, specifically when handling statistics for tables with high cardinality skew.

**Root Cause Analysis (Sanitized):**
Analysis of the core dump indicates a use-after-free error in the `query_planner::estimate_cost` module.
1.  **Trigger:** The planner incorrectly frees a statistics buffer associated with a temporary table created during sub-query expansion.
2.  **Failure Point:** Subsequent access to this freed memory occurs when calculating join selectivity for the outer query.
3.  **Evidence:** The stack trace confirms the fault address lies within the planner's cost estimation loop, immediately following a memory deallocation call in the temporary table cleanup routine.

**Reproduction Steps (Generic):**
1.  Create a table with >1M rows and highly skewed distribution on Column A.
2.  Execute a query joining this table with a derived sub-query that filters on Column A and performs a `COUNT(DISTINCT ...)` aggregation.
3.  Observe immediate crash during planning phase before execution begins.

**Proposed Fix:**
The fix involves deferring the deallocation of the statistics buffer until the completion of the entire cost estimation pass for the current query block. A patch is attached (`fix_planner_uaf.patch`) which:
-   Moves the `drop()` call for the stats buffer to the end of the `optimize_join` scope.
-   Adds a regression test case simulating high-cardinality skew to prevent recurrence.
