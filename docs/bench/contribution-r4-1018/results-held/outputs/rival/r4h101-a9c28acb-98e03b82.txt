## Summary
Fixes a critical deadlock in the broker configuration startup sequence caused by inconsistent lock ordering, which currently causes the application to hang after 45 seconds of inactivity under multi-threaded load.

## What
- Refactored the synchronization logic in the broker initialization module to enforce a strict, deterministic lock acquisition order.
- Added a guard to prevent recursive lock attempts during the configuration loading phase.
- No changes to public APIs or configuration file formats.

## Why
When multiple threads access custom broker configurations during startup, the current implementation acquires locks in an order dependent on input parsing speed. This race condition leads to a circular wait (deadlock). The 45-second timeout is the system's default thread-block threshold triggering the failure. This fix ensures thread safety regardless of configuration complexity or load.
