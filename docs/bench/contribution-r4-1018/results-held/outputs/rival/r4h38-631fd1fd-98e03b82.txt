**Subject: Design Proposal: Extensible Plugin API for Custom Rule Injection**

**Summary**
This proposal outlines a new plugin architecture for StaticLint to allow users to inject custom analysis rules without modifying the core codebase. Currently, extending StaticLint requires forking the project, which creates maintenance burdens for users and fragments the ecosystem. By introducing a stable, documented hook system, we can empower the community to address domain-specific linting needs while keeping the core project lean and focused.

**Problem Statement**
StaticLint excels at standard code analysis, but diverse industries often require specialized checks that fall outside the scope of a general-purpose tool. At present, teams facing unique constraints (such as proprietary coding standards or domain-specific anti-patterns) must maintain private forks. This leads to:
*   **Drift:** Private forks struggle to merge upstream improvements.
*   **Redundancy:** Multiple organizations independently solve similar extension problems.
*   **Barrier to Entry:** Users without deep Python expertise cannot easily customize the tool.

**Proposed Solution: The `staticlint-plugins` Interface**
We propose a formal plugin entry point using Python's native `pkg_resources` or `importlib.metadata` systems. This allows external packages to register themselves as StaticLint extensions.

1.  **Hook Definition:** A clear abstract base class (`BaseRule`) defining the interface for custom rules (e.g., `visit_node`, `report_issue`).
2.  **Discovery Mechanism:** StaticLint will scan for registered entry points at startup, loading valid plugins dynamically.
3.  **Configuration:** A section in `.staticlintrc` to enable/disable specific plugins and pass generic configuration parameters (e.g., thresholds, file patterns).

**General Use Cases**
This architecture supports a wide range of community needs beyond standard linting:
*   **Framework-Specific Checks:** Rules tailored for niche web frameworks or data pipelines not yet supported in core.
*   **Legacy Migration:** Temporary rules to enforce patterns during large-scale refactors or language version migrations.
*   **Security Hardening:** Organization-specific security policies that exceed general CWE coverage.
*   **Educational Tools:** Custom rules for teaching environments to enforce specific style guides or architectural constraints.

**Implementation Plan**
1.  **Phase 1 (Core):** Define the `BaseRule` interface and the discovery logic. No UI changes.
2.  **Phase 2 (Documentation):** Publish a "Writing Your First Plugin" guide with a reference implementation.
3.  **Phase 3 (Ecosystem):** Create a curated list of community plugins in the README to demonstrate viability.

**Backward Compatibility**
This change is purely additive. Existing installations and configurations will remain unaffected. The core rule set remains the default; plugins are opt-in.

**Request for Feedback**
Before proceeding with implementation, we seek maintainer feedback on:
*   The proposed interface design for `BaseRule`.
*   Preferences for the discovery mechanism (entry points vs. config-path loading).
*   Any security concerns regarding dynamic code loading that should be addressed in the design phase.

This approach ensures StaticLint remains adaptable to evolving industry needs while maintaining the stability and simplicity of the core project.
