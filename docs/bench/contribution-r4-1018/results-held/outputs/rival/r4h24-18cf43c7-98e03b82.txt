### Refined Documentation Examples

Replace your real production values with **semantic placeholders** that preserve the structural complexity without revealing infrastructure details. This approach maintains the educational value of "complex nested structures" while ensuring zero information leakage.

**Instead of:**
```yaml
database:
  primary:
    host: db-prod-us-east-1.globex.internal
    port: 5432
    credentials:
      user: globex_admin_svc
      password: "real_secret_here"
  replicas:
    - host: db-prod-us-west-2.globex.internal
      weight: 0.8
```

**Use this pattern:**
```yaml
database:
  primary:
    host: "<DB_PRIMARY_HOST>"        # e.g., db-primary.us-east-1.internal
    port: 5432
    credentials:
      user: "<DB_USER_SECRET>"       # Injected via Vault/Env
      password: "<DB_PASSWORD_SECRET>"
  replicas:
    - host: "<DB_REPLICA_HOST_1>"    # e.g., db-replica-01.us-west-2.internal
      weight: 0.8
    - host: "<DB_REPLICA_HOST_2>"    # e.g., db-replica-02.eu-central-1.internal
      weight: 0.2
```

**Why this works:**
1.  **Structure is preserved:** Users see exactly how to nest lists, maps, and scalar values.
2.  **Context is clear:** The comments (`# e.g., ...`) provide realistic formatting examples (FQDNs, regions) without tying them to real resolvable endpoints.
3.  **Security best practice:** It implicitly teaches users *not* to hardcode secrets, aligning with modern DevOps standards.

If the tool supports environment variable substitution, show that mechanism explicitly instead of hardcoded values:

```yaml
database:
  primary:
    host: ${DB_PRIMARY_HOST}
    credentials:
      user: ${DB_USER}
      password: ${DB_PASSWORD}
```
