### Strategy: Separate Technical History from Attribution

Do **not** include "Fixed by Hooli" or any company name in the commit message. In functional programming communities and most mature open-source projects, commit messages are treated as immutable technical logs. Inserting corporate attribution into the `git log` is widely perceived as noise and self-promotion, which can trigger immediate skepticism from maintainers, regardless of the fix's quality. It violates the "spirit" of a technical changelog even if no explicit rule forbids it.

Instead, adopt a **two-layer attribution strategy**: keep the commit history purely technical to satisfy the project culture, and place the corporate credit prominently in the PR description and metadata where it belongs.

#### 1. The Commit Message (Technical Only)
Strictly follow the project's functional/technical format. Focus entirely on the *what* and *why* of the code change, sanitized of client data.

**Format:** `<type>(<scope>): <technical description>`

**Example:**
```text
fix(indexer): prevent corruption on multi-byte Unicode normalization

The index writer failed to handle specific combining character sequences,
leading to state corruption during concurrent writes. This patch ensures
all input strings are normalized to NFC form before hashing.

- Add normalization step in `Index.build`
- Extend property tests to cover edge-case Unicode ranges
- Fix off-by-one error in buffer flush logic
```
*Note: No mention of Hooli, the client, or the support case.*

#### 2. The PR Description (Attribution & Context)
This is where you satisfy your manager's requirement for visibility. The PR body is the appropriate place for narrative context, sponsorship acknowledgment, and sanitized case background.

**Structure to use:**

*   **Summary:** Briefly state the fix.
*   **Motivation (The Credit):** Explicitly state the origin.
    > "This fix was prioritized and engineered by **Hooli** engineering teams after encountering a critical production issue affecting a major enterprise deployment. We are contributing this back to ensure the wider community benefits from the resolution."
*   **Sanitized Context:** Describe the trigger without leaking data.
    > "The issue was triggered by high-volume ingestion of specific Unicode combining sequences common in internationalized datasets. Specific query patterns from the incident have been abstracted into new property-based tests to prevent regression without exposing proprietary data."
*   **Test Plan:** List the commands and the new test coverage.

#### 3. Protecting Client Confidentiality
You mentioned specific query patterns triggered the bug.
*   **Do not** paste raw logs or specific search strings into the PR, even if you think they are obscure.
*   **Do** convert the specific pattern into a generalized unit test or property test. For example, instead of testing the exact client string, test the *class* of Unicode characters (e.g., "Combining Diacritical Marks") that caused the failure.
*   State in the PR: "Reproduction steps have been generalized into property tests to protect user privacy while ensuring the bug class is covered."

#### 4. Execution Checklist
1.  **Commit:** Write the message purely technically.
2.  **PR Body:** Add the "Sponsored by/Fixed by Hooli" line in the **Motivation** section.
3.  **Author Metadata:** Ensure your git config email matches the one linked to your GitHub account, and that your GitHub profile clearly lists your employment at Hooli. This provides permanent, clickable attribution on your profile without cluttering the code history.
4.  **Internal Reporting:** Show your manager the PR URL. The web view prominently displays "Contributed by [You] at Hooli" via your profile and the PR body text, which satisfies the engagement strategy without risking the PR being closed for poor etiquette.

This approach respects the maintainers' culture (clean history) while securing the visibility your employer requires (narrative credit), all while maintaining strict data hygiene.

*Note: If the project has a `CONTRIBUTING.md` file, double-check it for any specific clauses regarding "corporate contributions" or "disclosure," though the strategy above is the standard best practice.*
