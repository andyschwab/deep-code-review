Do not push back yet; the maintainer's request is standard for mature libraries, even for tiny fixes, when the change alters observable behavior.

Your fix changes a "silent failure" into an "error." To a user, this is a **breaking change**, not a bug fix. Code that previously ran (ignoring the bad config) will now crash. In semantic versioning, this requires a major version bump or a very clear migration path. The maintainer isn't testing your commitment; they are protecting users from unexpected crashes and ensuring the release notes explain *why* their app suddenly stopped starting.

**Immediate Action Plan:**

1.  **Reframe the Change:** Acknowledge in the PR that while the code diff is small, the *behavioral* diff is large. "Silent ignore" → "Throw Error" is a contract change.
2.  **Draft the Changelog Entry:** Keep it brief but precise.
    *   *Example:* "Breaking: Parser now throws an error on nested keys with trailing whitespace instead of silently ignoring them. This prevents invalid configurations from being loaded."
3.  **Write the Migration Note:** One sentence is often enough.
    *   *Example:* "If your configuration files previously contained trailing spaces in nested keys, remove them to prevent startup errors. The parser now strictly validates key names."
4.  **Update API Docs:** Add a single line to the parsing function's documentation stating it "throws on invalid key formatting, including trailing whitespace."

**Response Template to Maintainer:**

> "Thanks for the review. I initially viewed this as a trivial bug fix, but you're right—changing from silent failure to an error is a breaking change for anyone relying on the old behavior.
>
> I will add:
> 1. A `BREAKING` note to the changelog explaining the shift to strict validation.
> 2. A migration snippet advising users to trim trailing spaces in their configs.
> 3. A docstring update clarifying the new error condition.
>
> I'll push these updates shortly. Thanks for catching the impact assessment."

This approach shows you understand the ecosystem impact, not just the code. It usually takes less than 30 minutes to write these three items, saving you from a contentious debate and getting your critical fix merged faster.

Note: If the project has no formal release process or versioning, ask if a "deprecation warning" first is preferred over an immediate hard error.
Note: Never argue that "the old behavior was unintentional" as a reason to skip documentation; users depend on what the code *did*, not what the author *meant*.
