Do not open a pull request with the current fix or data. You cannot satisfy the project's requirement for "reproducible using only public data" while relying on non-anonymizable internal PII, and submitting a PR that requires private data to verify will result in an immediate closure or request for changes that you legally cannot fulfill. Furthermore, do not fabricate a test file; if the specific byte sequence is required to trigger the crash, a fabricated file fails to prove the fix works, violating the self-audit principle of only claiming what you can defend with evidence.

Instead, pivot your contribution strategy to one of the following three paths that respect both legal constraints and project rules:

1.  **Synthetic Reproduction:** Isolate the specific hex pattern causing the `0x8007000B` error (e.g., a specific invalid byte sequence or malformed header) and write a small script to generate a synthetic file containing *only* that pattern mixed with generic, public dummy text. If the crash is truly a text encoding/stream parsing issue, it should trigger on the specific byte sequence regardless of the surrounding "customer" context. This creates a public, reproducible fixture.
2.  **Unit Test the Logic:** If the crash occurs in a specific method during stream initialization, extract that logic into a unit test that feeds the problematic byte array directly into the method, bypassing the need for a full "file upload" fixture. Unit tests can assert on byte arrays without needing a physical file that resembles real PII.
3.  **Issue-First Approach:** If you cannot synthesize the crash without the real data, close your code editor. Open an issue on the repository instead. Describe the bug, the error code, the region affected, and the *nature* of the encoding failure without sharing the data. Explicitly state: "I have a fix verified internally against private logs, but I cannot generate a public reproduction case without violating data privacy policies. I am seeking maintainer guidance on how to proceed—can we establish a private channel for verification, or is there a specific synthetic pattern you recommend testing?"

**PR Description Strategy (Only if you achieve Path 1 or 2):**
If you successfully create a synthetic reproduction, your PR description must include a "Test Plan" section that explicitly documents how the synthetic file was generated (e.g., "Generated via `scripts/generate_bad_utf8.py` to inject byte sequence `0xEF 0xBB 0xBF` at offset X"). Do not mention Acme Corp, internal logs, or PII. The narrative must be: "This PR fixes error 0x8007000B caused by malformed stream headers. A new public test fixture `test_apac_encoding_fail.bin` reproduces the crash using synthetic data mimicking the observed byte pattern."

**Note:** Never attempt to describe hex patterns of private data in a public issue if there is any risk they constitute unique identifiers; stick to describing the *class* of error.
**Note:** If the maintainers do not respond to the issue regarding private verification, do not submit the code; the contribution barrier is currently insurmountable under their stated rules.
