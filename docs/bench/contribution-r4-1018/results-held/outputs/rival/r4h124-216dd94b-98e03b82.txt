### Proposed Solution: Generic CA Bundle Injection via Environment Variable

To satisfy the maintainers' strict policy against bundling private certificates while solving your SSL handshake error, you must implement a **generic, user-provided CA bundle loader**. This approach shifts the trust anchor injection from the codebase to the runtime environment, ensuring zero traces of Globex's specific CA appear in the PR.

#### 1. Code Modification Strategy
Modify the Go client's TLS configuration initialization to check for a specific environment variable (e.g., `MQ_EXTRA_CA_CERTS`). If present, the code should read the file path(s) listed in this variable, parse the PEM blocks, and append them to the system's default certificate pool.

**Key Implementation Details:**
*   **No Hardcoded Paths:** Do not reference any specific directory or filename associated with Globex.
*   **No Embedded Data:** Do not include any certificate strings, base64 blobs, or hex dumps in the source code or comments.
*   **Fallback Behavior:** If the environment variable is unset, the client must behave exactly as it does today (using only the system trust store). This ensures backward compatibility.
*   **Error Handling:** If the path is invalid or the file contains no valid certificates, log a warning but allow the application to continue (or fail gracefully depending on existing error policies), rather than crashing immediately.

**Conceptual Logic:**
```go
// Pseudocode for the modification
rootCAs, err := x509.SystemCertPool()
if err != nil {
    // Handle system pool failure per existing project standards
}

if caPath := os.Getenv("MQ_EXTRA_CA_CERTS"); caPath != "" {
    customCAs, err := os.ReadFile(caPath)
    if err != nil {
        log.Printf("Warning: Could not read extra CA certs from %s: %v", caPath, err)
    } else {
        if !rootCAs.AppendCertsFromPEM(customCAs) {
            log.Printf("Warning: No valid certificates found in %s", caPath)
        }
    }
}

// Use rootCAs in tls.Config
```
