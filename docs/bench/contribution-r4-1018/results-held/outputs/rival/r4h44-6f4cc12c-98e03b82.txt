Do not open the pull request yet. Submitting a PR that explicitly fails the project's "test on all supported platforms" requirement without a prior agreement is the fastest way to have your contribution closed as "non-compliant." Instead, follow this protocol to secure the necessary testing coverage while maintaining professional credibility:

**1. Open a Pre-PR Issue (The "RFC" Approach)**
Create a new issue titled something like `RFC: Fix for glyph clipping at 14pt (Linux verified, macOS test needed)`. In the body:
*   **Describe the bug** and your specific fix (bounding box calculation).
*   **Provide Evidence:** Paste the exact Linux build commands you ran, the test output logs, and a link to a Gist containing your diff. This proves the work is real and the Linux path is green.
*   **State the Blocker Clearly:** Explain that you lack macOS build capabilities due to IT restrictions and cannot satisfy the `CONTRIBUTING.md` requirement for macOS verification.
*   **Make a Specific Ask:** Request one of three things:
    *   Can a maintainer pull your branch and run the macOS CI/tests?
    *   Is there a Docker-based or cross-compilation method you missed that simulates the macOS environment on Linux?
    *   Can they grant temporary access to a CI runner or provide a test binary?

**2. Leverage Continuous Integration (CI)**
Check if the repository uses GitHub Actions, CircleCI, or similar. If so:
*   Push your fix to a branch on your fork.
*   See if the CI automatically spins up a macOS runner for your branch (many projects do this for all PRs/branches).
*   If the CI runs and passes on macOS, you have your proof. If it fails, you have the specific error log to discuss.
*   If the CI *doesn't* run automatically for fork branches without a PR, mention this in your issue: "I cannot trigger the macOS CI runner without opening a draft PR. Would you be open to me opening a **Draft** PR solely to trigger the CI matrix?"

**3. The "Draft PR" Compromise**
If the maintainers respond positively to your issue, they may invite you to open a **Draft Pull Request**.
*   Mark it clearly as `[WIP]` or `Draft`.
*   In the description, reiterate: "Linux tests passed locally. macOS verification pending CI run/maintainer review due to contributor hardware constraints."
*   This keeps the conversation in the PR thread where code review happens, but the "Draft" status signals you are not yet claiming the work is merge-ready.

**Why this works:**
Maintainers appreciate contributors who respect their quality gates. By flagging the gap *before* submitting, you show you read the rules and are trying to comply, rather than ignoring them. It shifts the dynamic from "Here is a broken PR" to "Here is a solution; how do we jointly verify the final step?"

**Note:** Never claim "tested on Mac" if you haven't; maintainers can often spot platform-specific artifacts in code or logs, and dishonesty here will blacklist you from the project. If the project refuses to help test and insists you provide macOS proof, you may have to pause the contribution until you can access the hardware.
