### Refactored Test Data Strategy

To eliminate the risk of exposing Initech's proprietary database schema, you must discard the AI-generated JSON structures entirely. Renaming fields is insufficient because the nesting depth, hierarchy, and specific combination of fields constitute a "structural fingerprint" that can still reveal internal architecture.

Follow this procedure to create safe, generic test data:

1.  **Flatten and Generalize the Schema**: Replace the complex, nested customer object with a minimal, flat structure containing only the primitives required for the currency calculation function.
    *   *Before (Risky)*: `{"client": {"profile": {"id": "...", "tier": "..."}, "accounts": [{"currency": "USD", "balance": ...}]}}`
    *   *After (Safe)*: `{"amount": 100.50, "source_currency": "USD", "target_currency": "EUR"}`
    *   If your function requires a context object, invent a generic name like `ConversionContext` rather than `CustomerProfile` or `AccountRecord`.

2.  **Use Synthetic, Domain-Agnostic Values**: Ensure values do not mimic real-world patterns specific to your client base (e.g., specific ID formats or tier names).
    *   Use standard ISO currency codes (USD, EUR, JPY) which are public knowledge.
    *   Use simple integers or decimals for amounts (e.g., `100`, `0.01`, `999999.99`) rather than values that might match real transaction logs.
    *   Remove any optional fields that are not strictly asserted in your test logic. If the test doesn't check a field, the input shouldn't contain it.

3.  **Validate Logic via Behavior, Not Structure**: Robust testing comes from asserting mathematical correctness and edge case handling (overflow, underflow, rounding modes, zero values), not from mirroring production data complexity.
    *   Create test cases for: `zero_amount`, `negative_amount` (if applicable), `maximum_precision`, `same_currency_conversion`, and `unsupported_currency`.
    *   Verify that the *output* of the conversion is correct given the simplified *input*.

4.  **Final Verification**: Before committing, review the diff. Ask: "If a competitor saw this JSON, would they learn anything about how we store customer data?" If the answer is yes, simplify further.
