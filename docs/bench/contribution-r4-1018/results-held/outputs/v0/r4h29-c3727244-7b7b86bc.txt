### Proposal Draft: Deprecating `processLayout` in Favor of `fetchDataAndRender`

**Subject:** Proposal: Deprecate misleading `processLayout` with non-breaking migration path

**The Problem: Active Source of Bugs**
The function `processLayout` is semantically incorrect; it performs data fetching and rendering, not layout calculation. This misnomer is not merely a stylistic issue but an active defect causing recurring bugs. Developers, trusting the name, call this function during layout passes, leading to performance jank and race conditions. At Hooli, this specific confusion has resulted in [X] production incidents where engineers assumed the method was safe to call on the main thread during UI updates. The current name violates the principle of least astonishment, directly undermining code safety.

**Respecting the No-Breaking-Change Policy**
We fully respect the project's strict policy against breaking changes in minor versions. We are **not** proposing an immediate rename that would break downstream dependencies. Instead, we propose a standard deprecation cycle that maintains 100% backward compatibility while guiding users toward the correct API.

**Proposed Migration Path**
1.  **Introduce `fetchDataAndRender`:** Add the new, accurately named function with identical implementation.
2.  **Deprecate `processLayout`:** Mark the old function as `@available(*, deprecated, renamed: "fetchDataAndRender")`. This generates compiler warnings for adopters but causes no runtime failures.
3.  **Documentation Update:** Clearly document the distinction and the migration step in the release notes.
4.  **Future Removal:** The old function remains functional until a future major version (e.g., v3.0), adhering to semantic versioning norms.

**Addressing Maintenance Overhead**
The maintenance cost of this approach is negligible. The "alias" is simply a compiler attribute and a thin wrapper (or direct call) to the new implementation. This is a standard Swift pattern supported by the language and IDEs, requiring no complex dual-logic maintenance. The benefit—preventing future bugs caused by confusion—far outweighs the trivial cost of maintaining a deprecated symbol for one major version cycle.

**Request**
We ask permission to open a PR implementing this deprecation cycle. This allows the community to migrate at their own pace without breaking builds, while immediately clarifying the API's intent for all new users.
