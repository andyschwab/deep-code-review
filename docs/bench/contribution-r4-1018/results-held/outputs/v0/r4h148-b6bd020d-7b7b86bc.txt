### Proposed Pull Request Structure

**Title:** feat: Add pluggable interface for regional holiday providers

**Problem:**
The current holiday lookup module hardcodes federal holidays, causing an `InvalidHolidayException` when users in regions with specific statutory observances attempt to schedule deliveries. The existing architecture lacks an extension point for local variations without modifying core logic.

**Proposed Change:**
Refactor the holiday resolution logic to support a generic `IHolidayProvider` interface. This allows external modules to inject regional rules dynamically.
1.  **Define Interface:** Create an abstract base class `IHolidayProvider` with a method `get_holidays(year, region_code)`.
2.  **Refactor Core:** Update the `HolidayService` to accept a list of providers. It will query the default federal provider first, then iterate through registered custom providers.
3.  **Plugin Mechanism:** Implement a discovery mechanism (e.g., entry points or configuration-based loading) to register third-party or local provider implementations at runtime.
4.  **Default Behavior:** Maintain backward compatibility by keeping the federal provider as the sole default implementation.

**Testing Strategy:**
*   Unit tests verifying the `HolidayService` correctly aggregates results from multiple mock providers.
*   Integration test demonstrating a custom provider injecting a synthetic "Regional Day" (e.g., "Example Region Observance") without altering the federal list.
*   Verification that missing providers fail gracefully without crashing the scheduler.

**Risk:**
Low. The change is additive and isolates new logic behind an interface. No existing federal holiday logic is modified.
