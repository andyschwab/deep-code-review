### Proposed Solution: Generic Cache Hook System

Do not propose the header-based logic, even as a configurable option with defaults. Defaulting to non-standard headers creates "slop" (confusion for users who don't have those headers) and implicitly documents your internal architecture. Instead, generalize the lesson into a **Generic Cache Hook System**. This allows any user (including yourself) to inject custom validity logic without the library assuming specific protocols.

#### 1. Generalization Strategy
*   **Remove:** All references to "OmniGlobal," specific header names (e.g., `X-Omni-Cache-TTL`), and any default behavior that inspects headers.
*   **Replace:** Hardcoded header inspection with a user-provided `isCacheValid(response, request)` callback function.
*   **Default Behavior:** The library defaults to standard HTTP caching (e.g., respecting `Cache-Control` headers) or simple time-based expiration if no hook is provided.
*   **Value Proposition:** Users can now implement custom invalidation logic for *any* proprietary gateway, CDN, or edge case without modifying the library source.

#### 2. Code Structure Changes
Refactor the caching layer to accept an optional configuration object:

```javascript
// Before (Conceptual - Do not use)
const client = new ApiClient({
  cacheHeaders: ['X-Omni-Cache-TTL'] // Leaks internal logic
});

// After (Proposed)
const client = new ApiClient({
  cache: {
    ttl: 30000, // Standard time-based fallback
    isValid: (response) => {
      // User-defined logic: Inspect custom headers, body content, or external state
      const ttl = response.headers['x-custom-ttl'];
      return ttl && Date.now() < ttl;
    }
  }
});
```
