**Immediate Action Plan**

1.  **Do Not Close or Reopen Yet:** Closing and reopening creates a new event that may draw more attention to the incident. The edit history is indeed permanent on most platforms, so the link likely still exists in the revision log.
2.  **Contact Maintainers Privately (Critical):** Immediately find a private communication channel (email, Discord DM, or a security contact listed in their `SECURITY.md`). Do not comment further on the public PR yet.
    *   **Message Draft:** "Hello, I made an error in PR #[Number] by briefly including a link to an internal, authenticated resource in the description. I have edited it out, but I know the edit history remains. The link requires authentication and exposes no public data, but I want to respect your privacy policies. Should I close this PR and open a clean one, or can you scrub the edit history on your end? I apologize for the oversight."
3.  **Prepare a Clean Replacement:** Locally create a new branch from the same base. Cherry-pick or copy your code changes (excluding the description). Prepare a new PR draft locally with a completely sanitized description that explains the logic using only public concepts or synthetic examples.
4.  **Follow Their Lead:** Wait for the maintainer's response. They may have admin tools to wipe the edit history entirely, which is the only way to truly "sanitize" it. If they ask you to close it, do so immediately, then open the fresh PR with the clean description.

**Direct Answer to Your Uncertainty**
You cannot fully sanitize the edit history yourself; only repository administrators can typically purge revision logs. Therefore, transparent communication is your only viable path to mitigation. Closing the PR without explanation might look suspicious; admitting the mistake privately demonstrates integrity and usually prevents a ban, especially since the link was not publicly accessible (required authentication).

**Fallback if Maintainers Are Silent**
If you receive no response within 24 hours, close the PR with a comment: "Closing to replace with a clean version due to an accidental inclusion of an internal link in the initial description history." Then, open the new PR with the sanitized content. This shows proactive remediation even without explicit permission.

**Note:** The fact that the link requires authentication significantly reduces the severity, as no actual confidential data was exposed to the public internet.
**Note:** Never attempt to rewrite git history (`git rebase`) to fix a PR description; that only affects code commits, not the web-based description metadata.
