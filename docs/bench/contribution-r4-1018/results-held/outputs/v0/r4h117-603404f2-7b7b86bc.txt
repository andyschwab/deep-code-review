**Subject:** Proposal: Deprecating `parseTimestamp` to resolve DST off-by-one errors (Prep for v2.0)

**The Problem**
Our current `parseTimestamp` utility contains a known logic flaw causing off-by-one errors during daylight saving time transitions. While currently tolerated by many, this introduces subtle data inconsistencies for users in affected timezones. As the library scales, these edge cases become critical liabilities.

**The Constraint**
We recognize that thousands of developers rely on the current behavior. An immediate fix introduces a breaking change that would disrupt existing workflows and violate our commitment to stability in minor releases.

**The Proposal**
Instead of an immediate breaking change, I propose a phased migration:
1.  **Introduce `parseTimestampStrict`:** A new, accurate implementation available immediately for users who need precision today.
2.  **Deprecate Legacy Behavior:** Mark the original function as deprecated with documentation highlighting the DST risk.
3.  **Grace Period:** Add a controlled warning mechanism to alert users of the deprecation, giving the ecosystem time to adapt before we schedule the breaking change for v2.0.

**Long-Term Benefit**
This strategy balances immediate accuracy for new adopters with stability for existing users. It allows us to gather real-world feedback on the new implementation and creates a clear, respectful timeline for the community to migrate. By planning the breaking change for a major version now, we ensure the library's long-term correctness without sacrificing current trust.
