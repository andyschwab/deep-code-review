### Generalized Bug Report & PR Draft

**Title:** Fix image corruption when resizing with specific aspect ratio flags (`--scale` + `--crop`)

**Problem:**
When invoking the tool with the `--scale` flag followed immediately by `--crop` using non-square aspect ratios (e.g., 16:9 or 4:3), the output image exhibits horizontal tearing and pixel corruption in the bottom 15% of the frame. This occurs regardless of the input image format (tested with PNG and JPEG) provided the dimensions trigger the internal buffer reallocation logic.

**Reproduction Steps (Synthetic):**
1.  Generate a synthetic test image: `convert -size 1920x1080 xc:blue test_input.png` (using standard tooling).
2.  Run the vulnerable command:
    ```bash
    ./target/release/image-tool --input test_input.png --output out.png --scale 0.5 --crop 16:9
    ```
3.  **Observed:** The output `out.png` contains visual artifacts/corruption.
4.  **Expected:** The output should be a cleanly resized and cropped image.

**The Fix:**
The issue stems from an off-by-one error in the buffer calculation when the stride changes during the resize operation. The current code calculates the destination buffer size before applying the crop aspect ratio constraint, leading to a truncated write.

*Patch logic:* Adjust the buffer allocation to occur *after* the final dimensions (scale applied, then crop constrained) are resolved.

**Testing:**
- Added a regression test using synthetic 1920x1080 and 1280x720 inputs with various aspect ratios.
- Verified that `cargo test` passes and the new test case fails on the previous commit but passes with this fix.
- Manually verified visual integrity of output files using a diff tool.

**Risk:**
Low. The change isolates the buffer calculation logic without altering the core resizing algorithm. No API changes.
