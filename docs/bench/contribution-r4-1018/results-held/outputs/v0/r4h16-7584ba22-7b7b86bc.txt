**Title:** Query Planner Memory Corruption Leading to Engine Crash on Complex Join Patterns

**Problem Description:**
The database engine crashes with a segmentation fault during the execution of specific multi-table join queries involving nested subqueries and aggregate functions. The crash occurs in the query planner phase when optimizing join order for tables exceeding a certain cardinality threshold. Analysis of the failure mode indicates a memory corruption issue where a pointer is dereferenced after being freed during plan node restructuring.

**Reproduction Steps (Synthetic):**
1. Initialize a database with three tables: `T1` (1M rows), `T2` (500k rows), `T3` (2M rows).
2. Execute a query joining all three tables with a nested subquery filtering on `T3` and grouping by `T1`.
3. Observe immediate crash during the planning phase before execution begins.
   *SQL Pattern:* `SELECT T1.a, COUNT(*) FROM T1 JOIN (SELECT * FROM T2 WHERE ...) AS sub ON T1.id = sub.id JOIN T3 ... GROUP BY T1.a;`

**Root Cause Analysis:**
During the reordering of join nodes, the planner frees a temporary statistics object associated with a subquery plan node. However, a dangling reference to this object persists in the parent context. When the optimizer attempts to recalculate costs for a alternative join path, it accesses the freed memory, leading to corruption and a subsequent crash.

**Proposed Fix:**
The fix ensures the statistics object lifecycle is extended until the full plan generation is complete, or that the reference is nullified immediately upon freeing. A guard clause has been added to verify pointer validity before dereferencing in the `planner_restructure_join_node` function.
