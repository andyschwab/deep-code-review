**Strategy: Escalate via Security Channels, Not Social Pings**

Do not ping Jane or comment on the PR again. A two-month silence on a known Remote Code Execution (RCE) vulnerability suggests the standard review process has failed or the severity is misunderstood. Since you cannot push the fix yourself (upstream authority lies with maintainers) and your production environment is currently exposed, you must shift the vector from a "feature request" style PR to a formal security disclosure.

**Immediate Action Plan:**

1.  **Verify Internal Policy:** Check your employment contract or security handbook for "Vulnerability Disclosure" or "Open Source Contribution" clauses. Most companies explicitly *encourage* escalating unpatched critical vulnerabilities in dependencies you rely on, provided you do not disclose private infrastructure details. You are protecting the company, not leaking secrets.
2.  **Locate the Security Contact:** Look for a `SECURITY.md` file in the repository root, a security policy on the project's website, or an email address like `security@northwind-framework.org`. If none exists, look for the project's listed maintainers on their homepage or package manager metadata.
3.  **Send a Formal Security Notice:** Draft a concise, private email to the security contact (or the lead maintainer if no specific contact exists). Do not mention "Acme Corp" or your specific production setup.
    *   **Subject:** `[SECURITY] Unaddressed RCE in Northwind Framework (PR #<Number>)`
    *   **Body:** "I submitted PR #<Number> two months ago patching a known RCE vulnerability in the file upload module. This issue allows remote code execution under specific conditions. Despite including required changelog entries and backward compatibility tests, the PR has received no response. Our team relies on this framework and is currently exposed. Please advise on the timeline for review or if there is a private security channel we should utilize instead. We are prepared to assist further but require acknowledgment due to the critical nature of the flaw."
4.  **Mitigate Locally:** While waiting, apply the patch internally via a private fork or use a Web Application Firewall (WAF) rule to block the specific file upload vector described in the vulnerability. Do not wait for the upstream merge to secure your production environment.
5.  **The "Nuclear" Option (Last Resort):** If there is absolutely no response to the security notice after 48-72 hours, and the project has no active security team, you may need to consider publishing a "Security Advisory" on your own company blog or via a CVE reservation (if your company is a CVE Numbering Authority), stating that the upstream project is unresponsive. This is rare and damages relationships, so use only if the risk to your users is imminent and unavoidable.

**Direct Answer to Your Uncertainty:**
You should not ping the PR publicly again; it is unlikely to help and may appear impatient. Instead, escalate privately through security channels. Your employer's guidelines almost certainly prioritize securing production systems over "politeness" to an unresponsive open-source project when RCE is involved.

**Fallback:**
If the maintainers remain silent after the security notice, treat the project as unmaintained for security purposes. Plan to fork the repository internally, apply the patch permanently, and evaluate migrating to a more actively maintained alternative in your next architectural cycle.

*Note: Never disclose specific logs, customer data, or internal architecture in your escalation communication.*
*Ensure any communication strips identifiers like "Acme Corp" or specific server hostnames.*
