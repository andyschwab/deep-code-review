# Preregistration: contribution skill, round 4, one edit, held-out n = 150 (2026-10-18)

This file, the harness and the frozen texts are hashed (`SHA256-prereg.txt`) after the tuning phase and before any held-out seed, scenario or answer exists. The held-out seeds and scenarios are then drawn and hashed together with everything above in `SHA256-frozen.txt`; the hash of that list is the first line of `ledger.jsonl`, before any held-out answer or judge call. Every model call goes to the PCSS endpoint ($0); no `claude -p`; all scenarios are fictional. Base: origin/main at d9da3a3b.

## Question

Rounds 2 and 3 (`docs/bench/contrib-narrow-r2-1018`, `docs/bench/contribution-r3-1018`) kept the narrowed skill on the paired rule but did not beat the rival github-contributor: 0.558 [0.458, 0.658] at n = 60 and 0.522 [0.439, 0.606] at n = 90 for the shipped text, and an Answer shape rewrite scored -0.050 [-0.156, 0.056] against it. This round tests one different edit on a fresh n = 150 set. v0 is `.claude/skills/contribution/SKILL.md` on origin/main (7495 bytes), byte-identical to round 3's v0. Does v1 beat v0 against the same rival, and does v1 beat the rival?

## Where the edit comes from (prior losses)

Round 3 kept only verdict numbers, so this round re-judged v0 against the rival on a fresh 30-scenario tune set with the analysis text kept (`tune_diag.py`, GLM-5.1, both orders) and I read the analyses of the 14 scenarios v0 lost in both orders (hand count, one primary reason each): the skill's answer is less concrete to the project than the rival's, which gives runnable test or generator code, a benchmark script or batch sizes (7); the skill refuses, forbids or overrides the requested task with a gate or an assumption about the situation (3); it answers about a draft the requester never pasted (1); other (3). A first edit aimed at the refusal reason (F1: deliver the artifact, a stop check conditions the send, say first when input is missing) scored worse than v0 twice (0.283 and 0.300 against 0.417), and round 3 already showed that answer-shape rewrites do not help. The remaining hypothesis is that the system prompt carries repo-internal text (the opt-in issue-filing paragraph with caps, logs and a script path) that has nothing to do with drafting an upstream PR and that the generator sometimes echoes. The edit removes that paragraph's detail, which is already documented in the script's own docstring (`scripts/share_learning.py`), and keeps the safety facts (issues only, never a PR or push, a privacy-gate failure refuses, default `ask` needs `--approve`).

## Tuning phase (logged in `ledger-tune.jsonl`)

One fresh tune set of 30 scenarios (ids r4t01 to r4t30, `scenarios-tune.json`, seeds in `prompts/seeds-tune.txt`), judge GLM-5.1 only, both orders, v2 protocol, rival answers shared between runs. Win rate against the rival: v0 0.417; F1 0.300 (0.283 in a first run with fresh rival answers); H1 0.508; H2 (H1 plus the repo-internal Rules bullets compressed) 0.433; H1b 0.383 (H1 with its pointer sentence corrected). H1 and H1b are the same edit up to one sentence and differ by 0.125, so the tune set is noise at this size and cannot rank candidates. H1b is frozen as v1 because it is the smallest edit that follows the diagnosis, picked before any held-out data exists; the tune data is no evidence for it. Candidates are in `prompts/variants/` (F1, H1, H1b, H2).

## Arms and data

- v0 = `frozen/contribution.v0.md`. v1 = `frozen/contribution.v1.md` (= `prompts/variants/H1b.md`, 7113 bytes): v0 with the opt-in issue-filing paragraph cut to three lines; if the keep rule holds, `SKILL.md` becomes byte-identical to v1 and its size budget is lowered. Both are final: no further tuning, no edit after the held-out result.
- Rival: `frozen/rival.md` (github-contributor, MIT, sha256 prefix 98e03b82), byte-identical to round 2 and 3. Its answer to each scenario is generated once and shared by both skill arms, so (v1 minus v0) is paired on identical rival text.
- Scenarios: 150 fresh held-out scenarios (ids `r4h01` to `r4h150`, the prefix plus the seed number), seeds drawn by the blind writer model (Qwen3.5-397B-A17B, temperature 0.9; it is shown every earlier contribution seed as an avoid list and a draw that repeats any is rejected), scenarios written in batches of 10 from `prompts/brief.txt` (temperature 0.7, no skill text shown). Disjointness, enforced by `bench.py write`: origin/main is re-fetched immediately before the draw and again immediately before the freeze; every scenario that shares more than 10% of its 6-word shingles with any `.md`, `.json`, `.jsonl` or `.txt` file under `docs/bench` on that base (every earlier scenario, seed, output and record, with this round's own tune scenarios included and its other files excluded) is regenerated, and the draw fails if any id appears anywhere there. The maximum overlap is recorded in `ledger.jsonl`.
- Generator for all arms: Qwen3.5-397B-A17B, thinking off, temperature 0.3, no tools, the harness GEN_TASK wrapper, never a judge.
- Judge: protocol v2 of `scripts/rival_eval.py` unchanged (random three-letter labels, analysis before verdict, both orders). The judge is the first of GLM-5.1, GLM-5.2, gpt-oss_120b whose slot-1 rate, pooled over both arms, is in 0.4 to 0.6; the same judge scores both arms. No healthy judge means no verdict, which means do not ship. A scenario scores 1 when the arm wins in both orders, 0 when it loses in both, else 0.5. Other judges are sensitivity only.

## Decision rule (stated before any held-out call)

- KEEP (ship the `SKILL.md` edit) only if at least 135 of 150 scenarios are scored by a healthy judge and the paired difference (v1 minus v0 win rate, mean of per-scenario score differences) has a 95% bootstrap CI (10,000 resamples over scenarios, percentile, seed 1) whose lower bound is above 0. Otherwise `SKILL.md` is not edited and only this bench record ships.
- Superiority over the rival is claimed only if v1's win-rate CI (same bootstrap) has a lower bound above 0.5. A win claim also requires the keep rule: an unshipped text is not claimed as a win.
- One run per arm; no re-runs, no judge swapping, no scenario edits after a result is seen. Records are never overwritten.

## Harness changes while drawing the held-out set (before any answer or judge call)

After `SHA256-prereg.txt` was written, the first `bench.py write held` attempts failed closed: two ran out of redraw rounds because a single-seed redraw returned a bare JSON object that the harness rejected, and the draft was lost. I then changed `bench.py` (accept a bare object, run batches and redraws in a thread pool, print per-round overlap counts, optional scratch copy of the draft via `DRAFT_OUT`), widened seed numbering to three digits for n = 150 and removed "two-character" from the id line of `prompts/brief.txt`, and corrected the loss count in this file. None of these touches the arms, the judge, the decision rule or the scenario distribution; the held-out seeds were drawn once (`prompts/seeds-held.txt`, rejected only if a line repeated an earlier seed). `SHA256-prereg.txt` therefore shows the earlier `bench.py`, `brief.txt` and this file; `SHA256-frozen.txt` carries the final versions and is the record the ledger hash covers. The first complete draw that passed the overlap bar is the held-out set.

## Known limits

One generator family writes the scenarios and every answer; judges are models; scenarios are fictional; one rival, run without its reference files; a FAIL means not shown better under this judge on this synthetic distribution, not a claim about real users.
